## 1. 결론

이 프로젝트의 문제는 "문서가 많다"가 아니라 **현재 기준, 근거, 작업 로그, 과거 진단이 같은 레벨에 섞여 있어 매 세션마다 무엇을 읽어야 하는지 불명확한 것**이다.

해결 방향은 명확하다.

1. **항상 로드하는 문서는 작게 유지한다.**
   기본 앵커는 `PROJECT_RULES.md`, `SESSION_HANDOFF.md`, `문서_인덱스.md`다.
2. **상세 문서는 인덱스로 점진 공개한다.**
   모든 문서를 처음부터 읽지 않고, 작업별 로드 가이드에 따라 필요한 것만 연다.
3. **한 주제는 한 원본만 둔다.**
   새 결론이 생기면 기존 원본을 갱신하거나 대체하고, 옛 문서는 삭제하지 않고 `temp/backups/YYYY-MM-DD/`로 보낸다.
4. **세션 상태는 압축된 handoff로 남긴다.**
   긴 로그가 아니라 최신 기준 파일, 확정 결정, 다음 액션, 주의할 함정만 남긴다.
5. **새 문서는 게이트를 통과할 때만 만든다.**
   기존 문서 갱신으로 충분하면 새 문서를 만들지 않는다.

권고 실행 순서:

```text
1. 문서_인덱스 보강
2. 중복 문서 SSOT 통합
3. 대체·구식 문서 백업 이동
4. 핵심 규칙을 PROJECT_RULES.md에 짧게 승격
```

## 2. 리서치 핵심 근거

### 2.1 긴 컨텍스트는 성능 보장이 아니다

Anthropic은 컨텍스트를 유한한 자원으로 보고, 에이전트가 원하는 결과를 내도록 **가장 작은 고신호 토큰 집합**을 구성해야 한다고 설명한다. 긴 작업에는 compaction, structured note-taking, sub-agent 방식이 필요하다고 정리한다.

Chroma의 Context Rot 연구와 "Lost in the Middle" 연구는 긴 입력에서 모델이 정보를 균일하게 쓰지 못하고, 입력이 길수록 중요한 내용이 묻힐 수 있음을 보여준다.

프로젝트 적용:

- "컨텍스트 창이 크니 전부 넣자"는 금지한다.
- 최신 기준은 짧은 앵커에 두고, 근거 문서는 필요할 때만 연다.
- 오래된 분석 원문은 활성 문서가 아니라 reference 또는 `temp/backups/YYYY-MM-DD/`로 둔다.

### 2.2 에이전트 지침 파일은 작아야 한다

OpenAI Codex 문서는 작업 전 `AGENTS.md` 계열 지침을 읽고, 전역 지침과 프로젝트 지침을 계층적으로 합친다고 설명한다. 기본적으로 합쳐진 프로젝트 지침 크기가 `project_doc_max_bytes` 32KiB에 도달하면 더 이상 추가하지 않는다.

Claude Code도 항상 로드되는 `CLAUDE.md`가 길어지면 컨텍스트를 많이 쓰고 지침 준수율이 떨어질 수 있다고 안내한다.

프로젝트 적용:

- `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`는 지금처럼 `PROJECT_RULES.md`를 가리키는 얇은 포인터로 유지한다.
- 세부 규칙을 포인터 파일에 추가하지 않는다.
- 실제 운영 규칙은 `PROJECT_RULES.md`, 작업별 상세 지식은 `문서_인덱스.md`와 주제별 SSOT 문서로 분리한다.

### 2.3 memory는 보조 기억이지 규칙 원본이 아니다

에이전트 memory는 이전 스레드의 유용한 맥락을 다음 작업으로 가져오는 보조 기능이다. OpenAI 문서는 반드시 적용되어야 하는 팀 지침은 `AGENTS.md`나 체크인된 문서에 두고, memories는 로컬 회상 계층으로 취급하라고 한다.

프로젝트 적용:

- 반복 선호, 자주 쓰는 경로, 알려진 함정은 memory에 저장될 수 있다.
- 공식 기준은 항상 `PROJECT_RULES.md`, `문서_인덱스.md`, 주제별 SSOT 문서에 둔다.
- memories를 공유 가능한 문서 체계의 대체재로 쓰지 않는다.

### 2.4 compaction은 요약이 아니라 다음 작업 상태 재구성이다

Compaction의 목적은 긴 대화를 줄이는 것이 아니라, 다음 작업에 필요한 상태를 정확히 남기는 것이다.

프로젝트 적용:

- `SESSION_HANDOFF.md`는 세션 로그가 아니라 compaction 산출물이다.
- 남길 것: 현재 작업, 최신 기준 파일, 확정 결정, 다음 액션, 주의할 함정.
- 남기지 않을 것: 도구 출력 전문, 긴 리서치 원문, 폐기된 가설, 이미 규칙 문서에 있는 내용.

### 2.5 prompt caching은 비용 최적화이지 문서 관리 대체재가 아니다

OpenAI Prompt Caching은 반복되는 정적 prefix가 같을 때 지연시간과 입력 토큰 비용을 줄일 수 있다. 정적 지침은 앞에 두고, 가변 정보는 뒤에 두는 구조가 유리하다.

프로젝트 적용:

- 안정적인 앵커 문서를 앞에 두는 구조는 비용 면에서도 유리하다.
- 캐싱은 불필요한 문서를 넣어도 된다는 뜻이 아니다.
- 정확도와 유지보수를 위해 문서 로드 자체를 줄이는 것이 우선이다.

### 2.6 문서는 목적별로 나눠야 한다

Diataxis는 문서를 튜토리얼, 방법 안내, 참조, 설명으로 구분한다. Atlassian의 SSOT 자료도 중복·상충 정보를 줄이고 현재 기준을 한 곳으로 모으는 접근을 강조한다.

프로젝트 적용:

- 규칙, 절차, 리서치 근거, 작업 로그를 한 문서에 섞지 않는다.
- 주제별 현재 결론은 SSOT에, 원문 근거는 reference 또는 `temp/backups/YYYY-MM-DD/`에 둔다.
- 문서마다 "언제 읽는지"가 분명해야 한다.

## 3. Claude 리서치에서 흡수한 핵심

Claude 문서는 짧지만 운영 규칙으로 바로 쓰기 좋은 압축안을 담고 있었다. 다음 내용을 통합본에 흡수한다.

| 항목 | 흡수 내용 | 적용 |
|---|---|---|
| 단일 원본 | 한 주제=한 권위 문서, 대체 문서는 `temp/backups/YYYY-MM-DD/`로 이동 | 문서 상태값과 백업 규칙으로 반영 |
| 점진적 공개 | 인덱스가 "무엇/언제 필요한지"를 설명해야 함 | `문서_인덱스.md` 강화 목표로 반영 |
| 린 앵커 | 항상 로드되는 문서는 짧고 안정적으로 유지 | 앵커 3종 원칙으로 반영 |
| 컴팩션 | 결정·미해결·경로만 남김 | `SESSION_HANDOFF.md` 형식으로 반영 |
| 문서 수명주기 | 활성/참조/백업 티어 | 상태값 모델로 반영 |
| 재발견 방지 | 비자명 지식만 영속화 | 새 문서 생성 게이트로 반영 |
| 인프라 없는 Graphify | 그래프 DB 없이 마크다운 인덱스로 관계를 표현 | 관계(대체/근거/파생) 필드로 반영 |

Claude 문서의 "Graphify 쿼리당 토큰 70~90% 절감" 주장은 약한 출처 기반이라 공식 원칙으로 채택하지 않는다. 대신 **원문 전체 로드 대신 인덱스·관계·요약을 먼저 보는 방향**만 채택한다.

## 5. 통합 운영 모델

### 5.1 문서 계층

| 계층 | 역할 | 파일 예시 | 로드 정책 |
|---|---|---|---|
| L0 규칙 앵커 | 절대 규칙, 안전, 작업 방식 | `PROJECT_RULES.md`, `00_공통_작업원칙.md`, `01_유튜브_제작_워크플로우.md` | 세션/작업 시작 시 필요한 만큼 |
| L1 세션 상태 | 현재 작업 상태, 다음 액션, 막힌 점 | `SESSION_HANDOFF.md` | 세션 시작 시 |
| L2 지도 | 어떤 문서를 언제 읽을지 | `문서_인덱스.md` | 세션 시작 시 |
| L3 주제별 SSOT | 기획, 편집, 채널 방향 등 현재 기준 | `기획단계_규격_2026-07-06.md` | 작업별로만 |
| L4 근거/백업 | 과거 리서치, 소비된 분석, 원문 근거 | `temp/backups/YYYY-MM-DD/` 문서 | 필요할 때만 |

기본 로드 원칙:

```text
PROJECT_RULES.md
SESSION_HANDOFF.md
문서_인덱스.md
-> 작업별 추가 문서 2~5개만 선택
```

### 5.2 문서 상태값

| 상태 | 의미 | 행동 |
|---|---|---|
| `authoritative` | 현재 기준 원본 | 충돌 시 우선, 짧고 안정적으로 유지 |
| `active` | 현재 작업에 자주 쓰는 산출/기획 문서 | 작업별 로드 가이드에만 노출 |
| `reference` | 근거·배경·이전 리서치 | 기본 로드 금지 |
| `superseded` | 새 문서가 대체함 | `temp/backups/YYYY-MM-DD/` 이동 후보 |
| `backup` | 보존만 하는 과거 문서 | 인덱스에는 대체 관계만 남김 |
| `ephemeral` | 임시 분석/실험 | 완료 후 보관 또는 요약 흡수 |

### 5.3 인프라 없는 Graphify

그래프 DB 없이 Graphify·Graphiti의 장점만 마크다운으로 근사한다.

| 그래프 개념 | 이 프로젝트 구현 |
|---|---|
| 쿼리 가능한 맵 | `문서_인덱스.md` |
| 노드 | 각 문서 |
| 엣지 | 대체/근거/파생 관계 |
| 시간성 | 날짜 파일명 + 상태값 + `temp/backups/YYYY-MM-DD/` |
| 현재 진실 | `PROJECT_RULES.md`, 주제별 SSOT, `SESSION_HANDOFF.md` |
| 요약 우선 탐색 | 인덱스 1줄 요지 -> 필요한 문서만 열기 |

### 5.4 새 문서 생성 게이트

새 문서는 아래 질문에 모두 통과할 때만 만든다.

1. 기존 authoritative 문서에 추가하면 안 되는가?
2. 기존 reference 문서의 섹션 추가로 충분하지 않은가?
3. 다음 세션에서 다시 찾을 만큼 비자명한 결정/근거/함정인가?
4. 새 문서가 대체할 기존 문서가 있는가?
5. 만들자마자 `문서_인덱스.md`에 상태, 읽는 조건, 대체 관계를 등록할 수 있는가?

하나라도 아니면 새 문서를 만들지 않는다.

## 6. 적용 계획

### 1단계: 인덱스 불일치 수정

목표:

- 컨텍스트 관리 문서의 단일 진입점을 이 통합본으로 맞춘다.

작업:

- `문서_인덱스.md`의 문서·컨텍스트 정리 항목을 이 통합본으로 수정한다.
- `CLAUDE_컨텍스트_리서치.md`는 통합 흡수됨으로 `temp/backups/YYYY-MM-DD/`로 이동한다.
- 기존 `컨텍스트_문서관리_리서치_2026-07-07.md`는 reference/backup 후보로 표시한다.

완료 기준:

- 컨텍스트 관리 주제에서 활성 문서는 이 통합본 하나만 남는다.

### 2단계: 인덱스 강화

목표:

- `문서_인덱스.md`를 단순 목록에서 작업별 로드 판단표로 바꾼다.

작업:

- 모든 문서에 상태값을 붙인다.
- 각 문서에 "언제 읽는지"를 적는다.
- 대체/근거/파생 관계를 표시한다.
- 보관 후보를 명시하되, 이동은 사용자 승인 후 진행한다.

### 3단계: SSOT 통합·보관

우선 대상:

| 주제 | 현재 | 권고 |
|---|---|---|
| 기획 단계 | `기획단계_규격`, `대사기반_방법론`, `스토리텔링`, `고도화_대화흐름` | `기획단계_규격`을 SSOT로, 나머지는 근거/재료 |
| 러프컷 진단 | `러프컷_품질개선`, `러프컷_개선_심화분석` | 최신 결론만 남기고 reference/backup |
| 스킬 진단 | `스킬_개선_및_신규스킬_검토안`, `스킬_워크플로우_실태진단` | 구축 완료분은 backup |
| 편집 분석 | `04_동기화`, `05_수정지시서`, `06_무음판정표` | v12에 소비된 것은 backup, 최신 기준은 `07_v12_컷결정_로그` |

### 4단계: 규칙 승격

`PROJECT_RULES.md`에 아래 수준으로 짧게 승격한다.

```md
## 문서·컨텍스트 관리

- 세션 시작 기본 앵커는 `PROJECT_RULES.md`, `SESSION_HANDOFF.md`, `문서_인덱스.md`다.
- 새 문서는 기존 SSOT 갱신으로 해결할 수 없을 때만 만든다.
- 문서를 추가·대체·보관하면 `문서_인덱스.md`를 함께 갱신한다.
- 한 주제의 현재 기준 문서는 하나만 둔다.
- 대체된 문서는 삭제하지 않고 `temp/backups/YYYY-MM-DD/`로 이동한다.
- `SESSION_HANDOFF.md`에는 현재 상태와 다음 액션만 남기고, 리서치 원문은 남기지 않는다.
```

## 7. 운영 체크리스트

### 작업 시작 전

- `PROJECT_RULES.md` 확인
- `SESSION_HANDOFF.md` 확인
- `문서_인덱스.md`에서 작업별 추가 문서만 선택
- 현재 작업의 기준 입력 파일 확인

### 새 문서 만들기 전

- 기존 SSOT 갱신으로 가능한지 확인
- 기존 리서치 문서 섹션 추가로 가능한지 확인
- 문서 상태값 결정
- 대체할 문서가 있는지 확인
- 인덱스 등록 문구까지 정한 뒤 생성

### 작업 종료 전

- 결정은 SSOT 또는 handoff에 흡수
- 근거 문서는 reference/backup으로 분류
- 새 문서/이동 문서는 인덱스 갱신
- 다음 세션이 읽을 파일을 3개 이하로 handoff에 기록

## 8. 레드팀 검토

| 리스크 | 근거 | 대응 |
|---|---|---|
| 통합 문서가 다시 비대해짐 | 모든 근거를 한곳에 넣으면 앵커로 쓰기 어려움 | 이 문서는 상세 reference로 두고, 실제 규칙은 `PROJECT_RULES.md`에 짧게 승격 |
| 백업 이동으로 근거를 잃음 | 과거 분석 문서에 당시 판단 근거가 있음 | 삭제 금지, `temp/backups/YYYY-MM-DD/` 이동, 인덱스에 대체 관계 기록 |
| 인덱스가 낡음 | 인덱스가 단일 진입점이면 최신성 의존도가 큼 | 문서 추가/대체/보관 시 인덱스 갱신을 완료 조건으로 고정 |
| memory를 규칙 원본으로 오해 | memories는 로컬 생성 상태 | 필수 규칙은 체크인된 문서에만 저장 |
| prompt caching 과신 | 캐싱은 비용/속도 최적화 | 불필요한 문서 로드 자체를 줄이는 방향 유지 |
| Graphify 수치 과신 | 일부 도구 효과 수치는 약한 출처 기반 | 도구 도입이 아니라 인덱스·관계·수명주기 개념만 채택 |
| 한 번에 대규모 정리 | 프로젝트 규칙은 한 단계씩 진행 | 인덱스 수정 -> 보관 후보 확정 -> 이동 -> 규칙 승격 순서 준수 |
