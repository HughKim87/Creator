# 러프컷 품질 개선 — 원인 진단 및 개선 방안 (2026-07-06)

사용자 피드백: v11이 (1) 직접 편집한 것처럼 자연스럽지 않고, (2) 중요한 부분이
빠진 것 같고, (3) 중요하지 않은 부분이 통째로 들어가 시간을 끈다.

## 1. 원인 진단 (데이터 실측)

### 진단 A — 편집 단위가 다르다 (자연스러움 문제의 핵심)

사용자 시연 구간(backroom.xml 앞 1:14)과 자동 생성 구간을 정량 비교한 결과:

| | 사용자 시연 구간 | v11 자동 구간 |
|---|---|---|
| 컷 단위 | 평균 1~4초 비트 단위 | 평균 11.4초, 최장 81.6초 |
| 취사 기준 | 문장 안에서도 재미 기여로 취사 | 구간(장면) 채택 후 무음만 제거 |
| 원본 대비 압축 | 소스 92초 → 약 28초 (70% 제거) | 채택 구간은 거의 원형 보존 |

즉 사용자는 **"비트(재미 단위)로 골라 담는"** 편집을 하는데, v11은
**"장면을 통째로 담고 무음만 빼는"** 편집이다. 리듬이 다를 수밖에 없다.

### 진단 B — 25초 이상 무편집 롱컷 13개가 러프컷의 47% (시간 끄는 느낌의 원인)

v11 총 20:41 중 **9.6분이 내부 편집 없는 롱컷 13개**다:
22_첫추격 81.6s · 23_막다른길 78.7s · 32_클라이맥스 73.0s · 13_빌드업비명 51.6s ·
24_학습도발 47.1s 등. "게임플레이 액션 중 소스 연속 유지" 규칙(Tier-2 원칙 4)이
이 블록들을 통과시켰고, 무음 판정(06 판정표)도 0.5초 이상 무음만 대상이라
**발화가 이어지는 늘어지는 구간은 아무 필터도 거치지 않았다.**
"문장 완결 원칙"이 약한 문장(리액션 없는 중계 멘트 등)까지 살리는 부작용도 있다.

### 진단 C — 선별 신호가 소리·자막 편향 (중요한 부분 누락의 원인)

하이라이트 선별(01 흐름표)은 오디오 RMS 피크 + 자막 텍스트가 1차 신호였다.
구조적으로 **조용하지만 화면에 사건이 있는 순간**을 놓친다. 실증 2건:

- v10에서 오디오만 믿고 자른 곳이 사망 테이프 화면이었음 (v11에서 복원)
- S4~S7 (자포자기 개그, 후반 사망 등)은 RMS가 놓쳐 자막 재검토로 뒤늦게 발굴

소스 사용 분포도 편중: 원본 60~70분 구간은 **0.8분만 사용** (다른 10분 구간은
2~4분). 후반부는 음량이 낮아 신호가 약했을 뿐, 재미가 없다는 근거는 없다.

### 진단 D — 공포 장르 리듬 미반영

공포 콘텐츠 편집 리서치 결론: 빌드업·정적(dread)은 **길게 유지해야** 무섭고,
배회·이동은 **과감히 잘라야** 지루하지 않다. 즉 "빠르게 vs 느리게"가 아니라
**구간 성격별로 리듬이 달라야** 하는데, 현재 파이프라인은 화면 사건 유무라는
단일 기준만 있다. 긴장 빌드업과 단순 배회가 같은 취급을 받는다.

## 2. 개선 방안 (옵션별)

### 방안 1 — 사용자 시연 정밀 역설계 → "취향 프로파일" 문서화 (필수, 선행)

시연 1:14에서 사용자가 **버린 것 전수 목록**을 원본과 대조해 뽑고,
"왜 버렸나"를 유형화한다 (이미 점프컷 원칙은 도출했지만, **문장 단위
keep/drop 기준**까지는 역설계하지 않았다). 결과물: 컷 취사 체크리스트.
이후 모든 자동 판단의 상위 기준으로 사용. 이번 피드백("시간 끄는 느낌"이 든
구체 위치)을 사용자에게 2~3곳만 받으면 정확도가 크게 오른다.

### 방안 2 — 롱컷 13개 비트 단위 분해 재판정 (효과 최대)

9.6분짜리 롱컷 13개를 발화·사건 단위 서브비트로 분해 → 각 비트를
"재미·긴장 기여"로 keep/drop 판정 (콘택트시트 + 자막 교차, 기존 인프라 재사용).
빌드업 비트는 유지, 중계·배회 비트는 제거. 예상 결과: 20:41 → 15분 안팎,
밀도 상승. Tier-2 원칙 4의 "게임플레이 소스 연속 유지"는
**"긴장·사건 진행 중"으로 한정**하도록 개정 필요.

### 방안 3 — 다중 신호 하이라이트 재스캔 (누락 복구)

RMS 단일 신호를 보강한다. 학계·업계에서 확립된 접근은 멀티모달(음성+화면)이다:

- **비명·웃음 오디오 분류**: RMS(크기)가 아니라 소리의 종류로 리액션 탐지.
  게임 실황 대상 연구가 다수 존재. 후반 저음량 구간에서 특히 유효.
- **화면 변화량 스캔**: 프레임 차이 수치화 인프라(무음 판정표에서 구축)를
  전 구간으로 확장 — 조용한 시각 사건 발굴.
- 우선 대상: 사용률 최저인 52~78분 구간 재스캔.

### 방안 4 — 완성본 던지기 → 후보 제시·선택 방식으로 전환 (프로세스)

지금은 "XML 완성 → 사용자 검수" 구조라 불만이 뒤늦게 발견된다. 판단이 갈릴
구간(롱컷 내부 트림, 하이라이트 채택 여부)은 **콘택트시트 + 2~3안**으로 먼저
물어보고 확정한다. 시연 1회(1:14)보다 훨씬 싼 비용으로 취향 데이터가 쌓인다.

### 방안 5 — "페이싱 스캔" 게이트 추가 (재발 방지)

경계 스캔처럼, XML 생성 전 자동 리포트를 게이트로 추가:
25초 이상 무편집 블록 플래그, 컷별 발화 밀도, 구간 성격(빌드업/배회/토크) 표기.
tools/synccheck에 영속화.

## 3. 권장 실행 순서

1. **사용자에게 확인 2가지**: ① "시간 끈다"고 느낀 위치 2~3곳, ② "빠졌다"고
   느낀 장면 (기억나는 대사·상황이면 충분)
2. 방안 1 (시연 역설계 → 취향 체크리스트) — 반나절
3. 방안 2 (롱컷 13개 분해 재판정) + 방안 3 (52~78분 재스캔) → **v12**
4. 방안 4·5는 v12 작업부터 프로세스로 적용
5. Tier-2 편집 원칙 4번 개정 (백업 후)
