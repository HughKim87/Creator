# 프로젝트 운영 문제 진단 및 개선안 (2026-07-07)

- 대상: 김실버유튜브 프로젝트 전체 운영 방식
- 범위: 문서 관리, 워크플로우 실행, 산출물 관리, 검증 루프
- 성격: 진단 보고서. 실행은 사용자 승인 후 단계별로 진행한다.
- 근거: `PROJECT_RULES.md`, `00_공통_작업원칙.md`, `01_유튜브_제작_워크플로우.md`, `SESSION_HANDOFF.md`, `README.md`, `기획_리서치/`, `workspace/outputs/`, `temp/backups/` 확인
- 검증 한계: Git 상태는 저장소 소유권 경고 때문에 확인하지 못했다. 아래 진단은 파일시스템 기준이다.

## 0. 결론 요약

현재 문제는 "문서가 많다" 하나가 아니다.

가장 큰 문제는 **현재 기준, 과거 산출물, 리서치, 작업 로그, 다음 작업 지시가 같은 레벨에 섞여 있어 매번 시작점이 흔들리는 것**이다.

핵심 증상:

- README는 진행 중 작업이 없다고 하지만, `SESSION_HANDOFF.md`는 백룸 기획서/편집 재개 작업을 다음 액션으로 들고 있다.
- `문서_인덱스.md`는 현재 존재하지 않는다.
- Markdown 문서는 총 60개 확인됐다. 이 중 `temp/backups/` 19개, `workspace/outputs/` 9개, `기획_리서치/` 18개가 운영 혼란의 주요 지점이다.
- Premiere XML은 `백룸_러프컷_v1.xml`부터 `v12.xml`까지 12개가 남아 있다.
- 5단계와 6단계는 매우 구체적이지만, 1·2·7단계는 기준이 얕고 3·4·8단계는 독립 실행 스킬이 없다.

## 1. 현재 상태 불일치

### 1-1. README와 SESSION_HANDOFF가 서로 다르다

`README.md`는 현재 상태를 "진행 중인 특정 영상 작업 없음"으로 적고 있다.

반면 `SESSION_HANDOFF.md`는 다음 작업을 백룸 영상 기획서 생성, 이후 기획서 승인 후 편집 재개로 적고 있다. 또한 구 편집 산출물 v12와 Premiere 미검증 상태도 남아 있다.

영향:

- 새 세션이 시작할 때 "새 영상 시작"인지 "백룸 영상 이어서 진행"인지 판단이 흔들린다.
- 에이전트가 README만 보면 작업 없음으로 이해하고, handoff를 보면 진행 중 작업으로 이해한다.
- 같은 작업을 다시 분석하거나, 이미 끝난 단계를 다시 시작할 위험이 있다.

### 1-2. handoff 자체도 일부 오래됐다

`SESSION_HANDOFF.md`는 "백룸 기획서 생성 대기"를 다음 작업으로 적고 있지만, 실제로는 `workspace/outputs/analysis/08_백룸_기획서_대사스파인_2026-07-07.md`가 이미 존재한다.

영향:

- 다음 세션이 이미 생성된 기획서를 다시 만들 수 있다.
- "기획서 승인 전 편집 금지"라는 중요한 통제는 맞지만, 현재 위치 표시는 갱신이 필요하다.

## 2. 문서 관리 문제

### 2-1. 단일 진입점이 없다

`컨텍스트_관리_최적화_통합_리서치.md`는 `문서_인덱스.md`를 단일 진입점으로 두고, 문서 상태를 `authoritative`, `active`, `reference`, `superseded`, `backup`, `ephemeral`로 나누자고 제안한다.

하지만 현재 `문서_인덱스.md`는 없다. 백업 폴더에는 인덱스 관련 백업 흔적이 있으나, 현재 활성 파일로는 존재하지 않는다.

영향:

- 어떤 문서가 현재 기준인지 알기 어렵다.
- 리서치 문서, 규격 문서, 과거 진단 문서가 모두 같은 폴더에 남는다.
- 세션마다 필요한 문서를 다시 찾느라 시간이 늘어난다.

### 2-2. 한 주제에 여러 원본이 있다

대표 중복 축:

| 주제 | 현재 파일 | 문제 |
|---|---|---|
| 기획 단계 | `기획단계_대사기반_메시지도출_방법론`, `5단계_기획방법_개선리서치`, `기획단계_규격` | 최신 기준과 근거 문서가 같은 레벨에 있음 |
| 러프컷 진단 | `러프컷_품질개선_진단_및_방안`, `러프컷_개선_심화분석_및_실행경로` | 원인 진단과 실행 경로가 분리된 채 둘 다 활성처럼 보임 |
| 컨텍스트 관리 | `컨텍스트_문서관리_리서치`, `컨텍스트_관리_최적화_통합_리서치` | 통합본이 생겼지만 원 리서치의 상태가 명확하지 않음 |
| 스킬 진단 | `스킬_개선_및_신규스킬_검토안`, `스킬_워크플로우_실태진단` | 과거 개선안과 현재 반영 상태가 섞임 |

영향:

- 같은 질문을 다시 조사하게 된다.
- 이미 흡수된 결론과 아직 유효한 결론이 섞인다.
- 에이전트가 오래된 기준을 현재 기준으로 잘못 사용할 수 있다.

### 2-3. 백업은 많지만 최신본 포인터가 없다

백업 규칙 자체는 안전하다. 문제는 백업 이후의 마감 절차가 약하다는 점이다.

현재 확인된 상태:

- `temp/backups/`에 백업 문서 19개, 백업 CSV 4개가 있다.
- `workspace/outputs/premiere_export/`에는 XML 12개가 있다.
- 최신 후보처럼 보이는 v12도 Premiere 미검증으로 기록돼 있다.
- `roughcut_cutlist.csv`와 `roughcut_cutlist_v12.csv`가 함께 있어 기준본이 헷갈린다.

영향:

- "현재 써야 하는 파일"을 매번 다시 판단해야 한다.
- 생성됨, 검증됨, 폐기됨, 참조용 상태가 파일명만으로 구분되지 않는다.

## 3. 워크플로우 실행 문제

### 3-1. 단계별 완성도가 불균형하다

`전체_워크플로우_단계별_개선진단_2026-07-07.md`와 실제 파일 구조가 일치한다.

현재 상태:

| 단계 | 상태 | 문제 |
|---:|---|---|
| 1 | 스킬 있음 | 인기 게임과 김실버 채널 적합도 구분 기준이 약함 |
| 2 | 스킬 있음 | 제목/썸네일 약속이 본문에서 충족되는지 검증 약함 |
| 3 | 스킬 없음 | 촬영 전 대본과 촬영 후 구성 초안이 분리되지 않음 |
| 4 | 스킬 없음 | 원본 자막, 분석용 자막, 업로드용 자막 구분 약함 |
| 5 | 규격 개선됨 | 워크플로우 본문과 v2 규격 동기화가 일부 부족 |
| 6 | 개선됨 | 실제 작업에서 하이라이트 수집 방식으로 되돌아갈 위험 |
| 7 | 스킬 있음 | 6단계 후보지도에서 컷리스트로 넘어가는 게이트 부족 |
| 8 | 스킬 없음 | 최종 검수 후 어느 단계로 되돌릴지 기준 부족 |

핵심 문제:

- 중간 단계인 5·6단계만 매우 정교하다.
- 앞단의 소재/기획 기준과 뒷단의 편집/검수 기준이 상대적으로 약하다.
- 실제 제작보다 워크플로우 개선 문서가 더 빨리 늘어난다.

### 3-2. 실패 루프가 너무 크다

백룸 작업은 러프컷 v1~v12까지 누적됐다. 여러 버전을 만든 뒤에야 "문제는 컷이 아니라 상위 기획"이라는 결론으로 이동했다.

진단:

- 상위 기준 없이 컷 생성부터 반복했다.
- 전체 러프컷을 만든 뒤 사용자 검토를 받는 방식이라 실패 비용이 크다.
- 대표 구간 2~3분으로 먼저 검증하는 작은 루프가 부족했다.

영향:

- 한 번 틀릴 때마다 문서, 컷리스트, XML, 백업이 함께 늘어난다.
- 사용자 피드백이 늦게 들어와 수정 범위가 커진다.
- "왜 또 새 파일이 생겼는가"라는 불신이 커진다.

### 3-3. 검증 수준이 섞인다

프로젝트 규칙상 `App-validated`는 Premiere Pro에서 가져오기, 미디어 연결, 오디오, 시퀀스 재생까지 확인된 상태다.

하지만 실제 산출물에는 다음 상태가 섞여 있다.

- 생성됨
- 스크립트/구조 검증됨
- 경계 스캔 통과
- Premiere 미검증
- 사용자 시연 기준 일부 반영

영향:

- "만들었다"와 "쓸 수 있다"가 혼동된다.
- Premiere에서 확인되지 않은 XML이 최종본처럼 보일 수 있다.
- 다음 작업자가 같은 파일을 다시 검증해야 한다.

## 4. 메타작업 과잉 문제

### 4-1. 개선 문서가 개선 대상을 압도한다

최근 문서 흐름은 다음과 같다.

1. 러프컷 품질 문제 진단
2. 러프컷 심화 분석
3. 기획 단계 재정립
4. 5단계 기획방법 개선 리서치
5. 6단계 영상분석방법 개선 리서치
6. 전체 워크플로우 단계별 개선 진단
7. 컨텍스트 관리 통합 리서치
8. 프로젝트 운영 문제 진단

진단:

- 작업 개선을 위한 분석은 필요했지만, 실제 영상 완주보다 분석 문서가 더 빨리 늘고 있다.
- 새 진단 문서가 또 다른 개선 백로그를 만든다.
- "한 번에 한 단계씩"이라는 규칙과 다르게, 실제로는 전체 체계를 계속 손보고 있다.

### 4-2. 규칙 문서가 사고 이력까지 품고 있다

`PROJECT_RULES.md`에는 현재 유효한 규칙뿐 아니라 v8 사고, 날짜별 개정, 과거 규칙 폐기 흔적이 함께 들어 있다.

영향:

- 세션 시작 시 읽어야 하는 기본 문서가 길어진다.
- 현재 기준과 역사적 이유가 섞여 빠르게 판단하기 어렵다.
- 규칙을 줄이려는 작업이 다시 새 문서를 만들 수 있다.

## 5. 개선안

### 5-1. 즉시 해야 할 일: 현재 위치 고정

가장 먼저 해야 할 것은 새 개선이 아니라 현재 작업의 기준 고정이다.

필수 결정:

1. 현재 백룸 작업의 기준 파일은 `08_백룸_기획서_대사스파인_2026-07-07.md`인지 확인한다.
2. v12 컷리스트/XML은 "참조용 구 산출물"인지, "7단계에서 재검토할 후보"인지 상태를 정한다.
3. `SESSION_HANDOFF.md`의 현재 위치를 실제 파일 상태와 맞춘다.
4. README의 "진행 중 작업 없음" 문구를 실제 상태와 맞춘다.

### 5-2. 문서 인덱스 복구 또는 신설

`문서_인덱스.md`를 만들어 최소한 아래 항목만 관리한다.

| 상태 | 의미 | 예시 |
|---|---|---|
| 현재 기준 | 충돌 시 우선하는 문서 | `PROJECT_RULES.md`, `기획단계_규격_2026-07-06.md` |
| 현재 작업 | 지금 이어서 써야 하는 산출물 | `08_백룸_기획서_대사스파인_2026-07-07.md` |
| 참고 | 근거·배경 자료 | 스토리텔링, 컷 연결, 러프컷 진단 문서 |
| 대체됨 | 새 문서가 흡수한 문서 | 컨텍스트 원 리서치 등 |
| 백업 | 보존만 하는 이전본 | `temp/backups/` |

운영 규칙:

- 새 문서를 만들면 인덱스에 상태와 읽는 조건을 함께 등록한다.
- 어떤 문서가 다른 문서를 대체하면 대체 관계를 적는다.
- 기본 로드 문서는 `PROJECT_RULES.md`, `SESSION_HANDOFF.md`, `문서_인덱스.md`로 제한한다.

### 5-3. 신규 개선 동결

백룸 영상 1편이 끝날 때까지 아래를 동결한다.

- 신규 스킬 신설
- 신규 리서치 문서 생성
- 전체 워크플로우 추가 개편
- 규칙 문서 확장

예외:

- 현재 작업을 끝내는 데 직접 필요한 작은 수정
- 사용자 확인을 받은 파일 정리
- 검증 결과를 기록하는 최소 로그

### 5-4. 작은 검증 루프 도입

풀 러프컷을 다시 만들기 전에 대표 구간 2~3분만 먼저 검증한다.

권장 흐름:

```text
5단계 기획서 기준 확인
↓
6단계 화면 검증 후보 2~3개만 선택
↓
7단계 미니 컷리스트/XML 생성
↓
Premiere에서 가져오기·오디오·재생 확인
↓
사용자에게 짧게 확인
↓
통과 기준 확정 후 전체로 확장
```

목적:

- 실패 비용을 줄인다.
- 사용자 취향 기준을 초기에 잡는다.
- v1~v12 같은 대형 반복을 방지한다.

### 5-5. 산출물 상태 라벨링

`workspace/outputs/`의 주요 산출물에는 다음 상태 중 하나를 명시한다.

- `Generated`: 생성만 됨
- `Parsed`: 문법 파서 통과
- `Structure-validated`: 기대 구조 확인
- `Tool-validated`: 로컬 도구가 성공적으로 소비
- `App-validated`: Premiere 등 최종 앱에서 확인
- `Superseded`: 대체됨
- `Reference-only`: 참고용

적용 대상:

- XML
- 컷리스트 CSV
- 러프컷 사용방법 문서
- 분석 문서
- 기획서

## 7. 레드팀 검토

### 위험 1. 정리 작업이 또 다른 메타작업이 될 수 있다

대응:

- 인덱스는 처음부터 완벽하게 만들지 않는다.
- 현재 작업에 필요한 문서부터 10개 이내로만 분류한다.

### 위험 2. 신규 개선 동결이 문제 방치로 이어질 수 있다

대응:

- 동결은 영구 중단이 아니라 백룸 1편 완주 전까지의 범위 제한이다.
- 완주 후 실제 실패/성공 데이터를 기준으로 개선을 재개한다.

### 위험 3. 과거 산출물을 너무 빨리 버릴 수 있다

대응:

- 삭제하지 않고 `reference-only` 또는 `superseded` 상태로 먼저 표시한다.
- 이동/삭제는 사용자 승인 후 한다.

### 위험 4. 작은 검증 루프가 전체 품질을 보장하지 않을 수 있다

대응:

- 작은 루프는 전체 품질 보장이 아니라 방향 검증이다.
- 통과 후에도 전체 컷리스트 생성 전 경계 검증과 Premiere 확인은 별도로 유지한다.

## 8. 최종 판단

현재 프로젝트는 자료가 부족해서 막힌 것이 아니다. 오히려 자료와 규칙이 많아져서 **무엇이 현재 기준인지 식별하는 비용**이 커졌다.

따라서 다음 개선의 핵심은 더 많은 리서치가 아니라:

1. 현재 위치 고정
2. 단일 문서 인덱스
3. 신규 개선 동결
4. 작은 검증 루프
5. 상태 라벨링

이 다섯 가지다.
