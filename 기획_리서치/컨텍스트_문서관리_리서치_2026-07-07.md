# 컨텍스트·문서 관리 — 심화 리서치 및 분석 (2026-07-07)

사용자 지적: 작업이 진행될수록 문서만 늘고 정리가 안 된다. **내용 정리 + 컨텍스트 사용
최소화**는 매 작업에 상시 필요한 원칙이다. 이 문서는 그 방법을 넓게 리서치하고 이 프로젝트에
매핑해 권고한다. (이번 문서는 **리서치·분석**이며, 실제 파일 정리·규칙 변경은 별도 승인 후.)

---

## 1. 문제의 본질 — "컨텍스트 실패"

리서치 공통 결론: **최근 에이전트 실패의 대부분은 모델 실패가 아니라 컨텍스트 실패다.**
문서·토큰이 늘면 한계에 닿기 전에 이미 **context rot**(토큰이 많아질수록 유효 recall 저하)가
생긴다. 우리 프로젝트는 지금 29개 문서·3270줄로, 세션마다 "어디를 읽어야 하는지" 불분명해
불필요하게 많이 읽게 되는 구조다 — 정확히 이 함정에 들어가 있다.

핵심 원칙(Anthropic): **"원하는 결과를 낼 가장 작은 고신호(high-signal) 토큰 집합을 찾는다."**
아래 모든 기법이 이 한 문장의 파생이다.

## 2. 검증된 패턴 6가지 (리서치 종합)

| # | 패턴 | 요지 | 출처 계열 |
|---|---|---|---|
| A | **단일 원본(SSOT)** | 한 주제=한 권위 문서. 새 문서가 대체하면 옛것은 보관. 중복 원본이 혼란·구식 답을 만든다. | SSOT/지식베이스 |
| B | **점진적 공개 + 인덱스** | 전체를 로드하지 않고, "무엇이 있고 **언제 필요한지**"를 기술한 인덱스만 먼저. 상세는 필요할 때 런타임에 가져온다(just-in-time). | Anthropic·progressive disclosure |
| C | **린 앵커 파일** | 항상 로드되는 파일(규칙·메모리)은 **짧고 안정적**으로. 상세는 참조/@import로 분리("거대 단일 파일" 금지). | Claude Code memory |
| D | **컴팩션·점진적 요약** | 길어지면 핵심(결정·미해결·경로)만 남기고 요약·재초기화. 오래된 진단문서는 결론만 남기고 압축. | Anthropic compaction·Forte |
| E | **문서 수명주기 거버넌스** | 활성/참조/보관 티어. 대체·구식은 **삭제가 아니라 보관**. 인덱스가 상태를 유지. | 지식 거버넌스 |
| F | **재발견 방지만 영속화** | 다시 알아내려면 비싼 **비자명 지식**(검증된 사실·경로·함정)만 문서화. 자명하거나 파일에서 보이는 건 남기지 않는다. | auto-memory 원칙 |

**핵심 통찰 (B에 대해):** 좋은 인덱스는 파일명 나열이 아니다. **"각 문서가 무엇을 다루고 언제
관련되는지"를 구조적으로 기술**해야 에이전트가 헤매지 않고 필요한 것만 집는다. 그렇지 않으면
에이전트는 전부 가져오거나(비용↑) 엉뚱한 걸 추측한다.

## 3. 이 프로젝트 진단 — 원칙 대비 어디가 어긋났나

| 패턴 | 현 상태 | 판정 |
|---|---|---|
| A SSOT | 러프컷 진단 2종 · 기획단계 3종 · 스킬 진단 2종이 **한 주제에 여러 원본** | ✗ 위반 |
| B 인덱스 | `문서_인덱스.md` 신설(진전) — 단 "언제 필요한지" 기술을 더 informative하게 | △ 부분 |
| C 린 앵커 | PROJECT_RULES(119)·워크플로우(175)는 양호. `SESSION_HANDOFF`(105)가 커지는 중, README와 역할 일부 중복 | △ |
| D 컴팩션 | 진단·리서치 문서가 **결론만 남기지 않고 전문 유지** → 로드 비용 누적 | ✗ |
| E 수명주기 | 소비된 편집 분석(04·05·06)·구식 대형문서(스킬 검토안 507줄)가 **활성 폴더에 그대로** | ✗ |
| F 영속화 | 환경 주의·경로·함정은 잘 기록됨(핸드오프) | ○ 양호 |

한 줄 요약: **인덱스는 만들었지만(B), SSOT 통합(A)·수명주기 보관(E)·오래된 문서 압축(D)이
안 돼 있어 여전히 "읽을 게 많은" 상태다.**

## 4. 권고 — 상시 운영 원칙으로 (실행은 승인 후, 단계별)

리서치를 이 프로젝트의 **표준 운영 습관**으로 옮기면:

1. **앵커 3종만 항상 로드.** 세션 시작 시 `PROJECT_RULES` + `SESSION_HANDOFF` + `문서_인덱스`
   만 읽는다. 나머지는 인덱스의 "작업별 로드 가이드"로 필요할 때만(패턴 B·C).
2. **인덱스를 '진짜 인덱스'로 유지.** 문서마다 한 줄 목적 + **언제 읽어야 하는지**를 적는다
   (이미 초안 있음, 이 기준으로 보강).
3. **SSOT 통합(A).** 겹치는 계열을 하나로 합치고 나머지는 보관:
   러프컷 진단(품질개선↔심화분석) → 1개 / 기획단계(방법론·규격·스토리텔링) → 규격을 원본으로,
   나머지는 근거·재료로 명시 / 스킬 진단 2종 → 구식이면 보관.
4. **수명주기 보관(E).** 소비된 편집 분석(04·05·06)·구식 대형문서는 `_archive/`로 이동(삭제 아님).
5. **핸드오프 = 컴팩션 산출물(D).** 매 세션 핵심(결정·다음 할 일·함정)만. 상세는 문서로 밀어내고
   핸드오프는 짧게 유지. 오래된 진단문서는 결론을 규칙/규격/핸드오프에 흡수한 뒤 원문 보관.
6. **재발견 방지 지식만 영속화(F).** 비자명 사실·경로·함정만. 자명한 건 문서화하지 않는다.

효과: 매 세션 로드량이 "29개 중 필요한 3~5개"로 줄어 context rot 위험이 크게 감소.

## 5. 관련 솔루션 — Graphify·Graphiti 등 (2026-07-07 조사)

사용자가 언급한 "그래픽파이"는 **Graphify**로 확인. 이 분야(에이전트 메모리·지식그래프) 도구:

| 도구 | 무엇 | 이 문제와의 관련 |
|---|---|---|
| **Graphify** | 코드·문서·노트를 쿼리 가능한 지식 그래프로 변환(오픈소스) | 원문 대신 그래프 결과 반환 → **쿼리당 토큰 70~90% 절감**. 우리 문제에 정면으로 겹침 |
| **Graphiti (Zep)** | 에이전트 메모리용 **시간형** 지식 그래프 | 사실마다 유효기간, 낡은 정보는 **버리지 않고 무효화**(이력 보존) — 구식 문서 처리 철학과 일치 |
| mem0 / Letta / GraphRAG | 개인화 기억 / 에이전트 자율 메모리(OS식) / 그래프 기반 검색 | 같은 계열 다른 접근 |

**Cowork 현실:** 지금 Cowork에 바로 설치할 지식그래프 메모리 **플러그인은 없다**(레지스트리·플러그인
목록 확인). Graphify·Graphiti는 **개발자 도구**(그래프 DB + CLI 필요)이고, 작업용 샌드박스는 세션마다
초기화돼 그래프 DB가 유지되지 않는다. 가장 가까운 커넥터는 Notion(외부 SSOT)·Context7·Readwise 정도.

## 6. 이 프로젝트 적용 계획 — "인프라 없는 Graphify"

핵심: 그래프 DB 없이 **Graphify·Graphiti의 효과만** 마크다운 인덱스·수명주기로 근사한다.

| Graphify·Graphiti 개념 | 이 프로젝트 구현 (인프라 0) |
|---|---|
| 쿼리 가능한 맵(그래프 개요) | `문서_인덱스.md` — 경로 + "무엇/언제 필요" |
| 원문 대신 타겟 결과(토큰↓) | 인덱스에 **문서별 1줄 요지** + 긴 문서엔 **섹션 목차** → 열지 않고 파악, 필요 부분만 로드 |
| 관계(엣지) | 인덱스에 **명시적 관계**(대체/근거/파생) 표기 |
| 시간형·supersession | 상태(활성/보관) + 날짜 파일명 + `_archive` 보존(삭제 안 함) + `SESSION_HANDOFF`=현재 진실 |
| 자동 갱신 | **세션 종료 시** 인덱스·핸드오프 갱신을 습관·규칙으로 |
| 영속 메모리 | 앵커 3종(규칙·핸드오프·인덱스)=세션 간 기억. 샌드박스 휘발 → 산출물은 워크스페이스에 |

**단계별 실행 계획 (한 단계씩, 각 단계 승인 후)**

1. **인덱스 보강**(저위험) — 각 문서에 1줄 요지 + "언제 읽는지" + 관계(대체/근거) 명시. 긴 활성
   문서(워크플로우·심층진단)엔 섹션 목차 한 줄. 새 문서는 만들자마자 인덱스에 등록.
2. **SSOT 통합·보관**(승인·백업 후) — 겹치는 계열(러프컷 진단·기획단계·스킬 진단)을 1개로, 소비된
   편집분석(04·05·06)·구식 대형문서는 `_archive`로 이동(삭제 아님).
3. **규칙화** — 6원칙 + "앵커 3종만 로드 / 세션 끝 갱신"을 PROJECT_RULES "중복 방지" 확장으로 승격.
4. **(미래·선택)** 이 프로젝트를 Claude Code + 그래프 DB로 옮기면 그때 실제 Graphify + Graphiti 도입.

## 7. 다음 (승인 필요)

각 단계는 독립적으로 승인·실행한다. **이번엔 분석·계획까지.** 시작한다면 **1단계(인덱스 보강)**가
저위험·즉효라 추천. 2·3단계(통합·보관·규칙화)는 백업 후 진행.
