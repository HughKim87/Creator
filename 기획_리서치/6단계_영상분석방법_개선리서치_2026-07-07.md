# 6단계 영상분석방법 개선 리서치 — 기획서를 화면으로 검증하는 법

- 작성일: 2026-07-07
- 대상 단계: `6. 영상 분석`
- 목적: 5단계 기획서 이후, 실제 원본 영상을 어떻게 분석해야 편집 단계가 흔들리지 않는지 조사하고 개선안을 제시한다.
- 상태: 보고서. 아직 `01_유튜브_제작_워크플로우.md`나 `skills/gameplay-video-analysis/SKILL.md`에는 반영하지 않음.

## 1. 결론

현재 6단계는 "원본 영상이 어떤 내용인지 파악하고 후보를 좁힌다"로 되어 있다. 방향은 맞지만, 5단계가 강화된 지금 기준으로는 더 명확해야 한다.

6단계의 목표는 **하이라이트 후보를 새로 발굴하는 것**이 아니라, **5단계 기획서의 대사 스파인과 6단계 검증 브리프가 실제 화면에서 성립하는지 확인하고, 편집 가능한 후보 지도를 만드는 것**이다.

핵심 개선은 아래 5개다.

1. **분석 단위를 "막/비트"로 고정한다.** RMS·키워드가 아니라 5단계의 막 구조와 대사 스파인이 기준이다.
2. **화면 검증 로그를 만든다.** 후보마다 실제 화면 증거, 대사 증거, 오디오 증거, 위험을 기록한다.
3. **대표 후보와 예비 후보를 구분한다.** 같은 기능의 장면을 모두 살리지 않고, 6단계에서 중복을 정리한다.
4. **시청각 충돌을 표시한다.** 대사는 좋은데 화면이 약하거나, 화면은 강한데 메시지와 안 맞는 구간을 별도 위험으로 기록한다.
5. **컷리스트가 아니라 분석 지도에서 끝낸다.** 6단계 산출물은 컷 경계 확정이 아니라, 7단계가 컷리스트를 만들 수 있는 검증된 후보표다.

## 2. 리서치 근거

### 2.1 무대본 영상 편집은 전사와 화면을 함께 로깅한다

다큐멘터리 페이퍼 에딧 워크플로우는 전사에서 대사를 고르고 타임코드를 붙이는 방식으로 이야기 설계도를 만든다. 하지만 영상 분석 단계에서는 그 대사가 실제 화면과 붙었을 때 작동하는지 확인해야 한다. Reduct의 페이퍼 에딧 설명은 전사 기반 선택과 원본 타임코드 연결을 강조한다. 이 원리는 6단계에서 "대사 스파인 → 화면 검증"으로 이어져야 한다.

적용:
- 5단계 대사 스파인의 각 비트에 대해 실제 화면 증거를 확인한다.
- 화면 증거가 약하면 후보를 낮추거나 예비 후보로 둔다.

### 2.2 다큐 편집은 스토리 아크를 기준으로 장면을 고른다

Doc Film Academy의 다큐 편집 워크플로우는 전사에서 테마, 스토리 아크, 캐릭터 변화를 표시하고 페이퍼 에딧을 만든 뒤 조립한다고 설명한다. 6단계는 이 중 "스토리 아크가 실제 클립으로 성립하는지 확인하는 단계"에 해당한다.

적용:
- 전체 영상을 "강한 반응 순"으로 보지 않는다.
- 5단계의 감정 아크 순서대로 대표 화면을 찾는다.
- 각 후보는 `동기`, `공포증거`, `자기인정`, `규칙학습`, `적응`, `퇴각` 같은 이야기 기능을 가져야 한다.

### 2.3 질적 분석은 코드와 증거를 분리해서 기록한다

Nielsen Norman Group의 thematic analysis 설명은 질적 데이터에서 코드를 만들고, 패턴을 찾고, 해석이 데이터에 근거해야 한다는 점을 강조한다. 6단계에 적용하면 화면 분석도 "느낌상 좋다"가 아니라, `코드`, `화면 증거`, `대사 증거`, `판단`이 분리되어야 한다.

적용:
- 후보별로 `story_function`, `screen_evidence`, `subtitle_evidence`, `audio_evidence`, `decision`을 분리한다.
- "재밌음" 같은 주관 판단만으로 후보를 확정하지 않는다.

### 2.4 영상 데이터 분석은 시간·순서·상호작용을 보존해야 한다

사회과학의 비디오 데이터 분석 방법론은 영상 자료를 볼 때 단순 내용뿐 아니라 시간 순서, 상호작용, 맥락을 함께 봐야 한다고 설명한다. 게임 실황도 마찬가지다. 조우, 사망, 반응, 시청자 조언은 순서를 잃으면 의미가 약해진다.

적용:
- "사건 화면"과 "직후 반응"을 분리해서 자르지 않는다.
- 문 규칙 발견, 사망, 도망, 엔딩처럼 앞뒤 맥락이 필요한 구간은 위험 표시를 한다.

### 2.5 YouTube 관점에서는 초반 기대와 핵심 순간의 위치가 중요하다

YouTube Help의 audience retention 문서는 첫 30초가 제목·썸네일 기대와 맞아야 하며, 핵심 순간을 앞쪽에 소개할 수 있다고 설명한다. 6단계에서는 아직 훅을 편집하지 않지만, 어떤 화면이 오픈 루프를 만들 수 있는지는 표시해야 한다.

적용:
- 6단계 후보표에 `hook_potential` 필드를 둔다.
- 훅 후보는 "가장 시끄러운 비명"이 아니라 "기획서의 질문을 여는 화면"이어야 한다.

## 3. 현재 6단계 방식의 부족한 점

| 현재 방식 | 문제 | 개선 |
|---|---|---|
| 전체 흐름표, 주요 내용, 음성 반응 후보 중심 | 다시 신호 기반 하이라이트 발굴로 돌아갈 위험 | 5단계 비트별 화면 검증으로 시작 |
| 화면 검증 구간이 별도 목록 | 왜 그 구간을 봐야 하는지 상위 기준이 약함 | `story_function`과 `기획서 비트 ID`를 붙임 |
| 하이라이트 후보표 | 비명·사망·큰 반응이 과대표집될 위험 | 대표/예비 후보, 중복 기능 정리 |
| 컷리스트로 빨리 넘어갈 수 있음 | 6단계와 7단계 경계가 흐려짐 | 6단계 산출물은 후보 지도까지만 |
| 화면 확인이 스냅샷 중심 | 사건-반응 순서가 끊길 수 있음 | 시작/사건/결과/반응을 함께 기록 |

## 4. 개선된 6단계 정의

### 한 줄 정의

6단계는 **5단계 기획서의 대사 스파인이 실제 화면·오디오·맥락으로 성립하는지 검증하고, 7단계가 사용할 후보 지도를 만드는 단계**다.

### 입력

- 원본 영상
- 원본 SRT
- 5단계 기획서
  - 컨트롤링 아이디어
  - 대사 스파인
  - 감정 아크
  - 포함/제외 기준
  - 6단계 검증 브리프

### 출력

- 막별 화면 검증표
- 후보 구간 지도
- 대표/예비 후보표
- 시청각 충돌·위험 목록
- 7단계로 넘길 분석 브리프

컷리스트, XML, 러프컷은 6단계 출력이 아니다.

## 5. 개선된 6단계 절차안

### 6-1. 기획서 비트 로드

5단계 기획서에서 아래를 가져온다.

| 필드 | 설명 |
|---|---|
| `bit_id` | 대사 스파인 번호 |
| `act` | 막 번호 |
| `story_function` | 동기, 공포증거, 자기인정 등 |
| `target_time` | 대사 타임코드 |
| `screen_question` | 화면에서 확인할 질문 |
| `must_preserve_sentence` | 문장 단위 보존 여부 |

### 6-2. 저비용 후보 범위 잡기

화면을 바로 많이 보지 않는다. 먼저 자막과 오디오로 확인 범위를 좁힌다.

- 대사 스파인 타임코드 주변 `-30초 ~ +60초`
- 직전 사건과 직후 반응이 필요한 구간은 `-90초 ~ +90초`
- 사망·추격·비명은 오디오 피크를 보조로 사용
- 조용한 소감 대사는 오디오 피크가 없어도 유지

이 단계에서 RMS·키워드는 **기획서 비트의 경계와 주변 사건을 찾는 보조**일 뿐이다.

### 6-3. 화면 검증

각 비트마다 화면을 확인한다.

확인 단위:
- `pre_context`: 대사 직전 무슨 일이 있었는가
- `event`: 화면에서 실제 사건이 보이는가
- `reaction`: 대사/표정/플레이 반응이 이어지는가
- `result`: 사망, 성공, 이동, 규칙 발견 같은 결과가 보이는가

후보별로 아래를 기록한다.

| 필드 | 설명 |
|---|---|
| `screen_evidence` | 화면에서 보이는 것 |
| `subtitle_evidence` | 대사 근거 |
| `audio_evidence` | 비명, 웃음, 침묵, 긴장 |
| `context_needed` | 앞뒤 맥락 필요 여부 |
| `risk` | 화면 약함, 반응 잘림, 중복, 공략 과다 등 |
| `decision` | 대표, 예비, 제외, 재검증 |

### 6-4. 대표/예비 후보 정리

각 이야기 기능마다 대표 후보와 예비 후보를 구분한다.

기준:
- 대표 후보: 해당 기능을 가장 잘 보여주는 장면.
- 예비 후보: 대표가 화면상 약하거나 길 경우 대체할 장면.
- 제외 후보: 같은 기능 반복, 화면 약함, 메시지와 무관한 장면.

같은 기능의 비명·사망·추격은 많이 남기지 않는다. "첫 붕괴", "허세 붕괴", "적응 증거"처럼 기능이 다를 때만 여러 개를 남긴다.

### 6-5. 시청각 충돌 점검

아래 상황은 위험으로 표시한다.

- 대사는 중요하지만 화면이 밋밋하다.
- 화면은 강하지만 메시지에 기여하지 않는다.
- 자막 타임코드와 실제 발화·화면 사건이 어긋난다.
- 사건 화면은 있는데 직후 반응이 빠져 있다.
- 시청자 조언·공략 설명이 길어져 주인공 변화가 묻힌다.

### 6-6. 7단계 인계 브리프 작성

6단계 끝에는 컷리스트가 아니라 7단계용 브리프를 만든다.

포함:
- 막별 대표 후보
- 예비 후보
- 반드시 보존할 앞뒤 맥락
- 압축 가능한 부분
- 자막 요약으로 대체할 부분
- 컷 경계 주의점
- 화면 확인 완료/미완료 표시

## 7. 완료 게이트

### G1. 기획서 추적성

통과:
- 모든 대표 후보가 5단계 기획서의 비트 또는 막에 연결된다.

실패:
- "재밌어서"만으로 들어간 후보가 있다.

### G2. 화면 증거

통과:
- 대표 후보에는 화면 근거가 있다.
- 화면 근거가 없는 대사 중심 후보는 그 이유가 기록되어 있다.

실패:
- 대사만 보고 화면 검증 완료로 처리한다.

### G3. 맥락 보존

통과:
- 사건, 결과, 반응의 보존 필요 여부가 기록되어 있다.

실패:
- 사망·조우·규칙 발견 구간에서 직전 사건이나 직후 반응이 빠진다.

### G4. 중복 정리

통과:
- 같은 기능의 후보는 대표/예비/제외로 구분되어 있다.

실패:
- 비슷한 비명, 실패, 탐색이 모두 후보로 남아 있다.

### G5. 7단계 인계 가능성

통과:
- 7단계가 컷리스트를 만들 때 필요한 역할, 보존 이유, 압축 가능성이 기록되어 있다.

실패:
- 후보표는 있지만 왜 살려야 하는지 알 수 없다.

## 8. 백룸 영상에 바로 적용할 방식

백룸 영상의 6단계는 아래 순서로 진행한다.

1. `08_백룸_기획서_대사스파인_2026-07-07.md`의 6막과 20개 스파인 비트를 로드한다.
2. 막별 대표/예비 후보를 화면으로 확인한다.
3. 첫 화면 확인 대상은 아래 6개다.

| 우선순위 | 구간 | 이유 |
|---:|---|---|
| 1 | 07:12~10:59 | 빈 공간 → 첫 엔티티 → 공포 시작 |
| 2 | 19:18~21:33 | 영화/직접 체험 차이와 몸 떨림 |
| 3 | 30:46~39:15 | 규칙 학습과 문 통제감 |
| 4 | 51:06~72:33 | 무섭지만 계속하고 적응하는 후반 |
| 5 | 78:36~82:05 | 소리 장치 이해와 아이러니 엔딩 |
| 6 | 00:34~01:55 | 도입 동기와 혼자 플레이 조건 |

4. 각 구간은 `pre_context`, `event`, `reaction`, `result`로 나눠 기록한다.
5. 결과는 컷리스트가 아니라 `09_백룸_6단계_화면검증_후보지도_YYYY-MM-DD.md` 같은 분석 문서로 저장한다.

## 9. 레드팀

- 리스크 1: 6단계가 너무 무거워질 수 있다. 해결: 모든 구간을 보지 않고 5단계 브리프의 대표/예비 후보부터 본다.
- 리스크 2: 다시 비명·RMS 중심으로 후퇴할 수 있다. 해결: 후보마다 `bit_id`와 `story_function`을 필수로 둔다.
- 리스크 3: 화면 스냅샷만 보고 사건 흐름을 오판할 수 있다. 해결: `pre_context/event/reaction/result`를 함께 기록한다.
- 리스크 4: 대사는 좋은데 화면이 약한 구간을 무리하게 살릴 수 있다. 해결: 화면 약함을 위험으로 표시하고 대사 중심 후보로 분류한다.
- 리스크 5: 6단계에서 컷 경계를 확정하려고 할 수 있다. 해결: 6단계 출력은 후보 지도와 인계 브리프까지만, 컷 경계는 7단계로 넘긴다.
