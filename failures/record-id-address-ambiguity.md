# 기록 ID와 저장 주소의 분리로 생기는 중복

- 상태: 해결·회귀 검증 완료
- 최초 확인: 2026-07-23 Stage 02 첫 테스트 후 자체 검토
- 마지막 검증: 2026-07-23
- 적용 범위: 파일 기록 ID, 저장 경로, 중복 거부, 전역 열거 방지

## 증상

첫 구현은 안전한 프로젝트 상대 경로라면 임의 파일명에 기록을 저장할 수 있었다. 테스트는 통과했지만 같은 ID를 서로 다른 파일명이나 디렉터리에 쓰면 전역 파일 열거 없이 중복을 막을 수 없었다.

## 확인된 원인

안정적인 기록 ID와 파일 저장 주소를 독립적으로 설계하면서 중복 검사의 책임을 별도 인덱스나 전체 탐색에 암묵적으로 넘겼다. Stage 02에는 그런 인덱스가 없고 보호 경계를 넘는 전역 탐색도 허용되지 않는다.

## 실패·해결 이력

| 시점·문맥 | 시도·결과 | 최고 연속 횟수 | 해결·검증 |
|---|---|---:|---|
| Stage 02 10개 테스트 통과 후 계약 재검토 | 임의 상대 경로 API로는 같은 ID의 복수 주소를 방지하지 못함 | 1 | 공통 기록 주소를 `data/records/<id>.json`으로 고정하고 파일명·ID 일치 검증과 회귀 테스트 추가 |

## 해결과 검증

- UUIDv4 ID 하나가 단일 `data/records/<id>.json` 경로에 대응하도록 계약했다.
- 다른 저장 루트와 ID가 다른 파일명을 모두 거부한다.
- 같은 ID를 새로 쓰면 같은 경로의 기본 덮어쓰기 거부가 중복을 차단한다.
- 별도 인덱스, 디렉터리 전역 열거, 보호 경로 접근 없이 회귀 테스트를 통과했다.

## 재사용 규칙

- 파일 기반 고유성을 요구하면서 중앙 인덱스가 없다면 ID와 저장 주소의 결정적 대응을 먼저 검토한다.
- 경로 자유도를 높여 중복 검사를 전역 탐색에 의존하게 만들지 않는다.
- 유형별 디렉터리가 필요해지면 같은 ID의 권위 범위와 충돌 검사를 먼저 다시 결정한다.
