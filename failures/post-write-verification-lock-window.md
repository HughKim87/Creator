# 쓰기 후 검증의 잠금 해제 경쟁 구간

- 상태: 해결·회귀 검증 완료
- 최초 확인: 2026-07-23 Stage 03 구현 자체 검토
- 마지막 검증: 2026-07-23
- 적용 범위: 원자 저장, 배타 잠금, 사후 재읽기, 동시 작성자 오류 판정

## 증상

첫 고수준 I/O 구현은 파일 교체 뒤 잠금을 해제하고 나서 결과를 재읽었다. 그 짧은 사이에 다른 승인 작성자가 정상적으로 갱신하면 첫 작성은 실제로 성공했는데도 사후 결과가 다르다는 실패를 반환할 수 있었다.

## 확인된 원인

원자 교체와 사후 검증을 하나의 트랜잭션 경계로 보지 않고 잠금이 쓰기 순간만 보호한다고 설계했다. 성공 판정에 사용하는 재읽기도 같은 배타 구간에 포함돼야 했다.

## 실패·해결 이력

| 시점·문맥 | 시도·결과 | 최고 연속 횟수 | 해결·검증 |
|---|---|---:|---|
| Stage 03 테스트 작성 전 동시성 검토 | create·update·append의 사후 검증이 잠금 밖에 있어 오판 가능 | 1 | 세 동작의 재읽기·내용 비교·stream hash 계산을 잠금 내부로 이동 |

## 해결과 검증

- record 생성과 갱신은 원자 교체 뒤 같은 잠금 안에서 다시 읽어 정확한 결과를 비교한다.
- event append는 같은 잠금 안에서 전체 stream을 다시 검증하고 최종 hash와 count를 계산한다.
- 잠금 충돌, 기대 hash 불일치, 교체 실패, 성공 흐름 회귀 테스트를 모두 통과했다.

## 재사용 규칙

- 성공 여부를 결정하는 사후 검증은 보호 대상 변경과 같은 잠금·트랜잭션 경계 안에서 수행한다.
- 잠금 해제 후 관찰값은 다른 작성자의 정상 변경을 포함할 수 있으므로 자기 쓰기 검증에 사용하지 않는다.
- 반환할 버전·hash·count도 잠금 내부에서 검증한 snapshot에서 계산한다.
