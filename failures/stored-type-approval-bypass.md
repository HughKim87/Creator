# 저장된 기록 유형의 승인 우회

- 상태: 해결·회귀 검증 완료
- 최초 확인: 2026-07-23 Stage 03 고수준 I/O 자체 검토
- 마지막 검증: 2026-07-23
- 적용 범위: 승인 유형 목록, 직접 삽입 파일, 한 건 조회·목록·갱신

## 증상

첫 `RecordStore`는 생성 요청과 목록 필터의 입력 유형만 승인 집합과 비교했다. 저수준 writer나 직접 파일 편집으로 스키마상 유효하지만 승인되지 않은 `record_type`을 넣으면 ID 조회가 이를 반환하고 목록은 조용히 건너뛸 수 있었다.

## 확인된 원인

승인 검사를 명령 입력 경계에만 두고 저장된 데이터가 이미 신뢰할 수 있다고 가정했다. 공통 스키마의 형식 유효성과 현재 단계의 사용 승인 여부는 별도 조건이었다.

## 실패·해결 이력

| 시점·문맥 | 시도·결과 | 최고 연속 횟수 | 해결·검증 |
|---|---|---:|---|
| Stage 03 24개 테스트 통과 후 저장 경계 검토 | 직접 삽입된 미래 유형이 get에서 노출되고 list에서 은폐될 수 있음 | 1 | get·list·update가 저장된 `record_type`도 승인 집합과 대조하고 불일치 시 전체 실패하도록 보강 |

## 해결과 검증

- 고수준 진입점이 읽은 모든 단일 기록의 저장 유형을 다시 승인 검사한다.
- 승인되지 않은 유효 기록을 직접 삽입한 fixture에서 get과 list가 모두 `unapproved_record_type`으로 실패함을 확인했다.
- 생성 호출의 승인 검사와 저장 데이터의 승인 검사를 독립적으로 유지한다.

## 재사용 규칙

- 입력 인수의 허용 목록과 저장 데이터의 허용 목록을 둘 다 검사한다.
- 알 수 없는 유형을 목록에서 조용히 건너뛰지 않는다. 직접 편집·구버전·우회 writer의 증거일 수 있으므로 fail-closed 한다.
- 구조 스키마에 맞는다는 사실을 현재 단계에서 승인된 의미 유형이라는 판정으로 사용하지 않는다.
