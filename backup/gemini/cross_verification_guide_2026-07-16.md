# 교차검증 가이드 — Gemini 프로젝트 진단 및 개선 청사진

- **작성일**: 2026-07-16
- **대상**: Gemini 외 다른 AI 에이전트 (Claude, Codex 등)
- **목적**: `blueprint_report` 문서에 기술된 프로젝트의 문제점 진단 및 4단계 개선 청사진에 대한 독립적이고 비판적인 교차검증을 수행한다.
- **원칙**: 이 검증 과정은 **읽기 전용**이다. 프로젝트의 실제 상태 파일이나 워크플로우를 승격하지 않는다.
- **보고 방식**: 검증을 완료한 후, 검증 결과 보고서는 gemini 폴더 내에 `cross_verification_report_[agent]_2026-07-16`(확장자 md) 형식의 파일명으로 작성하여 추가한다.

## 2. 자동 및 로컬 환경 사실 검증 (체크리스트)

검증자는 아래 명령을 직접 실행하고, 그 결과가 청사진 보고서의 진단 내용과 부합하는지 재현 및 대조해야 합니다.

### 2.1. 프로젝트 사전 검사 및 현황 확인
```powershell
tools\project_preflight.bat
```
- **기대값**: `PROJECT CONTROL CONTEXT`에서 active task 정보, `outputs/SESSION_HANDOFF.md` 존재 여부, git dirty 상태를 확인하고 기록합니다.

### 2.2. 정형 문서 검사 (`doccheck` 상태 확인)
```powershell
tools\run_doccheck.bat
```
- **기대값**: `gemini/` 폴더가 최상위의 미분류 폴더(허용되지 않은 폴더)로 등록되어 있어 `[ERROR] gemini - 미분류 디렉토리. 모든 작업물은 outputs/ 아래에 둔다` 오류가 검출되는지 확인합니다.
- **주의**: 이 오류가 검출되는 것은 사용자 요청에 따른 정형 구조 충돌이므로 정상입니다. 파일 내에 한글 고유명사(특정 채널명 등)와 같은 `task facts`에 의한 위반 에러가 전부 정비되었는지 확인합니다.

### 2.3. Git 경계 및 `outputs/` 추적 여부 진단
```powershell
git status
git ls-files outputs
```
- **기대값**: 
  - `outputs/` 내의 파일들이 Git에 의해 강제로 추적되고 있는지, `.gitignore`에 정의된 정책(inputs/는 배제, outputs/는 추적)이 실제 `PROJECT_RULES.md`의 "outputs는 커밋 금지"라는 원칙과 모순되는 구조를 가지고 있는지 재현하여 기술합니다.

## 3. 비판적 문서 검토 (판단 및 제안 검증)

자동 검사로 확인하기 어려운 아키텍처 제안의 타당성을 아래 질문들에 따라 검토하고, 반증 논리를 제시합니다.

### 3.1. [제안 1] 행동 회귀 Fixture의 실효성
- **질문**: `tests/fixtures/`에 예외 동작 시나리오를 만들고 `preflight`/`doccheck`에 녹여내는 것이 에이전트의 이탈 행동(inputs 무단 수정 등)을 실질적으로 통제할 수 있는가? 아니면 검사 자체를 우회하는 fail-open의 허점이 여전히 존재할 것인가?

### 3.2. [제안 2] Graphify 지식 그래프 도입 리스크
- **질문**: `.graphifyignore`로 `inputs/`와 `outputs/`를 가리는 것만으로 외부 API 및 로컬 분석 시 발생할 수 있는 데이터 누출(특히 미디어 전사 텍스트 내 개인정보 등)을 완전히 차단할 수 있는가?
- **질문**: 로컬 지식 그래프의 색인 유지를 위한 비용(토큰 및 생성 시간)이 실제 에이전트의 재탐색 비용보다 정말 적은가?

### 3.3. [제안 3] Git Worktree와 심볼릭 링크 격리성
- **질문**: Windows OS 환경에서 에이전트가 `outputs/`에 접근할 때 심볼릭 링크(또는 Junction) 생성 권한 오류가 발생할 가능성이 높다. 이 장벽을 넘기 위한 헬퍼 스크립트나 격리 시나리오가 현실적인가?

### 3.4. [제안 4] 대표 샘플(7C) 승인 록(Lock) 메커니즘
- **질문**: 7C 단계 통과 전 7D 전체 타임라인 확장을 기술적으로 락킹(locking)하는 제안이 사용자의 작업 지연(병목)을 지나치게 유발하지는 않는가? 사용자가 부재중일 때의 'Draft Mode' 우회 설계가 거버넌스의 허점이 되지 않겠는가?
