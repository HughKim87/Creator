# 레이어 기반 개선 실행 계획

- 작성일: 2026-07-18
- 상태: 정본(active). `docs/rebuild/AGENT_EXECUTION_PLAN.md`를 **대체**한다.
- 대상 독자: 이 프로젝트를 이어받는 모든 에이전트와 사용자.

## 0. 이 문서의 위상과 사용법

이 문서는 프로젝트 개선 작업의 **유일한 실행 정본**이다. 실행할 내용, 하지 않을
내용, 완료 판정 기준을 모두 여기에 둔다. 다른 문서는 이 문서를 링크하되 절차를
복사하지 않는다.

읽기 순서:

1. `AGENTS.md`
2. `PROJECT_RULES.md`
3. `SESSION_HANDOFF.md` (현재 상태·다음 행동)
4. **이 문서** (무엇을 왜 어떻게)
5. 현재 레이어의 §5 해당 절만

### 이 문서가 길고 상세한 이유

세션과 에이전트가 바뀌어도 같은 결과가 나와야 한다. 계획이 요약본이면 다음
에이전트가 빈칸을 자기 판단으로 채우고, 그 판단은 거의 항상 "더 크고 더 안전하게"
쪽으로 기운다. 2026-07-17 세션이 정확히 그렇게 실패했다(§1).

**문서는 상세하게, 작업은 작게.** 이 둘을 혼동하지 않는다. 길이를 줄여야 할 대상은
구현 범위와 절차 비용이지 명세의 정밀도가 아니다.

## 1. 배경: 왜 계획을 바꿨는가

### 1.3 사용자 의도와 방향 (2026-07-18, 원문 보존)

> 소프트웨어급의 절차를 도입하기보다는, 프로젝트가 안정적으로 일정한 퀄리티를
> 만들어낼수있는 기본적인 워크플로우와 프레임워크 구축을 다지고 싶었던 거라고...

> "내가 원하는 그림은, 정말 꼭 필요한 구조를 단계별로 도입하는거였어.

> 3. 파일을 좀더 빠르게 읽고 쓰기 편하도록 플러그인 또는 툴 도입
> 4. 파일 사용 및 관리 룰 적용
> 5. 프로젝트 워크플로우 룰 적용
> 6. 프로젝트 워크플로우 구조 도입
> 7. 프로젝트 워크플로우 플러그인 또는 툴 도입
> 8. 프로젝트 워크플로우 스킬 다듬기
>
> 뭔가 이런 느낌으로 기본적인 프로젝트의 룰과 구조, 개선을 진행하고 그 위에
> 이 프로젝트의 목적에 맞는 룰, 구조, 개선을 또다시 진행하고..
>

> 그런 재구축 작업을 하고싶었어. 모든걸 다 부수고 아예 새롭고 번거로운 비싼비용의
> 과정을 마구잡이로 때려넣는게 아니라..."

문서 형식에 대한 지시:

> "문서자체는 디테일하고 길어야지. 그래야 세션이 바뀌어도 agent 가 바뀌어도
> 의도한대로 실행할수있잖아."

### 1.4 위 원문에서 도출한 실행 원칙

1. **교체가 아니라 보강.** "모든걸 다 부수고"가 아니라 "기존의 체계에서 꼭 필요한
   새로운 구조만". `backup/`은 폐기 대상이 아니라 자산이다.
2. **2층 구조.** 먼저 **기반**(프로젝트 일반의 룰·구조·툴 = L1~L4), 그 위에
   **영상 제작 목적에 맞는 층**(워크플로우 룰·구조·툴·스킬 = L5~L8). 순서를
   뒤집지 않는다. 이 계획의 레이어 번호는 사용자의 8단계와 1:1 대응한다.
3. **단계별 도입.** 한 번에 완성이 아니라 레이어 단위로 얹고, 각 레이어에서 멈출 수
   있어야 한다.
4. **문제 개선과 생산성 향상은 한 세트.** 안정성만 올리고 작업이 느려지면 실패다.
   그래서 §2.1의 원칙 2(생산성 정당화)가 게이트다.
5. **비용 상한이 설계 제약이다.** "미칠듯한 비용폭발"을 피하는 것이 요구사항이므로,
   반나절 원칙(§2.1-3)과 금지 목록(§2.3)은 편의가 아니라 필수 조건이다.
6. **문서는 상세하게, 작업은 작게.** 다음 세션·다른 에이전트가 같은 결과를 내야
   한다. 계획 축약은 금지, 구현 범위 축약은 필수.

즉 판정 기준은 테스트 개수나 아키텍처 완성도가 아니라 **실제 작업 속도와 결과
일관성**이다.

### 1.4 이번 계획이 바꾸는 것

| 구분 | 기존 계획 | 이 계획 |
|---|---|---|
| 기본 자세 | 신규 구조로 이식 | 기존 체계 위에 얹기 |
| 단위 | 단계(Stage), 며칠~주 | 레이어(Layer), 반나절 |
| 성공 판정 | 테스트·증거 패키지 | "무엇이 빨라졌나" 한 줄 |

| 폐기 대상 | — | 증거 패키지 규약, 레드팀 절차, 골든 비교 의무, 30일 관찰 |

## 2. 모든 레이어에 적용되는 판단 기준

### 2.1 원칙 (예외 없음)

1. **기존 것 위에 얹는다.** `backup/`의 룰·문서·툴·스킬은 자산이다. 대체가 아니라
   정리·연결·강제화가 기본이다. 재작성은 "고쳐 쓰는 비용 > 다시 쓰는 비용"이
   명백할 때만 하고, 그 근거를 레이어 기록에 남긴다.
2. **생산성 정당화.** 각 레이어는 착수 전에 "이걸로 무엇이 빨라지거나 덜 틀리는가"를
   한 문장으로 쓴다. 못 쓰면 그 레이어는 건너뛴다. 이건 형식이 아니라 게이트다.
3. **반나절 원칙.** 한 레이어의 구현은 2~4시간 안에 끝난다. 넘어가면 중단하고
   범위를 쪼개거나 버린다(§7).
4. **되돌릴 수 있게.** 각 레이어는 삭제·되돌리기 절차를 함께 남긴다. 원본
   영상·자막과 `inputs/`는 어떤 레이어에서도 건드리지 않는다.
5. **강제되지 않는 룰은 룰이 아니다.** 문서에만 있고 아무도 검사하지 않는 규칙은
   지켜지지 않는다. 룰 레이어(L1·L4·L5)는 반드시 그 룰을 검사하는 수단(체크
   명령, 훅, 템플릿 중 하나)을 함께 만든다. 단, 검사 수단은 **한 개 명령**을 넘지
   않는다.

### 2.2 레이어 착수 전 4문항 (핸드오프에 답을 기록)

1. 이 레이어가 없어서 지금 실제로 겪는 불편이 무엇인가? (구체 사례 1개)
2. 이걸로 무엇이 빨라지거나 덜 틀리는가?
3. `backup/`에 이미 있는 것은 무엇이고, 실제 델타는 무엇인가?
4. 반나절 안에 끝나는가? 아니면 어디를 잘라야 하는가?

### 2.3 이 계획에서 금지하는 것

- 구체계 기능의 전면 재작성, 신규 상태 정본 추가(정본은 항상 하나)
- 단계별 증거 패키지(`STAGE_REPORT`/`COMMAND_RESULTS`/`FILE_CHANGES`/
  `RISKS_AND_ROLLBACK` 4종 세트) 생산
- 독립 QA 에이전트·레드팀 에이전트 역할 분리 절차
- 골든 비교 의무, 30일 관찰 기간, 실제 제작 10건 게이트
- 레이어당 2개를 초과하는 신규 CLI 명령 추가
- `inputs/`·`outputs/` 트리 열람·복사·인덱싱 (PROJECT_RULES의 User Data Boundary)
- 사용자 승인 없는 커밋·푸시·태그·설치·외부 전송

### 3.3 실측된 진짜 문제 3가지

기존 계획이 해결하려던 것 중, 실제로 후후님이 겪는 비용이 확인된 것만 남긴다.

| # | 문제 | 증상 | 해당 레이어 |
|---|---|---|---|
| P1 | **상태 분산** | 현재 작업 상태가 `outputs/SESSION_HANDOFF.md`, `CURRENT.json`, `WORKFLOW_STATE.json`, `WORKFLOW_RULE_REGISTRY.json`, `edit_memory/CURRENT.json`, 산출물 메타데이터 블록에 흩어져 있음. 세션마다 재파악 비용 발생 | **L2** |
| P2 | **룰 미강제** | 룰이 문서에만 있어 위반이 조용히 통과. 실패가 성공처럼 보고된 이력 있음 | **L1**, L4 |
| P3 | **도구 발견성** | `tools/` 아래 도구가 무엇을 언제 쓰는 것인지 매번 다시 확인해야 함 | **L3**, L7 |

이 3개 외의 문제는 이 계획의 범위가 아니다. 새 문제가 발견되면 §7 절차로 사용자에게
보고하고 레이어를 추가할지 결정한다.

| L5 | 워크플로우 룰 | — | L4 | 2~3시간 |

| L7 | 워크플로우 툴 | P3 | L6 | 2~3시간 |
| L8 | 스킬 다듬기 | — | L7 | 2~4시간 |

합계 예상 19~28시간(약 3~5 작업일). 기존 계획의 15~22 인일 대비 대폭 축소.

**레이어는 순서대로 진행하되, 각 레이어 종료 시 사용자가 "다음 레이어 진행 / 여기서
멈춤 / 실제 영상 작업 먼저"를 선택한다.** 전부 완주가 목표가 아니다. 어느 레이어에서
멈춰도 그 시점까지가 온전히 동작해야 한다.

## 5. 레이어별 상세

각 레이어는 동일한 8개 항목으로 기술한다. 구현 에이전트는 해당 절만 읽고 작업한다.

### L0 — 정리와 기준선

**목적.** 두 체계(legacy + 2026-07-17 재구축)가 동시에 "정본"처럼 보이는 상태를
끝내고, 새 세션이 항상 이 계획에 도달하게 한다.

**생산성 정당화.** 다음 세션 에이전트가 폐기된 9단계 계획을 읽고 다시 확장하는 것을
막는다. 이 레이어를 건너뛰면 이번 실패가 그대로 재발한다.

**현재 상태.** `AGENTS.md`와 `SESSION_HANDOFF.md`가 `docs/rebuild/AGENT_EXECUTION_PLAN.md`를
가리킨다. 재구축 코드 약 2,000줄이 미커밋 상태로 워킹트리에 있다.

**실제 델타.**

1. `docs/rebuild/AGENT_EXECUTION_PLAN.md` 최상단에 폐기 블록 삽입(삭제하지 않음):
   ```
   > **폐기됨(2026-07-18).** 이 계획은 전면 재작성을 전제해 비용이 폭발했다.
   > 현재 정본은 `docs/improvement/LAYER_PLAN.md`다. 이 문서는 이력 보존용이며
   > 실행 근거로 사용하지 않는다.
   ```
2. `docs/rebuild/stage-05~08` 지시서 4개에 동일한 폐기 블록 삽입.
3. `AGENTS.md`: 실행 라우팅을 `docs/improvement/LAYER_PLAN.md`로 변경.
4. `PROJECT_RULES.md`의 `Document Read/Write` 시작 순서에서 master plan 지칭을 이
   문서로 교체.
5. `SESSION_HANDOFF.md`를 이 계획 기준으로 재작성(현재 상태 / 다음 레이어 / 대기 결정).
6. 재구축 산출물을 **동결 보관 목적으로 커밋**(사용자 승인 필요). 커밋 메시지에
   "동결 보관, 이 계획의 어떤 레이어도 이 코드에 의존하지 않음"을 명시.
   - Windows에서 `.git/index.lock`(0바이트 잔존) 삭제가 선행돼야 한다.

**완료 기준.**

- 새 세션이 `AGENTS.md`부터 읽었을 때 3단계 안에 이 문서에 도달한다.
- 폐기된 계획 문서 5개 모두 최상단에 폐기 블록이 있다.
- `git status`가 깨끗하다(재구축 산출물이 커밋되어 보존됨).

**하지 않을 것.** 재구축 코드 삭제, `docs/rebuild/stage-00~04` 보고서 수정,
legacy 문서 수정.

**예상.** 1~2시간. **롤백.** 문서 편집만이므로 `git revert` 1회.

### L1 — 기본 프로젝트 룰 적용

**목적.** legacy `PROJECT_RULES.md`의 파일 입출력·폴더 구분 규칙을 현재 저장소에
실제로 적용하고, **그 규칙을 검사하는 한 개 명령**을 붙인다.

**생산성 정당화.** "이 파일 어디에 둬야 하지"를 매번 판단하지 않는다. 규칙 위반을
사람이 눈으로 찾지 않는다(P2).

**현재 상태.** legacy `backup/PROJECT_RULES.md`의 `File Rules` 절에 이미 완성도 높은
규칙이 있다(inputs/outputs 경계, ASCII 이름, 원본 덮어쓰기 금지, `temp/` 금지,
프레임워크와 영상별 자산 분리, 커밋 대상 제한). 현재 저장소 루트의
`PROJECT_RULES.md`는 재구축용으로 작성되어 이 규칙이 빠져 있다.

**실제 델타.**

1. 루트 `PROJECT_RULES.md`에 `File Rules` 절 이식. **legacy 문구를 그대로 가져오되**
   현재 구조에 맞는 최소 수정만 한다. 새 규칙을 발명하지 않는다. 이식할 항목:
   - `inputs/`는 사용자 원본 전용. 에이전트는 명시 요청 없이 아무것도 바꾸지 않는다.
   - 입력에서 파생된 모든 파일은 `outputs/` 아래에 둔다.
   - `docs/`·`tools/`·`skills/`·`tests/`는 영상과 무관한 재사용 프레임워크 전용.
   - 폴더·파일 이름은 ASCII를 쓴다.
   - 원본 영상·자막·사용자 작성 파일을 덮어쓰지 않는다.
   - 프로젝트 `temp/` 디렉터리와 중복 백업본을 만들지 않는다.
   - `inputs/`·`outputs/`는 절대 스테이징·커밋하지 않는다.
2. 기존 `workflow check`에 **룰 검사 1개**(`project_rules`) 추가. `src/video_workflow/checks/`
   에 파일 1개, 100줄 이내. 검사 항목:
   - 루트에 `temp/`가 존재하지 않는다.
   - `git ls-files` 기준 추적 파일에 `inputs/`·`outputs/` 경로가 없다.
   - 프레임워크 폴더(`docs/`·`tools/`·`skills/`·`tests/`) 추적 파일 이름이 ASCII다.
   - **주의:** 이 검사는 `git ls-files` 결과만 쓴다. `inputs/`·`outputs/` 내부를
     재귀 열거하지 않는다(User Data Boundary).
3. 폴더 스캐폴드: `inputs/`·`outputs/`가 없으면 만들고 각각 `.gitkeep`과 한 줄
   설명 `README.md`를 둔다.

**완료 기준.**

- `workflow check --scope fast`가 `project_rules` PASS를 보고한다.
- 일부러 `temp/` 폴더를 만들면 그 검사가 FAIL한다(1회 확인).
- 루트 `PROJECT_RULES.md`를 처음 읽는 사람이 "어떤 파일을 어디에 두는가"에 답할 수 있다.

**하지 않을 것.** 새 규칙 발명, legacy 규칙 문구 재작성, `tools/guard/agent_guard.py`
포팅, 훅 체계 신설.

**예상.** 2~3시간. **롤백.** 검사 파일 1개 삭제 + `PROJECT_RULES.md` revert.

### L2 — 기본 프로젝트 구조 (파일 기반 데이터 처리)

**목적.** P1(상태 분산) 해결. **영상 프로젝트 하나당 상태 정본 파일 하나.**

**생산성 정당화.** 세션 재개 시 파일 하나만 읽으면 현재 상태를 안다. 목표: 재개까지
2분 이내. 지금은 5곳 이상을 확인해야 한다.

**현재 상태.** 상태가 다음에 분산되어 있다: `outputs/SESSION_HANDOFF.md`(작업 카드),
`outputs/WORKFLOW_STATE.json`, `outputs/WORKFLOW_RULE_REGISTRY.json`,
`outputs/07_edit_export/edit_memory/CURRENT.json`, 각 산출물 파일의 메타데이터 블록.

**설계 결정(고정).** 저장 방식은 **JSON 파일**이다. SQLite를 쓰지 않는다. 사용자가
"파일을 기반으로 한 데이터 처리 구조"를 명시했고, 1인·순차 작업에는 동시 writer
제어가 필요 없다. 2026-07-17 재구축의 SQLite 저장소는 §3.2에 따라 동결 상태다.

**실제 델타.**

1. **상태 파일 스펙 문서** `docs/improvement/STATE_FILE_SPEC.md` 작성. 위치는
   `outputs/<project>/state.json`. 필드(초안, L2 착수 시 사용자 확정):
   ```json
   {
     "schema_version": 1,
     "project_id": "사람이 읽는 짧은 식별자",
     "source_id": "원본 식별자",
     "source_fingerprint": {"sha256": "...", "size": 0},
     "path": "촬영전 | 촬영완료본",
     "current_stage": 6,
     "stage_status": "in_progress | waiting_user | blocked | done",
     "blocker": null,
     "artifacts": [
       {"role": "cutlist", "path": "outputs/07_.../cuts.csv",
        "sha256": "...", "approval": "draft", "stage": 7}
     ],
     "decisions": [
       {"at": "2026-07-18T10:00:00+09:00", "who": "user",
        "what": "소재 확정: XX", "stage": 1}
     ],
     "updated_at": "2026-07-18T10:00:00+09:00"
   }
   ```
   기존 `CURRENT.json`·`WORKFLOW_STATE.json`·작업 카드의 필드를 여기로 흡수한다.
2. **읽기/쓰기 모듈** `src/video_workflow/project_state.py` — 200줄 이내, 표준
   라이브러리만. 내용: 로드, 검증(필수 필드·타입), 원자적 저장(임시 파일 →
   `os.replace`), 상태 요약 문자열 생성.
3. **사람이 읽는 뷰** `outputs/<project>/STATE.md`를 `state.json`에서 생성.
   파일 상단에 `<!-- 생성 문서: state.json에서 만들어짐. 직접 편집 금지 -->`.
   생성 명령은 L3에서 CLI에 붙인다. L2에서는 함수까지만.
4. **마이그레이션 안내** `docs/improvement/STATE_MIGRATION.md`: 기존 분산 파일의 어떤
   필드가 `state.json`의 어디로 가는지 대응표. **자동 변환 스크립트는 만들지 않는다.**
   실제 영상 작업에서 처음 필요할 때 사용자와 함께 1건 수동 이행한다.

**완료 기준.**

- 상태 정본이 파일 1개다. 스펙 문서에 모든 필드의 의미가 적혀 있다.
- 샘플 `state.json` 하나로 저장·로드·검증·STATE.md 생성이 동작한다(단위 테스트 3~5개).
- 잘못된 상태 파일(필수 필드 누락, 타입 불일치)은 조용히 통과하지 않고 실패한다.

**하지 않을 것.** SQLite·DB·이벤트 소싱·append-only 로그, 낙관적 동시성 제어,
승인 challenge/provenance 체계, 산출물 staging/quarantine 생명주기, 상태 전이
함수의 코드화(전이 규칙은 L5에서 문서로).

**예상.** 3~4시간(이 계획에서 가장 큰 레이어). **롤백.** 신규 파일 3개 삭제.

### L3 — 파일을 빠르게 읽고 쓰기 위한 툴

**목적.** P3(도구 발견성) 1차 해결. 자주 하는 파일 작업을 외우기 쉬운 한 명령으로.

**생산성 정당화.** 도구 경로·옵션을 매번 다시 확인하지 않는다. 목표: 자주 쓰는 작업
3개가 각각 명령 1줄로 끝난다.

**현재 상태.** `backup/tools/`에 8개 이상 도구가 있고 `tools/README.md`가 있으나,
호출 규약이 제각각이고(`.bat` 래퍼, 직접 python 실행) 언제 무엇을 쓰는지가 분산돼 있다.

**실제 델타.**

1. **사용 빈도 조사 후 상위 3개 선정.** 후보: `projectctl.py`(프로젝트 조작),
   `source_frame_assets.py`/`register_source_assets.py`(원본 자산 등록),
   `edit_quality_audit.py`(컷리스트 감사), `synccheck/`(자막·오디오 동기). **선정은
   사용자에게 물어서 확정한다**(추측 금지).
2. 선정된 것만 `workflow` CLI 하위 명령으로 노출. **신규 명령 최대 2개.**
   기존 도구는 그대로 두고 얇게 감싼다(재작성 금지).
3. `state.json` 갱신이 필요한 도구는 L2의 `project_state.py`를 통해서만 쓴다.
4. `tools/README.md`를 "언제 무엇을 쓰는가" 한 줄 요약표로 갱신.

**완료 기준.** 선정된 3개 작업이 각각 한 명령으로 실행된다. README 표만 보고 어떤
도구를 쓸지 결정할 수 있다.

**하지 않을 것.** 도구 재작성, 사용하지 않는 도구의 이관·정리, 새 도구 신설.

**예상.** 2~3시간. **롤백.** CLI 하위 명령 제거(기존 도구는 무변경).

### L4 — 파일 사용 및 관리 룰

**목적.** 산출물의 이름·버전·승인 상태·보관 규칙을 **실사용 가능한 크기로** 정하고
검사한다.

**생산성 정당화.** "이 파일이 최신인가, 승인된 것인가"를 파일을 열어보지 않고 안다.
지금은 산출물마다 17개 필드짜리 메타데이터 블록을 읽어야 한다.

**현재 상태.** legacy `01_youtube_production_workflow.md`에 산출물 메타데이터 17개
필드와 승인 상태 7종(`draft`/`needs_user_decision`/`approved_for_calibration`/
`approved_for_next_stage`/`revision_requested`/`superseded`/`blocked`)이 정의돼 있다.
정확하지만 매번 작성하기에 무겁다.

**실제 델타.**

1. **승인 상태 축소 제안**(사용자 확정 필요): 7종 → 4종
   `draft` / `needs_user_decision` / `approved` / `superseded`.
   `approved_for_calibration`과 `approved_for_next_stage`의 구분은 실제로 7단계에서만
   의미가 있으므로, 상태 대신 `stage` 필드와의 조합으로 표현한다.
2. **산출물 메타데이터 축소**: 17개 → 필수 6개
   (`role`, `path`, `sha256`, `approval`, `stage`, `source_id`).
   나머지는 `state.json`의 `decisions`나 파일 자체 내용으로 대체.
   메타데이터의 위치는 **각 파일 상단 블록이 아니라 `state.json`의 `artifacts` 배열**
   로 옮긴다(정본 1개 원칙).
3. **파일명 규칙** 1줄 정의: `<stage>_<role>_v<n>.<ext>`. 기존 파일 소급 개명은 하지
   않는다.
4. `workflow check`에 검사 1개 추가: `state.json`의 `artifacts` 목록에 적힌 파일이
   실제로 존재하고 sha256이 일치하는가. 불일치는 실패로 보고하되 **자동 수정하지 않는다.**

**완료 기준.** 승인 상태 4종·필수 필드 6개가 문서로 확정됐고, 검사 명령이 상태
파일과 실제 파일의 불일치를 잡는다.

**하지 않을 것.** 승격 프로토콜, staging/ready/quarantined 생명주기, 자동 격리·삭제,
기존 산출물 일괄 마이그레이션.

**예상.** 2시간. **롤백.** 문서 revert + 검사 1개 제거.

### L5 — 프로젝트 워크플로우 룰

**목적.** 8단계 제작 워크플로우를 **실제로 지켜지는 크기로** 단순화한다.

**생산성 정당화.** 단계 완료 조건이 1~3개면 매번 확인 가능하다. 지금은 단계마다
게이트·하위 단계·품질 게이트가 중첩돼 있어 실제로는 건너뛰게 된다.

**현재 상태.** `01_youtube_production_workflow.md`가 8단계와 게이트를 잘 정의하고 있고,
`docs/WORKFLOW_CONTRACT.json`이 기계 판독용 계약을 담고 있다. 7단계는 7A~7D로 다시
나뉘고, `EDITING_QUALITY_STANDARD.md`의 Q0~Q6가 추가로 걸린다. **정의는 훌륭하지만
총량이 과하다.**

**실제 델타.**

1. `docs/improvement/WORKFLOW_RULES.md` 신설. 8단계는 **그대로 유지**하고 각 단계에
   대해 3줄만 남긴다: (입력 / 산출물 / 완료 조건 1~3개).
   원본 정의는 `backup/01_youtube_production_workflow.md`를 참조 링크로 남긴다.
2. **사용자 판단 지점만 명시적으로 고정**: 소재 확정(1), 콘셉트 확정(2), 대표 샘플
   편집 방향(7), 업로드(8). 이 4개는 에이전트가 대신 결정하지 않는다.
3. `WORKFLOW_CONTRACT.json`은 **참조 자료로 강등**한다. 실행 규칙은 위 문서가
   정본이고, 계약 JSON을 코드로 해석하지 않는다.
4. 7A~7D 하위 단계와 Q0~Q6 품질 게이트는 **7단계 내부 체크리스트**로 유지하되,
   워크플로우 전이 게이트로는 쓰지 않는다.

**완료 기준.** 한 페이지짜리 워크플로우 규칙 문서가 있고, 각 단계 완료 조건이 3개
이하이며, 사용자 판단 지점 4개가 명시돼 있다.

**하지 않을 것.** 새 단계 발명, 단계 번호 변경, 전이 함수 코드화, 승인 게이트 자동 차단.

**예상.** 2~3시간. **롤백.** 신규 문서 1개 삭제(legacy 문서 무변경이므로 즉시 복구).

### L6 — 프로젝트 워크플로우 구조

**목적.** L5의 규칙이 폴더·파일 구조로 실제 드러나게 한다.

**생산성 정당화.** 새 영상을 시작할 때 폴더 구조를 매번 손으로 만들지 않는다.
현재 단계가 폴더만 봐도 보인다.

**현재 상태.** `outputs/` 아래 단계별 폴더 관례가 있으나(예: `07_edit_export`), 생성은
수동이고 프로젝트마다 편차가 생긴다.

**실제 델타.**

1. 표준 프로젝트 폴더 레이아웃을 `docs/improvement/WORKFLOW_RULES.md`에 확정:
   ```
   outputs/<project>/
   ├─ state.json          (L2 상태 정본)
   ├─ STATE.md            (생성 뷰)
   ├─ 04_subtitles/
   ├─ 06_analysis/
   ├─ 05_planning/
   ├─ 07_edit_export/
   └─ 08_review/
   ```
   (단계 번호는 legacy 관례를 그대로 보존한다. 촬영완료본 실행 순서는 6→5다.)
2. 프로젝트 생성 명령 1개: 폴더 스캐폴드 + `state.json` 초기화 (L7에서 CLI 노출).
3. 단계 폴더는 **필요할 때 생성**한다. 빈 폴더를 미리 만들지 않는다(legacy 규칙 유지).

**완료 기준.** 새 프로젝트 생성이 명령 1회로 끝나고, 결과 구조가 문서와 일치한다.

**하지 않을 것.** 기존 프로젝트 폴더 일괄 재배치, 단계 폴더 자동 생성 강제.

**예상.** 3시간. **롤백.** 명령 제거 + 생성된 폴더 삭제(사용자 승인 후).

### L7 — 프로젝트 워크플로우 툴

**목적.** 현재 상태 확인과 단계 전환을 명령으로 만든다.

**생산성 정당화.** "지금 어디까지 했지"에 명령 1개로 답한다. 목표: 세션 재개 2분 이내
(L2의 목표를 실제로 달성하는 수단).

**현재 상태.** `backup/tools/workflow_gate.py`, `projectctl.py`가 원형이다.

**실제 델타.** 신규 CLI 명령 **최대 2개**:

1. `workflow status --project <name>` — `state.json`을 읽어 현재 단계, 상태, 블로커,
   다음 필요 행동, 미승인 산출물을 출력. `STATE.md`도 갱신.
2. `workflow next --project <name> --to <stage> --reason "..."` — 단계 전환.
   L5의 완료 조건을 확인하고, 미충족이면 **이유를 출력하고 거부**한다. 상태 파일은
   변경하지 않는다.

두 명령 모두 L2의 `project_state.py`만 통해 상태를 읽고 쓴다.

**완료 기준.** 두 명령이 동작하고, 완료 조건 미충족 시 전환이 거부되며 그 이유가
사람이 읽을 수 있는 문장으로 출력된다.

**하지 않을 것.** 승인 challenge·provenance 체계, 이벤트 로그, 자동 단계 진행,
동시성 제어.

**예상.** 2~3시간. **롤백.** 명령 2개 제거.

---

### L8 — 워크플로우 스킬 다듬기

**목적.** 스킬 11개를 실사용 기준으로 정리하고, L2~L7에서 정한 규약에 맞춘다.

**생산성 정당화.** 실제로 쓰는 스킬이 상태 파일·폴더 규약과 맞물려 돌아간다. 안 쓰는
스킬을 매번 후보로 고려하지 않는다.

**현재 상태.** `backup/skills/` 11개(1~8단계 8개 + 보조 3개), `SKILL_CONTRACT.md`로
공통 항목 관리. 문서상 상태는 "1차 보강 완료" 수준.

**실제 델타.**

1. **사용 실태 분류**(사용자 확인 필수): 각 스킬을 `유지` / `보류` / `폐기 후보`로
   분류한다. 추측하지 않는다.
2. `유지` 스킬만 다음을 맞춘다:
   - 입력·출력 경로를 L6 폴더 레이아웃 기준으로 기술
   - 산출물 등록을 L4 규약(`state.json`의 `artifacts`)으로 통일
   - 단계 완료 조건을 L5 문서와 일치시킴
3. `보류`·`폐기 후보`는 **건드리지 않고 목록만 남긴다.** 삭제는 사용자 승인 후 별도 작업.

**완료 기준.** 유지 스킬의 입출력이 실제 폴더·상태 규약과 일치하고, 각 스킬 문서
상단에 해당 단계와 완료 조건이 한 줄로 적혀 있다.

**하지 않을 것.** 새 스킬 작성, 스킬 로직 재작성, 폐기 후보 즉시 삭제.

**예상.** 2~4시간(유지 스킬 개수에 비례). **롤백.** 스킬 문서 revert.

## 6. 레이어 공통 실행 절차

한 레이어 = 한 세션이 원칙이다. 세션이 길어지면 §7로 간다.

1. **시작.** `AGENTS.md` → `PROJECT_RULES.md` → `SESSION_HANDOFF.md` → 이 문서의
   해당 레이어 절만 읽는다. 다른 레이어 절, 폐기된 계획, `docs/rebuild/` 보고서는
   읽지 않는다.
2. **착수 확인.** §2.2의 4문항에 답을 적는다. 답이 안 나오면 사용자에게 묻는다.
3. **사용자 확인이 필요한 항목 처리.** 해당 레이어에 "사용자 확정 필요"로 표시된
   항목(L3 도구 선정, L4 승인 상태 축소, L8 스킬 분류 등)은 **추측하지 말고 먼저 묻는다.**
4. **구현.** 델타 목록만 수행한다. 목록에 없는 개선이 필요해 보이면 하지 말고
   `SESSION_HANDOFF.md`의 "발견 사항"에 적는다.
5. **검증 1회.** 레이어 말에 `workflow check --scope full` 1회. 개발 중 반복 실행하지
   않는다(`PROJECT_RULES.md`의 Test Execution Policy).
6. **기록.** `SESSION_HANDOFF.md` 갱신: 완료한 레이어, 실제 소요 시간, 실측된 효과
   (무엇이 빨라졌나), 다음 레이어, 대기 중인 사용자 결정.
   - **레이어당 증거 패키지 문서를 만들지 않는다.** 핸드오프 갱신이 기록의 전부다.
7. **보고.** 사용자에게 3줄로 보고: 무엇을 했나 / 무엇이 빨라졌나 / 다음 선택지.

## 7. 중단 조건

다음 중 하나라도 해당하면 **즉시 작업을 멈추고 사용자에게 보고**한다.

- 한 레이어가 예상 시간의 2배(대개 반나절)를 넘었다.
- 델타 목록에 없는 작업을 해야만 진행이 가능하다.
- 같은 목표에서 3회 연속 실패했다(legacy `PROJECT_RULES.md`의 중단 규칙 유지).
- legacy 파일을 수정해야만 진행이 가능하다.
- 신규 상태 정본이 하나 더 필요해 보인다.
- 어떤 레이어의 생산성 정당화(§2.2 2번)를 한 문장으로 쓸 수 없다.
- 사용자 확정이 필요한 항목을 추측으로 채우려 하고 있다.
- 사용자가 같은 방향을 두 번 거절했다.

멈춘 뒤에는 원인·선택지·권고를 각각 한 줄로 보고하고 지시를 기다린다.

## 8. 세션 재개 방법

새 세션 시작 문구(사용자용):

```
PROJECT_RULES.md와 SESSION_HANDOFF.md를 읽고,
docs/improvement/LAYER_PLAN.md의 현재 레이어만 진행해.
```

에이전트가 확인할 것:

1. `SESSION_HANDOFF.md`의 "현재 레이어"와 "대기 중인 사용자 결정".
2. 대기 결정이 있으면 먼저 해소한다. 임의로 진행하지 않는다.
3. 이 문서 §5의 해당 레이어 절만 읽고 §6 절차를 따른다.
