# 변경 제안 0001 — 검증 가능한 변경 관리와 컨텍스트 효율적 재개

- 역할: 프레임워크 변경을 승인된 설계에서 시작하게 하고, 작업 재개 컨텍스트와 검증 부작용을 함께 줄이는 통합 제안
- 읽는 시점: 이 변경을 승인·구현·검증하거나 관련 예외를 판단할 때
- 보존 조건: 구현 후에도 변경 근거와 승인 기준으로 유지하며 후속 변경은 새 change ID로 작성한다.
- 상태: `proposed` — 사용자 승인 전 구현 금지
- change_id: `0001`
- 적용 원칙: P1 프레임워크 재사용, P2 결정적 검증, P3 에이전트 중립, P4 컨텍스트 예산
- 대체 대상: 이전 SDD 단독 제안과 컨텍스트 효율 재개 상세 제안

## 1. 통합 판단

문서 기준 개발을 강제하는 체계와 컨텍스트 효율적 재개 구조는 별도 문제가 아니다. 전자는 프레임워크 변경의 통제 방식이고, 후자는 그 통제가 해결해야 할 첫 번째 실제 변경이다.

둘을 분리한 채 적용하면 다음 문제가 생긴다.

- 변경 제안 문서가 늘어나면서 시작 컨텍스트가 다시 커질 수 있다.
- 문서가 존재하기만 하면 구현을 허용해 승인되지 않은 형식적 제안이 통과할 수 있다.
- 커밋 시점에만 검사하면 잘못된 구현을 모두 끝낸 뒤에야 위반을 발견한다.
- 로컬 저장소, 상위 Tier-1 저장소, 개인 스킬, 영상별 출력 상태의 소유권이 섞인다.
- 성공한 검증이 전체 로그와 상태 스냅샷을 출력해 검증 자체가 컨텍스트 낭비가 된다.

따라서 이 제안은 변경 관리와 재개 효율을 하나의 폐쇄 루프로 설계한다.

```text
proposal -> user approval -> claimed mutation -> deterministic checks
         -> compact verification -> commit/CI enforcement -> audit
```

## 2. 목표

### 2.1 변경 관리 목표

- 프레임워크 구현은 승인된 change ID에서만 시작한다.
- 제안 작성, 구현, 검증, 예외를 서로 다른 상태로 기록한다.
- 에이전트 종류와 무관하게 Git 훅과 CI에서 동일하게 검사한다.
- 제안이 없는 변경보다 제안을 따르는 비용이 더 낮아야 한다.
- 커밋 이전에도 잘못된 변경 시작을 드러낸다.

### 2.2 컨텍스트 목표

- 단순 재개 필수 문서는 최대 5개, 합계 200줄·10,000자 이하로 제한한다.
- 성공한 검증 기본 출력은 2,000자 이하로 제한한다.
- 상세 근거는 감사 또는 실제 변경 직전에만 지연 로드한다.
- `status`와 `validate`는 데이터와 수정시간을 변경하지 않는다.
- 새 재개 상태 파일을 만들지 않고 기존 핸드오프를 단일 정본으로 유지한다.

## 3. 비목표

- 사용자 승인 없이 현재 영상의 편집 단계나 기준본을 승격하지 않는다.
- 영상별 `inputs/`와 `outputs/`를 프레임워크 커밋 대상으로 만들지 않는다.
- 모든 설계 근거를 시작 문서나 핸드오프에 복사하지 않는다.
- 로컬 저장소의 게이트로 상위 저장소나 개인 스킬 변경까지 승인한 것으로 간주하지 않는다.
- Git 훅만으로 사용자 승인 주체를 완전하게 증명할 수 있다고 주장하지 않는다.

## 4. 변경 제안 상태 모델

모든 변경 제안은 다음 상태 중 하나를 가진다.

| 상태 | 의미 | 구현 허용 |
|---|---|---:|
| `proposed` | 검토 전 초안 | 아니요 |
| `approved` | 사용자가 범위와 승인 기준을 승인 | 예 |
| `implemented` | 적용은 완료됐으나 최종 검증 전 | 후속 수정만 |
| `verified` | 승인 기준과 회귀검사를 통과 | 완료 |
| `rejected` | 방향이 거절됨 | 아니요 |
| `superseded` | 새 change ID로 대체됨 | 아니요 |

필수 필드:

- `change_id`
- `status`
- 목적과 적용 원칙
- 적용 범위와 제외 범위
- 영향 파일 또는 경로 집합
- 승인 기준
- 검증 계획
- 위험과 rollback 조건

제안 문서만 추가하는 커밋은 `proposed` 상태에서도 허용한다. 프레임워크 구현 파일이 함께 변경되면 해당 change ID가 `approved` 이상이어야 한다.

## 5. SDD 강제 체계

### 5.1 도구

신규 `tools/sdd_gate.py`는 다음 명령을 제공한다.

```text
sdd_gate propose <id> <title>
sdd_gate check --message-file <path>
sdd_gate check-range <base> <head>
sdd_gate audit [range]
```

- `propose`: 필수 필드가 있는 짧은 제안 템플릿을 생성한다.
- `check`: staged framework diff, 변경 제안 상태, 커밋 태그를 검사한다.
- `check-range`: CI에서 커밋 범위 전체를 검사하고 로컬 훅 우회를 차단한다.
- `audit`: 과거 준수율과 미해결 waiver를 보고하되 상태를 변경하지 않는다.

### 5.2 커밋 계약

프레임워크 구현 커밋은 다음 태그 중 하나를 포함한다.

```text
[change: 0001]
[waiver: <approval-record-id>]
```

`[change: 0001]`은 존재하는 제안만이 아니라 구현 가능한 상태의 제안을 가리켜야 한다. waiver는 자유 형식 사유만으로 통과시키지 않고 사용자 승인 기록의 식별자를 요구한다.

도구가 확인할 수 있는 것은 승인 기록의 존재와 형식까지다. 실제 승인 주체의 신뢰성은 보호 브랜치, 사용자 소유 승인 표면 또는 별도 서명 정책이 있을 때만 강하게 보장된다. 그 전에는 이 한계를 검증 보고서에 명시한다.

### 5.3 강제 지점

1. `projectctl start`: 프레임워크 작업이면 change ID를 기록한다.
2. 편집 전 훅: 활성 change ID 없이 프레임워크 경로를 변경하려는 시도를 조기 차단한다.
3. `.githooks/commit-msg`: 커밋 메시지와 staged diff를 검사한다.
4. CI `check-range`: `--no-verify`, 미설정 `core.hooksPath`, 다른 clone의 우회를 차단한다.
5. `projectctl finish`: 승인 기준에 연결된 로컬 검증을 실행한다.

### 5.4 경로 분류

기본 프레임워크 경로:

- 루트 진입 문서와 워크플로 문서
- `docs/`, `tools/`, `skills/`, `tests/`
- `.githooks/`, `.github/`
- `planning_research/`의 재사용 설계

기본 제외 경로:

- `inputs/`
- `outputs/`
- 영상별 산출물과 실행 상태

`docs/changes/`만 변경하는 제안 커밋과 승인된 구현 커밋은 별도 규칙으로 검사한다. 여러 change ID를 한 커밋에 섞는 것은 기본 금지하며, 불가피하면 명시적 통합 change ID를 먼저 만든다.

## 6. 컨텍스트 효율적 재개 모델

### 6.1 `fast_resume`

적용 요청:

- 핸드오프 읽기
- 작업 준비
- 현재 상태 또는 다음 행동 확인

필수 읽기:

1. 상위 안전 핵심 규칙
2. 로컬 `PROJECT_BOOTSTRAP.md`
3. 로컬 `docs/INDEX.md`
4. 루트 핸드오프 포인터
5. `outputs/SESSION_HANDOFF.md`의 재개 캡슐

허용 범위:

- 현재 단계, 후보, 첫 미착수 작업, 차단 요소, 금지 행동 보고
- compact preflight와 상태 조회

금지 범위:

- 상세 근거 일괄 로드
- 전체 테스트와 정밀 감사
- DB 검증 명령
- 상태 변경과 핸드오프 수정

### 6.2 `audit`

상태의 정확성, stale 지침, usable revision 또는 실패 원장을 확인할 때 사용한다. 현재 단계 계약과 직접 연결된 근거만 읽고, 검증 명령은 읽기 전용이어야 한다.

### 6.3 `mutation`

파일, 상태 또는 기준본을 실제로 변경할 때 사용한다. `projectctl start`와 change ID를 기록하고, 변경 대상의 계약과 소유권을 확인한 뒤 변경한다.

## 7. 핸드오프와 라우팅 변경

`outputs/SESSION_HANDOFF.md`의 첫 15줄 안에 다음 재개 캡슐을 둔다.

- 현재 단계와 활성 후보
- 승인 기준본 유무
- 첫 미착수 작업
- 활성 차단과 검증 한계
- 지금 허용된 행동과 금지된 행동

핸드오프의 문서 목록은 필수 읽기 순서가 아니라 조건부 라우팅으로 표현한다.

```text
필수: 현재 핸드오프
단계 변경 시: workflow contract + workflow state
편집 기억 변경 시: edit memory kernel + database/view
근거 재검증 시: 현재 design/analysis evidence
```

별도 `RESUME.json`이나 복제 핸드오프는 만들지 않는다.

## 8. 도구 변경

### 8.1 `projectctl`

- `start --change <id>`를 지원한다.
- 기본 `verify`는 검사명, PASS/FAIL, 경고·테스트 수만 출력한다.
- 실패한 검사만 관련 로그를 출력한다.
- 전체 JSON은 `--verbose`에서만 출력한다.
- 내부 검증 결과 구조는 유지해 `finish`와 테스트가 재사용한다.

### 8.2 `edit_memory`

| 명령 | 연결 | 스키마 생성 | `updated_at` 변경 | 기본 출력 |
|---|---|---:|---:|---|
| `init` | read-write | 허용 | 허용 | 초기화 결과 |
| `apply` | read-write | 금지 | 이벤트 적용 시 허용 | applied/skip 수 |
| `export` | read-only | 금지 | 금지 | 경로·이벤트 수 |
| `status` | read-only | 금지 | 금지 | 압축 상태 |
| `validate` | read-only | 금지 | 금지 | 오류·경고·이벤트 수 |

전체 스냅샷은 `--verbose`에서만 출력한다. 초기화되지 않은 DB는 `status/validate`가 자동 생성하지 않고 명확한 오류로 종료한다.

### 8.3 사전점검

- 플랫폼별 래퍼와 CJK·공백 경로를 회귀 테스트한다.
- compact 모드는 필수 파일, Python, Git 루트, projectctl context만 출력한다.
- 사전점검 실패가 다른 정상 도구 표면을 작업 차단으로 확대하지 않도록 동등 검증 경로를 기록한다.

## 9. 문서 검사와 컨텍스트 예산

`doccheck`에 다음 검사를 추가한다.

- `fast_resume` 필수 문서 수 5개 이하
- 필수 경로 합계 200줄·10,000자 이하
- 성공 검증 출력 2,000자 이하
- 핸드오프 필수 링크 수와 재개 캡슐 필드
- 상위 작업 상태가 하위 프로젝트 재개에 자동 포함되는지
- `status/validate` 전후 파일 해시·수정시간 불변 테스트 존재 여부

UI의 컨텍스트 잔여율은 플랫폼 지침과 도구 스키마도 포함하므로 승인 기준으로 사용하지 않는다. 프로젝트가 직접 추가한 문서와 출력 총량을 측정한다.

## 10. 저장소 경계

이 change ID가 직접 다루는 범위:

- 현재 영상 워크플로 저장소의 진입 문서, 계약, 도구, 테스트, 훅과 CI
- 현재 저장소 안의 재개·검증 구조

별도 change ID가 필요한 범위:

- 상위 Tier-1 저장소의 진입 규칙과 안전 커널
- 프로젝트 외부 개인 handoff-manager 스킬

커밋 대상이 아닌 실행 상태 갱신:

- 현재 `outputs/SESSION_HANDOFF.md`의 재개 캡슐 마이그레이션

로컬 SDD 게이트가 저장소 밖 변경까지 승인했다고 간주하지 않는다.

## 12. 구현 순서

1. 사용자가 이 제안의 범위와 승인 기준을 승인한다.
2. 제안 상태를 `approved`로 변경한다.
3. SDD 게이트와 회귀 테스트를 먼저 구현하고 이 change ID로 스스로 통과시킨다.
4. `edit_memory` 읽기 전용 계약과 `projectctl` compact 출력을 구현한다.
5. `fast_resume/audit/mutation` 라우팅과 컨텍스트 예산 검사를 구현한다.
6. CI `check-range`와 로컬 훅의 동등성을 검증한다.
7. 실제 새 세션에서 재개 시뮬레이션을 실행한다.
8. 모든 승인 기준 통과 후 상태를 `verified`로 변경한다.

각 단계는 독립 커밋으로 나눌 수 있지만 모두 `[change: 0001]`을 사용한다. 구현 중 범위가 Tier-1 또는 개인 스킬로 확장되면 이 문서를 늘리지 않고 별도 제안을 만든다.

## 13. 검증 계획

### SDD 게이트

- 제안만 추가 + `proposed` -> 통과
- 프레임워크 구현 + 제안 없음 -> 차단
- 프레임워크 구현 + `proposed` -> 차단
- 프레임워크 구현 + `approved` + 올바른 태그 -> 통과
- 자유 형식 waiver -> 차단
- 승인 기록 waiver -> 정책 범위 안에서 통과
- `inputs/outputs`만 변경 -> SDD 구현 게이트 제외
- 여러 change ID 혼합 -> 차단
- 로컬 훅 우회 커밋 -> CI `check-range`에서 차단

### 재개와 도구

- `fast_resume` 문서·줄·문자 예산 통과
- 핸드오프만으로 단계·후보·첫 행동·금지 행동 식별
- `projectctl verify` 성공 출력 2,000자 이하
- `edit_memory status/validate` 전후 DB 해시, 수정시간, `updated_at`, 이벤트 수 불변
- 초기화되지 않은 DB의 읽기 명령이 파일을 만들지 않고 오류 반환
- Windows CJK·공백 경로와 다른 지원 플랫폼에서 preflight 통과
- `projectctl finish`, doccheck, workflow gate, 전체 단위 테스트 통과

## 14. 레드팀 검토

### 형식적 제안으로 게이트 우회

문서 존재만 검사하면 에이전트가 빈 제안을 만들 수 있다.

대응: 구현 커밋은 `approved` 상태와 필수 필드, 승인 기준을 모두 검사한다.

### waiver 자기 승인

커밋 메시지 사유만으로는 사용자 승인을 증명할 수 없다.

대응: waiver는 승인 기록 ID를 요구하고 보호된 사용자 승인 표면이 없으면 검증 한계를 명시한다.

### 로컬 훅 우회

`--no-verify`, 훅 미설정, 다른 clone은 로컬 훅을 우회할 수 있다.

대응: CI `check-range`를 최종 강제점으로 둔다.

### 안전 규칙 축소

컨텍스트를 줄이는 과정에서 필수 안전 규칙이 빠질 수 있다.

대응: 상위 안전 커널은 별도 소유 범위에서 단일 정본으로 설계하고 복제본을 만들지 않는다.

### stale 핸드오프 신뢰

빠른 재개가 오래된 상태를 그대로 사용할 수 있다.

대응: `fast_resume`은 보고만 허용하고 실제 변경 전 `mutation`에서 상태 원본을 확인한다.

### 거버넌스 비용 증가

모든 작은 수정에 긴 제안을 요구하면 우회 동기가 커진다.

대응: `propose`가 짧은 템플릿을 즉시 만들고, 위험도에 따라 필수 필드의 깊이는 달리하되 change ID와 승인 상태는 생략하지 않는다.

## 15. 승인 기준

다음 조건을 모두 충족해야 `verified`로 전환한다.

- 제안 상태와 커밋 태그를 로컬 훅과 CI가 동일하게 판정한다.
- 승인되지 않은 프레임워크 구현과 자유 형식 waiver가 차단된다.
- `fast_resume`이 5개 문서, 200줄, 10,000자 이하다.
- 성공 검증 출력이 2,000자 이하다.
- 읽기 전용 명령이 DB와 상태 파일을 변경하지 않는다.
- 핸드오프의 단일 정본과 실패 기억이 유지된다.
- doccheck, workflow gate, 전체 단위 테스트와 diff 검사가 통과한다.
- 실제 새 세션 재개 시뮬레이션에서 필요한 다음 행동과 금지 행동을 정확히 보고한다.

## 16. 현재 결정 상태

- 제안: 작성 완료
- 적용: 없음
- 검증: 문서 구조와 현재 경로 기준 검증 예정
- 사용자 결정: 이 통합 범위와 승인 기준의 승인 여부
