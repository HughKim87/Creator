# 옵시디언 전면 도입 토큰 비교

## 결론

옵시디언을 단순 검색 도구로만 붙이면 세 작업 합계가 23,490에서 21,627 추정 토큰으로 7.9% 감소한다. 문서를 Properties, 도메인 폴더, Base, 원자 문서에 맞게 재구성하면 17,835로 줄어 직접 라우팅 대비 24.1%, 단순 적용 대비 17.5% 감소한다.

따라서 전면 도입은 타당하다. 효과의 핵심은 옵시디언 자체가 아니라 옵시디언이 정확히 좁혀 읽을 수 있도록 문서의 역할과 경계를 재설계한 데 있다.

## 공정한 비교 기준

- 대표 작업은 세 조건에서 동일하다: 현재 작업 재개, 활성 문서 하나의 이동·경로 변경, 지정 영상 상태의 검증·승격·다음 사용 판단.
- 토큰은 실제 청구량이 아니라 모든 조건에 동일하게 적용한 `ceil(문자 수 / 4)` 추정치다.
- 직접 라우팅과 단순 적용은 구조 변경 직전의 같은 스냅샷을 사용했다.
- 최적화 조건은 구조 변경 후 실제 시작 문서, 공식 옵시디언 CLI의 검색·Properties 출력, 최종 선택 원자 문서를 사용했다.
- 검색 결과의 후보 수나 링크 수가 아니라 실제로 반환하거나 읽은 문자열만 계산했다.
- 정확성 조건은 관련 없는 문서 0개, 예상 정본 선택, 보호 경로 미탐색이다.

## 조건별 의미

### 1. 기존 직접 라우팅

`AGENTS.md`, `PROJECT_RULES.md`, `SESSION_HANDOFF.md`를 읽은 뒤 경로 변경은 기존 문서 등록부 전체, 상태 처리는 기존 파일·데이터 계약 전체를 읽는 조건이다. 선택은 정확하지만 서로 다른 책임이 한 문서에 섞여 있어 작업별 읽기량이 크다.

### 2. 옵시디언 단순 적용

문서 내용과 폴더를 그대로 둔 채 공식 CLI 검색, 후보 메타데이터, 개요, 필요한 절을 사용했다. 문서 경로 변경은 17.8% 줄었지만 상태 처리는 1.8%만 줄었다. 기존 상태 계약 안에 모델, 스키마, 정상 입출력, 생명주기가 함께 있어 옵시디언이 문서 하나를 찾은 뒤에도 넓게 읽어야 했기 때문이다.

### 3. 옵시디언용 문서 최적화

- 시작 문서의 중복 안내를 제거하고 핸드오프를 현재 상태 중심으로 축약했다.
- 활성 문서를 `navigation`, `rebuild`, `workflow`, `tooling`, `state` 도메인 폴더로 이동했다.
- 모든 관리 노트에 `doc_id`, 종류, 도메인, 생명주기, 권한, 대상, 언어, 검증, 목적, 범위, 읽기·수정 시점을 YAML Properties로 기록했다.
- 수동 전체 목록 대신 `AGENT_DOCUMENTS.base`가 Properties에서 도메인 화면을 자동 생성하게 했다.
- 문서 배치와 분류를 `DOCUMENT_PLACEMENT.md`와 `DOCUMENT_REGISTRY.md`로 분리했다.
- 정상 상태 작업과 상태 모델 변경을 `STATE_OPERATIONS.md`와 `VIDEO_TASK_STATE.md`로 분리했다.

최종 재개 조건은 시작 문서 20,644자만 읽어 5,161 토큰이다. 문서 이동은 CLI 검색·Properties 399자와 `DOCUMENT_PLACEMENT.md` 4,219자를 더해 총 25,262자, 6,316 토큰이다. 상태 처리는 CLI 검색·Properties 421자와 `STATE_OPERATIONS.md` 4,364자를 더해 총 25,429자, 6,358 토큰이다.

## 실제 옵시디언 검증

- `AGENT_DOCUMENTS.base`의 활성, Navigation, State, Historical evidence 화면이 Properties에 맞는 문서만 반환했다.
- 문서 이동 검색은 `DOCUMENT_PLACEMENT.md`와 분류 등록부 두 후보만 반환했고 목적·권한 비교로 배치 문서를 선택했다.
- 상태 작업 검색은 `STATE_OPERATIONS.md`와 상태 모델 두 후보만 반환했고 목적·권한 비교로 작업 문서를 선택했다.
- 검색과 Base 조회는 공식 옵시디언 CLI에서 종료 코드 0으로 확인했다.
- 사용자 데이터와 보호 경로는 검색하거나 색인 결과로 반환하지 않았다.

## 해석과 제한

- 재개 비용의 6.0% 감소는 옵시디언 검색 덕분이 아니라 항상 읽는 핸드오프와 라우터의 중복을 줄인 결과다.
- 큰 절감은 검색 엔진 변경보다 문서 책임을 원자 단위로 나눈 데서 발생했다.
- 이 값은 문서 컨텍스트 추정치다. 모델의 내부 추론, 답변, 캐시, 도구 호출 포장, 실제 API 토크나이저 비용은 포함하지 않는다.
- 문서가 늘어도 Properties와 Base가 후보를 도메인으로 제한하지만, 새 문서의 속성과 책임 경계를 잘못 작성하면 정확도와 절감률이 다시 나빠질 수 있다.
- 동일 기준 비교를 유지하려면 대표 작업, 계산식, 정확성 조건을 바꾸지 말고 새 스냅샷에서 세 조건을 함께 다시 측정해야 한다.
