# 샌드박스·권한 반복 실패 분석

- 정본 여부: 역사 증거다. 재발 방지 규칙은 `PROJECT_RULES.md`, 활성 도구 계약은 `docs/agent/tooling/TOOL_REQUIREMENTS.md`가 정본이다.
- 상태: 2026-07-20 기준 역사 기록, 수정 조치 완료.

## 결론

이번 낭비는 권한이 새로 발생해서가 아니라, 공식 Obsidian CLI 실행 파일이 기본 샌드박스 밖에 있다는 사실을 이미 확인하고도 Python 래퍼를 기본 샌드박스에서 다시 실행한 판단 실패였다. 래퍼는 호출자의 실행 경계를 그대로 상속하므로 권한 문제를 해결하지 못했고, 공식 CLI에 허용된 실행 승인도 Python 프로세스에 자동 승계되지 않았다.

따라서 해당 래퍼와 전용 테스트를 제거했다. 에이전트 문서 탐색은 실행이 확인된 공식 `Obsidian.com` 명령을 같은 승인 경계에서 직접 호출한다. 실패·불일치·보호 경로 발견 시 다른 탐색기로 자동 전환하지 않고 사용자에게 보고한다.

## 발생 순서

1. `C:\Users\Hugh\AppData\Local\Programs\Obsidian\Obsidian.com`의 존재를 확인했다.
2. Obsidian 앱이 실행되지 않은 상태에서 공식 CLI가 종료 코드 1과 함께 앱 실행 필요를 정확히 보고했다.
3. Obsidian을 실행한 뒤 동일한 공식 CLI를 승인된 외부 실행 경계에서 호출해 버전 `1.12.7`, `search`, `search:context`, `outline` 동작을 확인했다.
4. 이 성공으로 실행 경계가 이미 확정되었는데도 `tools/obsidian_document_search.py`를 만들고 기본 샌드박스에서 실행했다.
5. Python 프로세스가 공식 CLI 경로에 접근하지 못해 예상 가능한 `PermissionError`가 발생했다.
6. 오류를 구조화한 뒤 래퍼를 승인 경계에서 다시 실행해 성공시켰지만, 이는 래퍼가 필요하다는 증거가 아니라 외부 실행 승인이 필요하다는 기존 사실을 재확인했을 뿐이다.

## 실패 원인

### 직접 원인

- 자식 프로세스인 공식 CLI의 승인 경계와 부모 프로세스인 Python 래퍼의 실행 경계를 같은 것으로 잘못 취급했다.
- “직접 공식 CLI 호출은 승인 경계에서 성공한다”는 확인 결과를 구현 선택의 제약으로 고정하지 않았다.
- 래퍼가 문서 범위 제한과 결과 정리를 제공할 수 있다는 장점만 보고, 실제 에이전트가 사용할 호출 경로가 더 복잡해지고 별도 승인을 요구한다는 비용을 먼저 차단하지 않았다.

### 절차 원인

- 알려진 실패 조건을 재시험하지 않는 규칙이 전역 실행 규칙에 명시되어 있지 않았다.
- 개발용 단위 테스트의 성공과 실제 실행 경계의 성공을 분리해 판단하지 않았다.
- 외부 CLI 연동 전에 “운영 진입점, 필요한 승인 경계, 실패 시 처리”를 먼저 확정하지 않았다.

## 영향

- 이미 결론이 난 권한 조건을 다시 확인하는 호출과 설명에 세션 시간과 토큰을 낭비했다.
- 실제 제품을 직접 쓰는 간단한 구조 대신 불필요한 래퍼와 테스트를 만들었다가 제거했다.
- 같은 실패를 개선하겠다는 기존 요구를 지키지 못해 사용자 신뢰를 훼손했다.
- Python 명령에 대한 별도 승인을 유도할 수 있어 향후 권한 마찰을 더 크게 만들 뻔했다.

## 수정 조치

1. 실패한 `tools/obsidian_document_search.py`와 `tests/test_obsidian_document_search.py`를 제거한다.
2. `PROJECT_RULES.md`에 확인된 외부 실행 경계 재사용, 래퍼의 권한 비승계, 알려진 실패 경계 재시험 금지 규칙을 추가한다.
3. 공식 Obsidian CLI를 실제 에이전트 탐색 진입점으로 직접 사용한다.
4. 탐색 범위를 `docs/agent`로 고정하고 결과는 최대 3개 후보 경로로 제한한다.
5. 후보는 권위 문서가 아니라 탐색 단서로만 취급하고, 문서 메타데이터와 필요한 제목 범위를 확인한 뒤 읽는다.
6. CLI 미실행, 권한 불일치, 무결과, 모호성, 보호 경로 위험은 보고 대상으로 처리하며 직접 라우팅이나 다른 검색기로 자동 전환하지 않는다.

## 재발 방지 기준

- 같은 외부 실행 파일의 권한 조건이 한 번 확인되면 이후 검증은 확인된 동일 경계에서만 수행한다.
- 래퍼는 권한 우회 수단으로 만들지 않는다. 실제 기능상 이득과 동일한 운영 경계가 모두 입증될 때만 도입한다.
- 단위 테스트가 통과해도 실제 앱·CLI 실행 검증을 대신할 수 없다.
- 최초 실패가 “앱 미실행”이면 앱 상태를 한 번 고친 뒤 재검증하고, 같은 상태를 반복 재현하지 않는다.
- 성공 여부는 종료 코드와 예상 결과를 함께 확인한다.
- 실패를 감추는 자동 대체 경로를 만들지 않는다.

## 확인된 결과

- 공식 Obsidian CLI 직접 호출: 앱 실행 후 성공.
- 확인된 제품 버전: `1.12.7`.
- 확인된 기능: 제한 경로 검색, 문맥 검색, 문서 제목 구조 조회.
- 사용자 데이터 접근: 없음. 검색은 `docs/agent`로 제한했다.
- Python 래퍼: 제거.
- 활성 재발 방지 규칙: `PROJECT_RULES.md#authorization-and-change-safety`.

## 수정 후 탐색 효율 검증

`검색 결과 문자 수 / 4`를 출력 토큰 근사치로 사용했다. 후보 선택 비용은 검색 JSON과 후보 3개의 `Purpose`, `Authority`만 합산했다. 동률이 없어서 `Scope`, `Read when`은 읽지 않았다.

선택 문서의 전체 제목 구조 조회는 약 239토큰이었다. 따라서 알 수 없는 작업의 정본 선택과 제목 탐색은 대표 사례에서 약 481~506토큰이었고, 이후 실제 필요한 제목 범위만 읽는다. 무결과 질의는 종료 코드 0과 `No matches found.` 약 5토큰을 반환했으며, 계약상 자동 대체 없이 보고한다.

기존 Graphify 비교에서는 알려진 세 작업에 대해 직접 라우팅보다 각각 21,054토큰, 14,197토큰, 40토큰이 더 들었고 앞의 두 작업은 잘못된 문서를 포함했다. 새 구조는 알려진 작업에는 검색 비용이 전혀 추가되지 않고, 알 수 없는 작업에만 위의 제한 비용을 사용한다. 이 수치는 공식 CLI가 의미를 자동 판정한다는 뜻이 아니라, 후보 범위를 작게 만드는 제품 검색기로 적합하다는 증거다.
