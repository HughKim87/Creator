## 2. 검증 방법과 환경

1. 원본 저장소를 수정하지 않기 위해 `backup/`, `.git/`, 보호 경로를 제외한 격리 복제본에서 `validate`와 테스트를 실행했다.
2. 검증 환경은 Linux + Python 3.10이며, `tomllib`가 없어 `tomli` 호환 shim을 `PYTHONPATH`로만 주입했다. 프로젝트 파일은 변경하지 않았다.
3. 저장된 R-4·R-5 결과는 원본 평가셋의 SHA-256을 재계산해 무결성을 확인했다.
4. Git 이력의 단계별 커밋에서 실제 코드·테스트 라인 수를 직접 계측했다.
5. 본 문서는 동시 실행 중인 다른 세션이 catalog를 갱신하고 있어 resolver/writer 폐루프 대신 **exact direct route**로 작성했다. 이 예외는 [AGENTS.md](../../AGENTS.md) 5항이 허용하는 fallback이며 여기에 기록한다.

검증 수준은 `structural`이다. 응용 프로그램 검증과 사용자 승인은 주장하지 않는다.

## 4. 1차 보고가 다루지 않은 결함

### F-1. catalog 증식이 통제되지 않는다 (심각도: 높음)

- `catalog/units.jsonl`은 33,594,564바이트(약 32MiB), unit 47,295개다. R-5 종료 시점 18,308개에서 하루 만에 2.6배가 됐다.
- unit의 **92.7%(43,825개)가 `context/`** 에서 나온다. 즉 정본 지식이 아니라 작업 부산물인 request·work context·payload가 projection을 지배한다.
- catalog 등록 파일 177개 중 102개(58%)도 `context/`다. 같은 시점 정본 지식은 knowledge 4, case 2, decision 17, relation 6이다.
- 결과: 구조 검증 1회가 로컬 SSD 복제본에서 약 60초, 마운트된 원본에서는 3분 이상 걸린다. 모든 write·resolve가 이 projection을 다시 만들기 때문에 비용은 작업량에 비례해 계속 증가한다.
- 승인 설계에는 fixture 보존 기간, 압축, projection 분리에 대한 계약이 없다. R-2A~R-5의 완료 게이트에 성능·규모 기준이 하나도 없다는 점이 원인이다.

### F-2. Python 최소 버전이 선언·검증되지 않는다 (심각도: 높음)

- `tools/context/context_system.py`는 `tomllib`를 import하므로 Python 3.11 이상이 필요하다.
- 그러나 `run_python.ps1`의 후보 검증은 `import sys; raise SystemExit(0)` 종료 코드만 본다. 버전은 확인하지 않는다.
- 저장소·규칙·계약·런처 어디에도 최소 버전 문구가 없다(전체 검색 결과 0건).
- 재현: Python 3.10으로 실행하면 `ModuleNotFoundError: No module named 'tomllib'`로 즉시 실패한다. 런처 우선순위에서 3.10 계열이 먼저 선택되는 환경이면 "검증된 런타임"을 고른 뒤 실패한다.
- 이는 R-3·R-5가 주장한 *LLM 기억 없는 새 세션 재현성*의 전제를 약화한다. 재현성은 인터프리터 버전 계약까지 포함해야 한다.

### F-3. 구조 검증이 `backup/` 존재에 의존한다 (심각도: 중간)

- 활성 보고서가 `backup/` 하위 경로를 Markdown 링크로 참조하고, 링크 검증기는 대상 파일 존재를 요구한다.
- `backup/`을 제외한 복제본에서 링크 오류 33건이 발생했다. 즉 `backup/`이 없는 클론에서는 `validate`가 실패한다.
- `backup/`은 불변 역사 증거이자 활성 런타임 의존이 아니어야 한다는 커널 규칙(`rule.core.backup-boundary`)과 검증 동작이 서로 어긋난다. 링크 종류를 구분하거나 역사 링크를 검증 대상에서 분리하는 편이 규칙과 일치한다.

### F-4. 동시 실행에 대한 계약이 없다 (심각도: 중간)

- 본 검증 중 다른 세션이 같은 저장소의 catalog와 `docs/reports/`를 동시에 갱신하는 것을 관측했다(13:36~13:37 사이 `catalog/files.jsonl`, `catalog/units.jsonl` 재작성).
- writer는 before hash로 단일 작업의 정합성은 지키지만, 두 프로세스가 같은 projection을 교대로 재작성하는 상황에 대한 lock·소유권·감지 계약은 없다.
- 실제 증상도 관측됐다. 같은 시각 `docs/agent/DOCUMENT_MAP.md`에 1차 보고 등록 행이 동일하게 2번 기록돼 있었고, 본 검증에서 중복 1행을 제거한 뒤 본 문서 행을 추가했다. 문서 권위 중복은 이미 `case.project.document-authority-duplication`으로 등록된 기존 사례이므로, 예방 계약이 동시 실행 상황을 포함하지 못한다는 증거다.
- R-3·R-4·R-5가 반복해서 "동시 사용자 파일 격리"를 실패 기록으로 남긴 것도 같은 결함의 다른 증상이다. 그때마다 우회했을 뿐 계약으로 고정되지 않았다.

주요 감점 사유만 적는다.

- **R-1**: 11개 커널·18개 규칙 안을 폐기하고 8/21로 다시 만들었다. 정정 판단은 옳았지만 설계 1회 전면 폐기와 보존 표식 정리는 비용이다.
- **R-2**: R-1.1이 이관 대상으로 열거한 실패 사례(실행 결과 오판, 잘못된 기본값, 보호 위반, Graphify, sandbox, Obsidian) 중 정식 case는 1건만 이관됐다. 지식 4건도 대표 subset이다.
- **R-3**: transactional rollback과 source review는 실제 결함을 자체 검토로 잡아낸 모범 사례다. 반면 도구가 1,444줄에서 2,501줄로 커졌고, R-2A에서 이미 관측된 Python 진입점 실패를 예방 계약으로 만들지 않아 뒤에 재발했다.
- **R-4**: 자체 작성한 8질의가 전부 recall·precision 1.0으로 통과했다. 실패를 만들어내지 못하는 평가셋은 변별력 근거가 약하다. FTS 비도입 결론 자체는 현재 corpus에서 타당하나 영구 결론으로 쓸 수 없다.
- **R-5**: 6/9 → 7/9 → 9/9의 실패 이력을 숨기지 않은 점은 신뢰할 만하다. 그러나 완료 조건에 성능·규모·동시성·환경 계약이 없고, 종료 문구가 R 범위 완료를 프로젝트 전체 완료처럼 읽히게 했다.

## 6. 권고 우선순위

1. **런타임 계약 고정**: 최소 Python 버전을 문서와 런처 검증에 함께 넣고, 버전 미달 인터프리터는 후보에서 즉시 탈락시킨다. 회귀 1건을 추가한다. (F-2)
2. **fixture 보존 정책 수립**: `context/` 산출물의 보존 기간과 압축·아카이브 기준을 정하고, unit projection에서 부산물을 분리하거나 제외한다. 현재 projection의 92.7%가 여기서 나온다. (F-1)
3. **검증 비용 기준 추가**: `validate` 1회 소요 시간과 projection 크기 상한을 완료 게이트에 넣는다. 지금은 어떤 단계도 성능 기준이 없다. (F-1)
4. **역사 링크 분리**: `backup/` 링크를 일반 로컬 링크 검증에서 분리해 클론 가능성과 커널 규칙을 일치시킨다. (F-3)
5. **동시 실행 규칙**: 저장소 단위 lock 또는 최소한 catalog 재작성 전 변경 감지 실패 규칙을 정한다. (F-4)
6. **평가셋 강화**: 현재 8질의에 실제 실패가 예상되는 질의를 추가해 변별력을 확보한 뒤 FTS 필요성을 재판정한다. (R-4)
7. `context_system.py` 분리는 사용자 승인 없이 착수하지 않는다. 위 1~5를 먼저 처리하는 편이 위험 대비 효과가 크다.

## 7. 검증 한계와 승인 경계

- 본 검증은 구조·CLI 수준이다. 실제 영상 제작 응용 검증과 사용자 콘텐츠 승인은 포함하지 않는다.
- 전체 테스트 29건은 Windows 전용 런처 회귀와 실행 시간 때문에 본 환경에서 완주하지 못했다. 1차 보고의 통과 주장을 반박할 근거는 없으며 미재현으로만 표기했다.
- 점수는 승인된 단계 계약 대비 실행 품질 평가이며, 과거 최종 교차검증의 36/100(목적 적합도)과는 평가 대상이 다르다.
- 원본 저장소의 파일은 이 보고서와 문서 지도 등록 외에 변경하지 않았다. commit, push, 배포, 게시, 외부 시스템 변경, 보호 데이터 접근은 수행하지 않았다.
