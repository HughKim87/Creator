## 1. 분석 결론과 작업 범위

세 보고서는 R 지식 시스템 완성에는 합의했지만 운영 지속성의 네 결함을 남겼다. 3차 교차검증 부록에서 F-4는 이론적 우려가 아니라 동시 sync가 `catalog/tmp*`를 활성 파일로 오인해 context 작업을 중단시킨 재현 결함으로 상향됐다. L 작업 전에 다음 네 항목을 닫는 것이 비용 대비 효과가 가장 높다고 판정했다.

| ID | 개선 목표 | 완료 조건 |
|---|---|---|
| F-4 | context 명령 동시 실행 안전성 | 저장소 단위 cross-process lock, 내부 temp/lock 탐색 제외, 사라진 파일의 복구 가능한 sync, 두 동시 sync 성공, ghost 0 |
| F-2 | Python 실행 환경 계약 | Python 3.11 이상과 `tomllib` capability를 후보 선택 전에 검사하고 미달 explicit runtime 회귀 통과 |
| F-1 | context projection 증식 통제 | request/work/payload 파일당 unit 1개, 현재 projection 5,000 unit·8 MiB 이하, 초과 시 validator 실패 |
| F-3 | 역사 링크와 활성 의존 분리 | `backup/` 링크는 존재 여부를 요구하지 않고 일반 누락 링크는 계속 오류 처리 |

제외 범위는 `context_system.py` 모듈 분리, R-4 평가셋 확대, FTS 도입, 과거 case 전면 이관, L0~L8 구현과 보호 데이터 접근이다.

## 3. 반복별 실행 결과

### 3.1 1차 개선 — 네 결함 동시 구현

구현 내용:

- 모든 context-system CLI 명령의 전체 수명에 repository-local cross-process lock을 적용했다.
- `sync_catalog()` 직접 호출도 같은 reentrant lock을 사용한다.
- atomic temp에 전용 이름을 부여하고 lock·신규 temp·과거 `catalog/tmp*`를 전역 파일 탐색에서 제외했다.
- active 파일이 사라져도 unit rebuild가 먼저 예외로 중단되지 않고 validator가 누락을 보고하게 했다.
- context request/work/payload를 `whole_file` unit 하나로 제한했다.
- 5,000 unit·8 MiB deterministic projection gate를 추가했다.
- Python 후보 probe를 3.11 이상과 `tomllib` import 검사로 강화했다.
- `backup/` 역사 링크의 존재 검사를 활성 링크 검사와 분리했다.

초기 sync 결과는 3,656 unit·2,541,758바이트, 3.841초였다. 첫 전체 회귀에서는 신규 기능 테스트를 포함한 34개 중 33개가 통과했고 통합 검증 1개가 실패했다. 원인은 변경된 5개 등록 source hash가 검토 전 상태였기 때문이다.

### 3.2 2차 개선 — source·knowledge 검토 폐루프

`check-sources`로 다음 5개 source를 `needs_review`로 전환하고 현재 내용과 범위를 검토한 뒤 `maintain-source`로 수락했다.

- `source.repo.context-retrieval`
- `source.repo.python-runtime-launcher-test`
- `source.repo.python-runtime-resolver`
- `source.repo.validation-rules`
- `source.repo.workflow`

영향받은 knowledge 4건도 source가 다시 활성화된 뒤 claim·범위가 유지됨을 확인하고 revision 8에서 9로 재검증했다. 그 결과 전체 **34/34**가 통과했다. 두 실제 sync 프로세스도 모두 exit 0과 동일한 projection 결과를 반환했고 ghost catalog row·temp file은 0이었다.

### 3.3 3차 개선 — 잠금 정리 사각지대 보완

자체 검토에서 lock file open, unlock 또는 handle close 예외가 발생하면 프로세스 내부 `RLock` 해제가 보장되지 않을 가능성을 발견했다. setup과 teardown 전체를 중첩 `finally`로 감싸 file handle과 process guard를 항상 해제하도록 수정하고, setup·close 실패 후 다른 thread가 다시 lock을 획득하는 회귀를 추가했다.

최종 전체 회귀는 **35/35** 통과했다. 최대 3회 반복 제한 안에서 목표를 달성했으므로 추가 구현 반복은 수행하지 않았다.

## 7. 잔여 위험과 L 작업 경계

- repository lock은 context-system CLI와 `sync_catalog()` 사용자를 직렬화한다. 외부 프로그램의 catalog 직접 편집까지 통제하지는 못하므로 직접 편집 금지 계약을 유지한다.
- 5,000 unit·8 MiB는 현재 pre-L baseline의 deterministic gate다. 실제 정본 증가로 상향이 필요하면 성능 실측과 계약 검토를 먼저 수행한다.
- launcher capability 회귀는 Windows에서 실행했다. 다른 OS의 전체 launcher 동작은 아직 응용 검증되지 않았다.
- `backup/` 링크는 역사 locator로 보존하되 대상 존재를 검증하지 않는 것이 의도된 계약이다. 링크 본문의 역사적 정확성까지 승인한 것은 아니다.
- `context_system.py` 단일 파일 집중, 작은 검색·운영 평가셋, 부분 corpus는 이번 범위 밖 잔여 위험이다.
- L0~L8 작업은 시작하지 않았다. 다음 작업은 pre-R 증거에서 완료 layer·첫 미착수 layer·L2/L4 선행 조건을 복원하는 것이다.

## 8. 최종 판정

**성공.** F-1~F-4의 L 작업 전 필수 운영 위험은 세 번의 개선 한도 안에서 자동 검증 가능한 계약과 회귀로 완화됐다. L 작업을 바로 구현할 권한으로 해석하지 않으며, 다음 게이트는 L0~L8 복귀점 재확정이다. commit, push, 배포, 게시, 외부 시스템 변경과 보호 데이터 접근은 수행하지 않았다.
