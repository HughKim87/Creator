- 작성일: 2026-07-16
- 목적: 현재 프로젝트의 문제점을 진단하고, 백지에서 다시 설계한 개선 구조를 제안
- 근거: 이 보고서의 상세 결정 기록은 docs/changes/0002 제안서와 연결된다.

## 1. 현재 구조의 문제점 진단

### 문제 1 — 매 세션 내는 "시작 세금"

세션을 시작할 때마다 규칙·인덱스·핸드오프를 읽는 데 컨텍스트를 소모한다.
실측으로 필수 시작 로드만 126줄(6,269자)이고, 규칙 관련 작업이면 PROJECT_RULES
160줄이 더해진다. 이 비용은 한 번이 아니라 **모든 세션이 영원히 반복**해서 낸다.

### 문제 2 — 규칙의 이중 장부

같은 규칙이 문서(산문)와 검사기(코드)에 두 번 존재한다. 에이전트는 둘 다
읽어야 하고, 둘이 어긋나면 어느 쪽이 맞는지 판정하는 비용이 또 든다.

### 문제 3 — 상태의 분산

"지금 어디까지 했지?"의 답이 6곳에 흩어져 있다: 루트 핸드오프, outputs 핸드오프,
AGENT_CONTROL, WORKFLOW_STATE, CURRENT.json, edit_memory DB. 재개할 때마다
이들을 대조해야 하고, 손으로 쓰는 핸드오프는 낡을(stale) 위험을 항상 갖는다.

### 문제 4 — 프레임워크와 영상 작업의 혼재

한 저장소에 둘이 섞여 있어 파일마다 "이건 프레임워크인가 작업물인가"를
판정해야 하고, 그 판정을 위한 규칙·게이트·예외 목록이 계속 자란다.
프레임워크를 고치는 메타작업이 정작 영상 편집보다 커졌다.

### 문제 5 — 문서의 전부-아니면-전무 읽기

문서를 "통째로 읽기" 아니면 "안 읽기"만 있고, 필요한 부분만 여는 중간 단계가
없다. 그래서 문서가 늘수록 읽기 비용이 정비례로 늘어난다.

## 2. 개선 원칙

1. **문서는 유지하고 강화한다.** 문서가 프로젝트의 영속 지식 자산이고,
   세션은 갈아끼우는 무상태 작업자다. 해법은 "덜 읽기"가 아니라
   **"정확히 조준해서 읽기"**다.
2. **모든 재사용 지식은 문서화한다.** 단, 하이브리드 경계를 지킨다:
   판단·결정·기준은 문서로, 기계 상태(단계·좌표·계보)는 구조화 데이터로,
   사람용 상태 뷰는 데이터에서 자동 렌더링으로.
3. **규칙 하나당 검사기 하나.** 검사할 수 없는 규칙은 만들지 않는다.
   반복 실수의 교정은 규칙 문장 추가가 아니라 검사 추가로 흡수한다.

## 3. 새 문서 아키텍처 (4계층)

### L0 — 기본규칙 (모든 세션의 유일한 필수 문서, 40줄 이내)

| 구성 | 내용 |
|---|---|
| 안전 커널 | 비밀 금지, 원본 보존, 삭제·푸시·업로드·결제 전 질문, 3회 실패 중단 |
| 라우팅 테이블 | "상황 → 어느 인덱스로 가라"의 결정적 규칙 |

같은 상황이면 어떤 에이전트(Claude·Codex·Gemini)든 같은 문서 경로가 나온다.

### 인덱스 계층 — 대분류 → 중분류 → 소분류

- 번호 주소 체계: 모든 문서가 단 하나의 주소를 갖는다. 예)
  `10 기획 / 20 자막 / 30 분석 / 40 편집 / 50 검토 / 90 프레임워크`,
  `43.02 = 편집 > 품질기준 > 컷 길이`
- 인덱스는 내용을 담지 않는다. 하위 항목의 이름·역할·읽는 시점만 담는다.
- 인덱스당 항목 10개 이하. 넘으면 분할한다.
- **인덱스는 손으로 쓰지 않는다.** 잎 문서의 머리말(프론트매터)에서 자동
  생성하고, 손편집은 커밋 검사가 차단한다. 인덱스와 실제 문서가 어긋나는
  순간 항해 전체가 무너지기 때문이다.

### 잎 문서 — 지식의 실체, 한 문서 한 유형

| 유형 | 담는 것 | 예시 |
|---|---|---|
| contract | 기준·계약·게이트 조건 | 컷 길이 경고선, 단계 통과 조건 |
| procedure | 절차·명령 | 자막 정리 순서, 내보내기 절차 |
| rationale | 근거·설명 | 왜 이 기준인가, 리서치 요약 |
| log | 결정 기록 | 이 영상에서 왜 이 컷을 버렸나 |

- 유형별 템플릿과 줄 예산을 검사기가 강제한다.
- 유형이 섞인 문서가 읽기 낭비의 주범이다. 계약만 필요한 세션이 근거
  설명까지 읽게 되는 구조를 없앤다.
- 모든 잎은 머리말 5~7줄을 갖는다: 이름, 역할, 읽는 시점, 유형, 예산,
  담당, 갱신일.

### 메타 프레임워크 — 문서의 문서

- 새 지식이 생기면 어느 주소의 잎에 쓸지 결정하는 규칙 (번호 체계가 답을 준다)
- 잎이 커지면 분할, 겹치면 병합, 낡으면 폐기하는 기준
- 신선도 감사: 갱신일·문서 간 모순·끊긴 참조를 주기적으로 검사해 보고서로
  올리고, 병합·분할·폐기는 **사용자 승인 후에만** 실행
- 같은 규칙이 두 문서에 있으면 오류 (중복 퇴적 방지)

### 읽기 프로토콜 — 전과 후 비교

| | 현재 | 개선 후 |
|---|---|---|
| 시작 로드 | 고정 문서 3~5개 통째 (126줄+) | L0 하나 (40줄) |
| 작업 진입 | 상황별 문서 통째 + 규칙 조건부 160줄 | 인덱스 경로 2~3개 + 잎 1~2개 |
| 문서가 2배로 늘면 | 읽기 비용도 거의 2배 | 읽기 비용 거의 불변 (트리 깊이만 +1) |

### 쓰기 프로토콜 — write-back 의무

- 세션에서 생긴 재사용 판단·결정을 올바른 주소의 잎에 기록해야 세션 종료
  게이트가 통과된다. 기록하지 않으면 다음 세션이 같은 고민을 반복한다.
- 컨텍스트 재활용은 읽기 기능이 아니라 **쓰기 기율의 결과물**이다.

## 4. 지원 구조

### 2-저장소 분리

```text
studio/        프레임워크 (버전 릴리스): L0, 인덱스, 잎 문서, 도구, 테스트
studio-work/   영상별 작업: inputs(원본), state.json(상태 원본),
               outputs(산출물), HANDOFF(자동 렌더링 뷰)
```

영상 작업 세션은 프레임워크 문서를 읽지 않는 것이 정상 상태가 된다.
"프레임워크인가 작업물인가" 판정과 그에 딸린 규칙이 통째로 사라진다.

### 상태 모델

- 영상당 상태 원본은 state.json **하나**. 필드: 단계, 후보, 결정 목록,
  첫 미착수 작업, 차단 요소, 지금 금지된 행동.
- 사람용 핸드오프와 에이전트용 재개 캡슐은 모두 여기서 자동 렌더링된다.
  손으로 쓰는 상태 문서는 존재하지 않으므로 낡을 수가 없다.
- 편집 판단 계보는 기존 edit_memory DB(이벤트 소싱)를 그대로 이식한다.

### 세션 수명주기 (명령 4개)

```text
vid context   시작: L0 + 라우팅 경로 + 재개 캡슐 (60줄 이내)
vid <작업>    단계 작업: 진입 시 해당 잎 문서 자동 안내
vid check     검증: 문서·테스트·게이트, 요약 출력 (2,000자 이내)
vid done      종료: 게이트 통과 시 상태 갱신 + write-back 확인 + 핸드오프 재렌더링
```

## 6. 마이그레이션 로드맵

1. **뼈대**: studio 골격 + L0 + 번호 체계 초안 + state.json 렌더링
2. **이식**: 진행 중 영상이 없는 시점에 기존 도구(edit_memory, synccheck,
   ffmpeg 래퍼, 품질 감사, SDD 게이트)와 테스트를 옮긴다
3. **문서 이주**: 기존 규칙·스킬 문서를 4유형 잎으로 분해해 주소에 배치
4. **파일럿**: 다음 영상 1편을 새 구조로 처음부터 끝까지 진행하며 실측
5. **전환**: 파일럿 통과 후 기존 저장소를 읽기 전용 보관으로

파일럿 통과 전까지 기존 저장소는 그대로 둔다. 되돌리기는 언제든 가능하다.

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| 재작성 자체가 메타작업 폭주 | 로드맵 순서 고정, 파일럿 1편 전 기존 구조 동결 금지 |
| 초기 대분류를 잘못 잡으면 재배치 비용 | 파일럿 전까지 번호 체계를 확정하지 않고 초안으로 운용 |
| 자동 생성 뷰가 원본과 어긋남 | 렌더링을 순수 함수로 만들고 스냅샷 테스트로 고정 |
| 규칙 분산으로 발견성 저하 | L0 라우팅 테이블 + 인덱스 자동 생성이 상쇄하는지 파일럿에서 실측 |
| 문서 관리 규칙의 재귀적 비대화 | 규칙 하나당 검사기 하나. 검사 불가능한 규칙은 도입 금지 |
