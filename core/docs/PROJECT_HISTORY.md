# 프로젝트 역사 요약

- 목적: 현재 운영에 필요한 결정과 재발 방지 교훈만 남기고 상세 과정은 Git 이력으로 조회한다.
- 갱신일: 2026-07-24
- 상세 복구: Git 커밋과 삭제 전 브랜치 `feature/refactorying_4th_extra`

## 남긴 결론

- 프로젝트의 최종 목적은 사용자의 수동 생산 작업을 줄이고, 승인된 목표와 안전 경계 안에서 에이전트가 유튜브 작업을 자율 수행하도록 돕는 것이다.
- 세션이 바뀌어도 현재 상태와 중요한 결정이 이어져야 하지만, 모든 명령·시도·보고서를 장기 보존하지 않는다.
- `inputs/`·`outputs/`는 사용자가 정확한 대상과 목적을 지정할 때만 접근한다.
- 중요한 활성 정보는 한 문서가 소유하고 다른 문서는 링크한다.
- 해결 실패는 원인별로 합쳐 재사용 규칙만 남기며, 일회성 명령 실수는 기록하지 않는다.
- 과거 복제본과 시점 보고서는 활성 트리에 두지 않고 Git 이력으로 복구한다.

## 재구축 결과

2026-07-22부터 2026-07-24까지 파일 데이터, 기록 I/O, 작업 상태, 지식 수명주기, 선택적 컨텍스트, 유지보수 검증, 유튜브 근거 패키지를 순차 구축했다. 이후 운영 마찰을 줄이기 위해 시작 문서와 조건부 규칙을 축소하고 `quick / standard / controlled` 작업 분류를 도입했다.

정리 직전 기준 전체 120개 회귀 테스트가 통과했다. 2026-07-24 정리에서 백업·보고서·단계 문서·legacy 데이터와 그 전용 검증 4개를 제거했고, 남은 116개 회귀 테스트와 문서·artifact·유지보수 검증이 통과했다.

같은 날 사용자의 구조 승인에 따라 도메인 중립 기반을 불변 `core/`로, YouTube·영상·작업 데이터와 runtime을 가변 `extension/`으로 분리했다. core 변경은 현재 대화의 exact 사용자 승인이 있을 때만 허용하며 자동 작업은 `core_change_required`로 실패하도록 검증 gate를 추가했다.

## 폐기한 접근

- 프로젝트 전체 복사본을 `backup/`에 누적하는 방식
- 완료 단계마다 장문 계획·점수·교차검증 보고서를 영구 유지하는 방식
- 같은 실패와 지식을 Markdown·record·projection·lifecycle에 중복 저장하는 방식
- 완료된 작업을 `SESSION_HANDOFF.md`에 계속 누적하는 방식
- 모든 작업에 번호 단계·별도 보고서·다중 검증을 자동 부과하는 방식

이 접근들은 복구 가능성보다 탐색 비용과 중복 권위를 더 크게 만들었다. 필요한 상세 사실은 Git 이력에서 정확한 커밋을 지정해 확인한다.
