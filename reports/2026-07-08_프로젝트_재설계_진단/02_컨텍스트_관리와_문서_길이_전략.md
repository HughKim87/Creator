## 1. 문제 정의

사용자가 지적한 것처럼 문서가 길어지면 AI가 전체를 안정적으로 반영하지 못한다. 긴 문서는 인간에게도 읽기 어렵지만, AI에게는 더 큰 문제가 된다.

AI는 긴 문서 안에서 다음 문제를 일으킨다.

1. 앞부분만 강하게 반영한다.
2. 최근에 읽은 내용을 과대 반영한다.
3. 반복되는 규칙 중 무엇이 현재 기준인지 혼동한다.
4. 오래된 산출물과 최신 기준을 섞는다.
5. 문서가 많을수록 "읽었다"와 "적용했다" 사이의 차이가 커진다.

따라서 프로젝트는 긴 문서를 없애는 것이 아니라, AI가 매번 짧고 정확한 작업 맥락만 보게 만들어야 한다.

## 2. 현재 프로젝트의 문제

현재 남은 문서들은 이전보다 줄었지만, 여전히 아래 위험이 있다.

| `SESSION_HANDOFF.md` | 현재 상태와 다음 작업이 섞이면 규칙처럼 오해될 수 있다. |
| `문서_인덱스.md` | 기준 문서 목록과 무효 참조가 늘어나면 또 긴 문서가 된다. |

## 3. 적용해야 할 핵심 구조

### 3.1 현재 작업 패킷

세션 시작 때 AI가 먼저 읽는 정보는 아래처럼 짧아야 한다.

```markdown
# CURRENT_TASK.md

현재 목표:
현재 단계:
현재 기준 파일:
입력 파일:
출력 파일:
이번 작업에서 하지 않을 일:
검증 기준:
멈출 조건:
```

이 파일은 길면 안 된다. 1~2 화면 안에 들어와야 한다.

### 3.2 기준 문서와 참고 문서 분리

문서는 아래 상태 중 하나만 가져야 한다.

| 상태 | 의미 |
|---|---|
| 기준 | 현재 단계의 판단 기준으로 사용 가능 |
| 참고 | 배경 이해용, 직접 기준 아님 |
| 산출물 | 특정 작업 결과 |
| 폐기 | 다음 작업에서 읽지 않음 |
| 보류 | 아직 검증되지 않음 |

이 상태가 없으면 AI는 참고 자료를 기준처럼 사용할 수 있다.

### 3.3 문서 길이 제한

권장 제한:

| 문서 유형 | 권장 길이 |
|---|---:|
| `PROJECT_RULES.md` | 150줄 이하 |
| `SESSION_HANDOFF.md` | 80줄 이하 |
| `문서_인덱스.md` | 100줄 이하 |
| 워크플로우 문서 | 150줄 이하 |
| 스킬 문서 | 200줄 이하 |
| 상세 리서치 보고서 | 길어도 됨. 단 기본 로드 금지 |
| 현재 작업 패킷 | 40줄 이하 |

중요한 것은 긴 문서를 아예 금지하는 것이 아니다. 긴 문서는 `reports/`나 참고 문서로 보내고, 세션 시작 기본 로드에서 제외해야 한다.

## 4. 외부 자료와의 연결

OpenAI Prompt Engineering 문서는 긴 작업에서 계획, TODO, 주요 도구 사용 전 설명, 검증을 강조한다. 이는 "긴 문서를 많이 읽히는 것"보다 "현재 작업을 추적 가능한 단위로 나누는 것"에 가깝다.

Context Engineering 자료는 정보 환경을 relevance, sufficiency, isolation, economy, provenance 기준으로 설계해야 한다고 본다.

## 5. 프로젝트에 필요한 적용안

1. `CURRENT_TASK.md` 또는 같은 역할의 현재 작업 패킷을 도입한다.
2. `문서_인덱스.md`에는 모든 문서를 나열하지 말고, 상태와 읽는 조건만 둔다.
3. 긴 리서치 보고서는 기본 로드하지 않는다.
4. 스킬은 해당 작업의 실행법만 담고, 전체 워크플로우를 반복하지 않는다.
5. 워크플로우는 단계의 목적과 완료 기준만 담고, 구체 실행은 스킬로 분리한다.
6. 현재 기준 파일이 없으면 산출물을 만들지 않는다.

## 6. 적용하지 말아야 할 방식

1. 모든 규칙을 `PROJECT_RULES.md`에 계속 추가하지 않는다.
2. 핸드오프를 장기 지식 저장소로 쓰지 않는다.
3. 문서 인덱스를 파일 목록 전체로 만들지 않는다.
4. 스킬마다 같은 원칙을 반복하지 않는다.
5. 긴 리서치 문서를 세션 시작 때 기본으로 읽게 하지 않는다.
