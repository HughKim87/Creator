## 1. 결론

현재 프로젝트는 **유튜브 제작 시스템이라기보다, 유튜브 제작 시스템을 안전하게 만들기 위한 범용 파일 데이터·상태·지식 기반**에 가깝다.

내부 기반의 품질은 높다. 파일 저장의 원자성, 해시 검증, 작업 상태, 지식 수명주기, 선택적 컨텍스트, 문서·schema 동기화, 보호 경로 검증이 코드와 계약으로 구현되어 있고 116개 회귀 테스트가 통과한다.

그러나 초기 목표였던 채널 관리와 영상 기획·대본·자막·분석·편집·검수의 실제 생산 흐름은 현재 트리에 거의 남아 있지 않다. 유튜브 도메인 기능은 **촬영 전 근거 패키지 1개**뿐이며, 계약에서 대본·자막·썸네일·촬영·편집·게시를 명시적으로 제외한다.

따라서 현재 상태를 한 문장으로 판정하면 다음과 같다.

> **튼튼한 기반은 완성됐지만, 사용자가 처음 원한 유튜브 제작 결과까지 이어지는 수직 흐름은 아직 완성되지 않았다.**

## 3. 초기 목표의 재구성

### 3.1 최초 목표

Git 최초 상태의 `PROJECT_RULES.md`는 프로젝트 목적을 다음 범위로 정의했다.

- 유튜브 채널 관리
- 업로드 영상의 전반적인 기획과 제안
- 영상 편집
- 자막 생성
- 하이라이트 장면 추천
- 제작 전 과정 지원

최초 `README.md`에는 이를 더 구체화한 7단계 흐름이 있었다.

`소재 조사 → 기획 → 대본 → 자막 → 영상 분석 → 편집 자료 → 검수`

당시에는 김실버 채널의 방향, 소재 우선순위, 실제 영상별 진척 상태도 연결되어 있었다. 즉 초기 목표는 추상적인 에이전트 프레임워크가 아니라 **특정 채널의 반복 제작 부담을 줄이는 실제 생산 시스템**이었다.

### 3.2 현재 문서가 정의하는 목표

현재 `README.md`와 `PROJECT_RULES.md`는 목적을 다음처럼 일반화했다.

이 방향은 초기 목표와 충돌하지 않는다. 오히려 장기적으로 더 좋은 상위 목적이다. 문제는 현재 구현이 이 목적의 **안전 기반**에는 충실하지만 **생산 결과**로 연결되는 도메인 기능은 충분히 복구하지 못했다는 점이다.

- schema·문서 링크·UTF-8·NUL·후행 공백·보호 경로·Git 변경 검증
- 49개 범용 CLI 진입점

유튜브 도메인에는 다음 한 가지 수직 기능이 구현되어 있다.

현재 유튜브 계약이 명시적으로 제외하고 실제 코드에도 없는 기능은 다음과 같다.

## 6. 강점

### 6.1 안전 경계가 명확하다

`inputs/`와 `outputs/`를 보호 경로로 분리하고 exact 대상과 목적 없이는 접근하지 않도록 했다. 원본과 사용자 데이터가 범용 검증이나 Git에 우연히 포함되는 위험을 낮춘다.

### 6.2 정본과 파생물을 구분한다

활성 정보의 단일 소유자, Markdown 정본, 결정론적 JSON artifact, Git 역사라는 책임 분리가 명확하다. 이전 구조에서 반복된 백업·보고서·상태 복제 문제를 실제 규칙과 검사로 줄였다.

### 6.3 저장과 상태 복구가 견고하다

원자적 교체, content hash, 예상 hash, event 재생, snapshot 재구축, strict JSON·UTF-8 검증이 구현되어 있다. 기록 손상이나 동시 수정 충돌을 조용히 성공으로 처리하지 않는다.

### 6.4 검증이 재현 가능하다

2026-07-24 직접 실행 결과는 다음과 같다.

| 검사 | 결과 |
|---|---|
| `python -m unittest discover -s tests -q` | 116개 테스트 통과, 약 24초 |
| `maintenance-verify` | 오류 0, drift 0, 중복 0 |
| 검증 범위 | 문서 26개, 링크 42개, Python 15개, schema 13개 |
| `maintenance-scan` | canonical failure 6개, runtime warning 없음 |
| 유튜브 evidence 예시 | 성공, selected item 1개, 결정론적 fingerprint 반환 |

### 6.5 공통 기반과 도메인 adapter가 분리되어 있다

유튜브 필드를 공통 record에 밀어 넣지 않고 `youtube_domain`이 별도 책임을 가진다. 이후 다른 제작 도메인을 추가할 때 기반을 오염시키지 않는 구조다.

## 7. 핵심 문제

### P0. 기반 완성과 프로젝트 목표 완성이 혼동될 수 있다

`SESSION_HANDOFF.md`는 현재 작업이 없고 116개 테스트가 통과한 상태를 “완료 후 대기”로 보고한다. 이는 현재 재구축 작업의 완료라는 뜻으로는 정확하지만, 유튜브 제작 프로젝트 전체가 완료된 것처럼 읽힐 위험이 있다.

프로젝트 수준의 완료 기준과 다음 유튜브 도메인 milestone이 활성 문서에 없기 때문에, 기반이 완성된 뒤 무엇을 생산해야 하는지가 시작 경로에서 보이지 않는다.

영향:

- 에이전트가 다음 사용자 요청을 기다리기만 하고 초기 목적을 향한 연속성이 끊긴다.
- 내부 검사 통과가 사용자 결과 달성으로 오인될 수 있다.
- 새 세션이 실제 채널 생산보다 기반 유지보수를 우선하기 쉽다.

### P0. 초기 유튜브 제작 범위의 대부분이 없다

초기 7단계 가운데 현재 직접 지원하는 것은 소재·기획 전에 필요한 근거 묶음 일부뿐이다. 대본부터 검수까지 이어지는 사용자 산출물이 없다.

현재 유튜브 기능의 범위를 정량화하면 다음과 같다.

- `src/file_data`: 5,182줄
- `src/youtube_domain`: 316줄
- 전체 구현 중 유튜브 도메인 비중: **5.7%**
- 전체 테스트 116개 중 유튜브 도메인 테스트: 8개, **6.9%**
- 범용 CLI 명령: 49개
- 유튜브 CLI 명령: 1개

코드 줄 수가 가치의 완전한 척도는 아니지만, 현재 투자 중심이 사용자 제작 기능이 아니라 기반임을 분명히 보여준다.

### P1. 운영된 데이터와 실제 채널 사례가 없다

유지보수 scan 결과 source, knowledge, decision, lifecycle state, work state, event가 모두 0건이다. 시스템이 테스트 fixture에서는 검증됐지만 실제 프로젝트 운영 기록으로 사용된 증거는 없다.

제공 예시의 영상 주제도 김실버 채널의 게임 콘텐츠가 아니라 “AI 작업 기억을 가볍게 만드는 선택적 컨텍스트”다. 따라서 다음은 아직 확인되지 않았다.

- 실제 게임 이슈 자료를 current 근거로 선별할 수 있는가
- 실제 기획자가 결과를 유용하다고 판단하는가
- 반복 제작에서 시간이 줄어드는가
- 제목·대본·편집 결정으로 자연스럽게 이어지는가

### P1. 깨끗한 환경에서 바로 실행되지 않는다

현재 루트에는 `pyproject.toml`, 설치 스크립트, 실행 wrapper가 없다. 일반 shell에서 문서의 명령을 그대로 실행하면 다음 오류가 발생했다.

```text
No module named file_data
No module named youtube_domain
```

`PYTHONPATH=src`를 설정하면 작동하고 테스트도 같은 방식을 사용한다. 즉 구현은 정상이나 사용자·에이전트의 첫 실행 경로가 완결되지 않았다.

영향:

- 새 세션이나 다른 PC에서 문서 예시가 그대로 재현되지 않는다.
- 49개 CLI 기능이 있어도 사용자가 발견하고 실행하기 어렵다.
- 실행 실패가 코드 결함인지 환경 설정 문제인지 구분하는 비용이 생긴다.

### P1. 사용자 작업 흐름보다 내부 계약이 앞에 보인다

현재 시작 문서는 정책·계약·검증 경로를 잘 설명하지만 “영상 하나를 만들려면 무엇을 입력하고 무엇을 받는가”를 보여주는 사용자용 경로가 없다.

문서 26개, 약 73,344자가 검증 대상이지만 실제 유튜브 사용 예시는 요청 JSON 1개뿐이다. 이는 시스템 유지자에게는 친절하지만 제작 사용자에게는 진입 장벽이 높다.

### P2. 범용 CLI 표면이 크고 orchestration이 없다

기반 CLI는 49개 세부 명령을 제공한다. 각 명령은 개별적으로 명확하지만 실제 작업자는 source 생성, knowledge 등록, lifecycle 전이, context 구성 등을 직접 조합해야 한다.

초기 목표는 수동 작업 감소였으므로, 내부 primitive가 많아도 사용자 관점의 단일 작업 명령이 없으면 자동화 효과가 제한된다.

### P2. 자동 검증이 수동 실행에 의존한다

유지보수 계약은 hook, CI, 예약 검사를 의도적으로 사용하지 않는다. 현재 규모에서는 합리적인 단순화지만, 에이전트가 검사를 빠뜨리면 보호 장치가 자동으로 작동하지 않는다.

이는 “자율 수행”을 목표로 하는 프로젝트에서 다음 위험을 남긴다.

- 새 변경이 116개 회귀를 통과했는지 강제되지 않는다.
- 문서와 schema drift가 commit 전 차단되지 않는다.
- 검증 명령을 아는 에이전트의 기억에 품질이 의존한다.

### P2. 사용자 성과 KPI가 없다

현재 metrics는 문서 문자 수, 실행 시간, context 절감률, drift 수를 측정한다. 이들은 기반 품질 지표이지 유튜브 제작 성과 지표가 아니다.

빠진 지표 예시:

- 기획안 초안 생성까지 걸린 시간
- 대본 수정 횟수
- 자막 교정 시간
- 원본 대비 추천 컷 채택률
- 영상 1편당 수동 작업 절감 시간
- 사용자가 그대로 채택한 제목·구성 비율

이 지표가 없으면 프로젝트가 초기 목적에 가까워지는지 객관적으로 판단하기 어렵다.

## 9. 권장 개선 순서

전체 과거 구현을 한꺼번에 복원하는 방식은 권장하지 않는다. 현재 기반을 유지하면서 **실제 영상 1편을 끝까지 통과시키는 가장 작은 수직 흐름**을 먼저 만드는 편이 낫다.

### 1순위: 프로젝트 완료 기준을 사용자 결과로 다시 고정

최소 완료 정의 예시:

> 사용자가 정확히 지정한 실제 영상 작업 1건에 대해 근거 패키지 → 기획안 → 대본 → 촬영/편집 체크리스트까지 생성하고, 각 결과를 사용자가 검토할 수 있다.

이 정의는 정책 변경이 아니라 다음 도메인 initiative의 목표로 관리할 수 있다.

### 2순위: 실제 김실버 콘텐츠 1건으로 수직 흐름 검증

사용자가 exact 보호 대상을 지정한 뒤 다음 흐름 하나만 구현한다.

`실제 근거 → 기획안 2~3안 → 선택 → 대본 초안 → 편집/촬영 체크리스트`

처음부터 영상 파일 처리와 업로드까지 넓히지 말고, 텍스트 중심 제작 전반부를 먼저 닫는 것이 비용 대비 효과가 크다.

### 3순위: 단일 유튜브 orchestration 명령 추가

49개 기반 명령을 사용자가 직접 조합하지 않도록 다음과 같은 도메인 진입점 하나를 둔다.

```text
youtube project-start
youtube plan-build
youtube script-build
youtube package-review
```

내부에서는 기존 record·work state·lifecycle·context 서비스를 재사용한다.

### 4순위: 설치와 실행 경로 정상화

다음 중 하나로 `PYTHONPATH` 의존을 제거한다.

- 최소 `pyproject.toml`과 editable install
- 프로젝트 전용 PowerShell wrapper
- 표준 모듈 실행을 보장하는 bootstrap command

README의 첫 사용 예시는 깨끗한 shell에서 그대로 성공해야 한다.

### 5순위: 비즈니스 acceptance test 추가

기반 단위 테스트와 별도로 다음 시나리오를 1개 추가한다.

1. 보호 데이터가 아닌 중립 유튜브 fixture를 입력한다.
2. 근거 패키지와 기획안, 대본 초안을 순차 생성한다.
3. 출처 trace와 approval gate를 유지한다.
4. 같은 입력에서 재현 가능한 결과 구조를 확인한다.
5. 최종 사용자 산출물의 필수 절을 검증한다.

### 6순위: 성과 지표를 작게 측정

첫 3건만 다음을 기록하면 충분하다.

- 작업 전 예상 수동 시간
- 실제 에이전트 실행 시간
- 사용자 수정 시간
- 초안 채택률
- 재작업 사유

이를 통해 기반 확장보다 어떤 제작 단계 자동화가 실제로 가치 있는지 결정할 수 있다.
