## 2. 합의점 — 양쪽이 독립적으로 확인한 동일 결함

두 보고서가 각자 실측으로 도달한 공통 판정. 신뢰도가 가장 높은 부분이다.

### 2.1 규칙이 작업별로 스코프되지 않는다

`F` (양쪽 확인) `PROJECT_RULES.md`는 매 세션 전체 완독 대상이고, `AGENTS.md`는 워크스페이스 내 모든 규칙 파일의 완독을 요구한다. 규칙별 적용 조건(applies_when), 제외 조건, 작업 태그가 없다.

`I` (양쪽 일치) 규칙은 "분리"된 것이 아니라 큰 문서 단위로 나뉘었을 뿐이다. Claude 보고서는 이를 `CONTEXT_RETRIEVAL.md` 자신의 계약("작업에 필요한 컨텍스트만 로드")을 규칙 문서가 위반하는 자기모순으로 지적했다.

### 2.2 지식 단위가 원자화·ID화되지 않았다

`F` (양쪽 확인) 기반 문서에 지식 단위 stable ID 0건, 상태·신뢰도·검토기한 적용 0건. 메타데이터는 문서 단위에만 존재한다.

### 2.3 기존 지식이 활성 구조로 이관되지 않았다

`F` (양쪽 확인) 결정 D-01~D-11은 849행 설계 보고서 속 표로만 존재한다. 분석 보고서가 발굴한 도메인 지식(원본 지문·source_id 불변, 6→5→7→8 순서, 7A~7D 검증 경계, Graphify·fail-open 등 실패 사례)도 긴 보고서와 `backup/` 링크에만 남아 있다.

`I` (양쪽 일치) 사용자 의도 기준으로 가장 큰 방향 오류다. 이미 존재하는 지식을 첫 corpus로 구성하지 않으면, 검색·관계·컨텍스트 설계가 실데이터 없이 다시 추상화된다.

### 2.4 탐색 단위가 문서 전체다

`F` (양쪽 확인) `DOCUMENT_MAP.md`의 "Read when"은 문서 단위다. "특정 작업에 규칙 3개와 사례 2개만 선택"하는 수준의 조립은 불가능하다.

### 2.5 관계가 데이터가 아니다

`F` (양쪽 확인) 문서 간 연결은 인라인 링크뿐이며 typed relation 레코드는 0건이다. (Claude 보고서: 링크 128개 전수 유효 — 추출 원료로는 깨끗함.)

### 2.6 재사용 가치가 있는 자산

`F` (양쪽 인정) 안전 경계(backup 불변, 보호 데이터), 출처·F/I/D 원칙, Markdown·JSONL 정본과 파생 인덱스 원칙, 단계 승인 구조, 벡터·그래프 조기 도입 보류 판정, 문서 단위 메타데이터 계약, 그리고 명령 3 보고서의 검증 주장이 실측과 일치하는 정직성.

## 3. 차이점 — 한쪽만 발견했거나 강조한 것

### 3.1 Claude 보고서만의 발견

- `F` **권위 모순:** `SESSION_HANDOFF.md`는 설계 보고서가 "결정 D-01~D-11을 소유"한다고 선언하는데, `DOCUMENT_MAP.md` 자체 분류상 보고서(Report)는 "활성 정책이 아님(not automatically active policy)"이다. 활성 결정의 소유자가 스스로 정의한 비권위 문서라는 자체 체계 내 모순.
- `F` **검증 도구 미축적:** 명령 3의 검증(링크 148개, UTF-8, 메타데이터)은 정확했으나 스크립트가 저장소에 없어 재현 불가. `WORKFLOW.md`의 "Automated" 등급을 달성할 수단이 프로젝트 안에 없다.
- `F` **version history 순환:** 규칙 2.5는 임시 백업 대신 version history를 지시하는데 커밋이 0건이고, 커밋은 규칙 6.5(명시 요청 필요)가 막고 있다. 위반이 아니라 규칙 설계의 순환 문제.
- `D` **재구조화 비용이 낮다는 평가:** 조항 번호 체계(1.1~6.5), D-ID·O-ID, 문서 메타데이터, 유효한 링크망이 원자화의 절단선과 준-레코드를 이미 제공하므로, 필요한 것은 재작성이 아니라 추출·재구조화다.

### 3.2 Codex 보고서만의 발견

- `F` **universal file catalog 부재:** 비보호 활성 Git 추적 파일 15개 중 `DOCUMENT_MAP.md` 레지스트리 등록은 11행. `.gitattributes`, `.gitignore`, 문서 지도 자신, 명령 3 보고서가 카탈로그 밖이다. 문서만이 아니라 코드·설정·테스트·스키마까지 모든 활성 파일이 선택 가능한 컨텍스트 노드여야 한다는 요구를 독립 배점(20점)으로 평가했다.
- `F` **쓰기 경로 부재:** 현재 가능한 것은 수동 읽기 라우팅뿐. 수정 대상의 owner·write_when·validator 선택, 변경 후 hash·관계·카탈로그 갱신, 작업 event 기록, 새 지식 후보 생성이 전부 없다. 읽기→작업→쓰기→축적의 폐쇄 루프가 닫히지 않는다.
- `D` **backup 이관 오염 방지:** 역사 문서를 그대로 색인하면 폐기된 규칙이 현재 지시처럼 실행될 수 있으므로 `historical_candidate` 상태 → 검토 → 승격의 migration namespace가 필요하다. 스냅샷별 우선 추출 대상 표(origin=도메인 규칙, snapshot_1=실패 원장, snapshot_2=직접 라우팅·문서 원자화)도 제시.
- `D` **구체 스키마 제안:** rule 레코드 필드(rule_id, rule_class, priority, applies_when, excludes_when, relations 등)와 file 노드 필드(read_when, write_when, consumes/produces, validators, content_sha256 등).
- `D` **D-01~D-11 재판정:** 유지 7건, 수정 3건(D-08 라우팅 단위, D-09 backup 이관, D-10 규칙 커널화), 철회 1건(D-11 "명령 3은 문서만").
- `D` **레드팀 경고:** 규칙 원자화 과잉(문장마다 파일을 만들면 관리비 폭증 — rule pack으로 묶을 것), 검색 점수로 규칙 우선순위를 정하지 말 것(적용 조건과 authority가 먼저), 카탈로그가 쓰기 흐름에서 자동 갱신되지 않으면 곧 낡는다는 유지비 경고.

### 3.3 점수 차이의 원인 (55 vs 27)

`D` 세 가지 가중치 차이로 설명된다. 사실 판정의 차이가 아니다.

1. **설계 문서의 가치:** Claude는 "목표 구조를 정확히 계약화한 설계"에 높은 점수(20점 중 17점)를 부여했다. Codex는 잘 쓰인 문서라도 목표 시스템과 다른 시스템이면 목적 적합도에 거의 반영하지 않았다.
2. **평가 범위:** Codex는 universal file catalog(20점)와 읽기·쓰기 폐쇄 루프(15점)를 독립 항목으로 넣었다. 둘 다 현재 0에 가까워 합계를 크게 끌어내린다. Claude 채점표에는 이 두 축이 명시 항목으로 없었다.
3. **재사용 원료 보정:** Claude는 기존 자산의 낮은 재구조화 비용을 각 항목 점수에 반영했고, Codex는 별도 보정 3점만 인정했다.

`D` 사용자 의도의 문언("모든 파일이 전부... 읽기 쓰기 컨텍스트 쌓기 최적화에 포함")에 비추면, Codex가 추가한 두 축은 정당한 평가 항목이다. Claude 채점은 이를 누락한 만큼 관대했다.

## 5. 통합 권고

두 보고서의 권고를 병합한 실행 순서. Codex의 R-단계 골격에 Claude의 저비용 보완 항목을 흡수했다.

### R-0: 즉시 처리 (설계 논의와 무관하게 이득)

1. 명령 3 검증 로직을 `tools/`에 영속화 — "Automated" 등급의 실제 수단 확보. (Claude)
2. Git 초기 커밋 여부 사용자 결정 — 규칙 2.5의 version history 성립. (Claude)
3. 권위 모순 해소 예약: D-01~D-11 소유권을 보고서에서 결정 레코드로 이관 예정임을 인수인계에 기록. (Claude)

### R-1: 설계 정정 (기존 Stage 4-A 대체)

1. 최소 상시 커널과 조건부 규칙의 경계 확정 — 커널은 사용자 지시 우선순위, 보호 데이터, 파괴적 행동 권한, 충돌 해결, resolver 진입 규칙 수준으로 축소. (Codex §3.1, Claude §6.1)
2. rule / file / knowledge / decision / case / relation / event 스키마 설계 — Codex 필드안을 출발점으로. 원자화 과잉 방지를 위해 rule pack 단위 허용. (Codex 레드팀 2)
3. task→rule→file→knowledge 선택 순서와 읽기·쓰기 공통 manifest 설계. (Codex)
4. backup migration namespace와 `historical_candidate` 승격 절차 확정. (Codex §8)
5. D-08·D-09·D-10 수정과 D-11 철회를 결정 레코드로 기록. (Codex §6)

### R-2: 기존 corpus 선이관 (양쪽 권고의 교집합, 최우선 실질 작업)

1. 활성 기반 지식부터: 규칙 24조항의 커널/모듈 분리, D-01~D-11 결정 레코드화, 실패 원장 2건 사례화, O-* 근거 20건 출처 레코드화, 링크 128개의 typed relation 추출. (Claude §6.2)
2. 모든 활성 비보호 파일을 universal file catalog에 등록 — orphan 파일 탐지 포함. (Codex)
3. `backup/`에서 분석 보고서가 이미 선정한 도메인 규칙·실패 사례를 `historical_candidate`로 추출·검토·승격. (Codex §8)
4. `SESSION_HANDOFF.md`를 재개점만 남기고 분해 — 용어·결정·실패·위험을 각 소유 레코드로 이관. (Claude §6.3)
5. 대표 작업 2~3개(보고서 작성, 스키마 설계 등)에서 필요한 항목만 선택되는지 수동 resolver로 검증. (Codex R-2.5)

### R-3: 최소 resolver와 writer

task request 구조화 → 커널+조건부 규칙+파일+지식의 예산 내 선택 → 쓰기 대상의 owner·validator 반환 → 작업 후 event·hash·관계·지식 후보 갱신 → 새 세션 재개 검증. (Codex §9)

### R-4: 검색 projection

정본과 resolver가 실 corpus에서 작동한 뒤에만 SQLite FTS5 추가. 벡터·그래프·Obsidian은 그 이후 평가로 결정. (양쪽 일치, 기존 D-02·D-05 유지)

### 완료 기준

Codex §10의 12개 항목을 통합 완료 기준으로 채택한다. 핵심만 꼽으면: 보고서 작성 작업에 영상 XML 규칙이 선택되지 않을 것, backup source locator에서 active rule까지 추적될 것, 새 세션이 채팅 기억 없이 task request와 정본 파일만으로 같은 컨텍스트를 구성할 것, 작업 결과가 다음 검색 corpus에 반영될 것.

## 6. 결론

`D` 두 보고서는 같은 진단에 도달했다: **설계 문서는 목표를 알고 있으나, 구축물은 그 구조를 자기 자신에게 적용하지 않은 정적 문서 체계다.** 차이는 "재정의한 4-A로 메울 수 있다"(Claude)와 "설계 정정부터 다시 해야 한다"(Codex)의 절차 차이인데, 실행 내용을 펼치면 두 경로는 §5의 동일한 작업 목록으로 수렴한다.

`D` 통합 판정 36/100. 권고: 기존 Stage 4-A는 시작하지 않는다. R-0(즉시 보완) → R-1(설계 정정) → R-2(기존 지식 선이관)를 승인 단계로 진행한다. 특히 R-2가 사용자 의도("이미 존재하는 데이터부터 구조에 맞춰 구성")의 직접 구현이며, 기존 자산은 버릴 것이 거의 없고 전부 이관 원료로 쓰인다.
