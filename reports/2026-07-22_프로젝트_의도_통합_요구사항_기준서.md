## 1. 통합 결정

현재 요구사항의 사실·수치·구조·수용 기준은 Codex 보고서를 기준으로 유지한다. Claude 보고서에서는 다음 세 분석만 필수 요구사항으로 병합한다.

1. 사용자의 인지가 토큰보다 앞선 복잡성 예산이라는 분석
2. 승인 절차가 있어도 사용자의 실제 결정으로 남지 않았던 승인 실패 분석
3. 범위와 의도를 정한 사용자 발언은 요약이 아니라 원문을 최상위 근거로 보존해야 한다는 분석

이 병합은 Codex 요구사항을 폐기하거나 Claude 보고서 전체를 추가하는 작업이 아니다. Codex의 현재 목적과 20개 필수 요구사항은 유지하고, 세 누락을 보완한다.

## 2. 현재 프로젝트 의도

### 2.1 현재 최상위 목적

최상위 목적은 **사람의 수동 생산 작업 없이 승인 범위의 작업을 에이전트 자율성에 맡겨 생산성을 극대화하는 것**이다.

작업 결과·실패·판단·경험을 출처와 함께 선별 축적하고 다음 작업에 필요한 것만 읽는 데이터 기반 지식 운영 기반은, 에이전트가 채팅 기억이나 사람의 수동 안내 없이 정확히 일하기 위한 수단이다. 사람은 목표·금지·보호·외부 영향·되돌리기 어려운 결정과 결과 확인을 맡고, 에이전트는 그 경계 안의 조사·안전한 기본값 선택·구현·검증·실패 복구를 수행한다.

현재 만들 것은 완성형 영상 제작 시스템이 아니다. 영상 제작은 이 운영 기반을 실제 도메인에 적용하는 후속 영역이다.

### 2.2 구축 순서

구축은 다음 순서를 따른다.

> 공통 규칙 → 정보·문서 책임 → Obsidian 문서 가시화·검토 → 파일 기반 데이터 → 읽기·쓰기 → 작업 상태·파일 관리 → 지식 유형과 수명주기 → 선택적 컨텍스트 → 유지보수 → 도메인 워크플로

영상 제작은 기반을 검증한 뒤 별도 승인을 받아 결합하는 후속 도메인이다. 최종 비전이 현재 단계의 완료 조건을 앞당기지 않는다.

## 3. 근거와 권위의 순서

충돌이 발생하면 다음 순서로 판정한다.

| 우선순위 | 근거 | 역할 |
|---:|---|---|
| 1 | 사용자의 최신 명시적 원문과 확인 | 목적·범위·승인·예외를 확정한다. |
| 2 | 이 통합 요구사항 기준서 | 현재 요구사항과 수용 기준을 소유한다. |
| 3 | 마스터 계획과 단계별 계획서 | 승인된 구현 순서와 해당 단계 범위를 소유한다. |
| 4 | Codex·Claude 역추론 보고서 | 분석 근거와 역사 해석을 제공한다. |
| 5 | `backup/`과 과거 산출물 | 사실 확인용 역사 증거이며 활성 지시가 아니다. |

이전 사용자 원문과 최신 사용자 원문이 충돌하면 이전 원문을 삭제하지 않고 역사 근거로 남기되, 최신 명시적 확인을 활성 판단으로 사용한다.

## 4. 병합한 세 가지 분석

### 4.1 인지 복잡성

문제가 된 복잡성은 문서 길이나 토큰 수만이 아니다. 사용자가 알지 못하는 구성요소, 승인, 내부 사건, 진입점, 상태 소유자가 늘어나면서 프로젝트의 전체 그림이 사용자의 인지 밖으로 벗어난 것이 핵심이다.

Claude 보고서가 확인한 대표 신호는 다음과 같다.

- 사용자가 변경 제안 0001·0002를 기억하지 못했다.
- 454KB 쓰기 계약과 Obsidian 진단이 사용자에게는 처음 듣는 내부 사건이었다.
- 문제의 발생·진단·수습은 에이전트 내부에서 끝났고, 사용자에게는 무겁고 비효율적인 결과만 남았다.

따라서 시스템은 기술적으로 정확한 것만으로 충분하지 않다. 사용자가 현재 목적, 활성 구조, 다음 단계, 중요한 결정을 자기 언어로 이해할 수 있어야 한다.

### 4.2 승인 실패

승인 파일이나 상태값이 존재한다고 해서 유효한 승인이 되는 것은 아니다. 승인 대상의 변화와 영향을 사용자가 이해하지 못했거나, 여러 단계가 한 번에 묶여 지나갔거나, 나중에 승인 자체를 기억하기 어려운 상태라면 절차만 존재한 형식적 승인이다.

승인은 다음 원칙으로 보정한다.

- 가역적이고 승인된 범위 안의 로컬 작업은 에이전트가 실행하고 보고한다.
- 비가역 행동, 외부 행동, 비용 발생, 범위 확대, 단계 전환은 사전 승인을 받는다.
- 승인 요청은 구현 세부 목록이 아니라 목적, 달라지는 점, 달라지지 않는 점, 주요 위험, 승인 후 다음 정지 지점을 설명한다.
- 사용자가 정확한 단계 묶음과 성공 게이트를 상시 승인한 경우 에이전트가 각 게이트 결과를 보고하며 연속 진행할 수 있다.
- 승인 근거가 불명확하거나 승인 후 대상이 실질적으로 달라졌다면 다시 확인한다.

### 4.3 사용자 원문 보존

에이전트의 요약은 편의를 위한 파생물이다. 목적·범위·금지·승인·거절·용어 정의에 영향을 주는 사용자 발언은 원문이 권위 근거이며, 요약문은 반드시 원문 위치를 가리켜야 한다.

원문 보존은 과거 프로젝트 자료 전체 보존과 다르다.

- 사용자 원문: 의도 이탈을 막는 최상위 증거로 보존한다.
- 과거 지식과 시스템 자료: 현재 목적에 필요한 것만 선택적으로 승계한다.
- 폐기·보류된 과거 자료: 활성 경로에서 제외하고, 필요할 때 판정 이유를 추적할 수 있게 한다.

## 5. 요구사항 활성화 원칙

요구사항이 최종 기준에 포함됐다는 이유만으로 Stage 00에서 전부 구현하지 않는다.

| 구분 | 적용 방식 |
|---|---|
| 즉시 적용 제약 | 현재 목적, 계층 순서, 임의 결정 금지, 사용자 원문 권위, 승인 경계, 데이터 보호, 정직한 완료 보고 |
| 단계별 기능 요구사항 | 표에 지정된 단계에 도달했을 때만 구현·완료 기준으로 활성화 |
| 조건부 확장 | 단순한 방식의 한계가 실측되고 사용자가 승인한 경우에만 활성화 |
| 미확정 수치·정책 | 관련 단계 착수 전에 사용자에게 질문하고, 답변 전에는 구현값으로 확정하지 않음 |

## 6. 통합 필수 요구사항

아래 UR 요구사항은 Codex 보고서의 M-01~M-20을 빠짐없이 재구성하고 Claude 분석의 세 보완 요구사항, 사용자가 추가로 확정한 문서 가시성 요구사항, Stage 10의 문서 기반 데이터·실행·검증 요구를 반영한 현재 필수 기준이다.

| ID | 활성 단계 | 요구사항 | 수용 기준 |
|---|---|---|---|
| UR-01 | 즉시·Stage 00 | 에이전트 자율 생산성이라는 최상위 목적과 계층 순서를 유지한다. `(M-01, M-02, 사용자 최신 확인)` | 시작 문서·계획·완료 보고가 지식 운영 기반을 자율 작업의 수단으로 명시하고, 기반 완료 전 영상 워크플로를 활성 다음 단계로 두지 않는다. |
| UR-02 | Stage 04 | 실제 작업의 결과·실패·결정을 추적 가능한 기록으로 남긴다. `(M-03)` | 대표 작업의 범위, 근거, 결과, 실패, 검증, 사용자 결정이 하나의 연결된 기록에서 확인된다. |
| UR-03 | Stage 05 | 작업 기록과 장기 지식을 분리하고 과거 지식은 선택적으로만 승계한다. `(M-04, M-05)` | 모든 기록을 자동 승격하지 않으며, 선택된 과거 항목만 보존 이유·출처와 함께 승격한다. 과거 전체 이관량을 완료 기준으로 사용하지 않는다. |
| UR-04 | Stage 02·05 | 지식의 출처와 유형을 명확히 한다. `(M-06, M-07)` | 재사용 지식에 안정 ID와 원출처 locator·무결성 근거가 있고, 사실·추론·결정·실패 사례가 구분된다. |

## 9. 승인 계약

### 9.1 사전 승인이 필요한 경우

- 파일 삭제·이동처럼 복구 비용이 큰 변경
- 커밋·푸시·외부 전송·설치·과금
- 사용자가 승인한 단계 범위의 확대
- 정본·정책·데이터 경계의 변경
- 다음 단계 착수

정확한 단계·범위·제외·성공 게이트를 사용자가 상시 승인한 경우 개별 단계 착수와 해당 단계 경계 커밋은 그 승인으로 대체할 수 있다. 범위나 위험이 달라지면 다시 확인한다.

### 9.2 자율 실행 후 보고할 수 있는 경우

- 승인된 단계와 파일 범위 안의 가역적 로컬 편집
- 읽기 전용 조사와 검증
- 승인된 목적 안의 합리적 기본값·구현 세부 선택과 실패 복구
- 합의된 형식에 따른 오탈자·링크·인코딩 보정
- 승인된 구현을 증명하기 위한 비파괴적 테스트

### 9.3 승인 요청의 최소 내용

1. 이번 결정의 목적
2. 승인하면 달라지는 것
3. 달라지지 않는 것과 제외 범위
4. 주요 위험·비용·되돌리는 방법
5. 승인 후 수행할 범위와 다음 정지 지점

승인 기록은 사용자 응답 원문, 승인 대상 문서나 변경안, 유효 범위를 연결해야 한다. 대상이 실질적으로 바뀌면 기존 승인을 재사용하지 않는다.

사전 승인이 필요하지 않은 구현 세부를 사람에게 떠넘기지 않는다. 에이전트는 선택 이유, 실제 영향, 검증 결과와 남은 위험을 진행 또는 완료 보고에 포함한다.

## 10. 사용자 원문 보존 계약

### 10.1 보존 후보

- 프로젝트 목적과 성공 기준
- 단계 범위와 우선순위
- 금지·허용·보호 경계
- 승인·거절·보류 결정
- 사용자가 직접 정의한 핵심 용어
- 이전 판단을 바꾸는 최신 확인

### 10.2 보존 방식의 원칙

- 원문은 수정하지 않고 날짜와 대화 맥락을 함께 둔다.
- 요약과 해석은 별도 항목으로 작성하고 원문을 가리킨다.
- 서로 충돌하는 원문은 둘 다 남기되 활성 판단과 역사 판단을 구분한다.
- 모든 대화를 무차별 저장하는 기능은 이 요구사항에 포함되지 않는다.
- 구체적인 저장 위치, 파일 형식, 보존 범위는 관련 단계에서 사용자 확인 후 결정한다.

## 14. 현재 결론

현재 요구사항은 Codex 보고서의 구조를 유지하되, 다음 여덟 제약을 같은 수준의 필수 기준으로 적용한다.

1. 사람의 수동 생산 작업을 승인 범위 안의 에이전트 자율 실행으로 대체한다.
2. 모든 지속 프로젝트 데이터는 사람이 읽을 수 있는 문서 하나를 활성 정본으로 가진다.
3. 프로젝트 작업은 관련 문서 owner를 읽고 결과·실패·검증·다음 행동을 그 owner에 갱신하는 흐름으로 수행한다.
4. 폴더·파일·문서 연결·machine artifact fanout을 현재 구조와 역사 실패까지 대조해 최적화한다.
5. Stage 10의 독립 교차검증 계약은 완료된 해당 단계의 역사다. 새 작업은 가장 낮은 충분 작업 등급을 사용하고, 독립 검증·숫자 점수·번호 stage는 사용자 또는 exact active plan이 요구할 때만 적용한다.
6. 기술 복잡성보다 먼저 사용자의 인지 복잡성을 관리한다.
7. 승인은 상태값이 아니라 사용자가 이해하고 기억할 수 있는 의미 있는 결정이어야 한다.
8. 사용자 원문은 에이전트 요약보다 높은 권위를 가지며, 과거 지식의 선택적 승계와 별도로 보존한다.

추가로 사용자가 모든 활성 프로젝트 문서·규칙과 연결 관계를 직접 확인하며 각 단계를 진행하겠다는 요구를 확정했으므로, Obsidian 문서 가시화·검토 환경을 Stage 01과 Stage 02 사이의 Stage 01.5로 활성화한다. 이는 정본 저장소나 지식 데이터베이스 도입 승인이 아니다.

이 기준서는 동적 구현 상태를 소유하지 않는다. 현재 단계와 첫 다음 행동은 [SESSION_HANDOFF.md](../SESSION_HANDOFF.md)가, 현재 Stage 11의 계획·실행·최종 보고는 [Stage 11 owner](../docs/build/stage-11-operating-friction-reduction.md)가 소유한다. 실제 도메인 작업은 별도 사용자 지시 없이 자동 착수하지 않는다.
