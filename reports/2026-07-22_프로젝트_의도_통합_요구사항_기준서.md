## 1. 통합 결정

현재 요구사항의 사실·수치·구조·수용 기준은 Codex 보고서를 기준으로 유지한다. Claude 보고서에서는 다음 세 분석만 필수 요구사항으로 병합한다.

1. 사용자의 인지가 토큰보다 앞선 복잡성 예산이라는 분석
2. 승인 절차가 있어도 사용자의 실제 결정으로 남지 않았던 승인 실패 분석
3. 범위와 의도를 정한 사용자 발언은 요약이 아니라 원문을 최상위 근거로 보존해야 한다는 분석

이 병합은 Codex 요구사항을 폐기하거나 Claude 보고서 전체를 추가하는 작업이 아니다. Codex의 현재 목적과 20개 필수 요구사항은 유지하고, 세 누락을 보완한다.

## 2. 현재 프로젝트 의도

### 2.1 현재 최상위 목적

현재 만들 것은 영상 제작 시스템이 아니다. 작업 결과·실패·판단·경험을 출처와 함께 선별 축적하고, 다음 작업에서 필요한 것만 효율적으로 읽고 다시 결과에 반영하는 **데이터 기반 지식 운영 기반**이다.

### 2.2 구축 순서

구축은 다음 순서를 따른다.

> 공통 규칙 → 정보·문서 책임 → Obsidian 문서 가시화·검토 → 파일 기반 데이터 → 읽기·쓰기 → 작업 상태·파일 관리 → 지식 유형과 수명주기 → 선택적 컨텍스트 → 유지보수 → 도메인 워크플로

영상 제작은 기반을 검증한 뒤 별도 승인을 받아 결합하는 후속 도메인이다. 최종 비전이 현재 단계의 완료 조건을 앞당기지 않는다.

### 2.3 현재 사용자 원문

아래 발언은 이 기준서의 범위와 진행 방식을 정한 현재 최상위 근거다. 에이전트 요약이 이 원문을 대체할 수 없다.

> “아니야 넌 지금 내가 하려는 가장 완성된 형태를 맨처음 시작부터 요구하고 있는거야. 그렇게 하면 문제가 많아져”

> “구현 단계를 나누고, 순차적으로 구조를 세우고 확장해 나가야된다고 생각해.”

> “각 단계별로 명확하지 않은 내용들은 임의로 채워넣지 말고 나에게 물어보고 진행해.”

> “아니 난 이 프로젝트의 규칙들을 포함한 모든 문서를 다 확인하고 어떻게 연결되는지 보면서 각 단계별 작업을 진행하고 싶어”

## 3. 근거와 권위의 순서

충돌이 발생하면 다음 순서로 판정한다.

| 우선순위 | 근거 | 역할 |
|---:|---|---|
| 1 | 사용자의 최신 명시적 원문과 확인 | 목적·범위·승인·예외를 확정한다. |
| 2 | 이 통합 요구사항 기준서 | 현재 요구사항과 수용 기준을 소유한다. |
| 3 | 마스터 계획과 단계별 계획서 | 승인된 구현 순서와 해당 단계 범위를 소유한다. |
| 4 | Codex·Claude 역추론 보고서 | 분석 근거와 역사 해석을 제공한다. |
| 5 | `backup/`과 과거 산출물 | 사실 확인용 역사 증거이며 활성 지시가 아니다. |

이전 사용자 원문과 최신 사용자 원문이 충돌하면 이전 원문을 삭제하지 않고 역사 근거로 남기되, 최신 명시적 확인을 활성 판단으로 사용한다.

## 4. 병합한 세 가지 분석

### 4.1 인지 복잡성

문제가 된 복잡성은 문서 길이나 토큰 수만이 아니다. 사용자가 알지 못하는 구성요소, 승인, 내부 사건, 진입점, 상태 소유자가 늘어나면서 프로젝트의 전체 그림이 사용자의 인지 밖으로 벗어난 것이 핵심이다.

Claude 보고서가 확인한 대표 신호는 다음과 같다.

- 사용자가 변경 제안 0001·0002를 기억하지 못했다.
- 454KB 쓰기 계약과 Obsidian 진단이 사용자에게는 처음 듣는 내부 사건이었다.
- 문제의 발생·진단·수습은 에이전트 내부에서 끝났고, 사용자에게는 무겁고 비효율적인 결과만 남았다.

따라서 시스템은 기술적으로 정확한 것만으로 충분하지 않다. 사용자가 현재 목적, 활성 구조, 다음 단계, 중요한 결정을 자기 언어로 이해할 수 있어야 한다.

### 4.2 승인 실패

승인 파일이나 상태값이 존재한다고 해서 유효한 승인이 되는 것은 아니다. 승인 대상의 변화와 영향을 사용자가 이해하지 못했거나, 여러 단계가 한 번에 묶여 지나갔거나, 나중에 승인 자체를 기억하기 어려운 상태라면 절차만 존재한 형식적 승인이다.

승인은 다음 원칙으로 보정한다.

- 가역적이고 승인된 범위 안의 로컬 작업은 에이전트가 실행하고 보고한다.
- 비가역 행동, 외부 행동, 비용 발생, 범위 확대, 단계 전환은 사전 승인을 받는다.
- 승인 요청은 구현 세부 목록이 아니라 목적, 달라지는 점, 달라지지 않는 점, 주요 위험, 승인 후 다음 정지 지점을 설명한다.
- 한 단계의 결과 확인과 다음 단계 착수 승인을 건너뛰는 묶음 승인은 허용하지 않는다.
- 승인 근거가 불명확하거나 승인 후 대상이 실질적으로 달라졌다면 다시 확인한다.

### 4.3 사용자 원문 보존

에이전트의 요약은 편의를 위한 파생물이다. 목적·범위·금지·승인·거절·용어 정의에 영향을 주는 사용자 발언은 원문이 권위 근거이며, 요약문은 반드시 원문 위치를 가리켜야 한다.

원문 보존은 과거 프로젝트 자료 전체 보존과 다르다.

- 사용자 원문: 의도 이탈을 막는 최상위 증거로 보존한다.
- 과거 지식과 시스템 자료: 현재 목적에 필요한 것만 선택적으로 승계한다.
- 폐기·보류된 과거 자료: 활성 경로에서 제외하고, 필요할 때 판정 이유를 추적할 수 있게 한다.

## 5. 요구사항 활성화 원칙

요구사항이 최종 기준에 포함됐다는 이유만으로 Stage 00에서 전부 구현하지 않는다.

| 구분 | 적용 방식 |
|---|---|
| 즉시 적용 제약 | 현재 목적, 계층 순서, 임의 결정 금지, 사용자 원문 권위, 승인 경계, 데이터 보호, 정직한 완료 보고 |
| 단계별 기능 요구사항 | 표에 지정된 단계에 도달했을 때만 구현·완료 기준으로 활성화 |
| 조건부 확장 | 단순한 방식의 한계가 실측되고 사용자가 승인한 경우에만 활성화 |
| 미확정 수치·정책 | 관련 단계 착수 전에 사용자에게 질문하고, 답변 전에는 구현값으로 확정하지 않음 |

## 6. 통합 필수 요구사항

아래 UR 요구사항은 Codex 보고서의 M-01~M-20을 빠짐없이 재구성하고 Claude 분석의 세 보완 요구사항과 사용자가 추가로 확정한 문서 가시성 요구사항을 반영한 현재 필수 기준이다.

| ID | 활성 단계 | 요구사항 | 수용 기준 |
|---|---|---|---|
| UR-01 | 즉시·Stage 00 | 현재 목적과 계층 순서를 유지한다. `(M-01, M-02)` | 시작 문서·계획·완료 보고가 지식 운영 기반을 현재 목적으로 명시하고, 기반 완료 전 영상 워크플로를 활성 다음 단계로 두지 않는다. |
| UR-02 | Stage 04 | 실제 작업의 결과·실패·결정을 추적 가능한 기록으로 남긴다. `(M-03)` | 대표 작업의 범위, 근거, 결과, 실패, 검증, 사용자 결정이 하나의 연결된 기록에서 확인된다. |
| UR-03 | Stage 05 | 작업 기록과 장기 지식을 분리하고 과거 지식은 선택적으로만 승계한다. `(M-04, M-05)` | 모든 기록을 자동 승격하지 않으며, 선택된 과거 항목만 보존 이유·출처와 함께 승격한다. 과거 전체 이관량을 완료 기준으로 사용하지 않는다. |
| UR-04 | Stage 02·05 | 지식의 출처와 유형을 명확히 한다. `(M-06, M-07)` | 재사용 지식에 안정 ID와 원출처 locator·무결성 근거가 있고, 사실·추론·결정·실패 사례가 구분된다. |
| UR-05 | Stage 06 | 지식의 수명주기와 충돌을 숨기지 않는다. `(M-08, M-09)` | 후보·검증·논쟁·대체·폐기 상태와 이유를 확인할 수 있고, 상충 지식과 현재 채택 근거가 함께 반환된다. |
| UR-06 | Stage 00·01 | 활성 정본과 재개 경로를 하나로 유지한다. `(M-10, M-11)` | 같은 주제의 복수 활성 소유자가 없고, 채팅 기억과 `backup/` 없이 현재 목적·상태·첫 행동·차단을 재구성한다. |
| UR-07 | Stage 07 | 필요한 컨텍스트만 선택하고 비용을 측정한다. `(M-12, M-13)` | 대표 질의의 필수 항목을 누락하지 않으면서 무관·폐기·보호 항목을 제외하고, 전체 로딩 기준선 대비 문자·토큰·중복을 측정한다. 수치 상한은 사용자 승인 전 임의 확정하지 않는다. |
| UR-08 | Stage 03·07 | 지식을 효율적으로 쓰고 다음 작업에 실제 환류한다. `(M-14, M-15)` | 지식 한 건의 추가·검토·대체가 복수 정본 수동 갱신 없이 완료되고, 다음 관련 작업에 선택 이유와 사용 흔적이 남는다. |
| UR-09 | 즉시·Stage 03 | 실패를 성공이나 검증 지식으로 보고하지 않는다. `(M-16)` | 비정상 종료, 의존성 부재, 부분 저장, 출처 불일치, 검증 실패를 비성공 상태와 원인으로 반환한다. 완료 보고에는 실제 검증 수준을 표시한다. |
| UR-10 | 즉시·Stage 00·02 | 사용자 데이터 경계를 사전 차단하고 원본과 파생물을 분리한다. `(M-17, M-18, M-19)` | 보호 트리는 접근 전 필터링하고, 원본 덮어쓰기·자동 삭제 경로가 없으며, 파생물은 재생성 가능하다. 활성 프로젝트는 `backup/` 의존 없이 동작한다. |
| UR-11 | Stage 08까지 누적 | 세 가지 대표 실사용 시나리오로 기반을 검증한다. `(M-20)` | 실제 데이터로 ① 필요한 기존 지식 읽기, ② 새 지식 추가·검토·재조회, ③ 실패 경험의 다음 작업 재사용을 통과하고 비용을 측정한다. 각 하위 기능은 해당 단계에서만 구현한다. |
| UR-12 | 즉시·전 단계 | 사용자의 인지를 첫 번째 복잡성 예산으로 취급한다. `(Claude 보완)` | 단계 시작·종료 보고에서 현재 목적, 활성 구성, 이번 변화, 다음 결정을 짧은 전체 그림으로 설명한다. 사용자가 알지 못하는 활성 구성이나 의사결정 경로를 조용히 늘리지 않는다. 수치 상한은 사용자 결정 전 임의 확정하지 않는다. |
| UR-13 | 즉시·전 단계 | 승인은 의미 있는 결정으로 작동해야 한다. `(Claude 보완)` | 승인 요청이 변화·영향·비변경 범위·위험·다음 정지 지점을 밝히고, 사용자 응답과 승인 대상을 연결한다. 가역적 세부 작업을 과잉 승인 대상으로 만들지 않으며 단계 경계를 묶어 건너뛰지 않는다. |
| UR-14 | 즉시·Stage 01 | 범위와 의도를 정한 사용자 원문을 보존한다. `(Claude 보완)` | 목적·범위·금지·승인·거절에 영향을 주는 원문과 날짜·맥락을 권위 근거로 두고, 모든 요약·계획이 해당 원문을 추적한다. 이전 원문은 최신 결정과 구분해 역사로 보존한다. |
| UR-15 | 즉시·전 단계 | 내부 복잡성 사건을 사용자 인지 밖에서 종결하지 않는다. `(Claude 보완)` | 구조·비용·일정·승인 범위를 실질적으로 바꾸는 내부 실패나 우회가 발생하면 원인, 영향, 임시 조치, 사용자 결정 필요 여부를 해당 단계 보고에 포함한다. |

## 9. 승인 계약

### 9.1 사전 승인이 필요한 경우

- 파일 삭제·이동처럼 복구 비용이 큰 변경
- 커밋·푸시·외부 전송·설치·과금
- 사용자가 승인한 단계 범위의 확대
- 정본·정책·데이터 경계의 변경
- 다음 단계 착수

### 9.2 자율 실행 후 보고할 수 있는 경우

- 승인된 단계와 파일 범위 안의 가역적 로컬 편집
- 읽기 전용 조사와 검증
- 합의된 형식에 따른 오탈자·링크·인코딩 보정
- 승인된 구현을 증명하기 위한 비파괴적 테스트

### 9.3 승인 요청의 최소 내용

1. 이번 결정의 목적
2. 승인하면 달라지는 것
3. 달라지지 않는 것과 제외 범위
4. 주요 위험·비용·되돌리는 방법
5. 승인 후 수행할 범위와 다음 정지 지점

승인 기록은 사용자 응답 원문, 승인 대상 문서나 변경안, 유효 범위를 연결해야 한다. 대상이 실질적으로 바뀌면 기존 승인을 재사용하지 않는다.

## 10. 사용자 원문 보존 계약

### 10.1 보존 후보

- 프로젝트 목적과 성공 기준
- 단계 범위와 우선순위
- 금지·허용·보호 경계
- 승인·거절·보류 결정
- 사용자가 직접 정의한 핵심 용어
- 이전 판단을 바꾸는 최신 확인

### 10.2 보존 방식의 원칙

- 원문은 수정하지 않고 날짜와 대화 맥락을 함께 둔다.
- 요약과 해석은 별도 항목으로 작성하고 원문을 가리킨다.
- 서로 충돌하는 원문은 둘 다 남기되 활성 판단과 역사 판단을 구분한다.
- 모든 대화를 무차별 저장하는 기능은 이 요구사항에 포함되지 않는다.
- 구체적인 저장 위치, 파일 형식, 보존 범위는 관련 단계에서 사용자 확인 후 결정한다.

## 14. 현재 결론

현재 요구사항은 Codex 보고서의 구조를 유지하되, 다음 세 제약이 같은 수준의 필수 기준으로 추가됐다.

1. 기술 복잡성보다 먼저 사용자의 인지 복잡성을 관리한다.
2. 승인은 상태값이 아니라 사용자가 이해하고 기억할 수 있는 의미 있는 단계 결정이어야 한다.
3. 사용자 원문은 에이전트 요약보다 높은 권위를 가지며, 과거 지식의 선택적 승계와 별도로 보존한다.

추가로 사용자가 모든 활성 프로젝트 문서·규칙과 연결 관계를 직접 확인하며 각 단계를 진행하겠다는 요구를 확정했으므로, Obsidian 문서 가시화·검토 환경을 Stage 01과 Stage 02 사이의 Stage 01.5로 활성화한다. 이는 정본 저장소나 지식 데이터베이스 도입 승인이 아니다.

현재 구현 단계는 여전히 Stage 00 미착수다. 이 문서가 생겼다는 이유로 Stage 01 이후 기능을 앞당기지 않는다.
