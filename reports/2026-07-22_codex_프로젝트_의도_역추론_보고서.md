# 프로젝트 의도 역추론 보고서

- 작성일: 2026-07-22
- 분석 대상: `backup/origin`, `backup/refactorying_snapshot_1`, `backup/refactorying_snapshot_2`, `backup/refactorying_snapshot_3`
- 문서 성격: 현재 구현을 정당화하지 않고, 버전 간 반복·변경·되돌림과 2026-07-22 사용자 확인 답변을 근거로 실제 의도와 요구사항을 복원하는 시점 분석
- 판정 표기:
  - **사실**: 파일, 코드, 테스트, Git 이력에서 직접 확인한 내용
  - **강한 추론**: 둘 이상의 독립 증거가 같은 방향을 가리키는 해석
  - **가설**: 설명력은 있으나 백업만으로 확정할 수 없는 해석
- 신뢰도: `높음` / `중간` / `낮음`

## 1. 한 문장으로 정리한 최종 의도

**작업의 결과·실패·판단·경험을 출처가 추적되는 데이터로 선별 축적하고, 세션과 에이전트가 바뀌어도 필요한 지식만 낮은 토큰 비용으로 정확하게 읽고 갱신하여 다음 작업의 결과를 계속 개선하는 개인용 지식 운영 기반**을 만들려 한 것으로 확정한다. **[사용자 확인+강한 추론, 신뢰도 높음]**

현재 단계의 최상위 목적은 영상 제작이 아니라 이 지식 기반 자체를 바로잡는 것이다. 영상 제작 워크플로는 기반이 충분히 잡힌 뒤 올라갈 후속 도메인 층이다. 과거 자료 전체도 보존 대상이 아니라 참고 원료이며, 앞으로 더 나은 결과를 만드는 데 꼭 필요한 지식만 선별해 살리거나 필요에 따라 보존한다. 이 우선순위는 2026-07-22 사용자 답변으로 확정됐고, 1차 재구축의 사용자 원문과 3차 지식 시스템 설계가 같은 계층을 뒷받침한다.

### 2.4 제외 범위와 안전 확인

- 경로의 어느 구간이든 `inputs` 또는 `outputs`인 트리는 열거·열람·요약하지 않았다.
- 비밀·인증·토큰·쿠키·키 가능성이 있는 파일은 파일 내용 접근 전 제외했다.
- `backup/` 내부는 수정·이동·삭제하지 않았고 새 파일도 만들지 않았다.
- 보고서는 활성 문서 저장 위치가 없는 현재 루트에서 `backup/` 밖의 `reports/`에 새로 저장했다.
- 실제 사용자 영상, 자막, 산출물, Premiere 환경은 확인하지 않았다. 사용자는 현재 제작 단계가 아니라고 확정했으므로 해당 자료와 도구는 현재 검증 범위가 아니다.

### 2.5 사용자 확인으로 확정된 사항

백업만으로 남아 있던 네 질문에 대해 사용자가 2026-07-22 직접 답했다. 이 답변은 역사 문서의 후속 해석보다 높은 권위를 가진다.

1. 지금은 데이터 기반 지식체계의 기본 구조를 바로잡는 단계이며, 영상 제작 워크플로는 기반 이후의 작업이다.
2. 과거 지식 전체를 소급 보존할 필요는 없다. 앞으로의 규칙과 결과 개선에 꼭 필요한 지식만 선별해 유지하며, 나머지는 제거할 수 있다.
3. 현재는 제작 경로나 제작 도구를 사용해 영상을 만드는 단계가 아니다.
4. 현재 검증 대상은 지식 축적, 기존 지식의 최적화된 컨텍스트 사용, 새 지식의 효율적인 읽기·쓰기, 토큰 소모량이다.
5. 궁극적 효용은 결과·실패·작업 경험을 다음 작업에 재사용해 결과물을 계속 더 완성도 높게 만드는 것이다.

이번 답변과 직접 일치하는 과거 증거도 확인됐다.

- [1차 세션 핸드오프](../backup/refactorying_snapshot_1/SESSION_HANDOFF.md) §1.1의 사용자 원문은 `기본 규칙 → 파일 기반 데이터 처리 → 더 빠른 읽기·쓰기 → 파일 관리 → 도메인 워크플로` 순서를 요구하고, 상세 문서로 세션·에이전트 교체에도 같은 실행을 원한다고 기록한다.
- [1차 레이어 계획](../backup/refactorying_snapshot_1/docs/improvement/LAYER_PLAN.md) §1.4는 아키텍처나 테스트 수가 아니라 실제 작업 속도와 결과 일관성을 판정 기준으로 삼는다.
- [3차 기존 프로젝트 분석](../backup/refactorying_snapshot_3/docs/reports/2026-07-20_기존_프로젝트_분석.md) §8.2·§9는 작업 기록, 지식 추출, 출처, 갱신, 토큰 예산 컨텍스트, 결과 재반영을 누락된 핵심 체계로 정의하면서 §12에서는 “검증된 지식만” 새 정본으로 이관하라고 결론 냈다.
- [3차 지식 시스템 설계](../backup/refactorying_snapshot_3/docs/reports/2026-07-20_프로젝트_기반_및_지식_시스템_설계.md) §2·§8은 작업 결과를 지식 후보·결정·실패 사례로 분리하고, 필요한 자료만 컨텍스트 예산 안에서 다음 세션에 공급한 뒤 결과를 다시 반영하는 폐루프를 사용자 승인 설계로 기록한다.

이 확인으로 기존 보고서 초안의 “영상 제작이 현재 최상위 목적” 해석과 후속 감사 문서의 “모든 과거 경험을 포괄 이관해야 함” 해석을 정정했다. **[사용자 확인, 신뢰도 높음]**

## 3. 버전별 변화

### 3.1 `origin` — 실제 영상 제작 능력을 중심으로 한 원형

**확인된 목적.** 여러 영상을 같은 규칙과 도구로 반복 처리하는 공용 영상 제작 프레임워크다. [원형 설계 원칙](../backup/origin/docs/DESIGN_PRINCIPLES.md)은 “프레임워크가 제품”, “에이전트를 작업에는 신뢰하되 품질에는 신뢰하지 않음”, “에이전트 교체 가능성”, “컨텍스트는 예산”, “창작 권한은 사용자에게”라는 다섯 원칙을 명시한다. **[사실, 신뢰도 높음]**

**실제 기능.** [영상 제작 워크플로](../backup/origin/01_youtube_production_workflow.md)는 촬영 전 경로와 촬영 완료본 경로를 나누고, 촬영 완료본을 `6 근거 분석 → 5 영상 기획 → 7 편집 자료 → 8 최종 검수` 순서로 처리한다. 7단계는 `7A 후보 해석 → 7B microbeat·경계 검증 → 7C 대표 캘리브레이션 → 사용자 방향 확인 → 7D 전체 확장`으로 나뉜다. 소스 자산, 동기 검사, Premiere XML, 편집 품질 감사, 편집 기억, workflow gate와 11개 스킬이 실제 코드·문서로 존재한다. **[사실, 신뢰도 높음]**

**해결하려던 문제.** 영상마다 기획·분석·편집 판단이 달라지고, AI가 원본 근거 없이 이야기나 컷을 확정하며, 세션마다 도구와 규칙을 다시 설명해야 하는 문제를 해결하려 했다. 원본 시간·프레임, `source_id`, 대표 표본, 사용자 방향 승인, 검증 수준을 연결한 이유가 여기에 있다. **[강한 추론, 신뢰도 높음]**

**남은 실제 결함.** 문서가 선언한 엄격함과 일부 실행 경로가 일치하지 않았다.

- `tools/run_python.bat`은 괄호 블록 안의 `%ERRORLEVEL%` 조기 확장 때문에 자식 종료 코드 `7`을 최종 `0`으로 바꿀 수 있었다. 이 현상은 후속 Stage 00 보고서에서 재현됐다.
- `tools/remux_mkv_to_mp4.bat`은 각 FFmpeg 실패를 출력하지만 전체 실패 상태를 누적하지 않고 마지막에 `[ALL DONE]`을 표시한다.
- `tools/guard/agent_guard.py`는 스스로 “fail-open by design”이라고 선언하고 파싱·의존성 예외에서 성공 종료한다.
- 상태가 핸드오프, `WORKFLOW_STATE.json`, 여러 `CURRENT.json`, 편집 기억 DB, 산출물 메타데이터에 분산됐다.
- 산출물 메타데이터 17개 필드, 승인 상태 7종, 7A~7D와 Q0~Q6 등 정밀한 계약이 실제 작업 때 모두 유지되기에는 무거웠다.

**다음 버전을 촉발한 핵심.** 기능 부족보다 “문서상 규칙을 실행이 보장하지 못함”, “현재 상태가 분산됨”, “도구 성공을 품질 성공으로 오해할 수 있음”이 더 큰 문제였다. **[강한 추론, 신뢰도 높음]**

### 3.2 `refactorying_snapshot_1` — 거짓 성공과 상태 불신에 대한 전면 재구축

**변경 방향.** 설치 가능한 `src/` 패키지, 단일 CLI, fail-closed 검사, 순수 도메인 전이, SQLite 단일 상태, append-only event, 낙관적 동시성, 승인 challenge, 산출물 staging/ready/quarantine, 훅·CI·다층 테스트를 도입했다. 실제 [SQLite 스키마](../backup/refactorying_snapshot_1/src/video_workflow/storage/migrations/0001_initial.sql)는 프로젝트·이벤트·소스·세대·산출물·승인 요청·승인·실패 테이블과 append-only trigger를 갖는다. **[사실, 신뢰도 높음]**

**해결하려던 문제.** 원형에서 확인된 거짓 성공, 원본 지문 표류, 잘못된 단계 전이, 승인 위조, 부분 저장, 산출물과 상태 불일치를 구조적으로 차단하려 했다. Stage 00은 자식 종료 코드 `7→0`, fail-open guard, probe 기본값, 보호 경계 문제를 기준선으로 동결했다. Stage 02~04는 부정 매트릭스, 상태 전이, 동시 writer, 승인 신뢰 경계, XML 특성 테스트로 이를 강제했다. **[사실, 신뢰도 높음]**

**교차 확인된 성과.** 저장된 Stage 04 보고서는 159 passed·1 skipped, clean-clone 통합 검사 통과를 기록한다. 실제 코드와 테스트도 승인·동시성·멱등성·원자성·격리 생명주기를 폭넓게 다룬다. 단순 문서 선언만 있었던 것은 아니다. **[사실, 신뢰도 높음]**

**교차 확인된 실패.** [세션 핸드오프](../backup/refactorying_snapshot_1/SESSION_HANDOFF.md)와 [레이어 계획](../backup/refactorying_snapshot_1/docs/improvement/LAYER_PLAN.md)은 다음을 스스로 인정한다.

- 실제 제작 영상 0건
- 측정된 생산성 개선 0건
- Premiere XML은 기존 기능 이식이라 기능 이득 0
- 1인 순차 작업에 SQLite, 승인 provenance, 산출물 승격 프로토콜이 과도함
- “신규 코드 약 2,000줄”이라는 요약과 실제 `src/` 6,456줄의 불일치

또한 Stage 00 초기 인벤토리는 Git 추적 목록이 아니라 파일시스템 전체를 먼저 열거해 보호 데이터의 파일별 메타데이터를 기록했다가 schema v2로 정정했다. 안전 강화를 위한 작업이 한 차례 안전 경계를 침범한 셈이다. **[사실, 신뢰도 높음]**

**버전 내부의 방향 전환.** 같은 스냅샷 후반의 레이어 계획은 9단계 전면 재구축을 폐기하고 다음 원칙으로 되돌아갔다.

- 기존 자산 위에 필요한 것만 얹기
- 한 레이어 2~4시간
- 각 레이어가 무엇을 빠르게 하거나 덜 틀리게 하는지 먼저 설명
- SQLite 대신 영상당 단일 `state.json`
- 도구는 실제 자주 쓰는 것만 얇게 연결
- 8단계 워크플로는 유지하되 완료 조건을 1~3개로 축소

즉 이 버전이 해결하려던 안전 문제는 실제였지만, 해결 범위가 사용자의 비용 상한과 실제 제작 순서를 넘어섰기 때문에 거절됐다. **[강한 추론, 신뢰도 높음]**

### 3.3 `refactorying_snapshot_2` — 파일 상태와 문서 원자화를 통한 단순화

**변경 방향.** 1차 재구축의 domain/service/storage 전체를 활성화하지 않고, 한 영상 작업의 상태를 `outputs/<project_id>/state.json` 하나로 축소했다. [상태 계약](../backup/refactorying_snapshot_2/docs/agent/state/VIDEO_TASK_STATE.md)과 `tools/state_io.py`는 정확한 키, 원본 지문, current/superseded/failed, 승인 범위, next-use, SHA-256, symlink·경로 탈출, 원자 교체를 검사한다. 구현은 528줄, 전체 테스트는 38개다. **[사실, 신뢰도 높음]**

**해결하려던 문제.** 상태 분산, 문서 권위 충돌, 매번 전체 문서를 읽는 비용, 사용하지 않는 인프라를 먼저 만드는 문제를 줄이려 했다. [재구축 원칙](../backup/refactorying_snapshot_2/docs/agent/rebuild/REBUILD_PRINCIPLES.md)은 관찰된 문제만 해결하고, 2~4시간 안의 작은 레이어를 사용하며, 데이터베이스·상태 머신·외부 메모리·병렬 조정·강제 게이트를 실제 실패 전에 만들지 말라고 명시한다. **[사실, 신뢰도 높음]**

**문서 체계 변화.** `AGENTS.md`는 작업 종류별 정확한 read delta와 write-back owner를 표로 만들었다. 문서에는 목적·권위·사용 시점 등의 Properties를 붙였고, Obsidian Base는 파생 인덱스로 사용했다. 알려진 작업은 직접 라우팅하고, 모르는 작업만 최대 3개 후보에서 하나의 원자 문서를 선택했다. **[사실, 신뢰도 높음]**

**새로 발생한 문제.** L5 영상 워크플로를 시작하지 않은 것 자체는 기반 우선 순서와 일치한다. 문제는 기반 작업의 성공 기준이 “파일을 더 빠르고 정확하게 읽고 쓰는가”에서 특정 문서 탐색 제품의 도입으로 이동한 점이다.

- L0~L4와 L3.1~L3.3을 기반 층으로 진행했고 L5 영상 워크플로는 보류했다.
- Graphify+Ollama 의미 탐색은 대표 3작업 중 2작업에서 관련 없는 문서를 8개와 5개 추가하고 문맥량을 각각 21,054, 14,197 추정 토큰 늘렸다.
- 정확한 결과를 낸 자체 typed 라우터는 Graphify를 호출하지 않았는데도 “Graphify-first”로 보고됐다.
- Obsidian CLI와 Base는 검증됐지만 마지막 핸드오프에서 GUI 주 창은 보이지 않았고 네 프로세스의 `MainWindowHandle=0` 문제가 남았다.

이 버전은 1차 재구축보다 단순했고 기반을 먼저 만든다는 순서도 맞았다. 다만 파일 기반 데이터와 읽기·쓰기 효율을 검증하기보다 문서 탐색 제품과 UI의 작동 여부가 중심이 되면서, 실제 토큰 비용과 지식 환류라는 기반의 효용이 흐려졌다. **[사용자 확인+강한 추론, 신뢰도 높음]**

### 3.4 `refactorying_snapshot_3` — 세션 독립 지식·컨텍스트 폐루프

**변경 방향.** 앞선 세 버전을 모두 역사 자료로 이동하고 빈 활성 루트에서 다시 시작했다. 프로젝트 규칙을 8개 boot kernel과 7개 규칙 pack의 조건부 규칙으로 분리하고, 모든 활성 파일을 catalog와 unit으로 투영하며, 구조화 task request → resolver → work context/write contract → writer → event/knowledge 반영 흐름을 만들었다. **[사실, 신뢰도 높음]**

**해결하려던 문제.** 원형과 2차 재구축에는 핸드오프와 문서 라우팅은 있었지만, 작업 경험·실패·결정에서 재사용 가치가 있는 지식을 LLM 기억과 독립적으로 축적·검색·갱신하는 시스템은 없었다. [지식 시스템 설계](../backup/refactorying_snapshot_3/docs/reports/2026-07-20_프로젝트_기반_및_지식_시스템_설계.md)는 작업 기록 → 후보 지식 → 출처·관계·검증 → 제한된 컨텍스트 → 작업 결과 재반영의 폐쇄 루프를 목표로 삼았다. **[사실+사용자 확인, 신뢰도 높음]**

**교차 확인된 성과.** 실제 `tools/context/context_system.py`에는 catalog 동기화, 규칙 선택, task request 검증, resolver, 원자 writer, 부분 실패 복원, knowledge/source 유지보수, 검색 평가, 운영 인수 평가가 구현돼 있다. R-4는 고정 질의 8/8에서 recall·precision·source trace 1.0, 보호 경로 노출 0을 기록했고, R-5는 9/9 운영 시나리오를 통과했다. **[사실, 신뢰도 높음]**

**교차 확인된 한계.** 최신 핸드오프와 감사 보고서, 실제 저장 규모는 구조 검증과 사용자 효용 검증의 차이를 보여 준다.

- 현재 정본은 decision 17건, verified knowledge 4건, case 2건, source 12건, relation 6건, 불변 세션 요약 1건이다. 이 수치는 현재 규모를 보여 줄 뿐, 적거나 많다는 이유만으로 성공·실패를 판정할 수는 없다.
- R-4의 8질의와 R-5의 9시나리오는 작은 코퍼스와 합성 운영 표면만 증명한다.
- decision·case lifecycle writer와 자동 review scheduler/queue는 미구현이다.
- `README.md`와 사용자 가이드는 여전히 R-2A를 다음 단계로 설명해 실제 상태와 충돌한다.
- `context_system.py`는 4,135줄·약 204KB의 단일 모듈이다.
- `context/`에는 request/work/payload 155개, 약 4.17MB가 있고, `catalog/`은 약 2.94MB다. work context는 평균 약 80KB, 최대 약 557KB였다.
- 가장 큰 work context 한 건은 하나의 write target을 위해 1,682개 unit ID와 hash를 포함한 약 454KB write contract를 보유했다. 이후 하드닝에서 context artifact를 whole-file unit 하나로 제한하고 projection 상한을 추가했다.

**목표 충돌.** 같은 시점의 두 보고서는 다음 행동을 다르게 제안했다. 하나는 L0~L8 영상 제작 로드맵 복귀점 감사를, 다른 하나는 지식 코퍼스 커버리지 원장을 우선했다. 2026-07-22 사용자 답변으로 둘 다 현재 우선순위가 아님이 확정됐다. 영상은 기반 이후이고, 과거 전체 coverage도 의무가 아니다. 현재 우선순위는 실제 지식 축적·효율적 읽기/쓰기·최적 컨텍스트·토큰 비용 검증이다. **[사실+사용자 확인, 신뢰도 높음]**

따라서 이 버전은 세션 독립성·출처·검색·write-back 문제를 가장 깊게 해결했지만, 시스템 내부 시나리오 통과를 실제 지속적 지식 사용과 비용 효율의 증거로 연결하지 못했다. 이후 감사는 이 간극을 과거 자료 전체 이관 문제로 잘못 확대했다. **[사용자 확인+강한 추론, 신뢰도 높음]**

### 3.5 전체 변화의 의미

```text
도메인 영상 기능을 먼저 축적
  → 공통 기반의 부재와 거짓 성공을 발견
  → 기반을 전면 소프트웨어 플랫폼으로 과도하게 재구축
  → 파일 기반 데이터 처리와 원자 문서로 다시 단순화
  → 작업 경험을 데이터로 축적하는 지식·컨텍스트 폐루프 구축
  → 과거 전체 보존과 시스템 자체 완결성으로 범위가 다시 확대
  → 현재는 “선별 지식의 실제 축적·효율적 읽기·쓰기”로 목표를 재확정
```

모든 버전은 이전 버전의 실제 결함을 정확히 하나 이상 고쳤다. 그러나 사용자가 원한 계층은 이미 [1차 재구축의 사용자 원문](../backup/refactorying_snapshot_1/SESSION_HANDOFF.md)에 `기본 규칙 → 파일 기반 데이터 처리 → 읽기·쓰기 도구 → 파일 관리 → 도메인 워크플로`로 기록돼 있었다. 문제는 이 계층을 따르지 않고 영상 기능, 안전 플랫폼, 문서 도구, 과거 코퍼스 완전성 중 하나를 그때그때 전체 목표로 승격한 데 있다. **[사용자 확인+강한 추론, 신뢰도 높음]**

| 기능과 자동화는 실제 반복 비용이 입증된 것만 활성화 | 1차 레이어 계획, 2차 재구축 원칙·deferred map, Graphify 취소, 3차 FTS 미도입 판정 | 과도한 도입 뒤 반복적으로 “측정 후 채택” 원칙으로 회귀 | 강한 추론·높음 |
| 상세한 명세와 작은 실행 단위를 동시에 원함 | 1차 사용자 원문 “문서는 디테일하고 길어야”, 반나절 레이어, 2차 atomic contract, 3차 unit | 문서 축약이 아니라 읽기 선택과 구현 범위 축소를 원함 | 강한 추론·높음 |
| 실패와 판단은 다음 작업의 지식으로 재사용되어야 함 | 원형 edit memory·failure rules, 1·2차 failure ledger, 3차 knowledge/case/event loop | 초기에는 편집 기억, 후반에는 프로젝트 전체 지식 수명주기로 확장 | 강한 추론·중간~높음 |
| 과거 자료는 보존 목적이 아니라 선별 지식의 원료임 | 3차 [기존 프로젝트 분석](../backup/refactorying_snapshot_3/docs/reports/2026-07-20_기존_프로젝트_분석.md) §12의 “검증된 지식만 이관”, 2026-07-22 사용자 답변 | 전체 백업 복원은 반복 거부됐고, 후속 감사의 포괄 이관 요구는 이번 답변으로 정정됨 | 사용자 확인+강한 추론·높음 |

## 5. 내가 실제로 원했던 프로젝트의 모습

### 5.1 사용 목적

현재의 주된 사용 목적은 **프로젝트에서 발생한 결과·실패·판단·작업 경험을 데이터로 남기고, 그중 재사용 가치가 있는 것만 지식으로 승격해 다음 작업에 낮은 비용으로 공급하는 것**이다. 시스템은 단순 저장소가 아니라 사용할수록 다음 결과가 더 정확하고 일관되게 개선되는 폐루프여야 한다. **[사용자 확인, 신뢰도 높음]**

영상 제작은 이 기반 위에 나중에 올라갈 중요한 도메인 소비자지만 현재 완료 기준은 아니다. 지금은 영상 기능 수나 제작 실적으로 기반의 성패를 판정하지 않고, 실제 지식의 축적·검색·컨텍스트 조립·갱신과 토큰 비용으로 판정한다. **[사용자 확인, 신뢰도 높음]**

### 5.2 사용자와 에이전트의 역할

| 주체 | 실제로 기대된 역할 |
|---|---|
| 사용자 | 프로젝트의 우선순위, 보존할 가치가 있는 지식의 기준, 중요한 결정과 예외, 외부·파괴적 행동 승인 |
| AI 에이전트 | 작업 수행, 결과·실패·판단 기록, 지식 후보 제안, 관련 지식 선택, 출처·충돌·최신성 검증, 불필요한 컨텍스트 제외 |
| 결정적 도구 | ID·해시·상태·관계·종료 코드·링크·무결성·재실행·토큰/크기·경계 검사 |
| 후속 도메인 앱 | 기반이 완성된 뒤 Premiere 등 해당 앱에서만 증명 가능한 도메인 검증 수행 |

AI는 반복 가능한 기록·검증·검색을 사용자에게 전가하지 않되, 무엇을 장기 지식으로 보존할지와 프로젝트의 방향을 임의로 확정해서도 안 된다. “운영에는 자율적, 가치 판단과 권한에는 종속적”인 역할 분담이 맞다. 영상 도메인이 재개되면 창작 방향·배포 권한도 같은 사용자 권한 층에 추가된다. **[사용자 확인+강한 추론, 신뢰도 높음]**

### 5.3 이상적인 작업 흐름

1. 작업 요청의 목적·범위·허용 행동과 컨텍스트 예산을 구조화한다.
2. 최소 공통 규칙, 현재 상태, 직접 지정 자료를 먼저 선택한다.
3. 관련성이 검증된 지식·결정·실패 사례만 출처와 선택 이유를 붙여 예산 안에서 추가한다.
4. 에이전트가 이 제한된 컨텍스트로 실제 작업을 수행한다.
5. 수행 결과, 실패, 사용자 결정, 검증 결과를 원본 작업 기록에 남긴다.
6. 다음 작업에도 쓸 가치가 있는 내용만 지식 후보로 추출한다.
7. 후보를 사실·추론·결정·실패 사례로 구분하고, 출처·상태·충돌·대체 관계를 검증한다.
8. 가치 없는 과거 내용과 중복 정보는 승격하지 않거나 명시적으로 폐기·대체한다.
9. 정본과 파생 검색 구조를 갱신하고 다음 관련 작업에서 새 지식이 실제로 선택되는지 확인한다.
10. 읽은 토큰, 선택 정확도, 쓰기 비용, 재사용 결과를 측정해 지식체계 자체를 개선한다.

이 흐름의 핵심은 **기록량을 늘리는 것이 아니라, 실제 경험을 검증된 재사용 지식으로 선별 전환하고 다음 결과에 환류하는 것**이다. 영상 제작을 재개할 때에는 기존 `6→5→7→8`과 대표 샘플 검증 같은 도메인 순서를 이 공통 폐루프의 소비자로 결합한다. **[사용자 확인+강한 추론, 신뢰도 높음]**

### 5.4 문서 및 규칙 체계

- 매 세션에 항상 필요한 안전·권한·데이터 경계만 작은 시작 커널에 둔다.
- 알려진 작업은 직접 경로로 정확한 문서를 선택한다.
- 상세 명세는 충분히 길 수 있지만, 작업 시에는 관련 문서 또는 관련 절만 읽는다.
- 규칙, 현재 상태, 계획, 기술 계약, 역사 보고서, 사용자 가이드는 서로 다른 소유자를 가진다.
- 검색 결과, Base, catalog, 컨텍스트 패키지는 정본이 아니라 파생물이다.
- 같은 내용을 새 단계·새 에이전트·새 검토라는 이유로 두 번째 활성 문서에 복사하지 않는다.

### 5.5 입력·출력 및 상태 관리

- 사용자 원본과 보호 데이터는 읽기 전용 또는 명시적 작업 경계 안에 둔다.
- 작업 원본 기록, 세션 요약, 지식, 결정, 실패 사례, 관계, 컨텍스트 패키지를 서로 다른 데이터 책임으로 분리한다.
- 한 작업의 현재 상태는 하나의 정본만 가진다.
- 사람이 읽는 핸드오프나 상태 화면은 정본에서 생성하거나 최소 포인터로 유지한다.
- 모든 재사용 지식은 stable ID와 정확한 source locator로 원본 작업·문서·검증에 역추적돼야 한다.
- 각 지식은 유형, 상태, 신뢰 근거, 충돌·대체 관계, 현재 컨텍스트 포함 가능성을 판정할 수 있어야 한다.
- 컨텍스트 패키지와 검색 인덱스는 정본이 아니라 재생성 가능한 파생물이어야 한다.
- 실패·대체된 버전은 자동 삭제하지 않는다.
- 프로젝트 공통 지식과 특정 작업의 보호 데이터는 별도 경계에 둔다.

과거 자료는 모두 이관하지 않는다. 재사용 가치가 확인된 내용만 선별 승격하고, 보존 가치가 없는 항목은 제거할 수 있다. 다만 구체적인 자동/수동 선별 기준과 보존 예외는 추가 수용 기준이 필요하다. **[사용자 확인, 신뢰도 높음]**

### 5.6 자동화 범위

자동화해야 하는 것은 반복 가능하고 판정 가능한 작업이다.

- 경로·권한·해시·형식·링크·종료 코드·재실행·보호 경계 검사
- 작업 기록 추가, 지식 후보 생성, 출처·상태·관계·충돌 검증
- 현재 상태와 다음 행동 요약
- 작업 목적에 맞는 지식 선택, 컨텍스트 예산 집행, 중복 제거
- 변경된 파일·상태·지식의 검증과 이력 연결
- 컨텍스트 크기·추정 토큰·선택/제외 결과 측정

자동화하지 않거나 사용자 결정을 요구해야 하는 것은 장기 보존 가치, 상충 지식의 최종 채택, 프로젝트 우선순위, 근거 있는 예외다. 모든 과거 기록을 자동으로 지식으로 승격하거나 모든 도구·스킬을 한꺼번에 활성화하는 구조는 원하지 않는다. **[사용자 확인+강한 추론, 신뢰도 높음]**

### 5.7 검증 및 완료 조건

완료는 파일 생성이나 테스트 통과 한 가지로 판정하지 않는다.

1. 기존 문서에서 재사용 가치가 있는 지식을 선별해 최적화된 컨텍스트로 사용할 수 있어야 한다.
2. 새 작업의 결과·실패·판단을 추가하고, 그중 필요한 내용을 지식으로 승격할 수 있어야 한다.
3. 새 지식이 다음 관련 작업에서 정확한 출처와 선택 이유를 가진 채 다시 읽혀야 한다.
4. 관련 없는 문서와 폐기·상충·오래된 지식이 기본 컨텍스트를 오염시키지 않아야 한다.
5. 같은 대표 작업에서 전체 문서 로딩보다 컨텍스트 토큰 사용량이 측정 가능하게 줄어야 한다.
6. 읽기와 쓰기의 총 절차 비용이 지식 재사용으로 절감되는 작업 비용보다 커지지 않아야 한다.
7. 테스트 통과와 실제 지식 축적·검색·재사용 성공을 분리해 보고해야 한다.
8. 이후 도메인 워크플로가 추가되면 해당 앱·콘텐츠·사용자 검증을 별도 수준으로 추가한다.

### 5.8 안전성과 사용자 데이터 경계

- `backup/`은 역사 증거이며 활성 런타임이 아니다.
- 보호 데이터는 정확한 항목과 목적 없이는 열거·색인하지 않는다.
- 보호 경로 필터는 파일을 읽은 뒤가 아니라 접근 전에 적용한다.
- 원본 덮어쓰기, 자동 삭제, 외부 전송, 게시, 커밋·푸시, 유료 작업은 명시적 권한을 요구한다.
- 비밀·개인 절대 경로·불필요한 사용자 내용은 전역 지식으로 승격하지 않는다.
- Obsidian 제외 설정이나 검색 UI는 보안 경계로 간주하지 않는다.

### 5.9 유지보수 방식

- 문제를 발견하면 가장 좁은 유효 계층에 수정한다: 설명, 계약, 도구 검사, 회귀 테스트 중 비용 대비 충분한 지점을 선택한다.
- 새 기능은 실제 반복 실패나 비용이 측정될 때만 활성화한다.
- 동적 Git 상태·파일 수·코드 줄 수는 문서에 고정하지 않고 필요할 때 조회한다.
- 현재 정본과 역사 근거를 분리하고, 충돌·대체·실패 이력은 보존한다.
- 한 번에 큰 재구축보다 실제 지식의 읽기·쓰기·재사용에 독립적으로 도움이 되는 작은 증분을 선호한다.
- 작업 결과가 다음 작업의 상태·결정·실패·지식에 반영되는 폐루프를 유지한다.

## 6. 반복 재구성에도 만족하지 못한 근본 원인

| 구조적 원인 | 유형·신뢰도 | 근거 | 실제 영향 |
|---|---|---|---|
| 사용자가 명시한 층별 순서가 후속 작업에서 유지되지 않음 | 사용자 확인+사실·높음 | 1차 사용자 원문은 공통 규칙→파일 데이터→읽기/쓰기→관리→도메인 워크플로 순서를 명시했지만, 버전별로 영상·상태 플랫폼·문서 도구·과거 코퍼스가 각각 전체 목표처럼 다뤄짐 | 현재 단계의 완료 기준이 계속 바뀌고 기반을 끝내기 전에 다음 층으로 가거나, 반대로 기반이 독립 제품처럼 팽창함 |

| 안전·품질 요구를 절차와 데이터 모델의 총량으로 해결 | 강한 추론·높음 | 원형의 17개 메타데이터·7상태·다중 gate, 1차 9단계 증거 패키지, 3차 request/context/payload 계약 | 오류 가능성은 줄지만 기록·읽기·승인 비용이 늘어 실제 작업이 뒤로 밀림 |

핵심 원인은 파일 수 자체가 아니다. **사용자가 원한 층별 순서와 실제 지식 폐루프의 효용 대신, 각 시점의 구조적 완결성·도구·과거 자료의 포괄성을 완료 기준으로 삼은 것**이 반복 실패의 중심이다. **[사용자 확인+강한 추론, 신뢰도 높음]**

## 8. 요구사항 간 충돌과 긴장 관계

### 8.1 자율성 대 통제 가능성

원하는 균형은 “모든 단계마다 허락”도 “AI가 모든 과거 기록을 자동 지식으로 승격”하는 것도 아니다. 에이전트는 읽기 전용 분석, 후보 생성, 되돌릴 수 있는 로컬 기록, 기본 결함 검증을 자율적으로 수행하고, 사용자는 보존 가치·상충 지식·프로젝트 방향·외부 및 파괴적 행동만 결정한다. TTY challenge 같은 매 작업 승인은 과도하지만, 지식의 장기 효력이 바뀌는 지점은 사용자 통제가 필요하다. **[사용자 확인+강한 추론, 신뢰도 높음]**

### 8.2 철저한 검증 대 빠른 실행

원하는 균형은 모든 것을 같은 강도로 막는 것이 아니다.

- 원본 보호, 지문, 경로, 종료 코드, 상태 손상, 잘못된 성공은 fail-closed
- 컷 길이, 리듬, 밀도는 advisory와 근거 있는 예외
- 전체 통합 검증은 의미 있는 레이어 또는 산출물 경계에서 한 번
- 실제 앱·사용자 품질은 해당 표면에서 별도 검증

즉 엄격함은 위험과 되돌림 비용에 비례해야 한다. **[강한 추론, 신뢰도 높음]**

### 8.3 완전한 문서화 대 낮은 컨텍스트 비용

사용자는 상세한 문서를 원했다. 줄여야 하는 것은 지식 총량이 아니라 매 작업의 기본 읽기량이다. 따라서 긴 정본 문서는 허용하되, 작은 시작 커널, 직접 route, 안정적인 heading/unit, 한 번의 소유권 기록으로 필요한 부분만 읽는 균형이 맞다. 문서 자체를 지나치게 분해해 탐색 파일 수를 늘리는 것도 실패다. **[강한 추론, 신뢰도 높음]**

### 8.4 범용 프레임워크 대 단순한 실제 사용 경험

내부 계약은 여러 작업과 에이전트에서 재사용 가능해야 하지만, 사용자는 현재 단계·다음 행동·필요한 결정·한두 개 진입점만 보면 되어야 한다. 범용성은 내부에 숨고, 실제 사용 표면은 “필요한 지식을 읽고, 작업하고, 새 지식을 남기는” 단순한 흐름이어야 한다. event·projection·catalog 세대를 사용자가 직접 관리하게 만들면 균형을 잃는다. **[사용자 확인+강한 추론, 신뢰도 높음]**

### 8.5 단일 정본 대 이력 보존

현재 판단은 하나여야 하지만 과거를 삭제하면 안 된다. 원하는 균형은 “현재 정본 1개 + 생성 뷰 + Git/append-only 이력 + 명시적 superseded/conflict 상태”다. 여러 current 파일이나 여러 현재 보고서는 금지하지만, 과거 버전 자체는 보존한다. **[강한 추론, 신뢰도 높음]**

### 8.6 지식의 포괄성 대 기록 비용

과거 전체를 보존하는 것이 목표는 아니다. 원하는 균형은 앞으로 발생하는 작업의 결과·실패·결정을 먼저 기록하되, 다음 작업의 품질을 높일 재사용 가치가 있는 내용만 지식으로 승격하는 것이다. 중복·저가치·복구 불필요 자료는 제거할 수 있고, 법적·안전·회귀·사용자 결정처럼 보존 이유가 있는 항목만 예외로 유지한다. 즉 **포괄 수집보다 선별 축적과 의도적 망각**이 우선이다. **[사용자 확인, 신뢰도 높음]**

### 8.7 도구 중립성 대 실제 도구 통합

상위 계약은 Claude·Codex·Gemini나 특정 검색 제품에 종속되지 않아야 한다. 그러나 Premiere, FFmpeg, Obsidian처럼 실제 앱 검증이 필요한 표면은 얇은 adapter로 정확한 공개 실행점을 사용해야 한다. “호환 형식”이나 “래퍼 이름”을 제품 사용으로 부르지 않는 것이 균형점이다. **[강한 추론, 신뢰도 높음]**

### 8.8 아카이브 독립성 대 검증된 자산 재사용

활성 프로젝트가 `backup/`을 런타임으로 참조해서는 안 되며 과거 전체를 이관할 필요도 없다. 다만 다음 결과를 실제로 개선하는 규칙·행동 계약·회귀 사례는 출처와 선택 이유를 붙여 좁게 승격할 수 있다. “복원”과 “폐기” 사이의 기준은 역사적 완전성이 아니라 앞으로의 재사용 가치와 검증 증거다. **[사용자 확인+강한 추론, 신뢰도 높음]**

## 9. 다음 구성에서 반드시 지켜야 할 설계 원칙

아래는 구현 방법이 아니라 다음 구성이 만족했는지 판정할 수 있는 상위 조건이다.

1. **현재 목표 고정**: 현 단계의 최상위 outcome은 데이터 기반 지식의 선별 축적·효율적 읽기·쓰기·재사용이며 영상 제작 기능을 완료 조건으로 끌어오지 않아야 한다.
2. **기반 우선의 층별 진행**: 공통 규칙→파일 기반 데이터→효율적 읽기/쓰기→관리 체계를 먼저 검증하고, 도메인 워크플로는 기반 완료 후 별도 승인으로 추가해야 한다.
3. **실제 폐루프**: 실제 작업의 결과·실패·결정이 기록되고, 재사용 가치가 있는 내용은 검증 지식이 되어 다음 관련 작업의 결과에 사용돼야 한다.
4. **선별 축적과 의도적 망각**: 과거와 미래의 모든 기록을 영구 지식으로 만들지 않으며, 보존·승격·대체·폐기 이유를 판정할 수 있어야 한다.
5. **지식 품질 우선**: 지식체계의 완전성은 파일·레코드 수가 아니라 관련성, 출처, 최신성, 충돌 가시성, 다음 작업 재사용 성공으로 판정해야 한다.
6. **활성 정본 단일성**: 규칙, 현재 작업 상태, 결정, 계획마다 활성 소유자는 정확히 하나여야 하며 모든 파생 문서는 정본 경로를 표시해야 한다.
7. **원본과 출처 보존**: 재사용되는 모든 지식은 stable ID와 원본 작업·문서·검증 위치로 역추적돼야 하며, 파생 검색 결과가 원본 권위를 대체하면 안 된다.
8. **사실·추론·결정 분리**: 높은 검색 점수나 신뢰도가 추론을 사실로 바꾸지 않으며, 상충·대체·오래됨 상태를 숨기지 않아야 한다.
9. **보호 경로 사전 차단**: 보호 데이터와 비밀 가능 경로는 inventory·index·hash·요약 전에 제외돼야 한다.
10. **원본 불변성**: 원본은 덮어쓰기·자동 이동·자동 삭제되지 않으며 파생 결과와 물리적으로 분리돼야 한다.
11. **세션·에이전트 독립성**: 채팅 기억 없이 정본 데이터만으로 현재 상태와 필요한 지식을 재현할 수 있어야 한다.
12. **컨텍스트 예산**: 같은 작업의 전체 문서 로딩 기준선과 비교해 선택된 총 컨텍스트·추정 토큰·관련 없는 항목 수를 측정하고, 승인된 상한을 지켜야 한다.
13. **효율적 쓰기**: 지식 하나를 추가·검토·대체하기 위해 프로젝트 전체를 다시 읽거나 다수의 수동 중복 문서를 갱신하지 않아야 한다.
14. **상세 명세의 조건부 로딩**: 상세 문서는 보존할 수 있지만 알려진 작업은 정확한 문서·절·지식으로 직접 라우팅되고 관련 없는 자료는 기본 컨텍스트에서 제외돼야 한다.
15. **검증 수준 분리**: schema·구조·검색·폐루프·사용자 효용 검증을 서로 대체할 수 없고 보고서가 실제 도달 수준을 표시해야 한다.
16. **실패 보존과 거짓 성공 금지**: 비정상 종료, 부분 결과, 의존성 부재, 예상 결과 불일치는 성공 상태나 검증 지식으로 승격될 수 없다.
17. **실측 후 인프라 활성화**: DB, FTS, 벡터, 그래프, Obsidian, CI/hook, 병렬 조정은 더 단순한 방법의 반복 실패와 같은 자료·작업의 비교 증거가 있을 때만 활성화해야 한다.
18. **자기증식 상한**: 컨텍스트·카탈로그·이벤트 같은 관리 산출물은 자기 자신을 무제한 재색인하거나 실제 지식 작업보다 많은 읽기·쓰기 비용을 요구해서는 안 된다.
19. **활성 경로 독립성**: 정상 실행·문서 라우팅·검증은 `backup/` 없이 완결되고, 과거 자료는 필요할 때만 후보 원료로 읽혀야 한다.
20. **현재 안내 일치**: 사용자 가이드, 핸드오프, 상태 출력은 같은 활성 정본에서 검증 가능해야 하며 상충하면 완료 판정이 실패해야 한다.

## 11. 최종 요구사항 명세

### 11.1 필수

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| M-01 | 현재 최상위 목적은 데이터 기반 지식 운영체계다. | 시작 문서·현재 계획·완료 보고가 지식의 선별 축적, 효율적 읽기·쓰기, 재사용을 최상위 outcome으로 명시하며 영상 제작이나 과거 이관량이 이를 대체하지 않는다. |
| M-02 | 기반과 도메인 워크플로의 순서를 분리한다. | 공통 규칙→파일 기반 데이터→읽기/쓰기→관리의 기반 완료 전 영상 제작 워크플로 구현이 활성 다음 단계가 되지 않는다. |
| M-03 | 의미 있는 실제 작업의 결과·실패·결정이 기록된다. | 대표 작업을 완료하면 작업 범위, 사용 근거, 결과, 실패, 검증, 사용자 결정이 하나의 추적 가능한 기록에 남는다. |
| M-04 | 기록과 장기 지식을 분리한다. | 작업 기록이 자동으로 모두 지식이 되지 않고, 재사용 가치 검토를 통과한 후보만 verified/accepted 상태로 승격된다. |
| M-05 | 과거 지식은 선택적으로만 승계한다. | 과거 전체 coverage를 완료 조건으로 삼지 않으며, 선택된 항목만 보존 이유·출처와 함께 승격되고 나머지는 제거하거나 비활성으로 둘 수 있다. |
| M-06 | 지식은 원출처로 역추적된다. | 재사용되는 각 지식이 stable ID, 원본 작업·파일·검증의 locator와 hash 또는 동등한 무결성 근거를 가진다. |
| M-07 | 사실·추론·결정·실패 사례를 구분한다. | 각 항목의 유형이 명시되고 추론·검색 점수·사용자 승인 중 어느 것도 근거 없이 사실 유형으로 변환되지 않는다. |
| M-08 | 지식 수명주기를 판정할 수 있다. | candidate, verified, disputed, superseded, stale, rejected 또는 동등한 상태와 검토·대체·폐기 이유가 기록된다. |
| M-09 | 충돌하는 지식을 숨기지 않는다. | 같은 주제의 상충 항목이 함께 반환되고 현재 채택 항목, 근거, 대체 관계를 확인할 수 있다. |
| M-10 | 규칙·계획·결정·현재 상태의 활성 정본은 하나다. | 자동 검사에서 동일 subject의 복수 활성 owner가 0건이며 모든 파생 뷰가 정본을 가리킨다. |
| M-11 | 에이전트와 세션이 바뀌어도 재개 가능하다. | 채팅 기억 없이 활성 정본만으로 2분 안에 현재 목표·상태·첫 행동·차단·금지 행동을 정확히 보고한다. |
| M-12 | 작업별 컨텍스트는 필요한 지식만 포함한다. | 대표 질의에서 필수 규칙·상태·지식·실패 사례를 모두 반환하고, 무관·폐기·보호 항목 노출은 0건이며 선택·제외 이유가 설명된다. |
| M-13 | 컨텍스트 토큰 비용을 측정하고 제한한다. | 같은 대표 작업의 전체 문서 로딩 기준선과 비교한 총 문자/토큰, 선택 항목 수, 중복률이 기록되고 사용자 승인 상한을 넘으면 완료가 실패한다. |
| M-14 | 새 지식을 효율적으로 쓸 수 있다. | 지식 한 건의 추가·검토·대체가 전체 프로젝트 재독해나 복수 수동 정본 갱신 없이 하나의 승인된 흐름으로 완료된다. |
| M-15 | 지식이 다음 작업에 실제 환류한다. | 새로 승격한 지식 또는 실패 사례가 다음 관련 작업의 컨텍스트에 선택 이유와 함께 포함되고, 결과 판단에 사용된 흔적이 남는다. |
| M-16 | 실패가 성공이나 검증 지식으로 보고되지 않는다. | 하위 비정상 종료, 의존성 부재, 부분 저장, source 불일치, 검증 실패가 모두 비성공 상태와 원인을 반환한다. |
| M-17 | 사용자 데이터 경계를 사전 차단한다. | 보호 트리 접근 전에 필터가 적용되고, 무지정 inventory/index/hash/요약 시도가 실패한다. |
| M-18 | 원본과 파생 결과를 분리하고 원본을 불변으로 취급한다. | 원본 덮어쓰기·자동 삭제 경로가 없으며 context/index/catalog는 삭제 후 정본에서 재생성 가능하다. |
| M-19 | 활성 프로젝트는 `backup/` 없이 동작한다. | 문서 route, 코드 import, 명령, 테스트, fixture의 활성 의존성이 0건이고 백업 접근 불가 상태에서도 필수 검증이 통과한다. |
| M-20 | 세 가지 대표 실사용 시나리오로 기반을 검증한다. | ① 기존 문서의 필요한 지식을 최적 컨텍스트로 읽기, ② 새 지식을 추가·검토·다시 읽기, ③ 실패 경험을 다음 작업에서 재사용하기가 각각 실제 데이터와 측정된 토큰/절차 비용으로 통과한다. |

### 11.2 중요

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| I-01 | 시작 컨텍스트 비용이 고정돼야 한다. | 필수 시작 문서 수와 크기 상한이 있고, 프로젝트 규모가 늘어도 전체 보고서 자동 로딩이 발생하지 않는다. |
| I-02 | 알려진 작업은 직접 라우팅한다. | 고빈도 작업은 검색 없이 정확한 권위 문서와 쓰기 소유자를 선택한다. |
| I-03 | 모르는 작업의 검색 결과는 권위가 아니라 후보다. | 후보 수가 제한되고, 원문 권위·상태·출처 확인 전 실행 지시로 사용되지 않는다. |
| I-04 | 문서는 상세하되 책임별로 원자적이어야 한다. | 목적·독자·수명주기·read/write trigger가 다른 내용은 분리되고, 같은 속성의 내용은 길이만으로 쪼개지지 않는다. |
| I-05 | 사용자 문서는 한국어, 에이전트 기술 계약은 영어를 기본으로 한다. | 활성 문서 언어 검사가 예외를 명시적으로 처리하며 기존 사용자 파일명은 보존한다. |
| I-06 | 정본과 검색·컨텍스트 파생물을 분리한다. | 파생 인덱스를 삭제해도 정본 지식이 남고 같은 입력과 버전에서 논리적으로 같은 결과를 재구축한다. |
| I-07 | 자주 쓰는 지식 작업만 얇은 진입점으로 제공한다. | 읽기·추가·검토·대체·폐기마다 사용자가 내부 경로와 모듈을 외우지 않아도 되는 단순한 진입점이 있다. |
| I-08 | 지식 선택 결과를 설명할 수 있어야 한다. | 반환 항목마다 직접 지정·규칙·관계·검색 등 선택 경로와 예산 때문에 제외된 후보를 확인할 수 있다. |
| I-09 | 관리 산출물의 자기증식을 제한한다. | catalog/context/event 파일의 수·크기·unit 상한과 자기 재귀 제외 규칙이 있고 초과가 완료 실패로 보고된다. |
| I-10 | 현재 안내 문서가 드리프트하지 않아야 한다. | 핸드오프·README·가이드의 핵심 상태가 동일 owner에서 파생되거나 일치 검사를 통과한다. |
| I-11 | 동적 사실은 실행 시 조회한다. | Git 상태, 파일 수, 테스트 수, 코드 줄 수, 코퍼스 수가 장기 정본으로 복제되지 않거나 freshness 검사를 가진다. |
| I-12 | 동일 실패가 재발하면 가장 좁은 회귀 방지를 남긴다. | 실패 기록에 원인·영향·검증·재개 조건이 있고 관련 검사나 계약이 같은 실패를 재현·차단한다. |

### 11.3 선택

| ID | 선택 기능 | 수용 기준 |
|---|---|---|
| O-01 | SQLite/FTS | 파일 상태 또는 직접·메타데이터 검색이 고정 평가에서 실패하고, SQLite가 같은 작업의 정확도·시간·유지비를 개선할 때만 채택한다. |
| O-02 | 벡터 검색·그래프 DB | 같은 말뭉치·질의에서 직접/lexical 기준보다 정확도 또는 총 컨텍스트 비용이 개선되고 보호 경로·출처 추적 회귀가 없을 때만 채택한다. |
| O-03 | Obsidian | Markdown 정본과 무관하게 선택 가능한 사용자 검토 UI로만 사용하고, CLI·GUI 각각의 검증 상태를 분리한다. |
| O-04 | hook·CI | 수동 통합 검사로 반복 방지하지 못한 동일 회귀가 있을 때 도입하고, 검사기 부재 시 fail-open하지 않는다. |
| O-05 | event sourcing·동시 writer 제어 | 실제 병렬 충돌, 쿼리 요구, 감사 손실이 반복될 때만 도입한다. |
| O-06 | 전체 역사 자료 소급 이관 | 특정 과거 지식의 재사용 가치와 보존 이유가 개별 확인된 범위에서만 수행하며 coverage 자체를 목표로 삼지 않는다. |
| O-07 | 추가 스킬·플러그인 | 실제 사용이 확인된 단계 책임과 대표 실행이 있을 때 하나씩 활성화한다. |
| O-08 | 영상 제작 워크플로 결합 | 지식 기반 필수 수용 기준을 통과하고 사용자가 다음 층 착수를 승인한 뒤, 보존된 도메인 계약을 선별해 별도 요구사항으로 활성화한다. |
| O-09 | 다중 에이전트 QA·레드팀 역할 | 독립 검증이 실제 결함 검출률을 높이고 조정 비용보다 이득이라는 측정이 있을 때만 사용한다. |

### 11.4 사용자 결정 필요

| ID | 결정 항목 | 왜 백업만으로 확정할 수 없는가 | 결정 후 수용 기준 |

## 12. 아직 확정할 수 없는 질문

기존 네 질문은 2026-07-22 사용자 답변으로 모두 해소됐다. 현재 단계에서 남은 것은 목적이 아니라 수용 기준의 수치와 판정 경계다.

1. **컨텍스트 효율의 수치 기준은 무엇인가?** 대표 작업별 허용 최대 토큰, 전체 문서 로딩 대비 목표 절감률, 필수 지식 recall 기준을 정해야 한다.
2. **어떤 지식을 자동으로 살리고 버릴 수 있는가?** 재사용 가치·중복·최신성·위험 기준과 반드시 보존할 안전·결정·회귀 예외를 정해야 한다.
3. **첫 세 대표 검증 사례는 무엇인가?** 기존 문서에서 지식 읽기, 새 지식 쓰기, 실패 경험 재사용 각각의 대상과 기대 결과를 지정해야 한다.

영상 제작 경로·도구·대표 영상은 기반 완료 뒤에 결정할 사항이므로 현재의 미확정 질문에서 제외한다.
