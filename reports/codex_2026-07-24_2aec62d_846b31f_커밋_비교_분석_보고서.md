## 1. 결론

`846b31f`는 `2aec62d`의 직계 후속 계보에 있는 다섯 번째 커밋이며, 이 범위는 Stage 10 공식 종료 직후부터 Stage 11 운영 단순화 완료까지를 포함한다.

전체 판정은 **적합 — 핵심 목표 달성, 실행 회귀 없음, 문서 상태 표현 1건 보완 권고**다.

핵심 성과는 다음과 같다.

1. `quick / standard / controlled` 작업 등급을 도입해 일상 작업에 번호 단계·점수·subagent·별도 보고서·경계 commit을 자동 부과하지 않도록 했다.
2. 문서 검증을 매 파일 저장 뒤가 아니라 논리적 변경 묶음의 완료 checkpoint에서 수행하도록 바꿨다.
3. 단발성 명령·인용·경로 실수를 장기 실패 지식으로 자동 승격하지 않도록 durable threshold를 도입했다.
4. 시작 3문서를 `38,739 bytes·412줄`에서 `10,142 bytes·151줄`로 줄였다.
5. 정본이 아닌 Obsidian 단계별 링크 뷰 11개를 제거하고 master·실제 stage owner·Git 이력으로 역사 탐색 경로를 통합했다.
6. 실행 코드의 유일한 변화는 generated inventory의 의미를 “활성 문서”에서 “전체 추적 문서”로 바로잡는 문구 변경이며, 탐색·필터·저장 동작은 바뀌지 않았다.
7. 현재 종료점에서 전체 120 tests와 maintenance 검증이 통과했다.

다만 [README](../README.md), [Obsidian 시작 화면](../docs/obsidian/START_HERE.md), [문서 진입 지도](../docs/obsidian/DOCUMENT_MAP.md)는 완료된 Stage 11을 아직 “현재 initiative”로 표시한다. ## 5. 의미별 변경 분석

### 5.1 작업 분류와 자율성

[AGENTS](../AGENTS.md)에 세 가지 작업 등급을 추가했다.

| 등급 | 핵심 경계 | 기본 절차 |
|---|---|---|
| `quick` | 안전하고 가역적인 소규모 로컬 작업 | 관련 owner·rule과 직접 검사 |
| `standard` | 여러 파일 또는 동작 변경이지만 로컬·가역 | 관련 테스트와 문서 검사 |
| `controlled` | 정책·구조·보호·삭제·외부·고비용 복구 또는 사용자 지정 단계 | exact plan과 명시 게이트 |

이는 [상시 정책](../PROJECT_RULES.md)의 “가장 낮은 충분 등급” 및 “위험 비례 검증”과 연결된다. 이전에는 번호 stage의 full gate, 점수, 실패 정리, boundary commit이 일상 작업에도 전파될 여지가 컸다. 이후에는 사용자가 요구하거나 실제 위험이 있을 때만 해당 통제를 활성화한다.

안전 경계는 유지됐다.

- 보호 데이터 exact 지정 전 접근 금지
- 비밀정보 접근·노출 금지
- 외부 쓰기·설치·비용·권한 변경 사전 승인
- 미승인 삭제·이동·commit·push 금지
- 무관 사용자 변경 보존

따라서 변화의 성격은 안전 통제 제거가 아니라 **통제 활성화 조건의 명시화**다.

### 5.2 문서 검증 비용

[문서 작업 규칙](../rules/document-work.md)은 “모든 write 뒤 전체 검사”에서 “논리적 batch의 완료 checkpoint에서 scoped 검사”로 바뀌었다.

또한 전체 maintenance는 controlled 구조 작업 또는 exact plan이 요구할 때만 실행하고, 일반 작업은 직접 관련 검사를 사용한다. generated inventory도 Markdown 경로 집합이나 H1이 달라질 때만 재생성한다.

이 변경은 쓰기 횟수에 비례하던 반복 비용을 줄이면서 strict UTF-8, NUL, 링크, 후행 공백, scoped diff 검사를 유지한다.

### 5.3 실패 지식의 승격 기준

[실패 기록 규칙](../rules/failure-records.md)은 다음 중 하나를 충족한 검증된 원인·해결만 장기 owner에 기록하도록 바뀌었다.

- 같은 root cause 재발
- 향후 정확성·안전·보호 데이터·복구에 영향 가능
- 비자명하고 재사용 가능한 해결
- 실제 작업 차단 또는 접근 방식 변경

그 결과 단발성 오타·옵션·인용·경로 가정·예상 negative test는 기본적으로 transient가 된다. 동시에 3회 연속 실패 blocker와 unresolved material blocker 보존 의무는 남아 있어, 실패 은폐보다 기록 품질 개선에 초점이 맞춰졌다.

### 5.4 현재 상태와 역사 분리

[세션 핸드오프](../SESSION_HANDOFF.md)는 Stage 10의 장문 완료 이력을 제거하고 현재 단계·판정·blocker·완료 경계만 남겼다.

Obsidian 구조도 다음 두 층으로 나뉘었다.

1. [START_HERE](../docs/obsidian/START_HERE.md)와 [DOCUMENT_MAP](../docs/obsidian/DOCUMENT_MAP.md): 현재 owner와 범주 진입
2. [generated inventory](../docs/obsidian/GENERATED_DOCUMENT_INVENTORY.md)와 [master](../docs/build/MASTER_BUILD_PLAN.md): 완료 stage와 보고서를 포함한 전체 역사 탐색

삭제된 11개 stage view는 실제 정본 내용을 갖지 않고 stage owner·계약·검증 파일로 연결하는 바로가기였다. 따라서 canonical information loss는 없고 Git 복구도 가능하다. 대신 과거 단계별 목표·검증 절로 한 번에 이동하던 curated shortcut은 사라졌으며, 사용자는 master owner 표를 한 단계 더 거쳐야 한다.

### 5.5 실행 코드

[maintenance.py](../src/file_data/maintenance.py)의 변경은 다음 세 줄의 inventory 설명에 한정된다.

- 제목: “활성 문서 inventory” → “전체 추적 문서 inventory”
- 목적: 역사 제외 표현 제거, 보호·backup 제외로 실제 동작과 일치
- 사용 경계: 완료 stage와 시점 보고서를 포함하므로 active owner 목록이 아니라는 안내 추가

파일 수집, 보호 경로 필터, 결정론적 정렬, 링크 생성, bytes 비교와 쓰기 로직은 변하지 않았다. 테스트 파일도 이 범위에서 수정되지 않았다. 따라서 코드 실행 위험은 낮고, 변경은 기존 실제 동작을 정확히 설명하는 의미 교정으로 보는 것이 타당하다.

## 8. 발견사항과 잔여 위험

### 8.1 보완 권고 — 완료된 Stage 11의 “현재 initiative” 표기

종료 상태는 다음과 같다.

- handoff: `현재 단계: Stage 11 완료`
- handoff: `next_action: null`
- Stage 11 owner: `상태: 완료`

반면 사용자 router 세 곳은 Stage 11을 여전히 현재 initiative로 표시한다.

- [README](../README.md): “현재 initiative 계획·실행·보고”
- [START_HERE](../docs/obsidian/START_HERE.md): “현재 Stage 11 계획·실행·보고”
- [DOCUMENT_MAP](../docs/obsidian/DOCUMENT_MAP.md): 현재 owner 절의 “현재 initiative”

링크 오류나 실행 결함은 아니지만, “완료 역사를 기본 현재 경로에서 분리한다”는 Stage 11 목표와 완전히 일치하지 않는다. 새 active initiative가 없을 때는 “최근 완료 initiative”로 명명하거나 current 표에서 제거하는 것이 좋다.

### 8.2 검증 불가 — 전원 종료

Stage 11 계획에는 모든 commit 뒤 컴퓨터 전원을 종료하는 단계가 있다. Git 커밋과 저장소 문서는 종료 명령의 실제 실행 여부를 증명할 수 없다. 따라서 본 분석은 커밋·worktree 완료는 확인하지만 전원 종료 이행은 **검증되지 않음**으로 남긴다.

### 8.3 선언된 잔여 위험 — Obsidian UI

Stage 11 owner도 Obsidian 앱 직접 확인을 수행하지 않았다고 기록했다. Markdown 링크와 maintenance 검증은 통과했지만, 실제 앱에서의 탐색 체감과 삭제된 shortcut의 사용자 영향은 app-validated가 아니다.

### 8.4 운영상 절충 — 과거 단계 탐색

11개 stage view 제거로 중복 유지 비용은 줄었지만 과거 단계별 curated shortcut도 사라졌다. 현재 구조는 master → exact stage owner의 두 단계 탐색을 의도한 것이다. 실제 사용에서 과거 단계 탐색이 자주 발생한다면 파일을 복원하기보다 master owner 표나 단일 history router의 링크 품질을 개선하는 편이 Stage 11 원칙과 더 잘 맞는다.

## 9. 최종 판정

두 커밋 사이의 변경은 Stage 11의 목적과 대체로 정확히 일치한다.

- 계획이 구현보다 먼저 존재한다.
- 커밋 경계가 단계별 책임과 일치한다.
- 시작 문맥과 장기 실패 기록이 크게 줄었다.
- 안전·보호·외부·파괴 경계는 유지됐다.
- runtime 동작 변경은 사실상 없고 전체 회귀가 통과했다.
- 삭제는 파생 링크 뷰 11개로 제한됐다.
- 문서·링크·inventory·schema·Python 검증이 모두 통과했다.

따라서 종료 커밋 `846b31f`는 기준 커밋 `2aec62d`보다 일상 작업의 인지·절차 비용을 실질적으로 낮춘 개선으로 판정한다.

후속 우선순위는 새 기능이나 추가 구조 작업이 아니라, 현재 활성 initiative가 없을 때 사용자 router가 완료 Stage 11을 “현재”로 표시하지 않도록 상태 표현을 한 번 정리하는 것이다. 전원 종료와 Obsidian UI는 저장소 검증 범위를 벗어나므로 별도의 외부 확인이 없으면 통과로 간주하지 않는다.
