## 1. 이전 판정 철회

이 보고서의 이전 판정인 목적 적합도 `89/100`과 “올바른 방향” 결론을 철회한다.

이전 평가는 다음 두 가지를 잘못 전제했다.

1. `PROJECT_RULES.md`에 공통 규칙을 모으고 절차 문서를 분리하면 기반이 충분하다고 보았다.
2. 기존 규칙·지식·결정·실패 사례의 구조화와 이관은 명령 4에서 나중에 해도 된다고 보았다.

사용자가 정정한 의도는 이보다 넓다.

- 최소 안전·권위 커널을 제외한 규칙은 작업별로 분류돼 필요한 작업에서만 탐색·로드돼야 한다.
- 문서뿐 아니라 코드, 설정, 스키마, 테스트, 보고서 등 모든 활성 파일이 읽기·쓰기 컨텍스트 체계에 포함돼야 한다.
- 이미 존재하는 프로젝트 규칙·지식·결정·실패 경험은 빈 구조만 만든 뒤 미루는 대상이 아니라, 초기 기반을 구성하는 첫 corpus여야 한다.
- 작업 수행 전의 읽기 컨텍스트와 작업 후의 쓰기·갱신 컨텍스트가 같은 구조에서 순환해야 한다.

이 기준에서는 현재 구축 방향이 핵심 목적을 충족하지 못한다.

## 3. 사용자 의도의 정확한 해석

### 3.1 최소 상시 커널

매 세션에 무조건 들어가는 내용은 작아야 한다.

- 사용자 지시 우선순위
- 보호 데이터와 비밀 경계
- 삭제·외부 변경·게시 권한
- 규칙 충돌 해결 원칙
- 작업 컨텍스트 resolver를 반드시 거친다는 시작 규칙

언어, 보고 형식, 검증, 도메인 워크플로, 도구별 안전, 파일별 수정 규칙 등은 모두 상시 커널 후보가 아니다. 각 규칙의 적용 조건에 따라 필요한 작업에서만 선택돼야 한다.

### 3.2 작업별 규칙 검색

규칙도 일반 문서와 같은 검색 대상이 아니라 **조건부 실행 권위를 가진 원자 레코드**여야 한다.

예를 들어 “사용자 보고서는 한국어”는 보고서 작성 작업에서, “JSON Schema Draft 2020-12”는 스키마 설계·검증 작업에서, “Premiere XML 경계 검증”은 편집 XML 작업에서만 활성 컨텍스트로 들어가야 한다.

각 규칙에는 최소한 다음이 필요하다.

| 필드 | 의미 |
|---|---|
| `rule_id` | 변경되지 않는 규칙 ID |
| `statement` | 규칙 본문 |
| `rule_class` | safety, authority, task, format, validation, tool, domain |
| `priority` | 충돌 시 우선순위 |
| `applies_when` | 적용되는 작업 의도·행동·도구·파일 종류 |
| `excludes_when` | 적용하지 않는 조건 |
| `applies_to` | 파일·경로·레코드·작업 범위 |
| `required_context` | 함께 읽어야 할 규칙·지식·파일 |
| `source_refs` | 사용자 지시, 기존 규칙, 결정, 공식 자료 |
| `owner`, `status`, `review_due_at` | 권위·상태·검토 기한 |
| `relations` | overrides, conflicts_with, depends_on, validates |

### 3.3 모든 활성 파일의 컨텍스트 편입

“모든 파일”은 모든 파일 내용을 항상 프롬프트에 넣는다는 뜻이 아니다. 모든 활성 파일이 **선택 가능한 컨텍스트 노드**로 등록돼야 한다는 뜻이다.

문서, 코드, 설정, 테스트, 스키마, 템플릿, 보고서, 인덱스 입력 파일은 최소한 다음 메타데이터로 연결돼야 한다.

| 필드 | 의미 |
|---|---|
| `file_id`, `path`, `kind` | 안정 ID, 상대 경로, 파일 종류 |
| `purpose`, `owner`, `authority` | 존재 이유와 수정 권한 |
| `read_when`, `write_when` | 어떤 작업에서 읽고 수정하는지 |
| `task_tags`, `domain`, `stage` | 작업 라우팅 키 |
| `consumes`, `produces` | 입력·출력 관계 |
| `depends_on`, `related_to` | 파일·규칙·지식 관계 |
| `validators` | 변경 후 적용할 검사 |
| `sensitivity`, `index_scope` | 보호 등급과 색인 범위 |
| `content_sha256`, `updated_at`, `status` | 변경 감지와 현재 상태 |

Markdown 문서는 자체 frontmatter를 가질 수 있다. 코드·설정·바이너리처럼 본문에 메타데이터를 넣기 어려운 파일은 별도 manifest/sidecar가 소유한다. 파생 인덱스는 이 정본 메타데이터에서 다시 만든다.

보호 사용자 데이터는 예외다. `inputs/`, `outputs/`의 개별 파일은 사용자가 정확한 작업을 지정했을 때만 해당 task namespace에 등록하며 전역 카탈로그에 열거하지 않는다.

### 3.4 읽기와 쓰기의 같은 루프

원하는 데이터 흐름은 다음과 같다.

```text
사용자 작업 요청
  → 작업 의도·행동·대상 파일 판정
  → 최소 상시 커널
  → 적용 가능한 규칙 선택
  → 관련 활성 파일 선택
  → 관련 지식·결정·실패 사례 선택
  → 출처와 예산이 포함된 읽기 컨텍스트
  → 작업 수행
  → 쓰기 대상의 owner·write_when·validator 확인
  → 파일 변경과 검증
  → 작업 event·파일 hash·관계 갱신
  → 새 지식 후보·결정·사례 추출
  → 다음 작업의 검색 corpus에 반영
```

현재 설계는 가운데의 지식 검색 패키지만 미래 기능으로 다루고, 앞의 규칙 선택과 모든 파일 선택, 뒤의 쓰기 owner·validator·catalog 갱신을 충분히 연결하지 않았다.

## 4. 현재 구축물과 정정된 의도의 차이

### 4.1 규칙이 여전히 상시 문서에 집중돼 있다

`F` 현재 [PROJECT_RULES.md](../PROJECT_RULES.md)는 6개 절, 29개 번호 규칙으로 구성되며 매 세션 전체를 읽는다.

`F` 규칙별 `applies_when`, `excludes_when`, `applies_to`, 작업 태그, 필요한 파일, 관련 validator가 없다.

`I` 따라서 규칙이 분리된 것이 아니라 “공통 규칙 문서”와 “절차·계약 문서”라는 큰 파일 단위로만 나뉘었다. 작업별 규칙 선택이라는 사용자 요구는 구현되지 않았다.

### 4.2 라우팅 단위가 원자 규칙이 아니라 전체 문서다

`F` [AGENTS.md](../AGENTS.md)는 `PROJECT_RULES.md`, `SESSION_HANDOFF.md`, `DOCUMENT_MAP.md`를 매번 읽고, 이후 전체 `WORKFLOW.md` 또는 전체 기술 계약을 연다.

`F` [DOCUMENT_MAP.md](../docs/agent/DOCUMENT_MAP.md)는 문서 단위의 `Read when`만 가진다.

`I` “영상 XML 생성 중 프레임 경계 규칙 3개와 관련 회귀 사례 2개만 선택”하는 수준의 컨텍스트 조립은 불가능하다.

### 4.3 모든 파일이 카탈로그에 포함되지 않는다

`F` 비보호 활성 Git 추적 파일은 15개다.

- `.gitattributes`, `.gitignore`
- 루트 문서 4개
- 에이전트 문서 5개
- 사용자 문서 1개
- 보고서 3개

`F` 문서 지도의 활성 레지스트리는 11행이다. `DOCUMENT_MAP.md` 자신, 명령 3 보고서, `.gitattributes`, `.gitignore`가 등록돼 있지 않다. 사용자 요청으로 생성된 현재 `reports/` 보고서도 별도다.

`F` 각 파일의 `write_when`, consumes/produces, validator, content hash, 작업 태그를 소유하는 universal manifest가 없다.

`I` 현재 구조는 “관리 대상 문서 목록”이며 “모든 파일의 읽기·쓰기 컨텍스트 카탈로그”가 아니다.

### 4.4 기존 지식이 분석 보고서에만 머물러 있다

`F` 기존 분석 보고서는 다음과 같은 가치 있는 지식을 이미 확인했다.

- 원본 지문과 `source_id` 불변성
- 촬영 완료본의 `6 → 5 → 7 → 8` 순서
- 7A~7D 편집 검증 경계
- 생성·도구·앱·사용자 검증 수준 분리
- 하위 프로세스 종료 코드 보존
- 보호 경로 선필터
- Graphify, fail-open 검사, 기본 미디어값의 실패 사례
- 파일 상태와 직접 라우팅의 장점

`F` 그러나 이 항목들은 원자 규칙·지식·결정·사례로 활성 이관되지 않았다. 긴 한국어 보고서와 `backup/` 출처 링크에만 남아 있다.

`F` README, 설계 보고서, 명령 3 보고서와 handoff는 기존 영상 기능과 지식 이식을 후속 작업으로 명시적으로 제외했다.

`I` 사용자의 정정 의도에서는 이 판단이 가장 큰 방향 오류다. 이미 존재하는 지식을 초기 corpus로 구성하지 않으면 검색·관계·컨텍스트 설계가 실제 데이터 없이 다시 추상화된다.

### 4.5 읽기 경로만 일부 있고 쓰기 경로는 없다

`F` 현재 가능한 것은 시작 문서→handoff→문서 지도→전체 계약 문서의 수동 읽기다.

`F` 다음 기능은 없다.

- 작업 의도에서 적용 규칙을 계산하는 resolver
- 수정 대상 파일의 owner와 `write_when` 선택
- 파일별 validator 자동 선택
- 변경 후 file catalog와 hash 갱신
- 작업 event와 파일 변경 관계 기록
- 결과에서 새 규칙·지식·결정·사례 후보 생성

`I` 컨텍스트가 쌓이는 시스템이 아니라 매 세션 문서를 다시 읽는 시스템에 가깝다.

| `D-11` | 명령 3은 문서 기반만 구현 | 철회 필요: 기반 단계에 기존 규칙·지식의 초기 분류·이관과 universal file catalog가 포함돼야 함 |

## 7. 올바른 기반 구조

아래는 구현 확정안이 아니라 수정 설계가 충족해야 할 책임 구조다.

```text
/
├─ AGENTS.md                     # 최소 bootstrap과 context resolver 진입점
├─ PROJECT_RULES.md              # 최소 safety/authority kernel
├─ SESSION_HANDOFF.md            # 현재 재개점
├─ context-system/
│  ├─ rules/                     # 원자 조건부 규칙
│  ├─ files/                     # 모든 활성 파일의 정본 catalog/manifest
│  ├─ knowledge/                 # 사실·절차·제약
│  ├─ decisions/                 # 승인 결정
│  ├─ cases/                     # 실패·해결 사례
│  ├─ relations/                 # rule/file/knowledge/task typed edges
│  ├─ events/                    # append-only 작업·변경 기록
│  ├─ schemas/                   # 위 레코드 계약
│  └─ migrations/                # backup→active 분류·승격 근거
├─ docs/                         # 사람과 에이전트가 읽는 실제 문서
├─ tools/                        # 실행 코드, file catalog에 등록
├─ tests/                        # 검증 코드, 대상 파일·규칙과 연결
└─ .project-index/               # 삭제 가능한 검색 projection
```

폴더 이름은 후속 설계에서 조정할 수 있다. 중요한 것은 규칙, 파일, 지식, 결정, 사례, 관계, event가 각각 정본을 갖고 서로 ID로 연결되는 것이다.

## 8. 기존 데이터의 초기 구성 방식

`backup/`은 수정하지 않고 이관 출처로만 사용한다.

### 8.1 출처별 역할

| 출처 | 우선 추출 대상 |
|---|---|
| `backup/origin` | 영상 제작 순서, 도메인 규칙, 도구 계약, 품질 기준 |
| `backup/refactorying_snapshot_1` | 실패 원장, 회귀 테스트 계약, 과도한 구축 사례 |
| `backup/refactorying_snapshot_2` | 직접 라우팅, 파일 상태, 문서 원자화, Obsidian·Graphify 판단 |
| 활성 분석·설계 보고서 | 유지·개선·폐기 분류, 승인 결정, 미결 충돌 |

### 8.2 이관 절차

```text
허용된 framework 파일 목록 확정
  → 파일별 source catalog 생성
  → 규칙·지식·결정·사례 후보 추출
  → 중복·충돌·폐기 상태 표시
  → 출처 locator와 hash 부여
  → 작업 유형·파일·validator 관계 연결
  → 검증·사용자 승인
  → active corpus 승격
  → 기존 작업 질의로 context 선택 평가
```

백업 문서를 그대로 활성 검색 결과에 넣어서는 안 된다. 역사 규칙이 현재 지시처럼 실행되지 않도록 `historical_candidate` 상태에서 검토한 뒤 활성 정본으로 승격해야 한다.

## 9. 수정된 구축 순서

### 단계 R-1: 설계 정정

1. 최소 상시 커널과 조건부 규칙의 경계를 확정한다.
2. rule, file, knowledge, decision, case, relation, event 스키마를 설계한다.
3. 작업 의도→규칙→파일→지식 선택 순서를 확정한다.
4. 읽기 컨텍스트와 쓰기 컨텍스트의 공통 manifest를 설계한다.
5. 보호 데이터와 backup migration namespace를 분리한다.

### 단계 R-2: 기존 corpus 선이관

1. 기존 분석 보고서가 이미 선정한 핵심 규칙·지식부터 원자화한다.
2. 모든 활성 비보호 파일을 universal file catalog에 등록한다.
3. 기존 실패 사례와 결정 근거를 사례·결정 레코드로 이관한다.
4. 규칙이 적용되는 작업 유형과 파일·validator를 연결한다.
5. 대표 작업에서 필요한 항목만 선택되는지 수동 resolver로 먼저 검증한다.

### 단계 R-3: 최소 resolver와 writer

1. task request를 구조화한다.
2. 상시 커널, 조건부 규칙, 파일, 지식을 예산 안에서 선택한다.
3. 수정 대상의 owner·write rules·validator를 반환한다.
4. 작업 후 event, file hash, 관계, 지식 후보를 갱신한다.
5. 같은 작업을 새 세션에서 재개한다.

### 단계 R-4: 검색 projection

정본과 resolver가 실제 corpus에서 작동한 뒤 SQLite FTS5를 추가한다. 벡터·그래프 DB·Obsidian은 그 이후 평가 결과에 따라 결정한다.

## 10. 완료 기준

수정된 기반은 최소한 다음을 증명해야 한다.

1. `PROJECT_RULES.md`를 읽지 않아도 된다는 뜻이 아니라, 그 파일이 최소 안전·권위 커널만 담는다.
2. 보고서 작성 작업에는 언어·근거·보고 검증 규칙만 선택되고 영상 XML 규칙은 제외된다.
3. 코드 수정 작업에는 대상 코드, 관련 테스트, 소유 문서, 검증 규칙이 함께 선택된다.
4. 새 파일을 만들면 file catalog, owner, read/write 조건, validator가 함께 등록된다.
5. 파일 변경 후 hash와 관계가 갱신되고 작업 event가 남는다.
6. 기존 영상 제작 규칙 하나가 backup source locator에서 active rule까지 추적된다.
7. 기존 실패 사례 하나가 관련 도구 수정 작업에서 자동 또는 결정적으로 선택된다.
8. 상충하는 과거 규칙은 합쳐지지 않고 상태와 우선순위가 함께 반환된다.
9. 모든 비보호 활성 파일이 catalog에 있고 orphan 파일이 탐지된다.
10. 보호 사용자 파일은 명시적 task scope 없이 목록·인덱스·오류 출력에 나타나지 않는다.
11. 새 세션이 채팅 기억 없이 task request와 정본 파일만으로 같은 컨텍스트를 구성한다.
12. 작업 결과가 다음 검색 corpus에 반영된다.

## 11. 위험과 레드팀 관점

1. **모든 파일=모든 내용 상시 로드 오해:** 목표는 전 파일 등록과 선택 가능성이지 전 파일 동시 로드가 아니다.
2. **규칙 원자화 과잉:** 한 문장마다 파일을 만들면 관리비가 폭증한다. 독립 적용·우선순위·검토 단위가 같은 규칙은 작은 rule pack으로 묶어야 한다.
3. **규칙 검색 권위 상실:** 검색 점수로 규칙 우선순위를 정하면 안 된다. 적용 조건과 authority가 먼저고 검색 점수는 후보 선택에만 쓴다.
4. **백업 지시 오염:** 역사 문서를 그대로 색인하면 폐기된 규칙이 현재 지시로 실행될 수 있다. migration namespace와 승인 승격이 필요하다.
5. **메타데이터 유지비:** file catalog가 실제 쓰기 흐름에서 자동·반자동 갱신되지 않으면 곧 낡는다.
6. **코드와 문서 중복:** 코드 동작을 문서에 복사하지 말고 file node가 코드, 테스트, 계약, 검증 결과를 연결해야 한다.
7. **쓰기 컨텍스트 누락:** 검색 결과가 읽기만 도와주고 변경 owner·validator를 제공하지 않으면 지식 축적 루프가 닫히지 않는다.

## 12. 최종 의견

`F` 현재 기반의 안전 경계, 출처 원칙, Markdown·JSONL 정본, 파생 인덱스, 단계 승인, 과도한 벡터·그래프 도입 보류는 재사용 가치가 있다.

`F` 그러나 규칙은 작업별 원자 레코드가 아니고, 모든 활성 파일은 컨텍스트 노드가 아니며, 기존 지식은 활성 corpus로 이관되지 않았고, 쓰기·갱신 루프도 없다.

`I` 따라서 현재 구조 위에 Stage 4-A 코드만 추가하는 것은 적절하지 않다. 저장 디렉터리와 검색기는 생겨도 사용자가 원하는 작업별 읽기·쓰기 컨텍스트 최적화에는 도달하지 못할 가능성이 높다.

`R` 다음 단계는 기존 Stage 4-A가 아니라 **설계 정정 단계 R-1**이어야 한다. R-1에서 rule catalog, universal file catalog, 기존 corpus migration, read/write resolver를 하나의 데이터 흐름으로 재설계한 뒤 승인을 받아야 한다.
