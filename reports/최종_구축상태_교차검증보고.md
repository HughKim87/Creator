## 4. 두 통합안이 일치한 핵심 사실

### 4.1 규칙은 작업별로 선택되지 않는다

`F` 루트 `PROJECT_RULES.md`는 대화 시작 시 전체 로드 대상이다. 규칙별 `applies_when`, `excludes_when`, task tag가 없으며 현재 라우팅 단위는 원자 규칙이 아니라 문서다.

`I` 공통 안전·권위 규칙을 상시 적용하는 것은 필요하지만, 보고서 작성·영상 처리·스키마 변경 등 특정 작업 규칙까지 같은 방식으로 상시 로드하면 최소 컨텍스트 목표를 달성할 수 없다.

### 4.2 지식과 결정이 독립 레코드가 아니다

`F` D-01~D-11은 849행 설계 보고서에 존재한다. 기존 분석에서 확인한 규칙, 근거, 실패 사례도 보고서와 `backup/` 출처에 남아 있으며 stable ID, 상태, 신뢰도, 적용 범위와 갱신 이력을 가진 활성 corpus로 이관되지 않았다.

### 4.3 관계는 데이터가 아니다

`F` 현재 연결은 주로 Markdown 링크다. relation type, 방향, 상태, 유효기간과 근거를 가진 typed edge가 없다.

### 4.4 모든 파일이 컨텍스트 노드가 아니다

`F` 분석 보고서 네 개를 제외한 비보호 활성 추적 파일은 15개이며 `DOCUMENT_MAP.md`의 활성 문서 레지스트리는 11행이다. `.gitattributes`, `.gitignore`, 문서 지도 자체, 명령 3 구축 보고서는 레지스트리 행으로 등록되지 않는다.

`I` 문서 레지스트리는 권위 라우터로 유효하지만 universal file catalog는 아니다. 코드·설정·테스트·스키마·보고서까지 포함하는 별도 파일 카탈로그가 필요하다.

### 4.5 읽기·쓰기 폐쇄 루프가 없다

`F` 직접 문서 라우팅과 미래 계약은 있으나 task resolver, write target owner, `write_when`, validator 선택, content hash 갱신, event 기록과 지식 후보 반영 기능은 없다.

`D` 검색 기능만 추가하면 읽기 후보는 늘지만 쓰기와 축적이 연결되지 않는다. 사용자가 요구한 시스템은 검색기가 아니라 작업 전후 상태가 같은 정본과 관계망에 반영되는 폐쇄 루프다.

### 4.6 재사용 가능한 기반은 존재한다

`F` 다음 자산은 유지 가치가 있다.

- `backup/` 불변과 보호 데이터 접근 제한
- 출처, stable locator와 사실·추론·결정 구분
- Markdown·JSONL 정본과 재생성 가능한 인덱스 원칙
- 문서별 목적·사용 시점·소유자·언어·위치 메타데이터
- 단계별 승인과 과도한 벡터·그래프 도입 보류
- 기존 분석이 선별한 규칙·결정·실패 사례와 유효한 링크

`D` 기존 기반은 폐기 대상이 아니라 새 구조의 첫 이관 원료다.

## 8. 최종 목표 구조

```text
minimal boot kernel
  → task request
  → conditional rule packs + stable rule IDs
  → universal file catalog
  → knowledge / decision / case / source / typed relations
  → bounded context package
  → work
  → owner / write rules / validators
  → file changes / hashes / events / relation updates
  → new or revised knowledge candidates
  → validation and retrieval projection refresh
```

### 8.1 최소 부트스트랩

상시 로드 내용은 사용자 지시 우선순위, 보호 데이터, 파괴적 작업 권한, 권위 충돌과 resolver 진입 규칙으로 제한한다.

### 8.2 조건부 규칙

규칙은 물리적으로 작은 pack에 묶되 각 규칙에 stable ID, authority, priority, applies/excludes 조건, source, status와 relations를 둔다.

### 8.3 universal file catalog

모든 비보호 활성 파일에 path, kind, purpose, owner, authority, read/write 조건, task tag, 입출력, validator, sensitivity, hash, status와 관계를 기록한다. 파일 전체를 항상 읽는 것이 아니라 모든 파일을 선택 가능한 노드로 등록한다.

### 8.4 기존 corpus 이관

현재 규칙 29개, D-01~D-11, 기존 분석의 지식·결정·실패 사례, 출처와 링크를 첫 corpus로 사용한다. `backup/` 자료는 `historical_candidate`로 격리하고 검토·승격 전 활성 규칙으로 검색하지 않는다.

### 8.5 resolver와 writer

resolver와 writer는 같은 manifest를 사용한다. resolver는 작업에 필요한 규칙·파일·지식만 선택하고, writer는 변경 대상의 소유권·검증 조건을 제공하며 작업 후 hash·event·관계·지식 후보를 갱신한다.

## 9. 최종 실행 순서

### R-1. 설계 정정 — 다음 승인 대상

1. 최소 커널과 조건부 규칙의 경계를 확정한다.
2. rule, file, knowledge, decision, case, source, relation, event 스키마를 확정한다.
3. read/write 조건과 resolver/writer 공통 manifest를 설계한다.
4. 보호 task namespace와 backup migration namespace를 분리한다.
5. 기존 D-01~D-11의 유지·수정·철회를 사용자 승인 대상으로 제시한다.

### R-2. 기존 기반 재구조화

1. 비보호 기반 파일 15개를 universal file catalog에 등록한다.
2. 규칙 29개를 최소 커널과 조건부 pack으로 분류한다.
3. D-01~D-11을 독립 decision record로 만든다.
4. 기존 지식·실패 사례·출처를 후보 레코드로 추출한다.
5. 유효한 Markdown 링크를 typed relation 후보로 변환한다.
6. 대표 작업에서 필요한 컨텍스트만 선택되는지 수동 평가한다.
7. 구조·링크·메타데이터 검증기를 영속화한다.

### R-3. 최소 resolver와 writer

task request를 구조화하고, task→rule→file→knowledge 선택과 변경 후 event→hash→relation→candidate 갱신을 구현한다. 새 세션에서 같은 컨텍스트가 재현되는지 검증한다.

### R-4. 검색 projection

실제 corpus와 resolver/writer가 동작한 뒤 SQLite FTS5를 검토한다. 벡터 검색, 전용 그래프 DB와 Obsidian은 동일 평가셋에서 필요성이 증명될 때만 추가한다.

## 10. 승인 전 완료 기준

1. 보고서 작성 작업에는 보고·언어·근거 규칙만 선택된다.
2. 영상 관련 작업에는 해당 도메인 규칙·도구·테스트·실패 사례만 선택된다.
3. 모든 비보호 활성 파일이 read/write 조건과 validator를 가진다.
4. 새 파일 생성과 변경 시 catalog hash와 event가 함께 갱신된다.
5. D-01~D-11이 독립 결정으로 조회되고 승인 상태가 표시된다.
6. `backup/` source locator에서 승인된 active record까지 추적된다.
7. 충돌·대체 관계가 보존되고 현재 우선순위를 설명할 수 있다.
8. 작업 결과가 다음 작업의 지식·결정·사례 후보로 돌아간다.
9. 보호 데이터가 승인 없는 전역 목록·인덱스·로그에 포함되지 않는다.
10. 새 세션이 LLM 기억 없이 task request와 프로젝트 정본으로 같은 컨텍스트를 재현한다.

- `F` 두 통합안은 핵심 결함과 다음 작업 목록에 실질적으로 합의한다.

- `I` 지금 검색 엔진이나 빈 디렉터리를 먼저 만들면 기존 데이터가 다시 구조 밖에 남는다.

- `I` file catalog와 writer가 같은 manifest를 쓰지 않으면 읽기 최적화와 쓰기 반영이 다시 분리된다.

- `D` 기존 기반은 폐기하지 않고 첫 corpus의 원료로 사용한다.
