# 구축 상태 분석 보고서 (명령 1~3) — 3차

- 작성일: 2026-07-20
- 목적: "규칙을 포함한 모든 지식이 작업별로 탐색·로드되는 파일 기반 컨텍스트 단위로 구성되어야 하고, 이미 존재하는 기반 지식부터 그 구조를 따라야 한다"는 사용자 기준으로 명령 3까지의 구축 상태를 재평가한다.
- 사용 시점: 명령 3 승인 여부와 명령 4의 범위 재정의를 결정할 때 사용한다.
- 작성·수정 주체: 검토 에이전트가 저장소 실측으로 작성한다. 판정은 사용자가 승인한다.
- 언어: 한국어.
- 저장 위치: `reports/claude_구축상태분석보고.md` (사용자 지정 경로).
- 개정 이력: 1차는 "도메인 기능 대비 문서 과잉"을, 2차는 "기반 우선 구축의 완성도"를 기준으로 평가했다. 3차는 사용자가 확정한 기준 — **기반 지식 자체가 처음부터 지식 시스템의 구조로 존재해야 함** — 으로 교체해 재평가했다.
- 표기: `F` 확인된 사실 / `I` 추론 / `D` 판단

## 1. 평가 기준

사용자가 확정한 목표 구조:

1. 규칙조차 상시 로드가 아니라, 작업 유형별로 분류된 별도 문서로 존재하고 해당 작업 시에만 탐색·로드된다.
2. 모든 파일이 읽기·쓰기·컨텍스트 축적의 대상이 되는 단위로 최적화되어 있다.
3. 이미 존재하는 기반 지식(규칙, 결정, 계약)부터 이 구조에 맞춰 구성되어 있어야 한다.

즉 "지식 시스템을 설명하는 문서"가 아니라 **"지식 시스템의 구조를 이미 갖춘 문서 집합"** 이 명령 3의 올바른 산출물이다.

## 2. 총평

**종합 점수: 55 / 100**

`D` 설계 문서는 이 목표 구조를 정확히 알고 있다. 원자적 지식 단위, ID·메타데이터·상태·관계, 직접 라우팅, 작업 범위 컨텍스트 — 전부 계약으로 적혀 있다. 그러나 구축된 실물은 그 계약을 **자기 자신에게 적용하지 않았다.** 규칙은 55행 단일 문서로 매 세션 전체 로드되고, 지식 단위 ID는 0개이며, 승인된 결정 11건은 849행 보고서 안에 묻혀 있고, 관계는 데이터가 아니라 본문 속 링크다. 지식 구조는 명령 4의 미래로 미뤄졌고, 그 결과 현재 기반은 전통적 문서 계층이다 — 나중에 전부 레코드 구조로 재편입해야 하는 이중 구조 부채를 안은 채로.

`D` 요약하면: **설계는 목표를 맞혔고, 구축은 설계를 자기 자신에게 적용하는 것을 빠뜨렸다.**

## 3. 실측 근거

### 3.1 규칙이 작업별로 스코프되지 않는다

`F` `PROJECT_RULES.md` 메타데이터: "Use when: **Read completely at conversation start** and apply throughout all project work." 6개 절 24개 조항 전부가 상시 로드 대상이다.

`F` `AGENTS.md` 시작 절차 1항: 워크스페이스 내 **모든** `PROJECT_RULES.md`를 **완독**하라. 프로젝트 수에 비례해 상시 비용이 선형 증가하는 구조다.

`F` 그런데 24개 조항 중 상시성이 실제로 필요한 것은 일부다. 예: Git·커밋 규칙(6.5)은 Git 작업 시에만, `inputs/`·`outputs/` 경계(2.2)는 사용자 데이터 접근 시에만, 색인 제외(5.5)는 인덱싱 구현 시에만 필요하다.

`I` `CONTEXT_RETRIEVAL.md`는 "Retrieve only the context required for the current task"를 계약으로 선언한다. **규칙 문서 자체가 이 계약을 위반하는 유일한 예외로 설계돼 있다.** 목표 구조에서는 규칙도 지식이고, 지식은 작업 범위로 로드된다.

### 3.2 지식 단위에 ID·메타데이터·상태가 없다

`F` 기반 문서 6종(`PROJECT_RULES`, `WORKFLOW`, 계약 3종, `DOCUMENT_MAP`)에서 지식 단위 수준의 stable ID는 **0건**이다. 메타데이터(목적·시점·주체·언어·위치)는 문서 단위에만 존재한다.

`F` `KNOWLEDGE_SYSTEM.md`가 모든 지식 항목에 강제하는 것: stable ID, 분류, 상태, 신뢰도, 출처, 관계, 검토 기한, 개정 이력. 이 요건을 충족하는 활성 파일은 **0개**다. 계약 문서 자신도 충족하지 않는다.

`I` 결과적으로 "규칙 2.2가 왜 존재하는가"를 추적하려면 사람이 475행 분석 보고서를 다시 읽어야 한다. 규칙→근거 사례→원 실패 기록의 관계가 데이터로 없기 때문이다.

### 3.3 승인된 결정이 구조 밖에 있다

`F` 승인 결정 D-01~D-11은 설계 보고서 §17에 표로 존재한다. `SESSION_HANDOFF.md`는 이 보고서가 "owns decisions D-01 through D-11"이라고 선언한다.

`F` 그런데 `DOCUMENT_MAP.md`의 권위 분류에서 Report는 "point-in-time evidence... **not automatically active policy**"다. **활성 결정의 소유자가, 스스로 정의한 분류상 활성 권위가 아닌 문서다.** 자체 권위 체계 안에서 모순이다.

`D` 목표 구조라면 D-01~D-11은 각각 독립 결정 레코드(ID, 상태 `accepted`, 승인자, 근거 링크, 대체 관계)로 존재하고, 보고서는 그 레코드를 인용하는 증거여야 한다. 설계서 §7.7이 정확히 이 결정 스키마를 정의해 놓고, 정작 첫 11건의 결정이 그 구조 밖에서 태어났다.

### 3.4 관계가 데이터가 아니다

`F` 활성 문서 간 연결은 로컬 Markdown 링크 128개다. 전부 본문 속 인라인 링크이며, 타입(derived_from, constrains, supersedes 등)·상태·방향을 가진 관계 레코드는 0건이다. 설계서 §7.9가 typed relation 스키마를 정의했으나 적용 대상이 없다.

### 3.5 탐색 단위가 문서 전체다

`F` `DOCUMENT_MAP.md` 레지스트리의 행 단위는 문서다. "Read when"도 문서 단위다. 어떤 작업이 어떤 **조항·절·지식 단위**를 필요로 하는지의 매핑은 존재하지 않는다.

`F` `SESSION_HANDOFF.md`(7.9KB)는 목표·용어정의·결정출처·재개점·구현표·검증·실패원장·위험·다음행동을 한 파일에 담는다. 설계서 §7.5가 세션 요약과 인수인계를 분리 카테고리로 정의한 것과 달리, 현재는 여러 지식 종류가 한 문서에 혼합돼 있다.

## 5. 인정할 부분

`D` 이 기준에서도 버릴 것은 거의 없다. 이미 만들어진 자산은 목표 구조의 **원료로 그대로 쓸 수 있다.**

- `F` 문서 단위 메타데이터 계약(목적/시점/주체/언어/위치)은 지식 레코드 메타데이터의 축소판이며 13개 문서 전부에 이미 적용돼 있다.
- `F` `PROJECT_RULES.md`의 절·조항 번호 체계(1.1~6.5)는 원자화의 절단선을 이미 제공한다.
- `F` D-01~D-11, 실패 원장 2건, O-* 외부 근거 20건, 분석 보고서의 F/I/D 판정들은 ID 체계를 이미 갖춘 준-레코드다. 추출만 하면 된다.
- `F` `DOCUMENT_MAP.md`는 인덱스의 원형이고, `AGENTS.md`는 로더의 원형이다.
- `F` 링크 128개가 전수 유효하므로 관계 레코드 추출 시 출발 데이터가 깨끗하다.

`D` 즉 필요한 것은 재작성이 아니라 **재구조화(원자화 + 메타데이터 + 관계 추출)** 다.

## 6. 권고: 명령 4 이전에 기반을 목표 구조로 재편

`D` Stage 4-A를 "빈 디렉터리와 스키마를 만들고 미래 레코드를 기다리는 단계"로 두지 말고, **"기존 기반 지식을 목표 구조로 재편입하는 단계"** 로 재정의할 것을 권고한다.

### 6.1 규칙의 이층화

- 상시 코어: 매 세션 반드시 필요한 것만 남긴 초소형 `PROJECT_RULES.md` (권위 순서, backup 불변, 승인 게이트, 보호 데이터 원칙 수준 — 10행 내외).
- 스코프 규칙 모듈: 나머지 조항을 작업 유형별 파일로 분리. 예: `rules/data-boundary.md`(사용자 데이터 접근 시), `rules/git-actions.md`(Git 작업 시), `rules/language-documents.md`(문서 작성 시), `rules/validation-reporting.md`(검증·보고 시), `rules/retrieval-indexing.md`(검색 구현 시). 각 모듈에 ID, 적용 트리거(use-when), 상태, 근거 관계를 부여.
- `AGENTS.md`는 "전부 완독"에서 "코어 완독 + 작업 유형 매칭 모듈 로드"로 전환.

### 6.2 묻힌 지식의 레코드 추출

- D-01~D-11 → 개별 결정 레코드 (설계서 §7.7 스키마 적용). 보고서는 출처 증거로 강등.
- 실패 원장 2건 → 사례 레코드 (§7.8).
- 분석 보고서의 재사용 지식·기존 문제 → 검증 지식 레코드 후보 (§7.6).
- O-* 외부 근거 20건 → 출처 참조 레코드 (§7.3).
- 이 추출이 곧 스키마의 실데이터 검증이 된다. §3.3의 권위 모순도 함께 해소된다.

### 6.3 인수인계 분해

- `SESSION_HANDOFF.md`를 "현재 재개점"만 남기고, 용어 정의·결정 출처·실패 원장·위험을 각 소유 레코드로 이관해 링크로 대체.

### 6.4 관계·인덱스

- 문서·레코드 간 관계를 typed relation 파일로 추출 (§7.9). `DOCUMENT_MAP.md`를 단위 수준 인덱스로 확장하거나 생성 인덱스의 정본 입력으로 전환.
- 명령 3 검증 로직을 `tools/`에 영속화해 재구조화 전후의 무결성을 자동 검사.

### 6.5 이후

- 위 재편이 끝나면 corpus(규칙 모듈 + 레코드 수십 건)가 실존하므로, 그 위에 Stage 4-B(FTS5 인덱스)와 4-C(컨텍스트 패키지)를 설계서대로 진행한다. 검색이 처음부터 실데이터를 색인한다.

## 7. 결론

`D` 현재 기반은 목표 구조의 **설계도와 원료**로서는 상위 수준이나, 목표 구조 **그 자체**로서는 아직 아니다 (55/100). 지식 시스템의 계약을 만들면서 그 계약을 기존 지식에 적용하는 단계가 빠졌고, 그 결과 규칙은 상시 완독 단일 문서로, 결정은 보고서 속 표로, 관계는 본문 링크로 남아 있다.

`D` 다만 격차의 성격이 좋다: 부족한 것은 새로운 내용이 아니라 **이미 있는 내용의 구조화**다. 문서 메타데이터, 조항 번호, 결정 ID, 유효한 링크망이 전부 준비돼 있어 재편입 비용이 낮다. 명령 4의 첫 단계를 "기존 기반 지식의 구조 편입"으로 재정의하면, 이 프로젝트는 사용자가 의도한 "모든 파일이 컨텍스트 축적 단위인 프로젝트"에 실제로 도달한다.
