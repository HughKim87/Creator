## 1. 최종 결론

사용자가 의도한 **“완성형 영상 제작 시스템을 처음부터 만들지 않고, 공통 기반을 단계적으로 세운 뒤 검증된 결과만 다음 단계로 넘기는 방향”**에는 대체로 맞게 진행됐다.

특히 다음 결과는 의도와 일치한다.

1. 세션 시작 상시 규칙과 특정 작업 규칙을 분리했다.
2. 현재 상태·계획·규칙·실패 지식의 소유자를 분리하고 단일 정본 원칙을 적용했다.
3. 보호 데이터와 `backup/`을 활성 실행에서 분리했다.
4. 파일 기반 데이터, 공통 I/O, 작업 상태, 지식 유형·수명주기, 선택 컨텍스트, 유지보수, 제한된 첫 도메인 순으로 구축했다.
5. FTS·벡터·그래프·CI·자동 삭제·전체 영상 제작 같은 미래 기능을 앞당기지 않았다.
6. 실패를 단계 문서에 흩어 놓지 않고 원인별 장기 지식으로 분리했다.

그러나 **Stage 00~09가 아무 보완 없이 완전히 종료됐다는 판정은 현재 증거와 맞지 않는다.** 이번 독립 재검증에서 Stage 08의 핵심 계약인 “유지보수 오류를 CLI 비성공으로 반환”이 구현되지 않은 사실을 확인했다. `maintenance-verify` 결과가 `status: fail`, `ok: false`여도 프로세스 종료 코드는 0이고 바깥 응답은 `ok: true`다. 자동화나 셸은 실패를 성공으로 오인할 수 있다.

보고서 이름 변경 직후에는 README·Obsidian 지도·Claude 보고서의 링크 6건과 generated inventory가 동기화되지 않아 유지보수 게이트가 실패했다. 검토 중 별도 문서 동기화가 반영돼 현재 링크와 inventory 검증은 다시 통과한다. 역사적 수치가 거짓이었던 것은 아니지만, 이름 변경 시 참조 전체를 같은 경계에서 검증해야 한다는 개선 근거다.

## 6. 잘못 작업됐거나 문제가 있는 부분

### 6.1 P0 — 유지보수 CLI가 실패를 성공 종료로 반환

확인된 사실:

- [유지보수 자동화 계약](../docs/MAINTENANCE_AUTOMATION_CONTRACT.md)은 오류·입력 불일치·Git 조회 실패를 CLI 비성공으로 반환한다고 규정한다.
- [CLI 구현](../src/file_data/cli.py)은 `_run()` 결과의 내부 `ok`를 확인하지 않고 바깥 payload를 항상 `{"ok": true, "result": ...}`로 출력한 뒤 0을 반환한다.
- [유지보수 테스트](../tests/test_maintenance.py)는 service의 실패 결과는 확인하지만 CLI 실패 경로의 종료 코드를 검증하지 않는다.
- 이번 실제 실행에서 verify가 링크 오류 6건과 `status: fail`을 반환했는데 프로세스 종료 코드는 0이었다.

영향:

- 사람이 JSON 내부를 끝까지 읽지 않거나 셸·자동화가 종료 코드만 보면 검증 실패를 성공으로 판단한다.
- Codex 보고서의 “수동 fail-closed 명령”과 전체 완료 판정은 이 범위에서 사실보다 강하다.
- Claude 보고서의 “불일치 0건”은 실패 경로를 검증하지 않아 이 결함을 놓쳤다.

### 6.2 해결됨 — 보고서 이름 변경 뒤 문서 연결 불일치

Codex 보고서는 이전 파일과 Git blob hash가 같아 내용 손실 없는 이름 변경이었다. 이름 변경 직후 README·Obsidian 지도·generated inventory·Claude 보고서·handoff의 참조가 한 경계에서 동기화되지 않아 최초 verify가 실패했다.

검토 중 실제 파일명으로 참조와 inventory가 동기화됐고, 첫 재실행에서 문서 84개·링크 651개·오류 0을 확인했다. 본 보고서와 지도 반영 뒤 최종 재실행도 문서 85개·링크 661개·오류 0·inventory 일치로 통과했다. 이 문제는 현재 해결됐지만 파일 이동·이름 변경 직후 전체 링크와 generated inventory를 같은 게이트에서 검사해야 한다.

### 6.3 P1 — 단계 상태 문구가 경계 커밋 전 상태에 고착

Stage 04~09를 포함한 여러 단계 문서의 헤더가 `경계 커밋 대기`로 남아 있다. 현재 상태는 핸드오프가 소유하므로 복수 정본 결함은 아니지만, 단계 문서를 단독으로 읽으면 이미 존재하는 커밋과 모순되어 보인다.

### 6.4 P1 — 요구사항 기준서의 동적 상태 문구가 오래됨

통합 요구사항 기준서는 현재 요구사항의 정본이지만 마지막에 “현재 구현 단계는 Stage 00 미착수”라고 적혀 있다. 요구사항 문서가 동적 현재 상태를 소유하지 않는다는 원칙과 맞지 않는다. “작성 당시”로 한정하거나 현재 상태는 핸드오프만 보도록 바꾸는 편이 안전하다.

### 6.5 P1 — 단계 자체 점수의 신뢰도 보완 필요

11개 단계 점수는 96~98점에 집중됐고 평균은 97.36점이다. 그러나 이번에 발견한 CLI 실패 종료 결함은 Stage 08 완료 게이트와 Claude 독립 검증 모두 통과했다. 이는 점수 산식 자체의 산술 오류가 아니라 **실패 경로 체크리스트가 충분히 적대적이지 않았다는 증거**다.

내부 단계 점수는 다음처럼 이름을 한정하는 것이 정확하다.

> 단계 계획 준수·내부 구현 품질 자체 점수

사용자 가치, 실제 운영 효과, 독립 감사 결과를 같은 점수로 읽으면 안 된다.

## 7. 잘못된 것으로 판정하지 않은 부분

다음은 문제처럼 보일 수 있지만 최신 사용자 승인이나 단계 경계와 일치하므로 잘못된 작업으로 판정하지 않았다.

- Stage 01~03 누적 커밋: 사용자가 허용했고 마스터 계획에 명문화됐다.
- Stage 09까지 권장안 자동 선택: 사용자의 최신 명시 지시가 기존 개별 질문 절차를 대체했다.
- 첫 도메인으로 YouTube 선택: 프로젝트 맥락과 활성 요구사항에 맞고 전체 제작이 아닌 한 작업으로 제한됐다.
- 실제 영상 원본·외부 앱 미검증: Stage 09의 명시적 제외 범위다.
- candidate 자동 승격 금지: 사용자 승인 경계를 지킨 결과다.
- FTS·벡터·그래프·CI 미도입: 기능 부족이 아니라 선행 복잡성 방지 결정이다.

## 8. 앞으로 진행할 작업

### 8.1 우선순위 P0 — Stage 08 보정 작업

새 기능이나 Stage 10을 시작하기 전에 다음을 하나의 보정 범위로 처리한다.

1. `maintenance-scan`, `verify`, `inventory`, `evaluate`의 논리적 실패가 비영(非零) 종료 코드로 전달되게 한다.
2. 바깥 `ok`와 내부 `result.ok` 또는 `matches`의 의미를 일치시킨다.
3. 성공 경로는 0, scan attention, verify fail, inventory mismatch, evaluate fail은 각각 비성공임을 회귀 테스트한다.
4. 서비스 결과, JSON payload, 프로세스 종료 코드 세 층을 함께 검증한다.
5. 95개 기존 회귀와 새 실패 경로 회귀를 모두 통과시킨다.
6. 해결 뒤 같은 원인의 실패 지식을 기존 `failures/` 정본에 병합하고 별도 보정 커밋으로 경계를 닫는다.

### 8.2 우선순위 P1 — 상태 문구 정리

1. Stage 00·04~09의 상태 헤더를 역사적 종료 상태와 일치시킨다.
2. 요구사항 기준서에서 동적 현재 단계 소유를 제거하거나 작성 당시 상태로 한정한다.
3. strict UTF-8, NUL 0, 후행 공백 0, 로컬 링크 0, inventory 일치를 다시 검증한다.

### 8.3 우선순위 P1 — 첫 실제 운영 파일럿

P0 보정 뒤 사용자가 정확히 지정한 보호 데이터 한 건과 목적 한 개만 승인받아 실제 작업을 수행한다.

측정할 항목:

- 작업 완료 여부와 결과 정확도
- 기존 방식 대비 시간
- 읽은 문서·record·context 크기
- 실패 지식 재사용 여부
- 사용자가 현재 구조와 결정을 이해하는 데 든 부담
- `review_required`에서 사용자가 실제로 수정하거나 승인한 내용

이 단계에서는 자동 게시·외부 앱·추가 도메인을 함께 넣지 않는다.

### 8.4 우선순위 P2 — 3~5회 운영 뒤 단순화 판단

실제 파일럿 3~5회의 측정이 쌓인 뒤에만 다음을 결정한다.

- 문서·record·event가 실제 재사용 가치보다 빠르게 늘어나는지
- 시작 문서 17,960자와 handoff 151줄이 재개에 과한지
- 선형 scan이 5초 경고를 반복하는지
- candidate 승격·폐기 검토가 병목인지
- 그때도 필요하면 인덱스·DB·CI를 별도 승인할지

현재 증거만으로 FTS·벡터·그래프·자동화 범위를 늘리는 것은 권장하지 않는다.
