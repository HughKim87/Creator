## 1. 결론

**현재 프로젝트에는 oh-my-codex(이하 OMX)를 즉시 전체 도입하지 않는 것이 타당하다.** 판단 상태는 영구 폐기가 아니라 **조건부 보류**다.

핵심 이유는 세 가지다.

1. 현재 프로젝트는 Stage 00 구현 전이며, 최소 시작 경로와 단일 상태 소유자를 먼저 확립해야 한다. OMX는 이 시점에 17.7KB 규모의 `AGENTS.md`, 다수의 스킬·에이전트, 훅, `.omx/` 상태·로그·계획 저장소를 한꺼번에 추가한다.
2. 현재 환경은 Windows 네이티브 Codex 데스크톱 앱이다. OMX 공식 문서는 macOS·Linux의 Codex CLI를 기본 경로로 권장하고, Windows 네이티브와 Codex App은 비기본·저지원 경로이며 불안정할 수 있다고 명시한다.
3. 최신 Codex 자체가 이미 `AGENTS.md`, 스킬, 플러그인, 훅, 병렬 서브에이전트를 지원한다. OMX의 핵심 차별점은 CLI/tmux 기반의 장기 실행 오케스트레이션인데, 현재 앱 환경에서는 그 런타임을 직접 사용할 수 없다.

따라서 현재 권고는 다음과 같다.

> **지금은 설치하지 않는다. Stage 00·01 이후 실제 운영 병목이 확인되면, 활성 프로젝트와 분리된 WSL2/Linux 환경에서 정확히 한 가지 사용 사례만 파일럿한다.**

## 4. OMX가 제공하는 것

OMX는 Codex를 대체하는 모델이나 독립 에이전트가 아니라 **Codex CLI 주변의 워크플로·오케스트레이션 계층**이다.

주요 기능은 다음과 같다.

| 영역 | 제공 기능 | 현재 프로젝트에 기대할 수 있는 가치 |
|---|---|---|
| 작업 라우팅 | 역할 프롬프트, 명시적 스킬, 키워드 기반 워크플로 선택 | 반복 작업의 진입점 표준화 |
| 계획·장기 실행 | `deep-interview`, `ralplan`, `ultragoal`, `ralph`, `autopilot` 계열 | 긴 작업의 계획·재개·완료 추적 |
| 다중 에이전트 | 네이티브 서브에이전트와 tmux 팀 런타임 | 독립 작업의 병렬화 |
| 상태·감사 | `.omx/` 아래 계획, 로그, 메모리, 모드 상태 | 세션 간 상태와 실행 흔적 보존 |
| 훅 | `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Stop` 등 | 라우팅·검증·중단 처리 자동화 |
| 작업 격리 | Git worktree 기반 실행 권장 | 병렬 변경 충돌과 원본 체크아웃 위험 완화 |
| 진단 | `omx doctor`, 실제 모델 호출 스모크 테스트 | 설치 상태와 실행 가능성 분리 검증 |

이 기능들은 완성된 코드 프로젝트에서 반복되는 복합 작업을 운영할 때 유용할 수 있다. 그러나 현재 프로젝트의 당면 목표는 오케스트레이션 강화가 아니라 **최소 프로젝트 기반을 먼저 확정하는 것**이다.

## 5. 설치와 변경 표면

### 5.1 패키지 설치 자체

공식 기본 설치는 다음과 같다.

```text
npm install -g oh-my-codex
```

현재 `postinstall` 소스는 글로벌 설치 시 버전 스탬프와 안내 메시지만 기록하고, `omx setup`을 자동 실행하지 않는다. 즉, 패키지 설치와 프로젝트 설정 변경은 분리돼 있다는 점은 긍정적이다.

### 5.2 `omx setup`이 실제로 바꾸는 것

설정 단계는 단순한 CLI 등록이 아니다. 공식 [OMX Setup 문서](https://github.com/Yeachan-Heo/oh-my-codex/blob/main/skills/omx-setup/SKILL.md)에 따르면 범위와 모드에 따라 다음 표면을 생성·병합·정리한다.

- `./.omx/setup-scope.json`
- `~/.codex/config.toml` 또는 `./.codex/config.toml`
- `~/.codex/hooks.json` 또는 `./.codex/hooks.json`
- 프롬프트, 스킬, 네이티브 에이전트 파일
- 프로젝트 루트 `AGENTS.md`
- `./.omx/hud-config.json`
- 알림 훅과 런타임 상태
- 프로젝트 `.gitignore`의 `.omx/`, `.codex/` 관련 항목

플러그인 모드도 완전히 수동적인 설치가 아니다. 번들 스킬은 플러그인으로 전달하지만 네이티브 에이전트 TOML, 런타임 기능 플래그, 네이티브 훅은 계속 설정한다.

`--dry-run`, `--verbose`, `--merge-agents`가 제공되고 설정 백업과 `omx uninstall` 경로도 있다는 점은 복구 가능성을 높인다. 다만 `config.toml`, `hooks.json`, `AGENTS.md`가 공유 소유 표면이 되므로 제거 후 원상복구를 자동으로 가정해서는 안 된다.

## 6. 현재 로컬 환경 적합성

읽기 전용 점검 결과는 다음과 같다.

| 항목 | 현재 상태 | 판정 |
|---|---|---|
| 운영 환경 | Windows 네이티브 Codex 데스크톱 앱 | OMX 공식 기본 경로 아님 |
| Node.js | `v20.11.1` | 최소 요구사항 충족 |
| npm | `10.2.4` | 설치 도구 사용 가능 |
| OMX | 미설치 | 기존 충돌 없음 |
| tmux | 없음 | 권장 팀 런타임 사용 불가 |
| psmux | 없음 | Windows 실험적 팀 경로도 사용 불가 |
| WSL2 | 실행 가능한 Linux 배포판 확인 실패 | 권장 Linux 파일럿 환경 미준비 |
| Codex 실행 파일 | 데스크톱 앱 번들 경로 감지 | CLI 인증·실행 스모크 테스트는 미검증 |

OMX 공식 README는 macOS·Linux Codex CLI를 주 지원 경로로 두고, Windows 네이티브와 Codex App은 깨지거나 일관되지 않을 수 있다고 밝힌다. 또한 OMX 템플릿 자체도 `autopilot`, `ralph`, `ultrawork`, `team` 같은 런타임 워크플로가 Codex App·비-tmux 환경에서 직접 사용할 수 없다고 설명한다.

이 환경에 바로 설치하면 핵심 가치는 받지 못한 채 설정·훅·지침 복잡성만 먼저 추가될 가능성이 높다.

## 7. 현재 Codex와의 중복

OpenAI 공식 [Codex 사용자화 문서](https://learn.chatgpt.com/docs/customization/overview)는 현재 Codex가 다음을 기본 확장 표면으로 제공한다고 설명한다.

- 저장소 상시 지침용 `AGENTS.md`
- 재사용 워크플로용 스킬
- 외부 도구 연결용 MCP
- 전문 작업을 위임하는 서브에이전트
- 설치 가능한 플러그인과 라이프사이클 훅

공식 [서브에이전트 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents)에 따르면 현재 Codex는 서브에이전트를 기본 활성화하며, 데스크톱 앱에서도 병렬 에이전트 활동을 표시한다. 따라서 “단일 Codex를 여러 전문 에이전트로 확장한다”는 이유만으로 OMX를 도입할 필요는 없다.

OMX가 추가로 제공하는 실질적 차이는 다음이다.

- 특정 계획·실행 방법론을 강하게 표준화한 워크플로
- `.omx/`에 저장되는 별도 장기 실행 상태
- tmux/HUD 기반 팀 운영과 복구
- 프롬프트 제출·도구 실행·중단 시점에 개입하는 다수의 훅

즉, 현재 판단 질문은 “다중 에이전트가 필요한가?”가 아니라 “OMX 고유의 상태 머신과 CLI 운영 계층이 현재 프로젝트의 복잡성을 줄이는가?”다. 현재 단계에서는 그렇지 않다.

## 8. 프로젝트 요구사항과의 적합성

### 8.1 긍정적 정합성

OMX에서 참고할 가치가 있는 부분은 있다.

- 작업 계획·로그·상태를 구분하려는 구조
- `doctor`와 실제 모델 호출 스모크 테스트를 분리한 검증 철학
- 이름 있는 worktree를 통한 변경 격리
- 설정 변경 전 `--dry-run` 지원
- 사용자 파일과 관리 파일의 소유권을 나누고, 설치 제거 시 사용자 훅을 보존하려는 처리
- 실패·중단·재개 상태를 명시적으로 다루려는 시도

이 요소들은 향후 Stage 04, 07, 08에서 비교 후보가 될 수 있다.

### 8.2 현재 단계의 직접 충돌

| 현재 기준 | OMX 기본 동작 | 충돌 판정 |
|---|---|---|
| UR-06: 활성 정본과 재개 경로를 하나로 유지 | `SESSION_HANDOFF.md` 외에 `.omx/` 계획·로그·메모리·모드 상태 추가 | 높음 |
| UR-12: 사용자 인지를 첫 복잡성 예산으로 취급 | 기본 `AGENTS.md`가 17.7KB이고 다수 역할·모드·규칙을 시작 시 주입 | 매우 높음 |
| UR-13: 단계 전환·범위 확대는 의미 있는 사용자 승인 필요 | 템플릿 첫 문장이 자동 진행과 병렬 위임을 강하게 권고 | 높음 |
| UR-10: 보호 경계와 최소 접근 | 훅이 프롬프트·도구·중단 단계에 개입하며 세션 작업 디렉터리에서 실행 | 검증 전 높음 |
| O-07: 추가 스킬·플러그인은 승인 단계에서 실제 사용 근거가 있을 때만 | 전체 카탈로그와 런타임을 선도입 | 직접 충돌 |
| O-09: 다중 에이전트 QA는 검출 이득이 조정 비용보다 클 때만 | 병렬 오케스트레이션을 핵심 운영 방식으로 제공 | 근거 미충족 |
| Stage 00: 최소 시작 경로만 구현 | AGENTS, 스킬, 훅, 상태, HUD, 알림, 에이전트 설정을 함께 추가 | 직접 충돌 |

특히 공식 OMX [AGENTS.md 템플릿](https://github.com/Yeachan-Heo/oh-my-codex/blob/main/templates/AGENTS.md)은 17.7KB이며, 자동 진행과 서브에이전트 사용을 강하게 지시한다. 일부 안전 문구가 뒤따르지만, 현재 프로젝트가 먼저 확정하려는 최소 권한·승인·인지 복잡성 계약보다 훨씬 큰 운영 계약이다.

## 9. 보안·운영 위험

### 9.1 훅의 실행 권한

OpenAI 공식 [Codex 훅 문서](https://learn.chatgpt.com/docs/hooks)는 훅이 에이전트 루프 중 결정적 스크립트를 실행하며, 여러 출처의 일치 훅이 모두 실행된다고 설명한다. 비관리 훅은 정의 해시를 사용자가 검토·신뢰해야 한다.

OMX는 다음 이벤트에 네이티브 또는 대체 훅을 연결한다.

- 세션 시작
- 사용자 프롬프트 제출
- 도구 실행 전·후
- 중단 및 자동 계속
- 세션 종료·유휴 상태의 대체 런타임 처리

공식 [OMX 네이티브 훅 문서](https://github.com/Yeachan-Heo/oh-my-codex/blob/main/docs/codex-native-hooks.md)는 설정이 OMX 소유 래퍼에 대한 `trusted_hash`도 기록한다고 설명한다. 이는 반복 검토 부담을 줄이지만, 설치자가 훅 코드를 사전에 신뢰한다는 의미다. 프로젝트의 보호 경계를 훅보다 상위에서 강제할 별도 검증이 필요하다.

### 9.2 승인·샌드박스 우회

OMX 문서는 강한 기본 세션 예시로 `--madmax`를 자주 제시한다. 이 플래그는 Codex의 `--dangerously-bypass-approvals-and-sandbox`에 해당한다. 공식 문서도 신뢰된 저장소에서만 사용하라고 경고하지만, 현재 프로젝트의 승인 계약과는 양립하지 않는다.

**현재 프로젝트에서는 파일럿을 하더라도 `--madmax`, `--yolo`, 훅 신뢰 우회 옵션을 금지해야 한다.**

### 9.3 공급망과 업데이트

긍정 요인:

- MIT 라이선스
- 직접 런타임 의존성은 `@iarna/toml`, `@modelcontextprotocol/sdk`, `zod` 세 개로 비교적 작음
- CI, Dependabot, 릴리스 검증 기록이 활발함
- `postinstall`이 자동 setup을 실행하지 않음

주의 요인:

- 버전이 아직 `0.x`이고 릴리스 변화 속도가 빠름
- npm 글로벌 설치와 실행 시 업데이트 확인 기능을 사용함
- 최신 설정 갱신이 관리 블록과 훅을 다시 쓸 수 있음
- Rust 네이티브 구성, 훅, MCP, tmux, worktree까지 실제 운영 표면은 직접 의존성 수보다 훨씬 큼
- GitHub 보안 페이지 기준 `SECURITY.md`가 없고 공개 보안 권고도 없음. 공개 권고가 없다는 사실은 취약점이 없다는 증거가 아님

파일럿에서는 정확한 버전을 고정하고 `OMX_AUTO_UPDATE=0`으로 자동 업데이트 확인을 끈 뒤, 버전 변경을 별도 검토 대상으로 두는 것이 안전하다.

### 9.4 운영 잠금과 상태 분산

OMX가 만드는 `.omx/` 상태가 유용해지면 이후 제거 비용이 커질 수 있다. 특히 다음이 발생하면 사실상 운영 잠금이 생긴다.

- 계획 정본이 기존 문서와 `.omx/plans/`로 분산됨
- 완료·중단 판정이 훅과 상태 파일에 의존함
- 에이전트가 OMX 키워드와 역할 명칭을 전제로 행동함
- 업데이트가 관리 섹션을 새 버전 계약으로 갱신함

현재 프로젝트는 이와 반대로 정본 수를 줄이고 백업·채팅·도구 런타임 의존성을 제거하는 단계다.

## 12. 권고 도입 경로

### 단계 A — 현재

- OMX를 설치하지 않는다.
- Stage 00·01에서 시작 문서, 승인 경계, 단일 상태 소유자를 먼저 확정한다.
- Codex 기본 서브에이전트·스킬·플러그인으로 해결되지 않는 실제 병목을 기록한다.

### 단계 B — 재검토 조건

다음 조건을 모두 만족할 때만 파일럿을 검토한다.

1. Stage 00·01이 완료돼 OMX가 덮거나 병합할 정본 경계가 명확하다.
2. 장기 실행 재개, 팀 병렬 작업, 반복 검증 중 적어도 한 가지 병목이 실제 작업에서 반복된다.
3. OMX가 Codex 기본 기능보다 나은 이유를 하나의 대표 시나리오로 설명할 수 있다.
4. WSL2 또는 Linux 환경과 Linux 파일시스템 안의 별도 테스트 저장소가 준비된다.
5. 설치·업데이트·제거 담당 범위와 복구 기준을 승인한다.

### 단계 C — 격리 파일럿

파일럿은 활성 프로젝트가 아닌 별도 깨끗한 체크아웃에서 진행한다.

1. 검토한 정확한 버전을 고정한다.
2. 자동 업데이트 확인을 끈다.
3. 별도 `CODEX_HOME`을 사용한다.
4. 먼저 `omx setup --dry-run --verbose` 결과를 파일 목록과 변경 유형으로 검토한다.
5. `--madmax`, `--yolo`, 훅 신뢰 우회를 사용하지 않는다.
6. `AGENTS.md`는 자동 덮어쓰기하지 않고, 프로젝트 최소 규칙과 충돌 여부를 문장 단위로 검토한다.
7. 훅은 해시와 실제 실행 명령을 검토한 항목만 신뢰한다.
8. 한 가지 대표 작업을 Codex 기본 경로와 OMX 경로로 각각 수행한다.
9. 완료 시간, 재시도 수, 토큰 사용, 규칙 위반, 상태 복구, 사용자 이해 비용을 비교한다.
10. 제거 후 설정·훅·상태 잔여물이 없는지 검증한다.

### 단계 D — 채택 게이트

다음 조건을 모두 통과해야 프로젝트 도입 후보가 된다.

- 보호 경계·승인·정본 규칙 위반 0건
- Codex 기본 경로 대비 명확한 품질·시간·복구 이득
- 사용자가 새로운 모드와 상태 소유자를 설명할 수 있을 정도의 인지 가능성
- 버전 업데이트 없이도 재현 가능한 고정 실행
- uninstall 후 원복 검증 통과
- 필요한 기능만 좁게 활성화할 수 있음

수치 임계값은 현재 보고서에서 임의 확정하지 않고 파일럿 설계 시 사용자와 정한다.

## 13. 레드팀 검토

### 반론 1: “인기 있고 기능이 많으니 지금 넣는 편이 빠르다.”

인기와 기능 수는 현재 단계 적합성을 증명하지 않는다. 이 프로젝트는 과도한 내부 구성과 사용자가 기억하지 못하는 승인·구조가 누적된 경험 때문에 최소 계층부터 다시 세우는 중이다. OMX 전체 도입은 바로 그 복잡성을 다시 선도입할 수 있다.

### 반론 2: “OMX가 상태를 관리하니 프로젝트의 지식 운영 목표와 맞다.”

이름은 비슷하지만 소유 범위가 다르다. OMX의 `.omx/`는 주로 실행 모드·계획·로그·메모리를 위한 런타임 상태다. 현재 프로젝트는 출처, 수명주기, 충돌, 선택적 컨텍스트, 사용자 원문 권위를 포함하는 장기 지식 운영 기반을 계층적으로 만들려 한다. OMX 상태를 그대로 정본으로 채택하면 요구사항을 충족했다는 착시가 생길 수 있다.

### 반론 3: “플러그인 모드면 가볍다.”

플러그인 모드는 레거시 스킬 복제를 줄이지만, 공식 setup 문서상 네이티브 에이전트 TOML, 런타임 기능 플래그, 네이티브 훅을 계속 관리한다. 현재 앱에서는 핵심 팀 런타임도 직접 사용할 수 없어 비용 대비 이득이 낮다.

### 반론 4: “나중에 제거하면 된다.”

파일 삭제 자체보다 어려운 것은 운영 습관과 정본 의존성 제거다. 계획·완료 판정·프롬프트 라우팅이 `.omx/`와 훅에 의존하면, uninstall 후에도 문서와 작업 방식에 잔여 계약이 남을 수 있다. 따라서 제거 가능성은 실제 파일럿에서 검증해야 한다.
