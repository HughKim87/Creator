# 문서 기반 데이터 구축 체계 제안 보고서

- 작성일: 2026-07-22
- 문서 유형: 조사·설계 제안 보고서
- 목적: 데이터 기반 지식 운영체계를 구축할 때 사용할 정본 기록과 운영 문서를 구분하고, 유형별로 저장할 최소 데이터를 제안한다.
- 사용 시점: 지식체계의 첫 데이터 영역, 기록 형식, 문서 템플릿, 지식 승격 기준을 결정할 때
- 작성 책임: 프로젝트 에이전트
- 상태: 제안 — 사용자 승인 및 구현 전
- 권위 범위: 이 문서는 시점 제안과 조사 근거이며, 프로젝트 규칙·기술 계약·현재 상태의 활성 정본이 아니다.

> 구현 순서 안내: 이 보고서의 구현 순서 제안은 이후 사용자 검토에서 완성 형태를 시작 단계부터 요구한다는 문제가 확인됐다. 2026-07-22부터 실제 구축 순서와 단계 경계는 [프로젝트 계층형 구축 마스터 계획](../docs/build/MASTER_BUILD_PLAN.md)이 대체하여 소유한다. 이 보고서는 문서·데이터 유형에 관한 조사 근거로 보존한다.

## 1. 요약

데이터 기반 지식 운영체계를 구축하려면 다음 두 가지를 먼저 정해야 한다.

1. 어떤 종류의 문서와 기록을 정본으로 사용할 것인가.
2. 각 종류에 어떤 데이터만 저장할 것인가.

그러나 이 두 가지보다 먼저 다음 질문이 확정돼야 한다.

> 이 데이터는 앞으로 어떤 작업의 어떤 질문에 답하기 위해 필요한가?

이 질문 없이 문서 유형과 필드를 먼저 만들면 언젠가 필요할 수 있다는 이유로 데이터가 계속 추가된다. 그러면 실제 지식보다 지식을 관리하는 문서, 카탈로그, 관계, 검토 이력이 더 빠르게 증가한다.

권장 설계 순서는 다음과 같다.

1. 개선하려는 작업과 질문을 정의한다.
2. 그 질문에 답할 정본 기록 유형을 선택한다.
3. 유형별 최소 데이터만 정의한다.
4. 사람이 읽는 문서는 정본에서 목적에 맞게 조립하거나 생성한다.
5. 다음 작업에서 실제 재사용 여부와 비용을 검증한다.

이 보고서의 핵심 제안은 문서를 데이터베이스처럼 사용하지 않고, 정본 데이터와 사람이 읽는 문서를 분리하는 것이다.

## 2. 연구 질문

이번 조사는 다음 질문을 중심으로 수행했다.

1. 데이터 기반 지식체계에서는 어떤 기록이 정본이어야 하는가?
2. 정책, 절차, 설명, 보고서, 핸드오프에는 각각 어떤 정보만 들어가야 하는가?
3. 출처와 변경 이력을 보존하면서도 본문 중복을 줄이는 방법은 무엇인가?
4. 현재 프로젝트에서 문서와 관리 데이터가 비대해진 원인은 무엇인가?
5. 새 지식을 추가할 때 필요한 최소 메타데이터와 승격 기준은 무엇인가?

## 3. 조사 결과

### 3.1 사용자 요구에 따른 문서 유형 분리

Diátaxis는 문서를 튜토리얼, How-to 가이드, 참조, 설명의 네 유형으로 구분한다. 각각 학습, 실제 작업, 사실 조회, 이해라는 서로 다른 사용자 요구에 대응한다. 이 체계는 서로 다른 유형의 내용을 한 문서에 섞을 때 문서가 산만해지고 길어진다고 본다.

출처: [Diátaxis 공식 가이드](https://diataxis.fr/start-here/)

이 프로젝트에 적용하면 다음과 같이 해석할 수 있다.

- 실제 작업 순서는 절차 문서가 담당한다.
- 필드, 허용값, 명령, 상태 정의는 참조·계약 문서가 담당한다.
- 설계 배경과 장단점은 설명 문서가 담당한다.
- 처음 사용하는 사람의 학습 흐름은 튜토리얼이나 사용자 가이드가 담당한다.

### 3.2 한 문서에는 하나의 주제 또는 질문

OASIS DITA는 문서의 기본 단위가 하나의 주제나 질문에 답할 만큼 구체적이어야 하고, 동시에 독립적으로 이해될 수 있어야 한다고 정의한다. 또한 개념, 작업, 참조 정보를 서로 다른 정보 유형으로 구분한다.

출처: [OASIS DITA Topics](https://docs.oasis-open.org/dita/v1.0/archspec/topicover.html)

따라서 파일을 단순히 짧게 나누는 것이 아니라 목적, 독자, 수명주기, 갱신 조건이 다른 내용만 분리해야 한다. 같은 목적의 내용을 길이라는 이유만으로 여러 파일로 나누면 오히려 탐색 비용과 중복이 증가한다.

### 3.3 콘텐츠 모델과 중복 방지

GitHub Docs는 각 문서 유형의 목적과 포함할 내용을 콘텐츠 모델로 정의한다. 이를 통해 독자가 문서의 구조를 예측할 수 있고, 작성자도 동일한 내용을 여러 문서에 반복하지 않게 된다. 참조 정보는 표·목록 같은 구조화 형식을 사용하고, 중복되는 긴 내용을 복사하기보다 하나의 적절한 소유 문서에 두고 연결한다.

출처:

- [GitHub Docs 콘텐츠 모델](https://docs.github.com/en/enterprise-cloud%40latest/contributing/style-guide-and-content-model/about-the-content-model)
- [GitHub Docs 참조 콘텐츠 유형](https://docs.github.com/en/enterprise-cloud%40latest/contributing/style-guide-and-content-model/reference-content-type)

### 3.4 공통 메타데이터와 스키마

Dublin Core는 제목, 유형, 작성자, 날짜, 식별자, 출처, 관계처럼 여러 기록에 공통으로 적용할 수 있는 메타데이터 어휘를 제공한다. JSON Schema는 구조와 허용값을 검증하면서 제목, 설명, 기본값, 예시 같은 보조 정보도 함께 정의할 수 있다.

출처:

- [DCMI Metadata Terms](https://www.dublincore.org/specifications/dublin-core/dcmi-terms/)
- [JSON Schema Annotations](https://json-schema.org/understanding-json-schema/reference/annotations)

이를 적용하면 장문 설명을 모든 기록에 반복하지 않고, 공통 메타데이터와 유형별 스키마를 통해 기록을 일관되게 검증할 수 있다.

### 3.5 출처와 파생 관계의 분리

W3C PROV는 결과물, 그것을 만든 활동, 관련 주체, 파생 관계를 분리하여 출처를 추적한다. 이 관점에서는 근거 원문을 여러 문서에 복사하는 대신 출처 ID와 정확한 위치를 연결한다.

출처: [W3C PROV Overview](https://www.w3.org/TR/prov-overview/)

### 3.6 결정 전용 기록

ADR은 중요한 선택을 일반 보고서나 현재 상태 문서에 섞지 않고, 문제·요구조건·선택지·결정·이유를 하나의 기록으로 남기는 방법이다. 결정이 바뀌면 이전 결정을 삭제하지 않고 대체 관계와 변경 이유를 남길 수 있다.

출처: [Google Cloud ADR 가이드](https://docs.cloud.google.com/architecture/architecture-decision-records?hl=en)

## 4. 현재 프로젝트 진단

현재 프로젝트의 의도 분석에서는 최상위 목적을 다음과 같이 정의했다.

> 작업 결과·실패·판단·경험을 데이터로 남기고, 재사용 가치가 있는 것만 지식으로 승격해 다음 작업에 낮은 비용으로 공급한다.

관련 문서: [프로젝트 의도 역추론 보고서](2026-07-22_프로젝트_의도_역추론_보고서.md)

역사 설계인 snapshot 3도 출처, 지식, 결정, 실패 사례, 관계, 작업 이벤트, 검토, 개정 이력을 서로 다른 데이터 유형으로 분리했다. 유형을 분리한 방향 자체는 적절했다.

그러나 다음 문제가 발생했다.

- 지식 한 건에 필수 필드가 25개까지 증가했다.
- 일반 파일까지 지식과 비슷한 수준으로 등록·검토·색인하려 했다.
- 관계, 검토, 개정, 이벤트를 범용적으로 관리하면서 쓰기 비용이 증가했다.
- 문서 지도에 개별 보고서까지 수동 등록해 문서 지도가 또 하나의 거대한 정본이 됐다.
- snapshot 3에 시점 보고서가 18개까지 증가했다.
- 실제 지식보다 카탈로그, 컨텍스트 패키지, 작업 계약 같은 관리 산출물이 더 빠르게 증가했다.

따라서 이전 설계의 문제는 데이터 유형을 분리한 것이 아니다. 모든 유형과 파일에 과도한 관리 계약을 적용하고, 미래 가능성을 이유로 너무 많은 데이터를 미리 수집한 것이 문제다.

## 5. 제안 구조

전체 구조를 다음 세 계층으로 분리한다.

| 계층 | 역할 | 정본 여부 |
|---|---|---|
| 정본 데이터 | 작업 경험, 출처, 지식, 결정, 실패, 현재 상태 저장 | 정본 |
| 운영 문서 | 정책, 계약, 절차, 설명, 사용자 가이드 제공 | 유형별 활성 소유자 |
| 파생 문서 | 보고서, 핸드오프, 상태 화면, 검색 결과 제공 | 정본 아님 |

### 5.1 정본 데이터 계층

실제로 데이터를 구축하는 정본은 여섯 종류로 제한한다.

| 기록 유형 | 권장 형식 | 저장할 데이터 | 저장하지 않을 데이터 |
|---|---|---|---|
| 작업 기록 | JSONL | 요청 목적, 범위, 사용 근거, 수행 행동, 결과, 실패, 검증, 사용자 결정 | 장문의 설명, 전체 콘솔 출력, 중간 사고 과정 |
| 출처 기록 | JSONL | 출처 ID, 유형, 위치, 제목, 관찰일, 권위, 해시·버전 | 출처 원문 전체 복사 |
| 지식 항목 | JSONL | 하나의 주장, 사실·추론·절차·제약 구분, 적용 범위, 근거, 상태, 검토 조건 | 여러 주장, 전체 작업 역사, 반복 설명 |
| 결정 기록 | Markdown와 구조화 메타데이터 | 문제, 요구조건, 선택지, 결정, 이유, 영향, 승인, 대체 관계 | 구현 절차 전체, 회의·작업 역사 |
| 실패 사례 | Markdown와 구조화 메타데이터 | 증상, 발생 조건, 확인 원인, 해결, 검증, 재발 조건, 방지책 | 일반적인 프로젝트 설명, 관련 없는 로그 |
| 현재 상태 | 단일 JSON | 현재 목표, 단계, 완료 항목, 차단 요소, 첫 다음 행동, 관련 기록 ID | 과거 작업 서사, 전체 변경 이력 |

관계와 변경 이력은 필요하지만 사람이 별도 장문 문서로 작성하지 않는다. 정본 기록을 변경할 때 도구가 다음과 같은 보조 기록에 자동으로 추가하는 구조가 적절하다.

- 관계 기록: supported_by, supersedes, contradicts, resolved_by
- 변경 이력: 변경 주체, 시점, 대상, 변경 이유, 변경 전후 식별값

### 5.2 운영 문서 계층

운영 문서는 데이터를 누적하는 장소가 아니라 행동과 해석을 통제하는 문서다.

| 문서 유형 | 반드시 포함할 내용 | 제외할 내용 |
|---|---|---|
| 정책·규칙 | 적용 범위, 필수·금지 행동, 우선순위, 승인 조건 | 실패 역사, 긴 설계 이유, 현재 작업 상태 |
| 계약·참조 | 필드 정의, 허용값, 불변 조건, 오류 조건, 짧은 예시 | 작업 절차, 의사결정 역사 |
| 절차·How-to | 목표, 입력, 사전조건, 단계, 기대 결과, 검증, 복구 | 개념 에세이, 관련 규칙 전체 복사 |
| 설명 | 배경, 작동 원리, 선택 이유, 장단점, 적용 예 | 강제 규칙, 현재 상태, 작업 로그 |
| 사용자 가이드 | 독자, 목적, 준비사항, 사용 순서, 예상 결과, 문제 해결 | 내부 감사 기록, 구현 세부사항 |

### 5.3 파생 문서 계층

다음 문서는 정본 데이터를 사람이 읽기 좋게 보여주는 뷰로 취급한다.

| 파생 문서 | 포함할 내용 | 제외할 내용 |
|---|---|---|
| 보고서 | 조사 질문, 기준 시점, 범위, 방법, 발견, 근거 ID, 제안, 한계, 승인 상태 | 관련 규칙·절차 전체 복사, 원시 로그 전체 |
| 핸드오프 | 현재 목표, 현재 단계, 차단 요소, 첫 다음 행동, 관련 정본 링크 | 전체 작업 역사, 동적 통계, 과거 보고서 요약 |
| 상태 화면·요약 | 정본에서 조회한 현재 상태와 핵심 지표 | 독립적인 수동 상태 값 |
| 검색·컨텍스트 결과 | 선택된 기록, 선택 이유, 출처, 제외 이유, 크기 | 새로운 정본 지식 |

## 6. 유형별 최소 데이터

### 6.1 공통 필드

모든 기록에 동일한 20개 이상의 필드를 강제하지 않는다. 공통 필드는 다음 정도로 제한한다.

| 필드 | 의미 |
|---|---|
| id | 기록의 안정적인 식별자 |
| type | 작업, 출처, 지식, 결정, 실패 사례, 상태 구분 |
| title | 사람이 식별할 수 있는 짧은 이름 |
| status | 후보, 활성, 검증, 대체, 폐기 등 현재 상태 |
| scope | 적용 프로젝트·작업·주제 범위 |
| source_refs | 근거가 되는 출처 ID와 위치 |
| created_at | 생성 시점 |
| updated_at | 마지막 의미 변경 시점 |

### 6.2 유형별 추가 필드

| 유형 | 추가 필드 |
|---|---|
| 지식 | statement, classification, confidence_basis, review_trigger |
| 결정 | context, requirements, options, decision, rationale, consequences, approved_by, supersedes |
| 실패 사례 | symptom, conditions, cause, resolution, verification, recurrence_trigger |
| 작업 기록 | task, action, result, failure, validation, decision_refs |
| 출처 | locator, authority, observed_at, content_hash |
| 현재 상태 | objective, stage, completed, next_action, blockers, evidence_refs |

작성자, 검토자, 주기 검토일, 검색 포함 여부, 관계 ID 같은 필드를 모든 기록에 무조건 강제하지 않는다. 해당 유형의 실제 사용 사례와 검증 필요가 확인될 때만 추가한다.

## 7. 지식 승격·보존·폐기 기준

### 7.1 반드시 보존하는 데이터

- 사용자가 명시적으로 확정한 결정
- 안전, 권한, 원본 보호와 관련된 경계
- 재현 가능한 실패 원인과 검증된 해결
- 여러 작업에 반복 적용되는 절차와 제약
- 현재 작업을 재개하기 위한 최소 상태

### 7.2 후보로 보존하는 데이터

- 다음 유사 작업에서 다시 사용할 가능성이 있는 판단
- 결과 품질이나 작업 비용을 실제로 개선한 방법
- 아직 검증되지 않았지만 명시적인 근거가 있는 추론
- 한 번 더 반복되면 일반 규칙이나 회귀 사례로 승격할 가치가 있는 실패

### 7.3 장기 지식으로 남기지 않는 데이터

- 일회성 명령 출력
- 중간 초안과 임시 계획
- Git 상태, 파일 수, 테스트 수처럼 다시 조회할 수 있는 동적 사실
- 다른 정본에 이미 존재하는 설명
- 어느 미래 작업에서 사용할지 설명할 수 없는 정보
- 결과에 영향을 주지 않은 중간 시행착오

### 7.4 기록 생성 게이트

새 기록을 만들기 전에 다음 질문을 통과해야 한다.

1. 이 정보가 어떤 미래 작업에 사용되는가?
2. 이 정보가 없으면 같은 판단이나 실패를 반복할 가능성이 있는가?
3. 출처 또는 검증 근거가 있는가?
4. 기존 기록과 중복되지 않는가?
5. 언제 오래된 정보가 되는지 판정할 수 있는가?
6. 기록하고 유지하는 비용이 기대되는 재사용 가치보다 작은가?

안전 경계, 명시적 사용자 결정, 재현 가능한 중대한 실패는 재사용 빈도가 낮아도 보존 예외로 둘 수 있다.

## 8. 문서 길이 방지 기준

다음 수치는 초기 검토 기준이며, 대표 작업 검증 후 조정한다. 초과 자체를 실패로 판정하기보다 분리·압축·링크 전환 검토를 시작하는 신호로 사용한다.

| 문서 | 초기 검토 기준 |
|---|---|
| 시작 규칙 | 500단어 이하 |
| 핸드오프 | 40줄 이하 |
| 결정 기록 | 한 결정, 800단어 이하 |
| 실패 사례 | 한 실패 유형, 800단어 이하 |
| 절차 문서 | 하나의 사용자 목표만 담당 |
| 보고서 | 요약 300단어, 본문 2,000단어 이내 |

추가 운영 원칙은 다음과 같다.

- 같은 설명이 두 번째 문서에 필요하면 복사하지 않고 정본을 연결한다.
- 현재 상태 문서에는 과거 서사를 넣지 않고 이력 ID만 연결한다.
- 원시 근거, 로그, 세부 표는 본문이 아니라 별도 증거 파일로 둔다.
- 문서가 길어졌다는 이유만으로 같은 목적의 내용을 무조건 여러 파일로 나누지 않는다.
- 보고서는 새로운 발견과 제안만 보유하고 기존 정책과 계약을 재서술하지 않는다.
- 검색 결과, 카탈로그, 상태 화면은 삭제 후 정본에서 다시 만들 수 있어야 한다.

## 9. 권장 구현 순서

### 9.1 대표 질문 확정

먼저 지식체계가 개선해야 할 대표 작업 질문 세 개를 정한다.

1. 기존 문서에서 필요한 지식을 최소 컨텍스트로 읽을 수 있는가?
2. 새 작업 경험을 지식으로 추가하고 다음 세션에서 다시 읽을 수 있는가?
3. 검증된 실패 경험을 다음 유사 작업에서 재사용할 수 있는가?

### 9.2 최소 기록 유형 승인

작업, 출처, 지식, 결정, 실패 사례, 현재 상태의 여섯 정본 유형과 최소 필드를 승인한다. 관계와 변경 이력은 보조 데이터로 두며 독립적인 장문 문서로 만들지 않는다.

### 9.3 작은 실제 사례 작성

유형별 예시를 대량 생성하지 않는다. 대표 작업과 직접 관련된 기록을 한 건씩만 작성한다.

- 기존 문서에서 선별한 지식 한 건
- 새 작업에서 발생한 지식 후보 한 건
- 반복 방지 가치가 있는 실패 사례 한 건
- 사용자가 확정한 결정 한 건

### 9.4 실제 읽기·쓰기·재사용 검증

다음 항목을 측정한다.

- 전체 문서 읽기 기준선의 문자·토큰 수
- 선택된 컨텍스트의 문자·토큰 수
- 필수 지식 누락 수
- 관련 없는 항목 수
- 출처 추적 성공 여부
- 지식 한 건을 추가·검토하는 데 필요한 단계와 수정 파일 수
- 새 지식이 다음 작업 결과에 실제 사용됐는지 여부

### 9.5 필요한 기능만 증분 도입

직접 경로와 단순 메타데이터 선택으로 대표 작업이 해결되지 않을 때만 검색 인덱스, SQLite, FTS, 벡터 검색, 그래프 관계, 자동 검토 큐를 검토한다. 도구 도입 자체를 완료 기준으로 삼지 않는다.

## 10. 수용 기준 제안

이 설계가 실제로 유효하다고 판단하려면 다음 조건을 만족해야 한다.

1. 동일한 사실이나 상태가 둘 이상의 활성 정본에 존재하지 않는다.
2. 작업 기록 전체가 자동으로 장기 지식이 되지 않는다.
3. 지식 한 건이 하나의 주요 주장만 가진다.
4. 지식·결정·실패 사례가 정확한 출처로 역추적된다.
5. 보고서와 핸드오프가 규칙·계약·역사 전체를 복사하지 않는다.
6. 정본 데이터에서 현재 상태와 필요한 문서를 다시 구성할 수 있다.
7. 대표 작업에서 전체 문서 로딩보다 컨텍스트 비용이 감소한다.
8. 필수 지식 누락과 보호 데이터 노출이 없다.
9. 지식 한 건을 추가하기 위해 프로젝트 전체를 다시 읽거나 여러 정본을 수동 갱신하지 않는다.
10. 새로 승격한 지식이나 실패 사례가 다음 관련 작업에 실제로 사용된다.

## 11. 위험과 반론

### 11.1 기록 유형이 다시 증가할 위험

새로운 사례가 생길 때마다 새 유형을 만들면 분류 체계가 다시 비대해진다. 기존 유형으로 표현할 수 없는 반복 사례가 실제로 두 번 이상 확인될 때만 새 유형을 검토해야 한다.

### 11.2 최소 필드가 근거 부족으로 이어질 위험

필드를 줄이는 목적은 근거를 없애는 것이 아니다. 출처, 상태, 적용 범위, 검토 조건처럼 지식 신뢰성에 직접 필요한 정보는 유지해야 한다. 줄여야 하는 것은 모든 유형에 일괄 적용한 불필요한 관리 필드다.

### 11.3 Markdown과 JSON의 이중 정본 위험

결정과 실패 사례를 Markdown으로 작성하면서 동일 내용을 JSONL에 다시 수동 복사하면 정본이 둘이 된다. Markdown의 구조화 메타데이터를 파싱해 파생 인덱스를 만들거나, JSON 정본에서 Markdown 뷰를 생성하는 방식 중 하나만 선택해야 한다.

### 11.4 지나친 길이 제한으로 의도가 손실될 위험

길이 기준은 강제 삭제 규칙이 아니다. 상세 근거가 필요한 경우 본문을 억지로 줄이지 말고, 정본 데이터·설명·증거 부록으로 책임을 분리해야 한다.

### 11.5 관리 자동화가 다시 본업을 압도할 위험

스키마, 카탈로그, 검토 큐, 검색 인덱스는 대표 지식 작업의 측정된 문제를 해결할 때만 추가한다. 관리 데이터의 파일 수, 크기, 작성 단계가 실제 지식보다 빠르게 증가하면 설계 검토를 중단하고 단순화해야 한다.

## 12. 최종 제안

이 프로젝트의 문서와 데이터 체계는 다음 원칙을 중심으로 구축하는 것이 적합하다.

> 작업에서 발생한 모든 것을 문서화하지 않는다. 작업 기록은 얇게 남기고, 다음 결과를 개선할 정보만 출처가 연결된 지식·결정·실패 사례로 승격한다. 규칙·계약·절차·가이드·보고서·핸드오프는 이 정본 데이터를 목적에 맞게 통제하거나 보여주는 서로 다른 문서 유형으로 유지한다.

현재 단계에서 바로 구현해야 할 것은 범용 지식 플랫폼이 아니다. 먼저 대표 작업 질문 세 개, 여섯 정본 기록 유형, 유형별 최소 필드, 지식 승격 기준을 확정하고 작은 실제 사례로 읽기·쓰기·재사용 비용을 검증해야 한다.
