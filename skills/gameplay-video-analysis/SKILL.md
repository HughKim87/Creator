# 게임 플레이 영상 분석

이 스킬은 워크플로우 **6단계 영상 분석**을 수행한다.

목표는 하이라이트를 새로 invent 하는 것이 아니라, **5단계 기획서의 대사 스파인과 검증 브리프가
실제 화면·오디오·맥락으로 성립하는지 확인하고, 7단계가 사용할 후보 지도와 인계 브리프를 만드는 것**이다.

6단계 출력은 컷리스트, XML, 러프컷이 아니다. 컷 경계 확정과 편집 자료 생성은 7단계
`premiere-editing-export`에서 한다.

## 선행 조건 — 영상 기획서 필수 게이트

이 스킬은 **영상 기획서가 확정된 뒤**에만 쓴다.

필수 입력:

- 컨트롤링 아이디어
- 대사 스파인
- 감정 아크
- 포함/제외 기준
- 6단계 검증 브리프

기획서가 없거나 G1/G2/G3/G4 게이트를 통과하지 않았으면 멈추고, 먼저
`기획_리서치/기획단계_규격_2026-07-06.md`에 따라 5단계를 수행한다.

## 핵심 원칙

- **분석 단위는 기획서의 막/비트다.** RMS, 키워드, 비명 크기가 상위 기준이 아니다.
- **신호는 보조다.** 자막·RMS·피크는 기획서 비트 주변의 사건·반응·경계를 찾는 데만 쓴다.
- **자막만으로 최종 판단하지 않는다.** 대표 후보는 실제 화면 근거를 확인한다.
- **화면만 무작정 많이 보지 않는다.** 5단계 검증 브리프의 대표/예비 후보부터 본다.
- **사건-결과-반응을 분리해서 자르지 않는다.** 조우, 사망, 규칙 발견, 엔딩은 앞뒤 맥락을 기록한다.
- **대표/예비/제외를 구분한다.** 같은 기능의 비명·사망·탐색을 모두 살리지 않는다.
- 원본 영상과 원본 자막은 절대 수정하지 않는다.
- 한 번 본 구간은 Markdown/CSV로 저장하고, 다음 세션에서 다시 이미지 판독을 반복하지 않는다.

## 입력 확인

1. 원본 영상 경로를 확인한다.
2. 같은 이름의 원본 `.srt`가 있으면 우선 사용한다. 새 전사는 비용이 필요할 때만 생성한다.
3. 5단계 기획서에서 아래 정보를 가져온다.

| 필드 | 설명 |
|---|---|
| `controlling_idea` | 컨트롤링 아이디어 한 문장 |
| `act` | 막 번호 또는 감정 아크 구간 |
| `bit_id` | 대사 스파인 번호 |
| `story_function` | 동기, 공포증거, 자기인정, 규칙학습, 적응, 퇴각 등 |
| `target_time` | 대사 타임코드 |
| `screen_question` | 화면에서 확인할 질문 |
| `must_preserve_sentence` | 문장 단위 보존 여부 |

4. `ffprobe`로 원본이 끝까지 읽히는지 확인한다. 메타데이터 길이만 믿지 않는다.

```powershell
tools\ffmpeg\bin\ffprobe.exe -v error -show_entries format=duration,size -of default=noprint_wrappers=1 "원본.mkv"
tools\ffmpeg\bin\ffprobe.exe -v error -read_intervals 02:24:00%+00:00:45 -select_streams v:0 -show_entries packet=pts_time -of csv=p=0 "원본.mkv"
```

## 토큰 예산 규칙

긴 영상 전체를 프레임으로 읽지 않는다.

| 작업 | 기본 화면 사용량 | 설명 |
|---|---:|---|
| 기획서 비트별 1차 확인 | 6~12프레임 | 비트 주변 사건 확인 |
| 후보 구간 1개 검증 | 8~16프레임 | 3~5분 구간 기준 |
| 사건-반응 경계 확인 | 6~12프레임 | 조우, 사망, 규칙 발견, 엔딩 주변 |
| 화면 글자 확인 | 1024px | 필요할 때만 사용 |
| 일반 흐름 확인 | 512px | 기본값 |

한 세션에서 이미지 읽기는 가능한 한 16~40장 안에 둔다. 더 필요하면 후보 하나를 끝내고 저장한 뒤 다음 후보로 넘어간다.

## 작업 순서

### 1. 기획서 비트 로드

5단계 기획서의 대사 스파인과 6단계 검증 브리프를 표로 옮긴다.

```csv
bit_id,act,story_function,target_time,screen_question,must_preserve_sentence
B01,1,동기,00:34~01:13,도입 화면이 영화/게임 연결을 보여주는가?,yes
B05,2,공포증거,10:39~10:59,엔티티/도망/반응이 모두 보이는가?,yes
```

이 표가 없으면 6단계를 시작하지 않는다.

### 2. 저비용 확인 범위 잡기

화면을 바로 많이 보지 않는다. 먼저 자막과 오디오로 각 비트의 확인 범위를 정한다.

- 일반 대사 비트: `target_time -30초 ~ +60초`
- 직전 사건과 직후 반응이 필요한 비트: `target_time -90초 ~ +90초`
- 사망·추격·비명 후보: 오디오 RMS/피크를 보조로 확인
- 조용한 소감·정리 대사: 오디오 피크가 없어도 유지

```powershell
tools\ffmpeg\bin\ffmpeg.exe -i "원본.mkv" -af "astats=metadata=1:reset=1,ametadata=print:key=lavfi.astats.Overall.RMS_level:file=rms.txt" -f null -
```

이 단계에서 만드는 것은 **후보 범위표**다. 컷 경계를 확정하지 않는다.

### 3. 화면 검증

`video-watch`로 후보 구간만 본다.

```powershell
C:\Users\Hugh\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe `
  skills\video-watch\scripts\watch.py "원본.mkv" `
  --no-whisper --start 00:07:00 --end 00:11:10 `
  --max-frames 16 --resolution 1024 `
  --out-dir temp\video-watch\구간명
```

큰 구간에서 사건·반응 경계가 거칠면 지정 시각 프레임만 추가로 뽑는다.

```powershell
C:\Users\Hugh\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe `
  skills\video-watch\scripts\watch.py "원본.mkv" `
  --no-whisper --detail transcript `
  --timestamps "00:10:35,00:10:45,00:10:58,00:11:05" `
  --start 00:10:20 --end 00:11:10 `
  --resolution 1024 `
  --out-dir temp\video-watch\구간명_cues
```

각 후보는 아래 네 단위로 본다.

| 단위 | 확인할 것 |
|---|---|
| `pre_context` | 대사 직전 무슨 일이 있었는가 |
| `event` | 화면에서 실제 사건이 보이는가 |
| `reaction` | 대사·플레이 반응이 이어지는가 |
| `result` | 사망, 성공, 이동, 규칙 발견 같은 결과가 보이는가 |

### 4. 후보 판정

후보마다 아래 필드를 기록한다.

| 필드 | 의미 |
|---|---|
| `candidate_id` | 후보 ID |
| `act` | 기획서 막 번호 |
| `bit_id` | 연결되는 대사 스파인 번호 |
| `story_function` | 동기, 공포증거, 자기인정, 규칙학습, 적응, 퇴각 등 |
| `screen_evidence` | 화면에서 보이는 것 |
| `subtitle_evidence` | 대사 근거 |
| `audio_evidence` | 비명, 웃음, 침묵, 긴장 |
| `context_needed` | 앞뒤 맥락 필요 여부 |
| `hook_potential` | 오픈 루프 후보 여부 |
| `risk` | 화면 약함, 반응 잘림, 중복, 공략 과다, 자막 어긋남 |
| `decision` | 대표, 예비, 제외, 재검증 |

판정 기준:

- 대표: 해당 기능을 가장 잘 보여주는 장면.
- 예비: 대표가 화면상 약하거나 길 경우 대체할 장면.
- 제외: 같은 기능 반복, 화면 약함, 메시지와 무관한 장면.
- 재검증: 화면·자막·오디오가 충돌하거나 경계가 불명확한 장면.

### 5. 시청각 충돌 점검

아래 상황은 반드시 위험으로 표시한다.

- 대사는 중요하지만 화면이 밋밋하다.
- 화면은 강하지만 컨트롤링 아이디어에 기여하지 않는다.
- 자막 타임코드와 실제 발화·화면 사건이 어긋난다.
- 사건 화면은 있는데 직후 반응이 빠져 있다.
- 시청자 조언·공략 설명이 길어져 주인공 변화가 묻힌다.
- 같은 기능의 비명, 실패, 탐색이 중복으로 남아 있다.

### 6. 7단계 인계 브리프 작성

6단계 끝에는 컷리스트가 아니라 7단계용 브리프를 만든다.

포함:

- 막별 대표 후보
- 예비 후보
- 반드시 보존할 앞뒤 맥락
- 압축 가능한 부분
- 자막 요약으로 대체할 부분
- 컷 경계 주의점
- 화면 확인 완료/미완료 표시

## 화면 판정 기준

### 사건 시작

아래 중 하나가 보이면 사건 시작 후보로 잡는다.

- 새 공간 진입
- 게임 플레이 화면으로 전환
- 적/엔티티 등장
- 추격 시작
- 퍼즐·문·장치와 상호작용 시작
- 시청자 조언을 받아 행동을 바꾸는 순간

### 사건 결과

아래 중 하나가 보이면 결과 후보로 잡는다.

- 사망, 실패, 클리어, 탈출, 다음 구역 진입
- 결과표, 테이프 화면, 챕터 전환
- 규칙 발견 후 안전 확보
- 대기방/시작 지점 복귀
- 직후 소감 또는 반응

### 보존 규칙

- 사건 전 맥락 발화가 있으면 필요한 만큼만 보존한다.
- 결과 화면과 직후 반응은 함께 판단한다.
- 질문/대답, 원인/반응은 함께 보존한다.
- 게임 한 판의 결과가 중요하면 시작, 진행, 결과, 후속 반응을 함께 보존한다.
- 대기방, 설정, 반복 탐색, 공략 설명은 기획서 기능이 없으면 줄인다.

## 저장 위치

화면을 확인한 구간은 반드시 Markdown과 가능하면 CSV로 저장한다.

권장 위치:

- `workspace/outputs/analysis/09_영상명_6단계_화면검증_후보지도_YYYY-MM-DD.md`
- `workspace/outputs/analysis/09_영상명_6단계_후보지도_YYYY-MM-DD.csv`

임시 프레임은 `temp/video-watch/구간명/`에 둔다. 최종 판단은 Markdown/CSV에 남긴다.

## 완료 게이트

### G1. 기획서 추적성

통과:
- 모든 대표 후보가 5단계 기획서의 비트 또는 막에 연결된다.

실패:
- "재밌어서", "리액션이 커서"만으로 들어간 후보가 있다.

### G2. 화면 증거

통과:
- 대표 후보에는 화면 근거가 있다.
- 화면 근거가 없는 대사 중심 후보는 그 이유가 기록되어 있다.

실패:
- 대사만 보고 화면 검증 완료로 처리한다.

### G3. 맥락 보존

통과:
- 사건, 결과, 반응의 보존 필요 여부가 기록되어 있다.

실패:
- 사망, 조우, 규칙 발견, 엔딩 구간에서 직전 사건이나 직후 반응이 빠진다.

### G4. 중복 정리

통과:
- 같은 기능의 후보는 대표/예비/제외로 구분되어 있다.

실패:
- 비슷한 비명, 실패, 탐색이 모두 후보로 남아 있다.

### G5. 7단계 인계 가능성

통과:
- 7단계가 컷리스트를 만들 때 필요한 역할, 보존 이유, 압축 가능성이 기록되어 있다.

실패:
- 후보표는 있지만 왜 살려야 하는지 알 수 없다.

## 편집 자동화 연결

6단계 산출물은 7단계의 입력이다. 컷리스트, XML, EDL, 러프컷은 여기서 만들지 않는다.

7단계에서 컷리스트를 만들 때는 먼저 6단계 후보 지도의 `decision`, `story_function`, `risk`,
`context_needed`를 확인한다. 결과가 이상하면 원본을 다시 무작정 보지 말고, 먼저 후보 지도의 판정 기준을 수정한다.

## 중단 조건

- 원본이 후반부까지 읽히지 않는다.
- 기획서 비트와 화면 근거가 충돌한다.
- 후보 구간의 화면 근거가 자막과 충돌한다.
- 사건의 시작/결과/반응을 화면으로 구분할 수 없다.
- 같은 후보가 두 번 이상 "포인트 누락" 또는 "필요 없는 부분 과다"로 실패한다.

이 경우 계속 후보를 늘리지 말고, 원본 상태, 기획서 비트, 화면 검증 방식 중 무엇이 문제인지 먼저 확인한다.
