# 파일 기반 다중 AI 에이전트 운영 솔루션 리서치

- 작성: 2026-07-14
- 역할: Graphify·Obsidian과 대체 운영 기법의 적용 가능성 및 도입 조건을 기록한다.
- 읽는 시점: 에이전트 기억·문서 중복·병렬 작업 문제를 다시 개선하거나 외부 도구 도입을 결정할 때만 읽는다.
- 결정 상태: 공통 제어층은 적용, Graphify·Obsidian과 나머지 외부 도구는 도입 보류.
- 보존 조건: 후보 도구를 실제 도입해 별도 운영 기준이 생기거나 이 문서를 대체하는 재평가 보고서가 작성될 때까지.

## 결론

현재 문제는 하나가 아니라 세 가지다.

1. 세션마다 규칙과 재개 지점을 다르게 해석한다.
2. 같은 판단을 다시 하면서 문서와 토큰 사용량이 늘어난다.
3. 여러 에이전트가 동시에 작업하면 파일과 완료 판단이 충돌할 수 있다.

Graphify는 2번의 탐색 비용을 줄일 가능성이 있고, Obsidian은 사람이 문서 관계를
보는 데 유용하다. 하지만 둘 다 1번의 규칙 준수나 3번의 파일 충돌을 직접 강제하지
않는다. 따라서 공통 시작·종료·검증 장치는 유지하고, 나머지는 아래 조건이 충족될 때
작은 범위로 시험한 뒤 도입 여부를 결정한다.

## 현재 적용된 기반

| 구성 | 해결하는 문제 | 한계 |
|---|---|---|
| 공통 bootstrap·index | 모든 에이전트의 첫 진입 경로 통일 | 에이전트가 지침을 무시하면 강제력이 없음 |
| `projectctl` | 활성 작업·담당자·완료 검증 통일 | 동시 편집 파일을 물리적으로 격리하지 않음 |
| `doccheck`·단위 테스트 | 구조 위반과 반복 가능한 오류 탐지 | 콘텐츠 판단의 품질은 별도 평가가 필요 |
| 단계별 skills | 필요한 절차만 선택적으로 로드 | 에이전트별 Skill 호환성 감사가 아직 필요 |

## 후보 비교

| 후보 | 주된 가치 | 현재 판단 | 다시 검토할 조건 |
|---|---|---|---|
| Graphify | 코드·문서 관계를 지식 그래프로 저장하고 질의 | 보류, 제한 파일럿 후보 | 파일 재탐색이 실제로 반복되고 5개 기준 질문에서 이득을 측정할 수 있을 때 |
| Obsidian | Markdown 링크·속성·그래프를 사람이 탐색 | 보류 | 사용자가 문서 관계를 눈으로 탐색하는 UI가 필요할 때 |
| Git worktree | 에이전트별 브랜치와 작업 폴더 격리 | 조건부 권장 | 두 에이전트가 동시에 프레임워크 파일을 수정할 때 |
| Agent Skills 표준 정렬 | Claude·Codex·Gemini 계열의 절차 이식성 향상 | 점진적 감사 후보 | 동일 스킬이 에이전트마다 다르게 실행될 때 |
| 행동 회귀 평가 | 같은 요청에 대한 규칙 준수와 결과 편차 측정 | 조건부 권장 | 재발하는 실패 사례가 3개 이상 모일 때 |
| 외부 메모리·벡터 DB·MCP | 대규모 장기 지식 검색 | 우선순위 낮음 | 그래프·파일 라우팅으로도 검색 비용이 줄지 않을 때 |

## Graphify

여기서 말하는 Graphify는 `Graphify-Labs/graphify`다. 공식 패키지 이름은
`graphifyy`이고 CLI 명령은 `graphify`다. 프로젝트 코드·문서·미디어를 분석해
graph.html, GRAPH_REPORT.md, graph.json을 생성하며 Claude Code, Codex,
Gemini CLI 등에 프로젝트 스킬로 설치할 수 있다.

### 기대 이점

- 매 세션마다 여러 파일을 처음부터 읽는 대신 관계 그래프를 질의할 수 있다.
- 명시적으로 추출한 관계와 도구가 추론한 관계를 구분해 표시한다.
- `.gitignore`와 `.graphifyignore`를 사용해 분석 대상을 줄일 수 있다.
- 로컬 그래프를 MCP로 제공하는 선택지도 있어 여러 에이전트가 같은 지도를 볼 수 있다.

### 위험과 비용

- 코드 파싱은 로컬이지만 문서·PDF·이미지·영상의 의미 추출은 선택한 모델이나 API
  백엔드를 사용할 수 있다. `inputs/`와 작업 산출물을 무심코 넣으면 외부 전송 범위가
  커질 수 있다.
- 질의 기록은 기본적으로 사용자 캐시의 JSONL 로그에 남는다. 민감한 질문을 다룰 때는
  로그 비활성화 여부를 결정해야 한다.
- 공식 팀 워크플로우는 `graphify-out/` 커밋을 권장하지만, 이 프로젝트에서는 그래프의
  정확성과 크기를 검증하기 전에 커밋하면 또 하나의 큰 파생 정본이 생길 수 있다.
- 자동 Git hook은 그래프 갱신과 merge driver를 추가한다. 현재 hook·doccheck와의 충돌을
  먼저 검증하지 않고 설치하면 안 된다.
- 관계 그래프가 있어도 잘못된 규칙, 오래된 문서, 완료 기준을 자동으로 바로잡지는 않는다.

### 도입 전 파일럿 규칙

1. 전역 설치가 아닌 프로젝트 한정 설치를 사용하고 버전을 고정한다.
2. 첫 분석 대상은 `PROJECT_*.md`, `docs/`, `skills/`, `tools/`로 제한한다.
3. `.graphifyignore`로 `inputs/`, `outputs/`, `.git/`, `tools/ffmpeg/`, 미디어와 비밀
   가능 파일을 명시적으로 제외한다.
4. 첫 파일럿에서는 Git hook, 공유 HTTP MCP, 자동 커밋을 사용하지 않는다.
5. `graphify-out/`은 파일럿 동안 추적하지 않고 재생성 가능한 파생물로 취급한다.
6. 아래 기준 질문을 기존 파일 검색과 Graphify로 각각 답해 정확도·읽은 파일 수·소요
   시간·출력 크기를 비교한다.

기준 질문:

- 현재 작업 상태의 단일 정본은 무엇인가?
- 특정 단계의 입력·출력·중단 조건은 어디에 있는가?
- 어떤 도구가 특정 산출물을 만들며 검증은 어디서 하는가?
- 같은 규칙이 여러 문서에 중복되어 있는가?
- 변경하려는 문서나 도구의 직접 소비자는 무엇인가?

정답률이나 탐색 비용이 개선되지 않으면 도입하지 않는다. 개선되더라도 그래프는 정본이
아니며 원본 파일 경로를 돌려주는 색인으로만 사용한다.

## Obsidian

Obsidian은 로컬 폴더의 Markdown 파일을 vault로 열고, 내부 링크를 노드와 선으로 표시한다.
속성은 YAML로 저장되므로 사람이 보는 문서 목록·결정 관계·상태 필터를 만들기 쉽다.

### 적합한 용도

- 사용자가 문서와 결정의 관계를 직접 탐색한다.
- 전역 그래프보다 현재 문서 주변의 로컬 그래프를 본다.
- 기존 Markdown을 그대로 두고 읽기·검색·링크 확인 UI로 사용한다.

### 부적합한 기대

- Obsidian을 열었다고 AI 에이전트가 규칙을 더 잘 지키지는 않는다.
- 명시적으로 링크되지 않은 의미 관계를 Graphify처럼 자동 생성하지 않는다.
- vault를 별도로 복사하면 프로젝트 문서와 Obsidian 문서 중 어느 쪽이 정본인지 다시
  문제가 생긴다.
- 커뮤니티 플러그인은 Obsidian과 같은 파일·네트워크 권한을 가질 수 있어 최소 권한
  격리가 어렵다.

도입한다면 프로젝트 폴더 자체를 하나의 vault로 열고 별도 문서 복사본은 만들지 않는다.
첫 단계는 Restricted mode를 유지한 순정 Obsidian으로 제한한다. `.obsidian/` 설정을
추적할지와 workspace 상태를 무시할지는 별도 결정 후 적용한다. Graph view를 위해 기존
문서를 대량으로 `[[링크]]` 형식으로 다시 쓰지 않는다.

## Git worktree와 병렬 에이전트

Git은 한 저장소에 여러 working tree를 연결해 각기 다른 브랜치를 동시에 체크아웃할 수
있다. 프레임워크 코드와 문서를 동시에 수정하는 에이전트의 작업 폴더를 분리하는 데 가장
직접적인 방법이다.

다만 이 프로젝트의 `inputs/`와 다수 `outputs/`는 Git 추적 대상이 아니므로 새 worktree에
자동 복제되지 않는다. 따라서 영상별 작업에 바로 적용하면 원본·산출물 경로가 달라질 수
있다. 초기 적용 범위는 공용 문서·tools·skills 수정으로 제한하고, 영상 작업에는 읽기 전용
입력 공유와 에이전트별 출력 소유권을 먼저 설계한다.

## Agent Skills와 행동 회귀 평가

Agent Skills 공개 규격은 최소 SKILL.md와 선택적 `scripts/`, `references/`, `assets/`를
사용하며, 메타데이터→본문→필요 자원의 순서로 점진적으로 로드하도록 권장한다. 현재
프로젝트의 단계 skills 방향과 맞지만, 각 에이전트가 동일하게 인식하는지는 별도 호환성
감사가 필요하다.

반복 실패는 규칙 문장을 계속 추가하기보다 고정 사례로 테스트한다. 우선 도구 설치 없이
아래 사례를 작은 fixture로 만들고 Claude·Codex·Gemini에서 같은 요청을 실행해 비교한다.

- `inputs/` 수정 거부
- 현재 단계와 핸드오프 경로 선택
- 기존 문서와 중복되는 새 문서 생성 거부
- 삭제·커밋·외부 쓰기 전 승인 요청
- 명시적 허가 없는 MP4 생성 거부
- 검증 실패 상태에서 완료 선언 거부

사례가 늘어나 수동 비교가 부담이 될 때 Promptfoo 같은 평가 도구를 검토한다. Promptfoo는
예상 문자열·JSON 구조·사용자 함수·모델 평가 등의 assertion을 지원하지만, 모델 호출 비용과
평가기 자체의 편차가 있으므로 결정적 규칙은 기존 단위 테스트가 우선이다.

## 채택 순서

1. 현재 공통 bootstrap, `projectctl`, doccheck, 단위 테스트를 실제 작업에 사용한다.
2. 반복 실패 사례를 행동 회귀 fixture로 축적한다.
3. 동시 프레임워크 수정이 시작되면 worktree 운영 규칙을 시험한다.
4. 파일 재탐색 비용이 계속 크면 Graphify를 제한 범위로 파일럿한다.
5. 사람이 문서 관계를 보는 화면이 필요하면 순정 Obsidian을 시험한다.
6. 측정 결과가 있는 후보만 정식 규칙·hook·MCP로 승격한다.

## 레드팀

- 현재 문서가 새 도구를 많이 나열했다는 이유만으로 모두 도입하면 관리 지점만 늘어난다.
- Graphify 결과가 그럴듯해도 `INFERRED` 관계는 원문 확인 없이 규칙이나 정본으로 사용하면
  안 된다.
- Obsidian 그래프를 예쁘게 만들기 위한 링크 작업이 실제 제작보다 커지면 즉시 중단한다.
- worktree는 파일 충돌을 줄이지만 판단 충돌과 최종 병합 책임을 없애지 않는다.
- 행동 평가를 통과해도 실제 영상 콘텐츠 품질과 사용자 승인을 대신하지 않는다.
