## 1. 결론

이 프로젝트의 목적은 편집 경험을 원문으로 축적하는 것이 아니라, **사용자의 수동 생산 작업과 반복 지적을 줄이고 에이전트가 승인된 방향과 안전 경계 안에서 재현 가능한 영상 편집을 수행하게 하는 것**이다.

이번 7개 문서를 다시 분석한 결과, 개선의 중심은 다음 세 가지여야 한다.

1. 대화와 작업 기록에서 확인된 판단 기준을 **12개 이하의 조건형 운영 규칙**으로 압축한다.
2. `1차 구성 편집`과 후보 범위 내부를 실제 컷으로 다듬는 `2차 편집`을 분리하고, XML 생성 전에 의미 검수를 끝낸다.
3. 코드가 확실히 판정할 수 있는 구조 오류만 자동 차단하고, 공포 리듬·인과·공간 이동·발화 자연스러움 같은 의미 판단을 숫자로 가장하지 않는다.

기존 계획처럼 규칙·대형 validator·XML 생성기·스킬을 한꺼번에 만드는 방식은 채택하지 않는다. 규칙 재현 시험을 먼저 통과하고, 그다음 최소 구조 validator, 그다음 XML adapter 순서로 진행한다. 새 스킬과 채널 성향 owner는 두 번째 독립 영상에서도 재사용성이 확인될 때까지 보류한다.

## 3. 재검증으로 확정된 문제 구조

### 3.1 원문이 길어진 근본 원인

원문이 부족해서 실패한 것이 아니다. 요약 과정에서 조건·예외·판정 방법이 빠졌고, 그 결과 다음 작업에서 반대 의미로 확대 해석됐다.

- “발화 중간 절단 금지”가 “긴 자막 cue 전체 보존”으로 확대됐다.
- “반복 감정 제거”가 “감정 설명 제거”로 확대됐다.
- “지루한 뒷부분 압축”이 “기능 블록 통삭제”로 확대됐다.
- “자연스러운 공간 연결”이 고정 컷 개수 규칙으로 바뀌었다.
- 한 영상에서 측정한 밝기·RMS·길이가 전역 임계값 후보가 됐다.

따라서 해법은 원문을 활성 프로젝트에 계속 보존하는 것이 아니라, 규칙마다 `조건 / 행동 / 예외 / 검증`을 갖추고 짧은 재현 사례로 효과를 확인하는 것이다.

### 3.2 편집 실패의 공통 원인

| 실패 | 실제 원인 | 필요한 개선 |
|---|---|---|
| 도주 이유·문 통과·엘리베이터 접근 누락 | 무발화 화면을 저정보로 분류 | 발화 여부가 아니라 스파인 기능·상태 변화·공간 인과로 판정 |
| 후보 구간이 통파일처럼 길게 남음 | 이야기 블록 선택을 완성 컷으로 오해 | 1차 구성 편집 뒤 2차 microbeat 편집 의무화 |
| 말끝·다음 발화 조각 절단 | 자막 시각 또는 길이만으로 경계 판정 | 실제 오디오와 화면을 함께 검수 |
| 화면이 갑자기 튀는 문제를 대사 문제로 추론 | 사용자 증상을 방법으로 바꿈 | 화면·오디오 사실 확인 후 원인 확정 |
| 반복 구간 과삭제와 장기간 복원 | 압축량을 목표로 기능 블록 삭제 | 반복만 줄이고 첫 맥락·변화·회수는 유지 |
| MP4·분석 파일이 계속 늘어남 | 단계별 산출물 계약과 파일 예산 부재 | 요청된 최종 형식만 영구 생성 |
| 편집본을 후속 분석 입력으로 사용 | 원본 계보 규칙 부재 | 영구 증거와 XML은 원본 단일 계보 |
| 기술 검증 통과 후에도 사용자에게 결함 노출 | 구조 검사와 의미 검사를 혼동 | 기술 게이트와 편집 의미 게이트 분리 |

### 3.3 프로젝트 차원의 핵심 교훈

후보 사건을 찾는 분석과 실제 컷 편집은 다른 작업이다. 앞으로는 다음 네 층을 혼동하지 않아야 한다.

1. `1차 내용 분석`: 원본에 무엇이 있는지 찾는다.
2. `2차 상세 분석`: 선택 방향에 필요한 후보 범위와 근거를 정한다.
3. `1차 구성 편집`: 사건 블록의 순서와 대략 범위를 배열한다.
4. `2차 편집`: 후보 범위 내부를 정보·행동·반응·화면 상태·자연스러운 발화 절 단위로 실제 분할한다.

XML은 4번이 끝난 뒤 생성하는 전달 형식이다. 후보 블록을 XML clip 하나로 옮겼다고 편집이 완료된 것이 아니다.

## 4. 기존 제안의 채택·수정·기각

### 4.1 그대로 채택

- 규칙은 `조건 / 행동 / 예외 / 검증`을 모두 가진다.
- 사용자 발언을 `증상 / 제안 방법 / 수치`로 분해한다.
- 사용자가 직접 수정한 범위는 이전 승인을 무효화한다.
- 편집 결과의 기술 검증과 의미 검증을 분리한다.
- XML과 영구 분석 자료는 원본 미디어만 소스로 삼는다.
- 요청하지 않은 MP4·WAV·스크린샷·재전사본을 기본 생성하지 않는다.
- 후보 블록 내부를 2차 편집하며 긴 컷에는 유지 이유가 있어야 한다.
- 원문 없이 규칙만으로 판단 가능한 재현 시험을 채택 게이트로 둔다.

### 4.2 수정 후 채택

| 기존 제안 | 수정된 운영 기준 |
|---|---|
| 공간 전환마다 `발견→접근·통과→도착 반응` 중 둘 이상 | 시청자가 위치·행동·결과를 이해하는 **최소 인과 연결**을 유지한다. 고정 개수는 두지 않는다 |
| 접합 luma Δ35 초과 차단 | 밝기 급변은 진단 신호로 사용하고, 수치는 영상별 calibration 값으로만 기록한다 |
| 반복 사건 길이 단조 감소 | 반복은 진행 정보가 줄수록 압축하되, 클라이맥스·새 실패·새 학습은 길어질 수 있다 |
| 자막 cue 내부 컷 금지 | 자연스러운 호흡·절·자기정정·정보 단위에서는 가능하다. 음절·단어·조사·미완성 생각·다음 발화 파편만 차단한다 |
| 최신 지시도 자동 실행 근거가 아님 | 명확한 최신 지시는 우선한다. 결과·권한·보호 경계를 바꾸는 실질적 충돌만 확인한다 |
| 사용자 수정본에 빠진 기능은 모두 최소 복원 | 사용자 수정은 우선 보존한다. 명시된 스파인·지시와 충돌할 때만 잃는 것과 최소 선택지를 보고한다 |
| RMS·앞뒤 여유를 고정 차단값으로 사용 | 영상별 오디오 calibration을 거친 진단값으로만 사용한다. 실제 청취 판정을 대체하지 않는다 |

### 4.3 이번 개선에서 기각 또는 보류

- `git status`가 일반적으로 `index.lock`을 남긴다는 규칙: 현재 `index.lock`은 없으며 재현되지 않았다.
- 화면 이동 누락을 큰 원본 점프와 luma만으로 자동 판정: 정보 가치와 공간 인과를 안정적으로 추론하지 못한다.
- 10초 이상 컷, 컷당 35% 제거율, 어두운 추격 4~6초, 안도 1~3초를 전역 기준으로 사용: 단일 영상 calibration이다.
- 중간 RMS 배열을 유지 문서나 커밋 대상으로 보존: runtime cache는 재생성 가능하고 폐기 가능해야 한다.
- 채널 성향 owner 즉시 신설: 한 영상에서 나온 취향과 채널 불변 조건이 아직 분리되지 않았다.
- 새 영상 편집 스킬 즉시 생성: 계약과 도구가 두 번째 독립 영상에서 재사용되기 전에는 유지 비용이 더 크다.
- C01~C17 전체 validator 일괄 구현: 의미 판단을 숫자로 가장하고 구현 범위를 불필요하게 넓힌다.

## 5. 최종 개선 범위

4. 4단계 분석·편집 모델

8. 기존 Extension 회귀를 포함한 통합 검증
9. 단계별 커밋과 최종 보고·복기

- 오디오 gap과 의도적 원본 시간 역전의 명시적 예외
- 합성 fixture를 이용한 end-to-end XML 생성 시험

### 보류

- 실제 영상의 luma·RMS 자동 판정
- 자동 스파인 의미 판정
- 사용자 XML과 정본의 대규모 diff 도구

- 새 영상 편집 skill
- 실제 보호 영상으로 수행하는 acceptance test

보류 항목은 두 번째 독립 영상에서 같은 실패가 재현되거나 사용자가 exact 대상과 목적을 승인한 경우에만 새 계획으로 올린다.

## 7. 단계별 실행 계획

사용자가 이 계획을 승인하기 전에는 아래 단계를 실행하지 않는다. 승인 후에는 각 성공 게이트를 통과한 단계만 커밋하고 다음 단계로 자동 진행한다.

### 단계 0 — 분석 자료 외부 백업과 작업 경계 고정

목표:

- 현재 분석 입력 7개를 저장소 밖 한 폴더에 모아 보존한다.
- 프로젝트 개선물이 이 백업과 무관하게 작동할 수 있는 경계를 만든다.

작업:

1. 현재 7개 문서의 상대 경로·크기·SHA-256 manifest를 만든다.
2. 저장소 밖 새 백업 폴더에 7개 문서를 복사한다.
3. 원본과 백업의 파일 수·크기·SHA-256을 전건 비교한다.
4. 이 단계에서는 저장소 안 원본 7개를 아직 삭제하지 않는다.
5. 이후 운영 계약·코드·테스트에 백업 경로, 원문 링크, 보고서 의존성을 넣지 않는다.

검증:

- 입력 7개 = 백업 7개
- 크기 불일치 0
- SHA-256 불일치 0
- 백업 폴더가 저장소 밖에 있음

성공 게이트 G0:

- 위 네 조건을 모두 만족해야 단계 1로 진행한다.
- 외부 백업은 Git 커밋 대상이 아니므로 이 단계에는 커밋이 없다.

실패 시:

- 저장소 원본을 유지하고 개선 작업을 시작하지 않는다.

### 단계 1 — 영상 편집 운영 계약과 재현 사례

목표:

- 원문 없이도 같은 핵심 판단을 재현하는 단일 운영 계약을 만든다.
- 코드를 만들기 전에 규칙 자체의 효과를 검증한다.

- 수정 `extension/README.md`
- 현재 계획 보고서를 승인된 계획으로 함께 보존

작업:

1. 6절의 R01~R12를 `조건 / 행동 / 예외 / 검증` 형식으로 작성한다.
2. 네 작업 단계와 각 단계의 시작·종료 조건을 정의한다.

## 8. 커밋·Git 통제

- 현재 계획 보고 단계에서는 스테이징·커밋하지 않는다.
- 승인 후 각 단계는 exact path만 스테이징한다. `git add -A`를 사용하지 않는다.
- 현재 분석 원문 7개와 `inputs/`, `outputs/`는 어떤 커밋에도 포함하지 않는다.
- 단계 게이트를 통과하지 못한 변경은 커밋하지 않는다.
- 기존 사용자 변경과 단계 범위 밖 파일은 건드리지 않는다.
- 현재 브랜치를 유지하며 별도 요청 없이 branch 전환·push·PR을 하지 않는다.
- 같은 성공 게이트가 3회 연속 실패하면 현재 변경과 증거를 보존하고 방법을 바꾸거나 사용자에게 blocker를 보고한다.

예상 커밋:

1. 운영 계약·재현 게이트
2. timeline schema·validator
3. Premiere XML adapter
4. workflow acceptance·routing
5. 최종 보고·handoff

## 10. 성공의 최종 정의

이번 개선은 파일을 많이 만들거나 규칙 수를 늘렸다고 성공한 것이 아니다. 다음 상태가 모두 충족될 때 성공이다.

1. 다음 세션이 7개 원문 없이 편집 단계와 판단 기준을 설명할 수 있다.
2. 12개 재현 사례를 전부 같은 결론으로 판정한다.
3. 후보 범위와 실제 2차 편집을 혼동하지 않는다.
4. 발화·인과·상태·공간·반복 문제를 고정 숫자 하나로 대신하지 않는다.
5. 구조 오류는 XML 생성 전에 자동 차단된다.
6. XML은 원본 미디어만 참조하고 요청하지 않은 미디어를 만들지 않는다.
7. 운영 계약·코드·테스트는 외부 백업이 없어도 동작한다.
8. Core·보호 데이터·기존 사용자 변경은 침범하지 않는다.
9. 각 단계가 검증된 개별 커밋으로 남고 push는 없다.
10. 활성 프로젝트에는 압축된 정본과 최종 보고만 남고 세션 원문은 남지 않는다.

## 11. 승인 후 자동 진행 경계

사용자가 이 계획을 승인하면 단계 0부터 단계 5까지 순차 진행한다. 각 단계는 자체 성공 게이트를 통과한 경우에만 다음 단계로 넘어가며, 일반적인 구현 선택은 이 문서의 권장안으로 자동 결정한다.

다음 상황에서는 자동 진행을 멈추고 사용자에게 보고한다.

- 실제 `inputs/` 또는 `outputs/` 항목을 열어야 하는 경우
- `core/**` 변경이 필요해진 경우
- 이 계획에 열거되지 않은 파일의 삭제·이동이 필요한 경우
- 사용자 수정본과 명시된 최신 지시가 결과를 바꿀 정도로 충돌하는 경우
- 같은 게이트가 3회 연속 실패한 경우

현재는 계획 보고만 완료한 상태다. 개선 구현, 분석 원문 백업·정리, 커밋은 아직 시작하지 않았다.
