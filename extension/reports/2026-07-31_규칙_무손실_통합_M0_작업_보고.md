## 2026-07-31 범위 교정

사용자는 정리 대상을 ignored 파일이나 문서에 한정하지 않고 tracked·untracked·ignored, 백룸·개선 산출물, `outputs/`, `extension/data/`를 포함한 작업트리 전체로 확정했다. 모든 내용을 흡수하는 것이 아니라 이후 workflow에 재사용할 가치가 있는 내용만 기존 canonical owner에 우선 병합하고, 최종적으로 Git과 물리 workspace가 모두 설명 가능한 clean 상태가 되는 것이 목표다.

따라서 아래 점수와 수치는 이전 규칙·문서 슬라이스의 검증 evidence로만 유지한다. 당시 M4 readiness·다음 행동은 더 이상 active instruction이 아니며, 현재 실행 owner는 `extension/work/repository-consolidation/W0_REPOSITORY_WIDE_INVENTORY_AND_CLASSIFICATION.md`다.

## 결론

M0~M3의 실제 변경은 단계별 허용 범위와 대부분 일치한다. 규칙 의미 78개를 계보·owner에 연결했고, M1에서 최소 변경 계약을 고정했으며, M2는 계약한 Core 5경로와 Extension 1경로에만 의미 공백을 복원했다. M3는 시작 경로를 M4 하나로 전환하고 정확한 처분 후보를 준비했다. 각 단계 커밋은 삭제·보호 데이터·외부 상태를 건드리지 않았다.

그러나 전체 설계의 최종 의도까지 달성했다고 볼 수는 없다. 1차 목표인 역할 종료 문서 제거는 M4 exact 승인 전이라 실행되지 않았고, 활성 규칙 읽기 비용은 M0 기준보다 토큰 430개(4.41%) 증가해 “활성 규칙과 startup-required 문서의 읽기 비용이 증가하지 않는다”는 전체 성공 기준을 충족하지 못했다. startup-required 3문서는 정규화한 문자 수 기준 15.23% 감소했지만 활성 규칙 증가를 상쇄하지는 않는다.

기존 최종보고서는 M1~M4를 “미착수”로 기록해 실제 커밋과 불일치했다. 이 보고서에서 M0~M4의 실제 상태, 단계별 점수, 측정값, 미완료 조건을 교정했다.

### M2 exact 변경 확인

M2 커밋의 정책 변경은 설계한 다음 6개 owner로 한정됐다.

- `PROJECT_RULES.md`: 외부 입력을 검증 전 신뢰하지 않는 경계, 최소 필요 데이터·권한
- `core/rules/boundary-routing-and-dependency.md`: 새 interface/tool의 최소 성공 호출
- `core/rules/cross-validation.md`: 1차 자료 우선, 변동 주장·약한 출처 검증
- `core/rules/document-work.md`: 조건부 red-team, write 성공과 콘텐츠 증거·복구 분리
- `core/rules/file-extraction.md`: 과거 evidence의 제한적 exact read와 현재 권위 분리
- `extension/rules/video-editing-validation-and-delivery.md`: generated·parsed·tool-validated 상태 분리

검토 결과 역사 문장을 그대로 복제하거나 신규 활성 rule file을 만든 변경은 없었다. 다만 구조 테스트는 active phase route 변경을 검증했을 뿐, 위 8개 의미의 동작을 각각 자동 검증하지는 않는다. 의미 보존 판정은 현재 owner와 커밋 diff의 수동 대조에 의존한다.

## 발견한 불일치와 교정

1. 기존 최종보고서가 M1~M4를 미착수로 기록했다. 실제 커밋 기준으로 이 보고서를 통합 보고서로 다시 작성했다.
2. M1·M2·M3 closeout은 passed였지만 lifecycle은 `in_progress`, 다음 transition은 `pending`이었다. 후속 checkpoint가 존재하므로 각각 `passed`로 교정했다.
3. M4 entry가 M3 checkpoint만 기록했다. M4 준비 checkpoint `11a6031`을 추가했다.
4. M4 문서의 `ainoteBook` 재확인 문구는 실제 path `codex_G2_ainotebook_상태이전.md`와 불필요하게 충돌해 실제 철자 일치로 교정했다.
5. M3의 후보 inventory는 exact path는 있었지만 모든 후보의 size/hash 증거를 본문에 남기지 않았다. 이번 감사에서 22개 파일의 존재·크기·SHA-256·Git 추적 상태를 직접 확인했으며, 최종 보고에는 bundle별 크기와 추적 결과를 보존했다.
6. 전체 설계의 비증가 기준을 기존 보고서가 평가하지 않았다. 현재 재측정으로 rule-surface 증가를 실패 기준으로 명시했다.

## 잔여 위험과 다음 gate

- M4 exact 삭제 승인이 없으므로 어떤 후보도 삭제하지 않았다.
- 처분 전에 실행 가능한 active Markdown/file link와 startup/current-state dependency를 0으로 만들고, retained 비링크 path 표기는 역사·처분·Git 복구 evidence인지 분류해야 한다.
- 22개 파일의 현재 size·SHA-256이 승인 시점과 다르면 해당 path를 삭제하지 않고 재검증해야 한다.
- M2 의미 보존은 구조·route 테스트 외에 수동 semantic diff에 의존한다. 향후 테스트를 추가한다면 자연어 literal이 아니라 행동·구조를 검증해야 한다.
- 활성 규칙 비증가 기준은 미충족이다. 보존된 의미를 훼손하지 않는 상쇄 압축안은 별도 Core exact 승인·게이트 없이는 실행하지 않는다.
- M4 완료 뒤에만 실제 삭제 목록, orphan link 0, 회귀·maintenance 결과, 최종 M4 점수를 확정할 수 있다.

현재 다음 행동은 기존 M4 삭제 승인이 아니다. 새 W0에서 프로젝트 전역 inventory·분류를 완료한 뒤 재사용 후보는 W1, 처분 후보는 W3의 새 exact manifest로 넘긴다.
