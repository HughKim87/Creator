# 백룸 영상 편집 재개 계획

- 목적: 최신 Creator 규칙과 사용자 피드백을 기준으로 백룸 영상 편집을 안전하게 재개한다.
- 읽는 시점: 백룸 영상의 기획·컷 편집·XML 생성·검증을 시작하기 전.
- 책임: 작업 에이전트가 단계별 근거와 검증 상태를 기록하고, 사용자 승인 전에는 결과를 확정하지 않는다.
- 상태: historical. 2026-08-26 당시의 참고 자료이며 현재 편집본·후보·승인·다음 행동을 선언하지 않는다. 활성 상태는 루트 `SESSION_HANDOFF.md`만 소유한다.
- 관련 권위: `core/PROJECT_RULES.md`, `PROJECT_RULES.md`, 승인 후 확인한 실제 작업 상태, 사용자의 명시적 피드백.
- 보존/만료: 고유한 교정 근거가 활성 rule·handoff·Git history에 흡수되고 사용자가 정리를 승인하면 archive 또는 삭제 후보가 된다. 그 전에도 이 문서의 단계·파일명·후보 판정은 실행 지시로 사용하지 않는다.
- 당시 종료 조건: 기술 검증과 의미 검수를 통과한 편집본을 사용자가 최종 승인하고, source lineage와 결과 상태가 기록되어야 했다.

## 1. 작업 목표

백룸과 리미널 스페이스에 관심을 갖고 들어온 시청자가 공간의 특징과 플레이 경험을 자연스럽게 이해하면서, 김실버의 반응과 캐릭터를 끝까지 즐길 수 있는 영상으로 완성한다.

다음 두 축을 함께 살린다.

- 백룸 공간의 낯섦, 규칙, 탐색 과정과 사건의 인과관계
- 김실버의 공포 반응, 판단, 실수, 웃음의 완급과 캐릭터 변화

설명을 나열하거나 공포 반응만 모으지 않는다. 한 영상에서 전달할 중심 약속과 메시지는 하나로 좁히고, 장면이 그 의미를 직접 보여주도록 편집한다.

## 2. 당시 확인된 작업 경계

- 백룸 브랜치에는 최신 Creator 규칙이 반영되어 있다.
- approved/current 편집 revision과 현재 검수 후보는 없다. v19-r2는 app import 실패 artifact다.
- 과거 XML·타임라인·검증 결과는 근거 자료일 뿐, 자동으로 재사용할 기준본이 아니다.
- 구조 검증 통과, 실제 미디어 검증 통과, 편집 앱 검증 통과, 사용자 승인은 서로 다른 상태로 관리한다.
- 승인된 MP4·SRT·v18 XML과 상태 파일은 확인했지만, 어떤 결과도 `current`나 `approved`로 선언하지 않는다.
- 과거 XML의 측정 길이와 새 XML의 결과 길이는 목표 시간·상한·합격 기준으로 사용하지 않는다.

## 3. 사용자가 바로잡은 편집 방향

### 3.1 이야기와 소재

- 시청자가 기대한 백룸·리미널 스페이스의 공간성과 분위기를 충분히 보여준다.
- 관전할 때의 인상과 실제로 플레이할 때의 경험 차이가 장면에서 드러나야 한다.
- 여러 주제와 설명을 체크리스트처럼 모두 넣지 않는다.
- 긴 설명은 그 설명을 뒷받침하는 화면과 사건이 있을 때만 사용한다.
- 김실버의 반응을 단순 리액션 모음으로 소비하지 않고, 탐색과 사건의 원인·결과 속에 배치한다.
- 공포가 계속 같은 강도로 이어지지 않도록 웃음, 안도, 재긴장의 리듬을 만든다.

### 3.2 2차 편집과 미세 컷

초벌로 선택한 긴 구간을 그대로 쓰지 않고 다음 변화 지점에서 다시 나눈다.

- 새로운 정보가 등장하는 지점
- 행동이 시작되거나 끝나는 지점
- 반응과 감정이 변하는 지점
- 화면 상태나 공간이 변하는 지점
- 말의 자연스러운 절·호흡·자기수정 지점

고정된 몇 초 단위로 자르지 않는다. 사건, 감정, 공간 경험에 필요한 길이는 근거가 있으면 유지한다. 반대로 반복, 무의미한 대기, UI 조작 지연은 줄인다.

자막 구간 내부도 자연스러운 호흡과 의미 단위라면 자를 수 있지만, 음절·단어·조사·미완성 의미를 끊어서는 안 된다. 진입, 이동, 도착, 밝기 변화, 사건의 발생과 결과처럼 인과를 만드는 과정은 필요한 만큼 보존한다.

### 3.3 revision 운용

- 이야기 구조를 바꿀 때도 이미 잘 작동한 훅, 리듬, 코미디 타이밍을 무조건 초기화하지 않는다.
- 검증된 기준본에 필요한 변화만 더하는 `baseline + delta` 방식으로 진행한다.
- 콜드 오픈은 미래 장면을 사용할 수 있지만, 본편에서는 이유 없는 시간 역행이나 미래 장면 삽입을 피한다.
- 새 결과는 새 revision으로 만들고 기존 결과를 덮어쓰지 않는다.

### 3.4 검수 책임

- 사용자는 기본 결함을 처음 발견하는 사람이 아니라 편집 방향과 완성도를 판단하는 사람이어야 한다.
- 에이전트가 먼저 컷 경계, 음성 단절, 화면·대사 불일치, 시간 순서, 반복, 의미 전달을 검수한다.
- 수치나 구조 점수만으로 품질을 주장하지 않는다. 실제 연속 재생과 의미 검수가 필요하다.

## 4. 반복하지 말아야 할 문제

- 긴 원본 구간을 XML에 옮긴 뒤 이를 완성 편집처럼 취급하는 것
- 규칙 문서만 추가하고 생성기나 검증 게이트에는 반영하지 않는 것
- 구조상 유효한 XML을 시청 가능한 영상으로 오인하는 것
- A/B/C 같은 분리 calibration sequence를 한 편의 연속 결과처럼 제시하는 것
- 이야기 수정 때 기존의 좋은 편집 문법까지 전부 버리는 것
- 에이전트가 확인할 수 있는 결함을 사용자 검수 단계까지 넘기는 것
- 목적이 겹치는 revision, 도구, 문서를 계속 늘려 기준을 불명확하게 만드는 것
- 기술 검증, 의미 검수, 사용자 승인을 하나의 `통과` 상태로 합치는 것

## 5. 작업 계약

### 허용되는 작업

- 비보호 경로의 규칙, 계획, 코드, 보고서 확인
- 사용자가 정확히 승인한 보호 파일의 목적 제한 확인
- 기존 결과를 보존한 새 revision 작성
- 단계별 검증 결과와 실패 근거 기록

### 별도 승인 없이는 하지 않는 작업

- 보호 경로의 열거 또는 승인받지 않은 형제 파일 확인
- 기존 편집본·XML·보고서 덮어쓰기나 삭제
- MP4 생성 또는 대용량 미디어 처리
- `current`, 기술 검증 완료, 의미 검수 완료, 사용자 승인 상태의 임의 승격
- commit, push, branch 변경

## 6. 당시 실행 계획 — 비활성

아래 단계는 2026-08-26 당시의 설계 기록이며 현재 실행 순서가 아니다. 재개 시에는 루트 `SESSION_HANDOFF.md`와 활성 workflow 계약에서 exact state owner·baseline·approval을 다시 확인한다.

### 단계 0. 실제 상태 확인

먼저 아래 보호 파일만 정확한 경로로 확인할 승인을 요청한다.

- `outputs/SESSION_HANDOFF.md`: 중단 지점과 명시된 후보 revision 확인
- `outputs/WORKFLOW_STATE.json`: 워크플로 상태와 source 식별자 확인
- `outputs/07_edit_export/CURRENT.json`: 현재 포인터가 있다면 대상 revision과 검증 범위 확인

보호 경로 전체를 열거하지 않는다. 이 단계의 산출물은 source ID·fingerprint, 후보 revision, 파일 경로, 각 검증 상태를 분리한 상태표다.

**통과 조건:** 실제 파일 근거로 후보와 상태를 식별했으며, 모르는 항목은 `미확인`으로 남아 있다.

### 단계 1. source lineage와 기준본 결정

상태 파일이 정확히 가리키는 컷리스트, XML, 검증 결과만 추가 승인을 받아 확인한다. 각 후보를 다음 기준으로 구분한다.

- source lineage가 확인되는가
- 구조 검증을 통과했는가
- 실제 미디어를 연속 재생해 검증했는가
- 편집 앱에서 가져오기와 재생을 검증했는가
- 의미와 편집 방향을 검수했는가
- 사용자가 승인했는가

**통과 조건:** 재사용할 기준본 하나를 근거와 함께 선택하거나, 신뢰할 기준본이 없어 새로 구성해야 한다는 결론을 기록한다.

### 단계 2. 간결한 편집 브리프 확정

전체 편집 전에 다음 항목을 한 페이지 이내로 확정한다.

- 시청자에게 약속할 한 문장
- 영상이 전달할 중심 메시지 하나
- 김실버의 감정과 행동 변화
- 반드시 보여줄 공간·사건·반응
- 과감히 제외할 반복 설명과 약한 구간
- 각 주장에 대응하는 source 장면 근거

**통과 조건:** 하나의 중심 방향으로 설명할 수 있고, 장면 근거 없는 주장이 없다. 이 단계에서는 전체 편집을 생성하지 않는다.

### 단계 3. 단일 sequence 2차 편집

사용자의 최신 교정에 따라 A/B/C를 독립 sequence로 만들지 않는다. v18의 전체 장면 지도를 사용하되 반복 기능을 제거하고, 첫 진입부터 방송 종료까지 처음부터 끝까지 이어지는 sequence 하나를 새 revision으로 만든다.

초벌 선택은 같은 사건의 미세 분절과 발화 cue를 다시 검토한다. 고정 길이를 적용하지 않고 기존 결과를 덮어쓰지 않는다.

**통과 조건:** sequence가 하나이며 시간 순서·인과·공간 이동·캐릭터 변화가 연결되고, SRT cue 내부 위험 경계와 반복 기능이 기록돼 있다. v19-r2는 parser 기준을 충족했지만 Premiere import 실패로 이 단계를 통과하지 못했다.

### 단계 4. 기술 검증과 의미 검수

가능하고 승인된 범위에서 실제 미디어를 처음부터 끝까지 연속 재생하고, 편집 앱 가져오기와 타임라인 상태를 확인한다.

- 구조 검증 결과
- 미디어 재생 검증 결과
- 편집 앱 검증 결과
- 의미·리듬 검수 결과

네 상태를 별도로 기록한다. 실패한 후보는 `candidate`로 남기고 추천본으로 승격하지 않는다.

**통과 조건:** 단일 sequence 후보가 모든 적용 가능한 사전 검증을 통과했고, 남은 미확인 범위가 명시되어 있다.

### 단계 5. 사용자 방향 승인

사전 검증을 마친 추천본 하나를 제시한다. 사용자는 기본 결함 탐색이 아니라 다음을 판단한다.

- 백룸 영상으로서 기대한 분위기와 정보가 살아 있는가
- 김실버의 캐릭터와 반응이 자연스러운가
- 컷의 호흡과 이야기 방향이 원하는 수준인가

**통과 조건:** 승인 대상 revision과 사용자의 판단이 정확히 기록되어 있다. 수정 요청은 다음 revision의 delta로 정의한다.

### 단계 6. 피드백 delta revision

v19-r2의 실제 연속 재생과 사용자 검토에서 확인된 결함만 새 revision에 반영한다. 방향 변경이 생겨도 v19-r2를 덮어쓰지 않고 필요한 구간만 수정한다.

**통과 조건:** 변경 이유와 영향 구간이 특정되고, 변경 구간 검증과 전역 연속성 검증을 모두 통과했다.

### 단계 7. 최종 검증과 확정

전체 재생, 편집 앱 상태, 의미 전달, source lineage, 결과 파일 관계를 마지막으로 확인한다. 기술 상태와 사용자 승인 상태를 분리해 기록한다.

**통과 조건:** 사용자가 특정 revision을 최종 승인했고, 승인받은 경우에만 current 포인터나 후속 전달 상태를 갱신한다.

## 7. 성공 게이트

| 게이트 | 확인할 내용 | 실패 시 조치 |
|---|---|---|
| 상태 | 실제 source와 후보 revision 식별 | 추측하지 않고 미확인 유지 |
| 기획 | 한 가지 약속·메시지·캐릭터 변화 | 브리프 수정 |
| 단일 sequence 기술 | 컷 경계, 음성, 화면, 순서, 앱 호환 | 새 후보 revision 생성 |
| 단일 sequence 의미 | 공간성, 인과, 리듬, 캐릭터 | 편집 delta 재설계 |
| 사용자 방향 | 원하는 편집 방향과 완성도 | 피드백을 delta로 기록 |
| feedback delta | 승인·교정된 변경만 반영 | 영향 구간부터 재검증 |
| 최종 | 전체 재생, lineage, 기술 상태, 사용자 승인 | current로 승격하지 않음 |
