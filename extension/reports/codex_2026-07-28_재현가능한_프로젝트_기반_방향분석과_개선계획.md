# 재현 가능한 프로젝트 기반 방향 분석과 개선 계획

- 작성일: 2026-07-28
- 실행 계획 보완일: 2026-07-29
- 기준 revision: `07a26a3df3299aed1051eb8f007ef2d58036b9b9`
- 목적: 현재 규칙·계약·코드·테스트·성공·실패를 사용자가 원하는 장기 프로젝트 방향과 대조하고, 새 컴퓨터 재현성과 다른 도메인 이식성을 갖춘 개선 순서를 결정한다.
- 독자: 프로젝트 방향과 core 변경 범위를 승인하는 사용자, 승인된 개선을 설계·실행할 프로젝트 에이전트
- 상태: 선택적 `reference-evidence`. 방향 분석·과거 측정·대안의 근거만 제공하며 활성 설계·현재 상태·실행 권한·다음 행동을 소유하지 않는다.
- 산출물 범위: 이 보고서 1개
- 제외: 규칙·계약·코드 변경, 보호 `inputs/`·`outputs/` 접근, 실제 영상 품질 재검수, 외부 서비스 변경, 커밋·push

## 1. 결론

사용자가 원하는 것은 단순한 영상 자동화 저장소가 아니다.

> 검증된 규칙과 실행 시스템이 결합되어, 새 환경에서도 일정한 수준의 결과를 반복 생산하고, 경험을 다시 규칙으로 환류하면서도 스스로 복잡성을 통제하는 재사용 가능한 프로젝트 운영 기반이다.

현재 프로젝트는 이 방향의 중요한 절반을 이미 갖췄다.

- 상위 정책과 조건부 규칙의 계층
- core와 extension의 책임 분리
- 단일 owner와 Git 기반 역사 보존
- 보호 데이터·승인·복구 경계
- 결정론적 validator와 243개 Python 회귀
- 영상 제작 단계 조정 스킬과 단계별 승인 gate
- 해결 실패와 영상별 후보의 승격 기준
- 문서·schema·링크·UTF-8·보호 경로를 검사하는 maintenance

그러나 아직 “새 컴퓨터에서 clone한 뒤 같은 품질을 보장한다”고 말할 수는 없다.

1. 환경 버전·외부 의존성·bootstrap·lock이 없다.
2. clean clone의 임의 경로에서 Core 회귀 1개가 실제로 실패한다.
3. 현재 컴퓨터의 site-packages가 없으면 Pillow 의존 테스트가 import 단계에서 실패한다.
4. core schema와 구현에 현재 프로젝트 ID와 YouTube extension owner가 남아 있다.
5. 유지보수 검증은 강하지만 CI·hook·단일 실행 wrapper 없이 사람이 명령을 기억해야 한다.
6. 제작 workflow는 단계 계약과 validator를 갖췄지만 전체 실행은 아직 agent 지침과 외부 브라우저 상태에 크게 의존한다.
7. 실패 지식은 잘 보존하지만 성공 절차의 효과·수동 시간 절감·첫 결과 채택률을 실제 작업에서 측정하는 닫힌 환류가 없다.
8. 복잡성 비용은 문서량과 실행 시간만 측정하며, 규칙의 실제 사용·효과·수동 단계 감소를 평가하지 않는다.

따라서 다음 개선의 중심은 “규칙을 더 많이 만드는 것”이 아니다.

> **규칙 → 설계 → 실행 → 검증 → 결과 증거 → 규칙 개선 → 복잡성 감사**가 한 방향으로 연결되고, 이 고리 자체가 clean clone에서 재현되는 상태를 만드는 것이다.

## 2. 사용자가 원하는 방향의 정확한 해석

### 2.1 규칙 기반 품질 보장

규칙 문서만으로 품질을 보장할 수는 없다. 보장 가능한 규칙은 다음 중 하나와 연결되어야 한다.

- 코드가 판정할 수 있는 구조 규칙: validator와 자동 회귀
- 사람이 판정해야 하는 의미 규칙: 검수 protocol과 replay 사례
- 권한·안전 규칙: 실행 전 gate와 fail-closed 상태
- 결과 품질 규칙: acceptance fixture 또는 실제 사용자 승인 증거

따라서 규칙의 완성 단위는 문장이 아니라 다음 묶음이다.

`observable trigger + owner + required action + verification + failure behavior + evidence`

### 2.2 법치주의 국가 비유의 구조적 의미

| 비유 | 프로젝트의 대응 owner | 현재 상태 |
|---|---|---|
| 헌법 | `PROJECT_RULES.md` | 구축됨 |
| 법률·절차법 | `core/rules/`, `extension/rules/` | 구축됨 |
| 입법 절차 | rule governance와 candidate promotion | 구축됨, 계층 판정 보강됨 |
| 행정부 | workflow code·skills·agent orchestration | 부분 구축 |
| 사법·집행 | validator·tests·maintenance·approval gate | 강하지만 수동 실행 의존 |
| 판례 | canonical failures·replay·Git history | 실패 중심으로 구축됨 |
| 감사원·예산 심사 | 복잡성·효과·운영 비용 평가 | 부분 구축 |
| 지방자치 | domain extension | 영상 domain 구축 중 |
| 헌법 수출 | domain-neutral core 이식·conformance | 미완성 |

이 비유에서 가장 중요한 원칙은 법의 개수가 아니라 집행 가능성과 권력 분리다.

- core는 domain extension을 소유하지 않는다.
- extension은 core의 승인된 interface만 사용한다.
- 규칙은 자기 검증을 직접 소유하거나 상위 router가 선택한 검증 owner를 가진다.
- 자동화는 사용자 승인과 보호 경계를 우회하지 않는다.
- 감사 시스템은 시스템을 더 복잡하게 만드는 새 문서 체계가 아니라 기존 정본에서 계산되는 파생 결과여야 한다.

### 2.3 설계와 실행의 분리

모든 작업은 의미상 설계와 실행을 구분해야 한다. 그러나 모든 작업에 장문 계획 파일을 만들면 과거의 과도한 시스템으로 회귀한다.

권장 해석은 “두 단계는 항상 존재하지만 표현 비용은 작업 등급에 비례한다”이다.

| 작업 등급 | 설계 표현 | 실행 진입 조건 |
|---|---|---|
| quick | 대화·작업 메모 안의 목표, 금지, 완료 조건 | 되돌릴 수 있고 결과가 명확함 |
| standard | 명시적 작업 plan과 acceptance, 기본적으로 비영구 | 관련 owner와 검증 경로가 확정됨 |
| controlled | 승인 가능한 지속 plan 또는 구조화 work request | exact 범위·위험·승인·복구·성공 gate가 고정됨 |

공통 불변식은 다음과 같다.

1. 설계 단계가 결과 계약을 고정한다.
2. 실행 단계는 승인된 설계를 임의로 확대하지 않는다.
3. 실제 결과가 설계와 다르면 성공 처리하지 않고 차이를 기록한다.
4. 완료 뒤 재사용할 지식만 규칙·candidate·failure owner로 환류한다.

## 3. 현재 상태의 직접 측정

### 3.1 저장소와 검증 표면

| 항목 | 직접 측정 |
|---|---:|
| Core active rules / routes | 10 / 10 |
| Extension active rules / routes | 6 / 6 |
| Core Python tests | 129 |
| Extension Python tests | 114 |
| 별도 Node 회귀 | 1 suite 통과 |

현재 revision의 Core·Extension 전체 회귀와 maintenance는 현재 작업공간에서 통과했다. Node 회귀의 첫 실행은 sandbox가 상위 사용자 경로 `lstat`을 막아 실패했으나, 같은 명령을 권한 있는 환경에서 다시 실행해 통과했다. 이는 프로젝트 결함으로 계산하지 않는다.

### 3.2 clean clone 재현

현재 revision을 임시 경로에 `git clone --no-hardlinks`로 복제해 tracked 파일만 있는 상태에서 재측정했다.

| 검사 | 결과 | evidence label |
|---|---|---|
| `extension/.runtime` 존재 | 없음 | direct remeasurement |
| Extension 114개 회귀 | 전건 통과 | direct remeasurement, 현재 host의 site-packages 사용 |
| maintenance verify | 통과 | direct remeasurement |
| Core 129개 회귀 | 128 통과, 1 실패 | direct remeasurement |
| site-packages 차단 후 upload package test | `PIL` import 실패 | direct remeasurement |

Core 실패는 `RecordStore._for_test(ROOT)`가 임시 clone의 실제 repository root를 source tree로 인식하지 못한 것이다. 구현은 `store.py` 기준 `parents[2]`, 즉 `core/`를 source root로 계산한다. 저장소 자체가 temp 아래에 있으면 repository root가 “허용된 임시 fixture”로 오인된다.

이는 단순 테스트 문구 문제가 아니다.

- 현재 설치 경로에서는 통과한다.
- clone 위치가 바뀌면 안전 경계 회귀가 달라진다.
- 동일 commit·동일 Python에서 경로만으로 결과가 변한다.

따라서 현재 상태는 “현 컴퓨터 green”이지 “arbitrary-path clone green”이 아니다.

### 3.3 환경 재현성

현재 host는 Python `3.12.13`, Node `20.11.1`이다. 저장소에는 다음이 없다.

- Python 최소·권장 버전 선언
- Node 최소·권장 버전 선언
- `pyproject.toml` 또는 requirements lock
- `package.json`·Node test 진입점
- bootstrap command
- 단일 전체 verify wrapper
- CI workflow
- Git hook

외부 Python 의존은 최소 다음이 확인된다.

- Pillow: skill script 3개와 Extension test 2개
- faster-whisper: SRT skill과 전사 script

`faster-whisper`는 사용자 승인 후 Git 제외 runtime에 설치하도록 되어 있어 보호·비용 경계는 좋다. 그러나 새 컴퓨터에서 어떤 버전을 설치해야 기존 품질과 호환되는지는 고정되어 있지 않다.

### 3.4 core 이식성

core는 개념적으로 domain-neutral이지만 machine interface에는 현재 프로젝트 결합이 남아 있다.

- 11개 core schema·contract 파일이 `$id`에 `urn:kim-silver-youtube`를 사용한다.
- `core/src/file_data/document_data.py`가 YouTube extension schema·example 3개와 그 owner를 직접 등록한다.
- core code·contract 10개가 고정된 `extension/data` 저장 경로를 전제로 한다.

`extension/data`는 모든 프로젝트가 같은 core/extension 골격을 사용한다면 공통 storage interface가 될 수 있다. 반면 YouTube artifact owner를 core 구현이 소유하는 방향은 현재 boundary 원칙과 충돌한다.

> Extension이 Core API를 사용하는 것은 허용되지만, Core가 특정 extension artifact 목록을 소유하면 새로운 game extension을 추가할 때마다 Core를 수정해야 한다.

이는 core 이식 전에 제거해야 할 reverse dependency다.

## 4. 과거 성공·실패에서 확인된 설계 원칙

### 4.1 유지해야 할 성공 패턴

1. **규칙 replay를 코드보다 먼저 검증**
   - 영상 편집 개선은 R01~R12와 TC01~TC12를 먼저 고정한 뒤 validator와 XML adapter를 만들었다.
   - 결과적으로 구조 자동화와 의미 판단의 경계를 보존했다.

2. **작은 수직 acceptance**
   - 보호 데이터 없는 timeline fixture에서 validator → XML까지 연결해 실제 실행 경로를 검증했다.
   - 단위 기능 수보다 사용자 결과에 가까운 한 경로를 먼저 닫는 방식이 효과적이었다.

3. **결정론적 구조 검사와 인간 의미 검수의 분리**
   - frame·track·hash·source lineage는 코드가 검사하고, 스파인·리듬·발화 자연스러움은 의미 gate가 소유했다.
   - 정량 proxy가 창작 판단을 대체하지 않았다.

4. **단일 owner와 Git 역사**
   - 상태·승인·규칙·실패 owner를 하나로 줄이고 완료 상세를 Git으로 이동하면서 startup context와 drift를 줄였다.

5. **실패에서 조건·예외·검증을 추출**
   - 보호 경로, 원자 쓰기, 문서 drift, 권한 오해, Windows text 경계가 재사용 가능한 기반 지식으로 정리됐다.

6. **단계 gate 뒤에만 다음 mutation**
   - 문서 계약 → schema → 구현 → acceptance 순서를 사용한 변경은 복구와 원인 판정을 쉽게 했다.

### 4.2 반복하지 말아야 할 실패 패턴

1. **기반 완성을 사용자 결과 완성으로 간주**
   - 내부 계약·CLI·문서가 늘었지만 실제 제작 흐름이 부족했던 시기가 있었다.

2. **모든 작업에 장문 계획·보고서·다중 검증 부과**
   - 500줄 이상 plan과 중복 보고가 정본을 흐리고 탐색 비용을 늘렸다.

3. **같은 상태와 지식을 여러 표현으로 보존**
   - handoff·보고서·record·projection이 같은 사실을 소유하며 drift가 발생했다.

4. **에이전트 제안과 사용자 권위 혼동**
   - 보고서나 첨부 대화의 제안을 승인된 정책처럼 실행한 재발이 있었다.

5. **현재 실행 환경을 보편 환경으로 가정**
   - Python path, 인코딩, cache, fixture 구조, sandbox 권한 차이가 실제 코드 결함과 섞였다.
   - 이번 clean-clone 경로 실패와 미고정 Pillow 의존도 같은 계열이다.

6. **규칙 수나 시스템 크기를 성과로 사용**
   - 사용자의 수동 시간·재작업·채택률 대신 문서·기능 수가 완성도의 대리 지표가 됐다.

## 5. 목표 아키텍처

### 5.1 세 계층

#### Root composition

프로젝트 정체성, startup, 환경 요구, 활성 domain, core version, 전체 verify 진입점을 소유한다. Root는 core와 extension을 조합하지만 세부 규칙 본문을 복제하지 않는다.

#### Portable Core

다른 프로젝트에서도 내용 변경 없이 사용할 수 있는 기반만 소유한다.

- 권한·상태·기록·지식·규칙·검증 계약
- 설계→실행 phase invariant
- domain-neutral storage·artifact interface
- clean-clone conformance
- 규칙·복잡성·효과 감사 framework
- 버전과 compatibility contract

Core의 성공 조건은 “YouTube 프로젝트에서 통과”가 아니라 다음이다.

> 빈 extension과 임의의 합성 extension 양쪽에서 같은 conformance를 통과하고, core/src와 core/schemas에 domain identity가 없다.

#### Domain Extension

영상·게임 같은 domain별 결과 계약과 adapter를 소유한다.

- domain rules와 replay
- domain schema·workflow·skill
- 외부 서비스 adapter
- protected input/output contract
- 실제 작업 KPI와 candidate

Extension은 Core interface를 사용할 수 있지만 Core owner registry를 수정하게 만들면 안 된다.

### 5.2 품질 보장 계층

| Level | 보장 대상 | 실행 위치 |
|---|---|---|
| Q0 | encoding·link·schema·routing·보호 경로 | maintenance |
| Q1 | function·state·validator 불변식 | unit tests |
| Q2 | domain synthetic workflow | vertical acceptance |
| Q3 | arbitrary-path clean clone·bootstrap | clone conformance |
| Q4 | 외부 도구·계정 capability | preflight, `ready / needs_user / unavailable` |
| Q5 | 실제 결과의 의미·사용자 채택 | approval와 production metrics |

낮은 단계 통과가 높은 단계 통과를 의미하지 않는다. Q0~Q3은 자동화할 수 있고, Q4는 환경별로 fail-closed 판정하며, Q5는 사용자 결과 증거가 필요하다.

### 5.3 자동화 경계

자동화의 목표는 승인 제거가 아니라 판단 가능한 단계를 기계가 반복 수행하게 하는 것이다.

- 자동 진행 가능: 환경 검사, schema, hash, 상태 전이, deterministic transform, test, archive plan
- agent 진행 가능: 자료 해석, 후보 생성, 의미 검수, 실패 복구
- 사용자 owner 유지: 창작 방향, 보호 데이터 범위, 외부 비용·게시, 결과 승인

새 컴퓨터에서는 계정·쿠키·Chrome profile을 clone하지 않는다. 대신 bootstrap 뒤 capability preflight가 필요한 사용자 연결만 정확히 보고해야 한다.

## 6. 설계→실행→학습 운영 모델

### 6.1 설계 단계의 최소 계약

모든 실행은 다음 여섯 항목을 먼저 고정한다.

1. desired outcome
2. exact inputs와 보호 경계
3. outputs와 artifact budget
4. 적용 owner와 금지 범위
5. acceptance와 recovery
6. agent 자동 진행 범위와 사용자 gate

Controlled work는 설계 fingerprint를 만들고 실행 중 의미가 바뀌면 기존 설계를 무효화해야 한다. Quick·standard work는 같은 필드를 더 짧게 표현하되 새 지속 문서를 기본 생성하지 않는다.

### 6.2 실행 단계

실행은 설계의 output contract와 gate를 읽고 다음 한 단계만 수행한다.

`next step 선택 → mutation → 직접 검증 → 상태 전이 → 다음 step`

실패 시:

- 같은 방법을 무한 반복하지 않는다.
- 설계 결함, 환경 결함, 구현 결함, 외부 blocker를 분리한다.
- 승인 범위를 넓히지 않는다.
- 복구 뒤에도 같은 acceptance를 다시 실행한다.

### 6.3 학습 단계

완료 뒤 모든 로그를 보존하지 않고 다음만 분류한다.

| 관찰 | 처리 |
|---|---|
| 기존 규칙이 결함을 예방 | 규칙 효과 evidence만 집계 |
| 기존 규칙이 결과를 방해 | owner의 조건·예외 보강 후보 |
| 한 작업의 새 판단 | domain candidate |
| 독립 작업에서 반복된 성공 절차 | 기존 active owner 보강 검토 |
| 원인·해결·검증된 재사용 실패 | canonical failure owner |
| task-specific 수치·파일·승인 | task evidence에 유지 |
| 완료 명령·과정 | Git 또는 disposable work history |

성공 사례도 실패 사례와 마찬가지로 “무엇이 잘됐는가”가 아니라 다음 형태로 추출해야 한다.

`적용 조건 / 사용한 절차 / 비교 기준 / 결과 증거 / 재현 범위 / 부작용`

## 7. 복잡성 자기 통제

### 7.1 현재 강점

- lowest sufficient task class
- artifact budget
- active information single owner
- rule candidate promotion gate
- completed detail의 Git 이전
- maintenance의 문서량·실행 시간 측정

### 7.2 추가해야 할 감사 질문

새 규칙·자동화·계약을 만들기 전에 다음을 계산한다.

1. 기존 owner로 해결할 수 없는 독립 trigger가 있는가.
2. 줄이는 수동 단계·오류·재작업은 무엇인가.
3. 추가되는 읽기·승인·설정·테스트 비용은 무엇인가.
4. 사용되지 않을 때 제거·대체할 수 있는가.
5. 자동 검증 또는 replay가 있는가.
6. 실제 작업에서 효과를 관측할 수 있는가.

### 7.3 권장 complexity metrics

처음부터 강제 임계값을 만들지 말고 baseline을 먼저 쌓는다.

- clone-to-green 시간
- bootstrap 사용자 행동 수
- 전체 verify 시간과 실패 원인 분포
- startup 필수 문자 수
- 작업당 읽은 active rule 수
- 작업당 생성한 지속 artifact 수
- 작업당 사용자 승인 대기 횟수
- 수동 단계와 자동 단계 수
- 첫 결과 채택률과 재작업 횟수
- 규칙별 trigger·예방 결함·오탐 횟수
- 후보→active 승격과 active→retired 건수

복잡성 감사 결과는 새 정본 보고서로 누적하지 않는다. 기존 owner와 실행 데이터에서 계산되는 비영구 report로 만들고, 실제 정책 변경만 canonical owner에 반영한다.

### 7.4 자동화 채택 gate

자동화는 다음을 모두 만족할 때만 유지한다.

- 반복 작업에서 실제 수동 단계 또는 결함을 줄인다.
- 실패 시 원인과 recovery가 보인다.
- 보호·승인 경계를 줄이지 않는다.
- clean clone에서 설치·검증할 수 있다.
- 유지 비용이 절감 효과보다 작다.

실제 evidence가 없는 자동화는 candidate이며, “미래에 유용할 것 같다”는 이유만으로 core에 넣지 않는다.

## 8. 단계별 개선 계획

### M0 — 기준과 목표 계약 고정

- 우선순위: P0
- 목표: 구현 전에 “재현 가능”과 “일정 품질”의 측정 가능한 의미를 확정한다.

설계:

- clean clone, 품질 level Q0~Q5, core portability, automation effectiveness의 success gate를 승인한다.
- 새 컴퓨터에서 자동 설치할 것과 사용자에게 요구할 외부 capability를 분리한다.
- 현재 test·문서·규칙·runtime baseline을 한 번 측정한다.

성공 gate:

- clone-to-green, deterministic gate, protected/external gate, 실제 결과 KPI의 owner가 각각 하나다.
- 이후 단계가 이 기준을 바꾸려면 설계 변경으로 처리한다.

### M1 — Fresh Clone Contract와 Core 순수성

- 우선순위: P0
- 목표: 임의 경로의 tracked checkout에서 기반 검증을 재현하고 Core의 domain reverse dependency를 제거한다.

예정 범위:

1. Python·Node 버전과 의존성을 선언하고 lock한다.
2. bootstrap과 single verify 진입점을 만든다.
3. temp 아래 clean clone에서 실패하는 isolated-write root 판정을 고친다.
4. `urn:kim-silver-youtube`를 domain-neutral identifier 또는 project-injected namespace로 교체한다.
5. YouTube artifact owner registry를 core에서 extension owner로 이동하거나 등록 interface로 역전한다.
6. 고정 `extension/data`를 명시된 neutral storage interface로 만들고 필요하면 root composition에서 주입한다.
7. 빈 extension fixture와 arbitrary-path clone conformance를 추가한다.

성공 gate:

- 임의 ASCII·한글·공백 경로 clone에서 bootstrap 후 Q0~Q3 전건 통과
- Git 제외 runtime이 없어도 bootstrap이 필요한 상태를 정확히 만든다.
- Core code/schema의 project·YouTube identity 0건
- Core가 extension artifact owner를 직접 열거하는 항목 0건
- 기존 영상 extension 전체 회귀 유지

중단 조건:

- 외부 계정·보호 데이터 없이는 검증할 수 없는 항목을 Q0~Q3 필수 조건에 넣으려는 경우
- dependency lock이 현재 사용하지 않는 대형 runtime까지 강제 설치하는 경우

### M2 — 설계·실행 phase contract

- 우선순위: P0
- 목표: 모든 작업이 결과 계약을 먼저 고정하되 작은 작업을 문서 과잉으로 만들지 않는다.

예정 범위:

- work request 또는 task contract에 `design / execution / verification / learning` phase를 표현한다.
- 설계 fingerprint, output contract, acceptance, autonomy, approval gate를 구조화한다.
- quick·standard·controlled의 표현 비용 차이를 규칙과 회귀로 고정한다.
- 사용자 교정 시 design invalidation과 재승인 범위를 검증한다.

성공 gate:

- 실행 mutation은 ready design 없이 시작할 수 없다.
- quick 작업에는 새 plan file이 자동 생성되지 않는다.
- controlled 작업의 범위·성공 gate 변경은 기존 design을 무효화한다.
- 완료 뒤 task detail이 startup 문서에 누적되지 않는다.

### M3 — 자동 집행과 단일 품질 gate

- 우선순위: P1
- 목표: 사람이 명령을 기억하지 않아도 비보호 결정론적 품질 검사가 항상 실행된다.

예정 범위:

성공 gate:

- clean checkout에서 한 명령으로 Q0~Q3 결과를 재현

### M4 — 제작 workflow의 실행 엔진화

성공 gate:

- 합성 job이 design → research fixture → video fixture → captions → title package → upload package를 같은 state machine으로 통과

- 중단 뒤 이미 검증된 단계를 재실행하지 않음

예정 범위:

## 11. 최종 성공 정의

이 방향의 프로젝트 기반은 다음이 모두 참일 때 완성됐다고 판정한다.

1. 새 컴퓨터의 arbitrary path clone에서 환경 요구가 명확하고 bootstrap이 재현된다.
2. 한 명령이 보호·외부 데이터 없이 Core·Extension의 Q0~Q3을 검증한다.
3. 외부 capability가 없으면 품질을 낮춰 성공하지 않고 정확히 `needs_user` 또는 `unavailable`로 멈춘다.
4. 모든 작업은 크기에 맞는 설계 계약을 가진 뒤 실행된다.
5. 구조 품질은 자동 gate, 의미 품질은 replay·검수·사용자 승인으로 보장된다.
6. 실제 작업 결과가 시간 절감·채택·재작업 지표로 측정된다.
7. 성공·실패가 기존 owner로 환류되고 task-specific 정보는 규칙으로 오염되지 않는다.
8. 새 규칙·자동화는 효과와 유지 비용을 함께 검증한다.
9. Core는 특정 domain identity와 artifact owner를 소유하지 않는다.
10. 동일 Core revision이 영상과 game extension에서 수정 없이 conformance를 통과한다.

### 역사적 실행 범위와 승인 경계

### 12.1 사용자의 장기 의도

다음 세션은 아래 목적을 기능 목록보다 우선한다.

1. 새로운 컴퓨터의 clone에서도 일정한 결과 품질을 재현한다.
2. 규칙을 실행·검증 가능한 gate로 연결한다.
3. 모든 작업을 크기에 맞는 설계와 실행 단계로 구분한다.
4. 성공·실패를 다음 작업의 간결한 행동으로 환류한다.
5. 시스템이 스스로 복잡성·과잉 자동화·중복 owner를 검사한다.
6. 영상 프로젝트에서 검증한 domain-neutral Core를 추후 게임 개발 프로젝트에 이식한다.

이 목적은 “특정 영상 하나를 완성”하거나 “규칙·문서 수를 늘림”으로 대체할 수 없다.

### 13.5 M1 구현 순서 — 별도 exact core 승인 후에만 사용

#### S1 — 환경과 검증 진입점

- runtime version과 dependency group을 고정한다.
- core-only, extension deterministic, optional external dependency를 분리한다.
- bootstrap dry-run 또는 preflight가 설치·외부 계정 필요 상태를 구분하게 한다.

Gate:

- 새 checkout에서 필요한 설치와 사용자 행동이 추측 없이 표시된다.
- faster-whisper·모델·Chrome profile을 기본 필수 dependency로 강제하지 않는다.

#### S2 — arbitrary-path 안전 회귀

- clean-clone root 판정 실패의 source-root 계산을 repository identity 기준으로 수정한다.
- 일반 temp fixture와 temp 아래 실제 clone을 서로 구분한다.

Gate:

- 현재 workspace와 임의 temp clone에서 Core 회귀 전건 통과
- test-only write capability가 실제 repository root를 계속 거부
- isolated temp fixture write는 계속 허용

#### S3 — project namespace와 storage interface

- 현재 project-specific URN의 compatibility·migration 방식을 먼저 고정한다.
- 기존 schema reference를 조용히 깨뜨리지 않는다.
- storage path가 convention인지 configurable interface인지 한 owner가 결정하게 한다.

Gate:

- Core code/schema의 project identity 0건 또는 승인된 compatibility alias만 존재
- 기존 Core·Extension fixture와 artifact semantic drift 0

#### S4 — artifact registry 의존 방향 교정

- Core의 YouTube artifact 직접 목록을 제거한다.
- Extension이 foundation verifier에 domain artifact contract를 제공하는 일방향 interface를 사용한다.

Gate:

- Core가 YouTube path·owner를 알지 않음
- Extension artifact drift 검증은 유지
- 빈 extension conformance 통과

#### S5 — single verify와 CI

- local과 CI가 같은 명령을 사용한다.
- Python·Node·maintenance·clean-clone을 한 결과로 집계한다.
- protected·browser·유료·사용자 승인 gate는 CI에서 실행하지 않는다.

Gate:

- tracked checkout에서 Q0~Q3 한 명령 통과
- 실패 종류와 복구 행동이 구분됨
- CI 부재나 외부 capability 부재를 품질 통과로 오인하지 않음

각 stage는 관련 gate를 통과한 경우에만 다음 stage로 이동한다. 사용자가 commit을 별도로 요청하지 않으면 stage 완료가 commit 권한을 뜻하지 않는다.
