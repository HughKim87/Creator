### 아직 검증되지 않은 가설

- 환생·이전 캐릭터 동행이 기존 RPG 시청자에게 흥미로운 차이로 받아들여질 것이라는 기획 판단.
- 현재 게임 화면을 짧게 보여주는 편이 상세한 개발 과정 설명보다 첫 영상의 제작 동기를 더 잘 전달할 것이라는 예상.
- 해당 게임이 실제 플레이어에게 과거의 즐거움을 줄 것이라는 목표. 타인 플레이 테스트·시청 반응·유지율로 확인한 사실이 아니다.

개발에 쓰는 생성형 AI와 게임 안 NPC의 행동 AI도 구분한다. 이 기록으로 NPC가 생성형 모델을 호출해 생각한다고 주장하지 않는다.

## 2. 자료가 구체적으로 남은 개발 에피소드: 걷는 네 장면을 직접 고르다

### 실제 대화에서 확인된 전환

‘캐릭터 모션 과장 방향 분석’의 시작 요청에는 공격할 때 팔을 크게 휘두르고, 걸을 때 발을 크게 내딛는 모션을 원한다는 설명이 있다.

후속 발화에서 사용자는 다음과 같이 말했다.

> “아니 계속 개선할수있다고 말만하고 계속 개선이 안되고있잖아 수십번은 다시 만든거같은데”

이는 반복 작업에 대한 사용자의 체감과 불만이다. **실제 생성 횟수가 수십 회였다는 계측값으로 사용하지 않는다.**

이후 사용자는 다음 방향을 제안했다.

> “이번세션에서 생성한 결과물들중에서 하나하나 한장면씩 고르다보면 괜찮은 결과물이 만들어질수있을것 같아.”

그리고 기존 그림을 직접 선택하고 GIF로 조합할 HTML 도구를 요청했다. 처음에는 검토만 요청했고, 다음 발화에서 기사 걷기 리소스로 도구 제작을 요청했다. 순서를 바꾸어 AI가 먼저 완성한 해결책처럼 소개하지 않는다.

### 프로젝트 자료에서 확인한 것

- 현재 [기사 걷기 조합실](</D:/AI Agent/GitHub/Chronella/Art/Generated/SlenderV3/FrameSelector/index.html>) HTML에는 방향 선택, 후보 선택, 4개 프레임 슬롯, 재생, 순서·위치 조정, 이전 프레임 겹쳐 보기, GIF·PNG 내보내기 UI가 있다. 이번에는 소스를 읽었으며 브라우저에서 도구를 조작하지 않았다.
- [현재 상태](</D:/AI Agent/GitHub/Chronella/SESSION_HANDOFF.md:18>)는 8방향 후보 320장면과 방향 미분류 연구 81장면을 모았다고 기록한다. 이것을 ‘서로 다른 401장의 새 그림을 이번에 생성했다’고 바꾸지 않는다.
- 같은 문서는 V6 걷기의 N/S는 사용자에게 괜찮다는 피드백을 받았고, 나머지 6방향은 발 교대로 반려되었다고 기록한다. 전체 방향의 완성·승인을 주장하지 않는다.
- 최신 사용자 GIF에서 추출한 [발 비교 이미지](</D:/AI Agent/GitHub/Chronella/Art/Generated/SlenderV3/FrameSelector/Analysis/UserWalkFeet-20261026/user-feet.png>)와 [기존 남쪽 발 이미지](</D:/AI Agent/GitHub/Chronella/Art/Generated/SlenderV3/FrameSelector/Analysis/UserWalkFeet-20261026/assistant-s-feet.png>)를 직접 보았다. 사용자 조합에서는 발을 높이 넘기는 자세와 지지하는 자세의 차이가 더 크게 보인다. 이는 정지 프레임에 대한 관찰이다.
- 측정 JSON과 해당 세션의 답변은 사용자 GIF의 발 영역이 남쪽 R5 4번→R5 1번→R2 2번→R5 3번과 가장 가깝다고 보고한다. 이번 조사에서 픽셀 비교를 재계산하지 않았다. 영상에는 R번호·픽셀값보다 네 자세가 이어지는 화면을 보여주는 편이 이해하기 쉽다.
- **조합 도구와 이미지 연구 결과는 게임 적용 완료가 아니다.** 현재 상태와 HTML의 안내 모두 새 이미지 생성·게임 적용 없이 기존 자료를 보존한 범위임을 밝힌다.

### 영상 자료로 쓸 수 있는 이유와 한계

‘캐릭터가 걷는다’는 것은 개발 경험이 없어도 판단할 수 있다. 문제→반복 시도→김실버의 판단 전환→직접 선택한 결과가 있어 AI와 작업하는 실제 과정을 보여준다. 동시에 옛 RPG의 느낌을 되찾고 싶다는 동기를 작은 화면 차이와 연결할 수 있다. 그러나 이것은 이해 가능한 자료라는 뜻이며, 기존 시청자가 오래 보고 싶어 하는 주제라는 입증은 아니다. 첫 편에서 제작 방법을 길게 설명하는 우선순위는 §9 재검토로 낮췄다.

이 에피소드의 도착점은 완벽한 걷기 완성이 아니다. **기존 결과물에서 원하는 움직임을 고르는 방식으로 바꿨고, 아직 남은 방향을 다듬는 중**이라는 사실까지다.

### 대본에 넣을 발화 초안 — 약 60~90초

> 사냥하는 모습을 만들다 보니까, 캐릭터가 움직이는 것도 계속 보게 되더라고요.
>
> 제가 원한 건 공격할 때 팔을 크게 쓰고, 걸을 때도 발을 좀 더 확실하게 내딛는 모습이었습니다.
>
> 그런데 그림을 다시 만들어도 제가 원하는 걷기가 계속 안 나왔어요. 네 장이 있다고 해서 자연스럽게 걷는 건 아니더라고요.
>
> 그래서 방법을 바꿨습니다. 이미 나온 그림 중에서 쓸 만한 장면을 제가 직접 골라보자고요.
>
> 이렇게 네 칸에 그림을 골라 넣고, 순서를 바꾸고, 재생해보는 도구를 만들었습니다.
>
> 제가 조합한 쪽은 이겁니다. 어느 발이 바닥을 딛고, 어느 발이 넘어가는지 보시면 차이가 조금 더 잘 보이실 거예요.
>
> 아직 전 방향이 끝난 건 아닙니다. 이건 지금 다듬고 있는 걷기 후보예요. 오늘 보여드리는 게임 플레이와는 구분해서 봐주세요.

본인의 체감과 맞는 표현을 사용한다. 도구 화면은 `기사 걷기 조합 도구`, 프레임 비교는 `아트 제작 중 · 게임 적용 전`이라고 표시한다. 도구 조작을 새로 촬영하면 당시 최초 선택을 그대로 재현한 것처럼 소개하지 않고 현재 조합 시연으로 쓴다.

## 3. 보조 에피소드: 동료가 포탈을 막았다

### 직접 확인한 사용자 제보와 선택

‘Continue I3 island map’에서 사용자는 포탈 자리에 사람이 죽으면 클릭과 이동이 안 된다며, 서 있을 수 없게 하거나 1칸 대신 4칸으로 넓히는 방법을 제안했다.

이후 사용자가 **포탈 2×2 확대, 쓰러진 NPC의 통행·클릭 방해 제거, 포탈 위 대기 방지, 기존 저장에서도 해결**하도록 지시했다. 세션 완료 보고와 현재 상태에는 N6 구현·자동검증 완료가 기록되어 있다.

### 대본에 쓸 발화 초안 — 약 25~40초

> 직접 해보면서 예상 못 한 문제도 나왔습니다. 포탈 자리에 NPC가 쓰러지니까 제가 이동도 못 하고, 클릭도 잘 안 되는 상황이 생겼어요.
>
> 그래서 통로를 네 칸으로 넓히고, 쓰러진 캐릭터가 통행과 클릭을 막지 않도록 수정했습니다.
>
> 이런 건 그냥 기능 목록만 봤을 때는 잘 안 보이더라고요. 제가 직접 돌아다니면서 계속 확인하고 있습니다.

위 두 번째 문장은 프로젝트에서 수정 완료가 보고된 사실을 설명할 수는 있으나, 이번 조사에서 현재 빌드의 통과 장면을 확보한 것은 아니다. 촬영 때 실제로 통과되는지 확인한다.

### 필요한 화면과 현재 공백

가장 좋은 화면은 과거 막힘 녹화→실제 요청 일부→현재 포탈 통과다. **과거 버그 녹화가 존재하는지는 확인하지 못했다.** 없으면 제보 문장과 단순 위치 표시로 상황을 설명하고 현재 통과 장면을 촬영한다. 게임을 일부러 망가뜨리거나 사용자 저장을 바꾸어 재현하지 않는다. 이미지로 설명하면 `당시 상황 설명`이라고 표시한다.

걷기 에피소드와 둘 다 길게 쓰면 본편 사냥이 밀린다. 첫 편에서는 걷기를 주 에피소드로, 포탈은 짧게 넣거나 후속 편으로 보류한다.

## 4. 게임의 독자성을 보여줄 장면: 과거의 내가 NPC로 남는다

[기록관 spec S44](</D:/AI Agent/GitHub/Chronella/Docs/Design/specs/02_ROSTER.md:29>)에는 실제 플레이했던 과거 용사가 성장·스킬·장비·자산을 지닌 채 다음 회차에 배치되고, 파티 영입 후 공격·스킬·성장을 이어가는 통합 상태가 기록되어 있다. [NPC spec](</D:/AI Agent/GitHub/Chronella/Docs/Design/specs/06_AI_PARTY.md>)에는 동료 영입과 자율 주민의 실제 필드 사냥·귀환 구조가 있다.

이것은 단순히 원작의 전투를 닮게 만드는 것 외에 Chronella만의 질문을 만들 수 있다.

> 혼자 하는 게임인데, 예전에 키웠던 캐릭터를 다음에 동료로 만나면 어떨까?

**현재 저장과 빌드에서 확인하고 촬영할 수 있을 때만** 다음 소개를 쓴다.

> 이 게임에는 제가 키웠던 캐릭터가 다음 회차에 NPC로 남는 구조도 있습니다. 이런 식으로 예전에 키우던 캐릭터를 다시 만나서 함께 사냥할 수 있어요.

새로 실행을 확인하지 않았으므로 실제 장면 없이 ‘완벽하게 작동한다’고 말하지 않는다. 화면은 기록관의 이름·직업·장비 이력→같은 인물의 다음 회차 배치→실제 동행 사냥이 연결되어야 한다. 개발용 임의 NPC를 실제로 키운 캐릭터인 것처럼 소개하지 않는다. 첫 편에는 15~25초만 보여주고 별도 영상으로 확장할 수 있다.

이때 **개발을 돕는 생성형 AI와 게임 속 NPC의 행동 AI를 구분**한다. NPC가 매 행동마다 챗봇과 대화하거나 생성형 모델로 판단한다는 자료는 확인하지 않았다. ‘AI 주민들이 실제 사람처럼 생각한다’는 표현은 사용하지 않는다.

## 5. 반드시 구분할 현재 구현·보고·계획

| 소재 | 확인한 상태 | 영상에서 허용할 표현 |
|---|---|---|
| 이동·전투·드롭·장비 | 이 대화에서 사용자 구현 확인. 프로젝트에 관련 설계·작업 이력 존재 | 실제 촬영 장면과 함께 현재 기능으로 소개 |
| 기사 걷기 조합실 | 파일·UI 직접 확인, 도구 실행 검증은 다른 세션의 보고 | 직접 선택해 조합하는 제작 도구. 게임 적용 전 |
| 사용자 발 조합 | 파생 정지 이미지 직접 확인, GIF 속도·픽셀 비교는 세션 보고 | 현재 선택 후보의 움직임 비교. 전체 방향 완성 주장 금지 |
| 포탈 2×2·쓰러진 NPC 통과 | 사용자 지시+완료 보고+handoff 일치 | 수정 에피소드로 사용. 현재 통과 장면은 촬영 시 확인 |

| UI·지도·파티 표시 | P01a/b 구현·자동검증 보고. ko/en 실제 화면·사람 조작은 미검증 항목 있음 | 촬영한 빌드 기준으로 보여주기. 과거 화면을 최신 UI라 부르지 않음 |
| 마왕 첫 승리 일행 타락·다음 대륙 해금 | 최신 확정 방향이나 P00 대조에서 후속 구현 영역 | 현재 완성된 게임플레이처럼 소개하지 않음 |
| 서먼·테이밍·무게·NPC 자율 파티·혈맹 | 최신 요청/계획에 포함. 전부 현재 구현됐다는 근거 없음 | 첫 편의 현재 기능 나열에서 제외 |
| ‘60분 안에 성장해야 한다’ | 초기 README·옛 보고에는 남아 있으나 후속 결정과 회차 spec에서 기한 제거 | 현재 게임 규칙으로 소개하지 않음 |
| ‘쉽고 빠르게 성장하는 게임’ | 최신 U64는 초반 사냥·육성 반복 자체를 핵심 재미로 유지 | ‘결제 대신 플레이하며 성장하고 싶다’는 동기와, 초반 반복을 건너뛰는 설계를 구분 |

특히 ‘NC의 BM이 싫었다’는 동기를 ‘제 게임은 강화 실패·반복 사냥·위험이 전혀 없다’는 약속으로 바꾸면 프로젝트 자료와 어긋난다. 2026-10-20 이력에는 주문서 강화와 실패 손실이 들어 있다. 구체 확률·현재 수치는 최신화 중이므로 첫 편에서 확정 수치로 홍보하지 않는다.

## 6. 실제 화면을 보고 바뀐 촬영 판단

[2026-10-25 시야 비교 캡처 zoom-140](</D:/AI Agent/GitHub/Chronella/Logs/ChronellaCli/camera-zoom/zoom-140.png>)를 직접 보았다. 하단 HUD·F키 단축칸·장비 관련 정보·마을 NPC와 파티 캐릭터가 보이며, 바닥은 아직 타일 구분이 드러나는 개발 화면이다. `Dev Hero`와 테스트 동료가 보이는 **개발 비교용 정지 캡처**다.

이를 근거로 완성된 상용 게임 같은 소개 영상을 구성하지 않는다. 실제 개발 중인 모습과 손보는 과정을 보여주는 편이 자료와 맞다. 해당 캡처는 최신 P01b 표시 변경 전 시점일 수 있으므로 현재 화면의 정확한 UI나 플레이 재미·NPC 동작을 입증하지 않는다.

이번 조사에서는 게임 실행·현재 빌드 재생·녹화·GIF 연속 재생·픽셀 계측 재실행을 하지 않았다. 테스트 통과 횟수는 다른 세션의 보고이며 영상의 재미를 검증하는 자료로 쓰지 않는다.

## 7. 기존 대본을 구체화하는 편집안

아래 표는 **자료 대응을 위한 초기안**이다. 이후 사용자 피드백에 따른 현재 편집 추천은 §9이며, 걷기 80~110초 중심 배분은 채택하지 않는다.

| 기존 장면 | 새로 사용할 내용 | 길이 배분안 |
|---|---|---:|
| 장면 1 결과 예고 | 현재 전투·드롭·장비를 먼저 보여줌 | 20~25초 |
| 장면 2 제작 동기 | 리니지를 하며 개발자를 꿈꾼 경험과, 플레이하며 성장하는 재미를 찾고 싶다는 본인 이야기 | 50~70초 |
| 장면 3 현재 구현 | 사냥·획득·장비 소개. 가능하면 과거 용사 NPC를 짧게 예고 | 45~60초 |
| 장면 4~5 개발 에피소드 | 추상적인 AI 요청·수정 예시를 **기사 걷기 실패→직접 선택 도구→사용자 조합**으로 대체 | 80~110초 |
| 선택 삽입 | 포탈 길막 사건. 자료가 부족하거나 분량이 길면 다음 편 | 0~30초 |
| 장면 6 실제 플레이 | 게임에 적용된 현재 아트로 사냥·획득·장비 교체. 조합 후보와 구분 | 90~130초 |
| 장면 7~8 평가·다음 질문 | 오늘 실제로 느낀 점과 개선할 부분. 원하면 걷기 A/B 한 질문 | 60~90초 |

새로 기능을 개발해야 촬영할 수 있게 만들지 않는다. 게임에 적용되지 않은 걷기는 도구의 제작 과정으로 보여주고, 실제 사냥은 현재 적용된 캐릭터로 찍는다. 전체 분량은 낭독·플레이 길이에 따라 정하며 8분 30초를 맞추려 빈 장면을 늘리지 않는다.

### 장면 2에 넣을 제작 동기 — 새 사용자 진술 반영

> 리니지를 하면서 작업장 문제와 계속 나오는 유료 상품을 보고 있었습니다. 그러다 문득 궁금해졌어요. 나는 어릴 때 그 게임의 뭐가 그렇게 재미있었던 걸까. 왜 그 게임을 하면서 개발자가 되고 싶다는 꿈까지 꿨을까.
>
> 제가 다시 느껴보고 싶은 건, 결제를 많이 하지 않아도 직접 사냥하고 아이템을 얻으면서 성장하는 재미였습니다. 그래서 AI의 도움을 받아 직접 RPG를 만들어보고 있습니다. 처음부터 혼자 하는 옛날 RPG 느낌으로요.

이 발화는 지금 대화의 동기를 바탕으로 쓴 초안이다. 회사의 공식 발언을 반박하는 문구를 넣을 경우 공식 원문과 시점을 따로 확인해야 한다. 내부 개발 기록이 그 외부 주장을 입증하지는 않는다.

### 개발 에피소드 뒤 실제 플레이로 돌아오는 연결

> 걷는 모습도 아직 이렇게 하나씩 고르는 중입니다. 이 후보가 전부 게임에 들어간 건 아니고요. 이제 현재 플레이할 수 있는 버전으로 돌아가서, 제가 원했던 사냥과 아이템 얻는 재미가 느껴지는지 해보겠습니다.

이 전환 한 문장이 아트 후보를 완성 게임의 전후로 오해하는 것을 줄이고, 영상의 중심 질문으로 돌아오게 한다.

## 8. 촬영 자료 우선순위와 완료 기준

**먼저 확보할 자료**

1. 현재 빌드의 실제 사냥·드롭·장비 교체 연속 녹화.
2. 기사 걷기 기존 후보와 사용자 조합의 같은 방향·같은 속도 비교. 후보와 적용본을 화면에 구분.
3. 현재 조합실에서 네 프레임을 선택·순서 조정·재생하는 시연. 최초 작업의 당시 녹화가 없으면 현재 시연임을 유지.
4. 실제 세션의 ‘한 장면씩 고르자’는 짧은 발화 또는 본인의 설명. 채팅 전문을 보여주지 않아도 됨.

**있으면 추가할 자료**

- 당시 포탈 길막 녹화와 현재 통과 장면. 전후 자료를 못 찾으면 개발 소감으로만 짧게 설명하거나 다음 편으로 보류.
- 과거 캐릭터의 이름·장비·스킬 이력을 확인할 수 있는 다음 회차 동행 사냥. 임의 테스트 캐릭터를 본인의 실제 이전 캐릭터로 가장하지 않음.

첫 편에서 확보할 가장 중요한 답은 완벽한 개발 성공이 아니다. **어릴 때 좋아했던 경험을 다시 만들려고 어떤 결과를 받아들이고, 어떤 결과를 거절하고, 무엇을 직접 바꾸었는지**가 실제 장면으로 전달되면 된다.

## 출처 관리 메모

원본 대화·프로젝트 파일은 Chronella에 그대로 두었다. 이 문서는 짧은 발화와 기획에 필요한 사실만 추출했으며 원본 이미지·코드·세션 전체를 Creator로 복제하지 않았다. 관련 세션의 완료 보고와 같은 자료를 인용한 handoff를 서로 독립된 실험으로 세지 않았다. 추가 촬영·실행 확인이 생기면 해당 에피소드의 상태와 사용할 발화만 갱신한다.

## 9. 시청자 관점 재검토 — 첫 편은 어떤 기대에 답해야 하나?

### 9.1 앞선 제안의 수정 이유

기존 제안은 프로젝트 내부에 남아 있는 구체적인 기록을 찾는 데 유효했지만, 자료가 많다는 이유로 걷기 제작 과정을 첫 편의 중심으로 두었다. **자료의 풍부함과 시청 수요를 혼동하면 안 된다.**

확인한 Studio 반응은 과금 구조·자동사냥 문제·공략 등에 관한 것이며, 발동작·프레임 조합·프롬프트 강의에 대한 김실버 시청자의 수요는 확인하지 않았다. 외부 개발 영상의 조회수는 개발 콘텐츠를 보는 시장의 존재를 보여줄 뿐, 그 시청자가 김실버 채널과 같거나 어느 구간 때문에 끝까지 봤는지 증명하지 않는다.

예를 들어 GIVEPRO 개발 후기 45,029회는 출시 결과·개인 경험에 대한 관심과 함께 관측됐고, 용사주식회사 이펙트 영상 28,183회는 시각적 기능 개선·도구 공유 형태다. 제목·설명·일부 댓글로 확인한 범위를 넘어 ‘프레임 선택 설명이 인기의 원인’이라고 말할 수 없다. 관측 시점과 출처는 [최근 영상 조사](02-recent-video-research.md)를 따른다.

### 9.2 우선 가정할 세 시청자와 질문

다음은 관측된 관심에서 출발한 편집 가설이다. 실제 집단 규모·중복·선호 순위를 측정한 것이 아니다.

| 시청자 | 먼저 궁금할 질문 | 초반에 보여줄 답 |
|---|---|---|
| 옛 리니지 경험자 | 저 사람이 말하는 그때의 재미가 뭔데? 내가 아는 느낌인가? | 구체적인 사냥·획득·장비 변화와 본인 기억 |
| 과금·운영 문제에 관심 있던 사람 | 직접 만들면 어떤 선택이 달라지나? | 지금 구현한 게임 규칙과 플레이 결과. 운영·수익화 미확정 사항은 약속하지 않음 |
| AI에 호기심 있는 새 시청자 | 그래서 실제로 할 수 있는 게임이 나왔나? | 실행되는 게임·시도와 한계. 사용법 강의는 첫 편의 필수 답이 아님 |

이들에게 처음부터 프레임 슬롯·발의 지지·원본 버전 번호를 설명하면, 게임을 보고 판단하기 전에 제작 방법을 배워야 하는 흐름이 된다. 반면 본인이 직접 고른 결과가 플레이에서 어떤 차이를 만들었는지 보이면 제작 장면의 역할이 생긴다.

### 9.3 첫 편이 줄 경험

중심 질문은 **‘어릴 때 좋아했던 RPG의 재미를, 지금 내가 만든 싱글 게임에서 다시 느낄 수 있을까?’**로 둔다.

시청자는 영상 안에서 세 가지를 확인할 수 있어야 한다.

1. 본인도 기억하거나 이해할 수 있는 재미: 사냥→아이템→성장.
2. 실제로 판단할 결과: 전투·획득·장비 변화가 충분히 보이는 플레이.
3. 이어서 궁금해질 선택: 만든 사람이 무엇이 부족하다고 느끼고 다음에 어떤 경험을 바꾸려 하는지.

개발자의 꿈은 영상의 동기가 된다. 길게 회고하는 것만으로 결과를 대신하지 않도록 첫 20초부터 현재 게임을 보여주고, 동기는 약 40~60초 안에서 연결하는 것을 잠정 추천한다. 길이는 공식 성공 기준이 아니며 장면에 맞춰 조정한다.

### 9.4 구체적 개발 과정의 채택 기준

해당 장면이 아래 중 하나에 답하면 남긴다.

- 시청자가 방금 본 게임 경험이 왜 어색하거나 재미있었는지 설명하는가?
- 다음 결과가 궁금해질 실제 장애물·결정을 보여주는가?
- 김실버의 선택이 게임을 어떻게 바꾸었는지 눈으로 확인할 수 있는가?

그렇지 않으면 후속 제작 이야기·관심 있는 시청자용 부록 후보로 둔다. 개발자가 오래 작업한 시간은 영상에서 길게 보여줘야 할 이유가 아니다.

| 소재 | 첫 편의 권장 취급 | 이유 |
|---|---|---|
| 발이 어색한 후보와 직접 고른 결과 | 약 10~20초의 보조 장면, 시각적 차이가 분명할 때 | 시행착오와 본인 판단을 짧게 전달 |
| 프레임 슬롯·지지발·배율·버전 설명 | 첫 편 본문에서 생략 | 제작 방법에 관심 있는 집단의 요구이며 현재 수요 미확인 |
| 포탈 길막 | 진행을 막는 실제 사건이 화면으로 전달되면 약 15~30초, 아니면 보류 | 플레이어가 이해할 장애물. 과거 녹화가 없으면 억지 재연하지 않음 |
| 사냥·득템·장비 교체 | 중심 장면 | 첫 편의 질문에 직접 답함 |
| 과거 용사가 동료로 남는 기능 | 현재 빌드 시연이 확보되면 짧게 포함 | 싱글 세계의 구체적 차이를 보여줌. 구현 기록과 현행 재생 확인 구분 |
| 개발 테스트 개수·코드 구조 | 생략 | 플레이 재미와 시청 만족의 근거가 아님 |

위 초 단위는 이번 파일럿의 편집 판단이고, 보편적인 유지율 기준이나 측정 결과가 아니다.

### 9.5 재편집한 이야기 순서

1. **현재 결과:** 실제 사냥·획득·장비 장면과 ‘다시 재미를 느낄 수 있을까’ 질문.
2. **왜 시작했나:** 리니지 경험과 개발자의 꿈, 플레이로 성장하는 재미를 원한다는 본인 동기.
3. **어떤 게임인가:** 현재 가능한 사냥과 싱글의 선택. 시연 가능하면 과거 용사 동행이라는 차이.
4. **직접 해보니:** 전투·전리품·성장 흐름과 실제 판단. 중간의 문제를 설명할 때만 개발 에피소드를 짧게 삽입.
5. **오늘의 답:** 좋은 점이 있으면 그 장면, 부족한 점이 있으면 그 이유. 다음에는 어떤 경험을 바꿔볼지.

실제 플레이에서 차이나 재미가 아직 읽히지 않으면 감성 내레이션·AI 로고·버그 몽타주를 늘려 덮지 않는다. 지금 플레이로 답할 수 있는 더 작은 질문으로 범위를 줄인다. 예: ‘장비 하나를 바꿨을 때 강해진 느낌이 드는가’. 그것도 확인되지 않으면 아직 완성된 재미를 약속하는 제목을 사용하지 않는다.

### 9.6 제목의 시청자 기대도 조정

기존 ‘AI로 싱글 RPG를 만들고 있습니다’는 제작 소식에 가깝다. 첫 편은 시청자가 공감하거나 판단할 질문을 더 앞세울 수 있다.

- 본인 경험형 후보: **리니지는 접었는데, 그때 그 재미는 다시 느끼고 싶었습니다** / 썸네일 `그래서 만들어봤습니다`와 실제 게임 화면.
- 질문형 후보: **옛날 RPG의 재미, 혼자 하는 게임에서도 느낄 수 있을까?** / 썸네일에서 본인이 AI와 개발 중인 게임임을 전달.

전자는 개인적 경험담을, 후자는 플레이 검증을 기대하게 한다. 어느 쪽이 더 높은 CTR을 낼지 확인된 근거는 없다. 영상에서 실제로 답할 수 있는 쪽으로 결정한다. ‘현질 없이 완벽한 리니지’, ‘작업장 없는 완성 MMORPG’ 같은 범위가 다른 약속은 하지 않는다.

### 9.7 ‘시청자가 원한다’는 결론은 어떻게 확인하나?

현재 판단은 **개발 방법 자체보다 실제 결과와 재미를 앞세우는 것이 채널에 더 맞을 가능성이 높다**는 가설이다. 전체 시청자 선호를 확정하지 않는다.

촬영본을 편집할 때는 개발 설명을 제거해도 본편 질문이 진행되는지 먼저 본다. 결과를 이해하는 데 필요한 장면만 다시 넣는다. 공개 후에는 개발 구간 진입·이탈 시점과 앞뒤 유지율, 유입 경로, 댓글이 묻는 내용을 대조한다. 특정 구간의 이탈만으로 기술 설명이 원인이라고 확정하지 않고 길이·전환·제목 기대와 함께 본다. 다음 편·플레이 결과에 대한 질문과 도구 사용법 질문을 구분한다.

YouTube도 정해진 최적 길이보다 내용에 필요한 분량과 실제 유지율을 보도록 안내한다. 출처: [추천 시스템 공식 안내](https://support.google.com/youtube/answer/16559651?hl=en). 친숙한 형식·진행자·시리즈는 재방문과 관련된 운영 선택이지만 개별 시청자의 관심을 보장하지 않는다. 출처: [시청자 구분 공식 안내](https://support.google.com/youtube/answer/10246996?hl=ko).
