# 김실버 첫 게임 개발 영상 · 대본의 실패와 개선 근거

- 목적: 첫 개발 영상을 만들며 이야기가 목적에서 벗어난 지점과 수정 근거를 보존하고, 다음 영상의 소재·장면·발화 설계에 활용한다.
- 읽는 시점: 다음 영상의 중심 질문과 대본을 정할 때. 실패담을 기획할 때는 관측과 해석·재구성을 구분한다.
- 책임: 김실버가 자신의 경험·감정·공개 범위를 판단하고, 기획 담당자가 출처와 미검증 범위를 유지한다.
- 상태: **active 분석 자료 · 다음 영상은 제안 단계**. 2026-10-27 KST. 다음 영상 제작·게시나 기존 영상 재편집을 확정한 문서가 아니다.
- 관련 권위: [채널 의도](01-channel-plan.md), [첫 편의 확정 선택](03-ai-game-development.md), [게임 화면 근거](05-chronella-story-evidence.md), [과거 리니지 경험](06-lineage-experience-review.md). 최신 영상 파일·승인·다음 작업은 [작업 상태](state.md)만 소유한다.

## 1. 이번에 남길 경험의 범위

사용자의 후속 확인은 **두 과정을 연결하되, 원하는 목적에 맞는 대본을 만드는 과정이 중심**이라는 것이다. 리니지에서의 과거 기억과 현재 게임 개발을 어떤 분량·내용으로 연결할지가 문제였으며, 이번 소개 영상은 대본을 먼저 정리한 뒤 녹음·녹화 자료를 편집했다.

Chronella 자체는 영상 소개 이전부터 개발 중이었다. 영상 제작 때문에 게임 개발을 처음 시작했거나, 완성된 영상을 분석한 다음 처음 대본을 쓴 것처럼 순서를 바꾸지 않는다. 다음 영상에서 다룰 것은 ‘게임 버그를 몇 개 고쳤는가’가 아니라 **이미 하고 있던 게임 개발을 어떤 말로 설명해야 내 의도가 전달되는가를 찾아간 경험**이다.

현재 근거로 확인할 수 있는 순서는 다음과 같다.

1. 리니지 경험과 개발자의 꿈, 개발 중인 싱글 RPG가 있었다.
2. 이를 소개할 첫 영상의 기획·대본을 여러 차례 검토했다.
3. 사용자가 과도한 회고·기능 설명·부자연스러운 연결과 임의의 감정 해석을 교정했다.
4. 보관 자료에서 본인의 실제 발화·사건을 확인하고, 현재 게임의 녹화 장면을 연결했다.
5. 대본·실제 녹음을 바탕으로 화면을 편집하고 자막·음악 등을 조정했다.

‘수없이 수정했다’는 사용자의 체감은 확인된다. 그러나 정확한 수정 횟수·작업 시간·비용은 계측하지 않았으며 숫자로 만들어 쓰지 않는다. 모든 중간 대본과 최초 생성 순간의 화면 녹화가 남아 있는지도 확인하지 않았다.

## 2. 직접 근거, 해석, 제안을 구분하는 방법

| 구분 | 의미 | 이번 자료의 예 |
|---|---|---|
| 사용자 직접 근거 | 본인이 무엇을 원했고 어디가 맞지 않았는지의 진술 | ‘내가 마주했던 느낌과는 전혀 달라’, ‘게임 설명이 너무 커졌다’, 이번 후속 답변 |
| 파일·화면 근거 | 해당 기록이나 촬영분에 실제 존재하는 내용 | 초기 기획의 개발 과정 시간표, 과거 개선 요청 영상, 환생·동료 장면, 음성 삭제 범위 |
| 기획 해석 | 근거가 설명하는 문제 구조에 대한 판단 | 과거와 현재를 잇는 행동의 이유가 약했다는 진단 |
| 다음 영상 제안 | 앞으로 보여주거나 말할 수 있는 구성 | 아래 4분 40초 가안과 발화 예시. 촬영·시청 성과로 검증한 결과가 아님 |

사용자 경험과 어긋난 대본은 AI의 문장 생성만의 문제가 아닐 수 있다. 이야기의 목적·자료 선택·분량 판단·검수 책임이 함께 관련된다. 모델·프롬프트별 성능 비교를 한 기록이 없으므로 ‘어떤 AI도 내 감정을 이해할 수 없다’거나 특정 모델의 일반적 결함으로 확대하지 않는다.

## 3. 핵심 실패·개선 사례

### S1. 무엇을 만들었는지 설명하다가 왜 만드는지가 사라졌다

- **관측:** 걷기 후보·제작 과정 설명이 계속 들어가는 데 사용자가 제외를 요청했다. 기능 설명을 늘린 뒤에는 ‘내가 만든 게임 설명 이야기가 너무 커진 것 같다’고 교정했다.
- **파일 근거:** [03 초기 기획 §8.4~8.7](03-ai-game-development.md)은 AI 요청·예상과 다른 결과·수정 전후 비교와 약 8분 30초 구성안을 보존한다. [05 초기 조사 §2~3](05-chronella-story-evidence.md)에 걷기 조합·포탈 수정 자료가 있다. 지금은 historical 범위이며 첫 편의 채택안이 아니다.
- **문제 해석:** 자료가 구체적이라는 이유로 중심 장면으로 삼으면 영상이 답하려던 질문이 ‘왜 만드는가’에서 ‘어떻게 만들었는가’로 바뀐다.
- **수정:** 첫 편의 목적을 제작 동기로 다시 고정하고, 구체적 개발 작업은 제외했다. 현재 게임 화면은 실제로 만들고 있다는 근거로 사용했다.
- **포기한 방법:** 첫 소개 영상 안에서 제작 강의·기능 소개·전후 실험을 모두 완결하려는 구성.
- **확인 수준:** 사용자가 채택한 목적·제외 범위와 기획 수정은 확인된다. 이 선택이 시청 지속에 더 유리한지는 미검증이다.
- **다음 영상에 쓸 것:** 초기 시간표에서 개발 과정 부분을 짧게 짚고, 무엇을 잘못 약속하게 되는지 현재 게임 화면과 비교한다. 코드 설명으로 다시 들어가지 않는다.

### S2. 그만둔 이야기를 보강했더니 지금 만드는 게임이 묻혔다

- **관측:** 사용자는 접은 이유를 앞에 보강해달라고 했지만, 이후 과거 설명이 길어 현재 게임이 묻히고 같은 감정이 반복되는지도 재검토해달라고 했다. 다시 게임 설명을 늘렸을 때도 과도하다고 교정했다.
- **직접 근거:** 이번 대화의 ‘과거 리니지 이야기가 너무 길어서 AI로 게임을 만드는 현재 이야기가 묻히지는 않는지’, ‘게임 설명 이야기가 너무 커진 것 같은데’, ‘아주 조금만 보강’이라는 피드백.
- **문제 해석:** 과거와 현재를 똑같은 비중으로 다 설명하려 하면 둘의 연결보다 두 개의 소개문이 된다. 어느 한쪽을 전부 빼는 것도 목적을 해결하지 않는다.
- **수정:** 과거는 떠난 이유와 남은 꿈을 이해시키는 근거로 줄이고, 현재는 만들고 싶은 경험과 환생·동료 같은 특징 하나를 짧게 보여주도록 했다.
- **포기한 방법:** ‘과거를 줄이면 해결’, ‘기능을 더 넣으면 해결’처럼 문단의 양만 오가는 수정.
- **확인 수준:** 원하는 균형과 채택 방향은 확인된다. 보편적인 최적 분량 비율은 측정하지 않았다.
- **다음 영상에 쓸 것:** 설명량의 증감 자체보다, 각 부분에 맡길 일을 구분한 과정을 보여준다. 리니지 회고를 다시 길게 재상영하지 않는다.

### S3. 문장은 이어졌지만 직접 게임을 만드는 이유가 납득되지 않았다

- **관측:** 사용자는 ‘그 마음은 아직 남아 있더라고요. 그래서 지금 만드는 게임에는…’라는 연결에 대해 행동의 근거가 너무 약해 납득·이해·설득이 안 된다고 지적했다.
- **문제 해석:** 꿈이 남아 있다는 감정과 게임을 직접 만드는 선택 사이에는 ‘무엇을 다시 생각했고, 왜 직접 해보려 했는가’가 빠져 있었다. 접었다는 사건만으로 개발이라는 행동이 자동으로 설명되지는 않는다.
- **보완한 내용:** 사용자가 어떤 게임을 좋아했고 왜 개발자가 되고 싶었는지 스스로 돌아보는 내용을 제안했다. 이어 좋아했던 경험을 직접 게임에 담아 다른 사람에게도 전하고 싶다는 동기를 정리했다.
- **자료 근거:** [03 확정 선택](03-ai-game-development.md)의 제작 동기, [06 §3 A와 D](06-lineage-experience-review.md)의 과거 꿈 발화·실험과 발견의 즐거움. 이 동기를 특정 게임 기능을 고안한 직접 원인으로 더 확대하지 않는다.
- **확인 수준:** 사용자가 밝힌 자기 고찰과 전달 동기는 직접 근거다. 시청자가 같은 이유로 공감할지는 가설이다.
- **다음 영상에 쓸 것:** 약했던 연결 두 문장을 실제 사용자 지적 사례로 소개하고, 새 발화에서는 ‘나에게 필요한 것은 연결어가 아니라 선택의 이유였다’는 구조를 설명한다. 옛 문장을 완성본 대사로 오인시키지 않는다.

### S4. 그럴듯한 감정 해석보다 본인이 남긴 기록이 더 정확했다

- **관측:** 사용자는 대본이 자신이 마주했던 느낌과 전혀 다르다고 말하고, 실제 리니지 영상·자료 폴더를 확인하도록 요청했다.
- **재조사 결과:** [06 결론과 §3 A~F](06-lineage-experience-review.md)에는 계속 즐기려고 개선을 요청한 경험, 개선에 기뻐한 발화, 사냥 대신 대응에 시간을 쓴 상황, 마지막 강화의 전환점이 정리되어 있다.
- **수정:** 단순한 과금 불만·성장 속도·경쟁 회피 같은 추정 대신, 계속 좋아하고 싶었지만 기대가 무너져 떠난 경험을 기획의 바탕으로 삼았다.
- **구분:** 이는 사용자 경험을 설명하는 근거이지 현재 서버 상황이나 회사의 모든 정책 주장을 검증한 자료가 아니다. 창작 가사를 실제 사건·현재 내면으로 전부 확정하지 않는다.
- **확인 수준:** 자료에서 확인한 사건·발화와 사용자 교정은 근거가 있다. 사용자 현재 감정을 대신 확정할 수는 없다.
- **다음 영상에 쓸 것:** 과거 개선에 기뻐한 짧은 장면과 꿈을 말한 장면을 사용한다. ‘사실은 내가 계속 좋아하고 싶어 했구나’라는 해석은 김실버가 지금도 동의하는 만큼만 말한다.

### S5. 자연스러운 문장 수정만 반복해서는 영상의 목적이 잡히지 않았다

- **관측:** 사용자는 문장·도입·연결·반복을 여러 번 교정했으며, 나중에는 대본 문장에만 집중하지 말고 이번 세션에서 제시한 고려 사항을 함께 보라고 요청했다.
- **문제 해석:** 문장 하나의 매끄러움과 영상 전체의 방향은 서로 다른 검사다. 같은 ‘꿈·재미·모험’을 다른 말로 반복하면 흐름이 자연스러워 보여도 새 정보가 늘지 않을 수 있다.
- **수정:** 목적, 실제 경험, 현재 게임, 시청자의 질문을 함께 검토하고, 대사에서는 같은 감정 설명과 부수적 에피소드를 줄였다.
- **재사용할 판단:** 각 문단이 ① 어떤 실제 근거를 추가하는지 ② 과거와 현재를 어떻게 연결하는지 ③ 다음에 무엇이 궁금해지게 하는지 확인한다. 이 세 질문은 이번 작업에서 얻은 편집 권고이며 새로운 전역 의무 규칙이 아니다.
- **확인 수준:** 반복 교정과 최종 선택은 확인된다. ‘이 방식으로 다음 대본을 한 번에 완성할 수 있다’는 보장은 없다.

## 4. 해결·우회·보류를 다르게 기록하기

| 분류 | 이번 사례 | 무엇을 남길 것인가 |
|---|---|---|
| 내용 수정 | 과거/현재 분량과 약한 개발 동기 연결을 재구성 | 사용자 교정, 당시 제안, 바꾼 이유, 제외한 장면 |
| 근거 보강 | 보관 리니지 자료와 제공 게임 녹화를 확인 | 원본 경로·시각·관찰 방식, 그 자료가 입증하지 않는 범위 |
| 우회 | 최초 개발 과정을 재현하려 하지 않고 현재 게임 화면으로 실제 행동을 보여줌 | ‘당시 개발 녹화’와 ‘현재 시연·설명’을 구분. 현재 시연은 앞으로 촬영할 경우의 방안 |
| 기술 수정 | 반복 발화 삭제, 고정 자막 배경 적용 | 아래 부록의 삭제·보존 구간과 R04/R05 비교 근거 |
| 미검증/보류 | 정확한 수정 횟수, 전편 직접 청취, 시청 성과, 모든 중간 대본의 보존 | 수치를 만들거나 기술 통과를 이야기 전달 성공으로 바꾸지 않음 |

이 경험의 의미를 ‘AI가 틀렸고 나는 맞았다’로만 정리하지 않는다. AI에 어떤 일을 맡길지, 본인이 무엇을 판단해야 하는지 구분하는 과정으로 보는 편이 현재 근거와 채널 의도에 가깝다. 이 해석에 김실버가 동의하는지도 다음 대본에서 확인한다.

## 5. 다음 영상으로 사용할 수 있는가

**사용할 수 있다. 다만 실패 이력 전체가 아니라 대본의 목적을 찾아가는 한 가지 이야기를 선택해야 한다.**

- 기존 게임 시청자에게 남길 질문: 김실버가 그리워하는 게임 경험은 무엇이며, 지금 만드는 게임에 무엇을 담으려는가.
- AI에 관심 있는 시청자에게 남길 질문: 실제 경험을 말로 정리할 때 AI가 도울 일과 본인이 확인할 일은 어떻게 달랐는가.
- 첫 영상을 보지 않은 사람에게 필요한 설명: ‘게임을 개발 중이고, 왜 만드는지 소개하는 영상을 준비했다’는 한 문장과 실제 게임 화면. 이전 영상 시청을 전제로 하지 않는다.

### 추천하는 중심 이야기 — 아직 제안

**게임은 이미 만들고 있었는데, 왜 만드는지 설명하려니 자꾸 다른 이야기가 되었습니다.**

이는 게임 개발의 성공담도, AI 편집 도구 강의도 아니다. 리니지의 기억과 현재 만드는 게임 사이에서 본인의 의도를 구체화한 과정이다. 게임의 실제 문제를 고친 사례는 근거와 촬영분이 확보되면 별도 후속 편으로 다룬다. 이번 기록만으로 새로운 게임 버그·해결 성과를 만들지 않는다.

### 영상화하기 어려운 형태

- 수정 요청과 AI 답변을 처음부터 끝까지 순서대로 읽는 영상.
- ‘수십 번 고쳤다’는 횟수와 짜증만 중심에 두고 무엇이 달라졌는지 보여주지 않는 영상.
- 첫 편의 리니지 이탈·꿈 이야기를 거의 그대로 반복하는 영상.
- 걸음 조합·오디오 파형·렌더 명령을 한 편에서 전부 설명하는 도구 강의.
- 초기 대본이 남아 있지 않은데 새로 만든 글을 당시 원문처럼 보여주는 연출.

최초 시행착오 화면이 없다면 채팅을 재연해 가짜 기록을 만들지 않는다. 남아 있는 문서·직접 발화·원본 장면과 현재의 설명으로 구성할 수 있다. 화면 캡처 전에 계정·연락처·프로젝트 비공개 정보는 가린다.

## 9. 기술 실패는 부록·별도 소재로 남길 것

다음 항목은 실제 제작 경험이지만, 대본을 중심으로 한 다음 영상에 모두 넣으면 주제가 분산된다. 필요하면 오디오 전후 비교 한 가지를 10~15초 보조 사례로 택하고 나머지는 별도 소재로 둔다.

### T3. 다른 작업과 분리한 우회와 검증 수준

초기 공용 실행기 문제에 대해 사용자는 별도 FFmpeg 실행과 다른 TTS 코드 보존을 지시했다. 작업 전용 스크립트로 다중 원본·자막·음악·아웃트로를 조립했고 공통 코드나 다른 작업을 수정하지 않는 범위를 유지했다. 이 대화에서의 방법 선택 기록이며 현재 공용 실행기의 같은 오류가 다시 재현된다는 주장은 아니다. 방법을 바꿀 때도 입력 원본·컷 길이·음성·최신 상태를 보존해야 한다는 경험으로 한정한다.

R06 조립 계획에는 본편 coded packet 보존 의도가 있지만 [실제 검증](work/screen-sample-r06/validation.json)은 coded packet 동일 `false`, decoded frame 동일 `true`다. 컨테이너/헤더 변환 뒤 실제 화면이 같다는 검사와 파일/패킷 바이트가 같다는 주장을 구분한다. 문서·계획의 ‘보존’ 문구만으로 성공을 설명하지 않는다.

음악 선택·음량 마감과 아웃트로 결합은 [R06 조립 기록](work/screen-sample-r06/assembly.json)의 사례다. 현재 최신 완성본·이후 음악 선택·승인은 작업 상태에만 맡긴다. 기술 내용은 다음 영상의 대본 주제를 대체하지 않는다.

## 10. 다음 작업에서 남길 최소 근거

추가 실험을 하게 되면 한 사례당 다음 여섯 항목이면 충분하다. 새 기록 파일을 자동 생성하거나 모든 채팅·영상의 복제본을 만들라는 뜻은 아니다.

1. 하려던 일과 시청자에게 전달할 목적 한 문장.
2. 기대와 어긋난 결과의 실제 문장·화면·소리와 원본 위치.
3. 원인으로 확인한 것과 아직 추정하는 것.
4. 바꾼 선택과 하지 않기로 한 선택. 시도와 실제 적용·채택을 구분.
5. 전후를 확인할 원본·편집본 위치와 관찰 방식.
6. 확인된 변화·남은 한계·다음에 확인할 질문.

우선 제작 후보로 권하는 것은 **S1~S4를 한 흐름으로 연결한 대본 이야기**다. 기술 부록 전부를 같은 영상에 넣거나 초기 제안의 모든 사례를 추가하지 않는다. 다음 영상의 최종 제목·대본·촬영·편집은 사용자 선택 후 별도로 확정한다. 아직 채널 조회수·CTR·유지율·반응으로 이 소재의 수요를 확인한 것은 아니다.
