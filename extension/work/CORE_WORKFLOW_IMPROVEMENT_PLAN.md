# Core 공통 워크플로우 개선계획

- 목적: 세션 분석에서 드러난 공통 실행·검증·재개 문제를 기존 Core 소유자에 대응하고, 필요한 최소 변경과 검증 기준을 정한다.
- 읽는 시점: Core 개선 범위를 승인하거나 Maintainer에서 구현을 시작하기 전.
- 책임: Creator 에이전트는 제안과 근거를 제공하고, Agent-Core Maintainer는 재현·설계·승인된 Core 변경을 수행한다.
- 상태: 제안된 개선계획. 문서 작성만 요청받았으며 구현·정책 변경·새 작업 생성 승인이 아니다.
- 관련 권위: [Core 정책](../../core/PROJECT_RULES.md), [소비 안내](../../core/docs/CONSUMER_GUIDE.md), [Creator 정책](../../PROJECT_RULES.md), [Extension 개선계획](EXTENSION_WORKFLOW_IMPROVEMENT_PLAN.md).
- 정보 유형·수명: 한시 개선 설계. 기존 규칙의 대체 정본이나 현재 상태 문서가 아니다. 구현 후 필요한 내용은 기존 소유자에 흡수하고 이 문서의 역할을 종료한다. 물리적 삭제·이동은 별도 승인 범위다.

## 1. 범위와 배치

이 문서는 Creator가 발견한 Core 개선 제안이므로 Host 소유의 `extension/work`에 보관한다. `core/`에는 쓰지 않는다. 아래 Core 경로는 **Maintainer의 Core root 기준 변경 검토 대상**이며, Creator가 내부 API를 import하거나 규칙을 직접 route할 근거가 아니다.

Core는 도메인과 무관한 보장과 공개 검증 계약을 소유한다. 영상 사건·컷·FFmpeg·Premiere·산출물 revision schema는 Extension이 소유한다. 구체적인 Windows 명령·sandbox 승인 호출·로컬 runner 구현도 Consumer/실행기 책임이지 Core 구현으로 옮길 대상이 아니다.

이번 문서 작성의 제외 범위는 Core·Extension 코드 및 활성 규칙 수정, 핸드오프 갱신, 보호 데이터 접근, checkout·merge·stage·commit·push, 설치·환경 변경이다. 향후 Core 구현에는 Maintainer 환경과 정확한 대상에 대한 사용자 승인이 필요하다.

## 2. 근거와 분류

계획 수립일은 2026-09-07이다. 아래는 현재 관찰의 근거이지 고정된 최신 상태 선언이 아니다. 구현 전에 해당 owner를 다시 확인한다. Core revision의 정본은 부모 gitlink이며 이 문서에 복제하지 않는다.

| ID | 문제와 근거 수준 | 기존 Core owner | 처리 방향 |
|---|---|---|---|
| C1 | 실제 확인보다 높은 완료·품질 표현이 사용됨. 세션 보고에 근거하며 과거 미디어는 재검수하지 않음 | `PROJECT_RULES.md` §5·9, `rules/work-contract.md`, `rules/cross-validation.md` | 원칙은 이미 존재한다. 관측 범위와 완료 주장을 대조하는 행동 검증을 먼저 보강하고, 실패가 재현될 때만 기존 문구를 최소 수정 |
| C2 | 사용자 위임·실행기 권한·명령 대상 문제를 혼동하고, 필요한 실행 능력을 늦게 확인함. 세션 실행 기록에 근거 | `rules/work-contract.md`, `rules/boundary-routing-and-dependency.md`, `rules/failure-records.md` | 기존 계약으로 처리 가능한 적용 문제. 구체 shell wrapper는 Core에 추가하지 않고 경계별 판정 사례로 검증 |
| C3 | 상태 문서 오류를 완전히 진단하기 전에 전체 gate 재실행을 반복함. 상태 검사 코드의 금지 제목·판정 하나 조건은 직접 확인 | `rules/handoff.md`, `docs/CONSUMER_GUIDE.md`, `src/core_check/integrity.py`, `tests/test_state_contract.py` | 공개 진단의 설명 가능성과 문서·검사 일치 개선 후보. 내부 helper를 Consumer 진입점으로 노출하지 않음 |
| C4 | 커밋·중단 뒤 핸드오프가 실제 작업 상태를 따라가지 못함. 백룸 문서와 관련 Git 이력 대조로 확인 | `rules/handoff.md`, `rules/staged-work-design.md` | 갱신 시점 원칙은 이미 있다. 중단·커밋 후 재개 사례로 누락을 검증. 실제 Creator 문서 정정은 Extension 계획 E1 소유 |
| C5 | 보고서의 좁은 검색 범위를 전체 능력 부재로 확대하거나, 큰 출력을 잘린 채 다룸. 앞선 분석과 원본 runtime 코드 대조에 근거 | `rules/cross-validation.md`, `rules/document-work.md` | 출처·범위·미확인 구분과 출력 완전성 확인을 적용. 추가 상시 보고서나 일률적인 다중 Agent 검토는 만들지 않음 |
| C6 | 소비 안내 §6은 HEAD·index gitlink·Core HEAD 일치를 요구하지만 §7은 새 Core checkout→gate→부모 commit 순서임. 문서상 선후관계 충돌 후보를 직접 확인 | `docs/CONSUMER_GUIDE.md`, 관련 `src/core_check/` 검사, `tests/test_integrity.py` | 실제 두 revision 갱신 사례를 Maintainer fixture에서 재현한 뒤 절차·검사 중 변경할 owner 확정. 이번 세션의 동일 revision 검사 성공을 갱신 경로 검증으로 보지 않음 |

새 규칙 파일을 기본 해법으로 삼지 않는다. 기존 요구가 충분하면 적용·검사만 고치고 `정책 변경 불필요`로 닫는다. 미재현 가설이나 거절 이력을 상시 실패 규칙으로 승격하지 않는다.

## 3. 단계별 개선계획

### 단계 A — 변경 필요성과 완료 조건 확정

- 진입: Maintainer에서 시작 문서와 현재 checkout을 확인하고, 사용자 승인 범위를 확인한다.
- 작업: C1–C6을 기존 구현/테스트에 대응한다. `기존 보장 적용`, `검사·진단 결함`, `실제 계약 공백`, `미재현`으로 나누고 새 구현이 필요한 항목만 남긴다.
- 최소 검증: §4의 부정 사례와 정상 대조 사례를 기존 공개 CLI 또는 실제 Agent 행동 관찰로 재현한다. 두 검증 방식은 분리한다.
- 성공: 각 항목에 owner, 변경 필요 여부, 재현 근거, 선택된 검사, 제외 범위가 있다. 단순 규칙 인용을 행동 통과로 기록하지 않는다.
- 전환: 정확한 변경 파일·효과를 사용자가 승인한 항목만 단계 B에 들어간다. 이미 충족하는 항목을 억지로 구현하지 않는다.

### 단계 B — 확인된 공통 결함의 최소 보완

우선순위는 거짓 완료 방지(C1), 실행·재개 경계(C2·C4), 진단 반복 감소(C3), 갱신 절차(C6), 검토 효율(C5)다. C6은 실제 새 Core 소비 전에는 선행 해소가 필요하지만 독립 Extension 작업의 일괄 차단 조건은 아니다.

1. **C1·C2·C4·C5:** 기존 규칙을 적용하는 재현 사례를 먼저 보강한다. 문구 모호성이 원인으로 확인될 때만 해당 기존 owner를 수정한다. API 응답 성공·합성 검사·보고서 동의를 실제 결과로 확대하지 않는 정상/위반 사례를 함께 둔다.
2. **C3:** 상태 문서 진단이 문제 위치, 위반 조건, 유효한 최소 예시를 설명하도록 검토한다. `직전 게이트` 판정 하나와 다른 절의 알려진 미검증 상태가 공존하는 정상 예시를 포함한다. 현재 상태 절을 통과시키려고 근거 없는 `pass`를 쓰는 해결책은 금지한다.
3. **C6:** 서로 다른 두 Core revision을 가진 비보호 임시 Consumer fixture에서 안내 절차를 실행한다. pre-commit 후보 진단과 post-commit 소비 완료를 분리할지, 공개된 안전한 후보 검증 경로가 필요한지 결정한다. Host 불변식·역할을 우회하거나 gate를 통과시키기 위해 무조건 먼저 commit하도록 바꾸지 않는다. 공개 계약 변경이 필요하면 별도 승인과 호환성 검토를 거친다.

- 성공: 재현된 결함이 해결되고 정상 대조 사례가 유지된다. 새 Core 코드가 Creator·영상 schema·사용자 경로를 소유하지 않는다.
- 복구: 승인된 범위의 변경을 Git diff로 분리하고 사용자 변경을 보존한다. 실패한 후보는 배포하지 않는다. 되돌리기·삭제·Git 조작은 해당 승인 범위를 먼저 확인한다.

### 단계 C — 영향 검증과 소비자 전달

- 진입: 단계 B의 선택된 검사가 통과하고 실제 변경 목록이 확정됐다.
- 검증: 변경한 검사 owner의 회귀 → 영향받은 공개 CLI/소비 fixture 순서로 확인한다. 공개 계약·릴리스·snapshot 재현성을 주장할 때만 그에 필요한 전체 gate와 clean-clone 검증을 추가한다.
- 전달: 실행한 검사와 `not_run`을 구분한다. Core 변경이 있을 때만 승인된 Maintainer commit/배포 절차를 따르고 Creator는 검증된 revision을 별도 소비 작업으로 적용한다.
- 성공: 확인된 결함 및 제외 항목이 모두 처분되고, 문서와 공개 동작이 일치하며, 요청된 완료 수준의 증거가 있다. 숫자 점수나 규칙 수 증가를 종료 조건으로 쓰지 않는다.

## 4. 필수 검증 시나리오

| 대상 | 실패/오인 방지 사례 | 정상 대조 사례 | 증거의 한계 |
|---|---|---|---|
| 완료 주장 | 실행하지 않은 실제 사용 검사를 pass로 보고하려 함 | 합성 검사만 통과했다고 범위를 한정 | 문자열 fixture 통과는 실제 Agent 준수 증명이 아님 |
| 능력·권한 | 작업 위임을 환경 권한으로 간주하거나 거절 뒤 같은 원인으로 재시도 | 정확한 원인을 해소한 승인 범위 내 재시도 | Core는 OS 권한 자체를 강제하지 않음 |
| 상태 진단 | 필수 절 누락·금지 제목·복수 판정 | 유효한 상태와 별도 위험 절 | 형식 검사는 실제 Git 사실의 진위를 보장하지 않음 |
| 중단·재개 | 커밋 완료 후 미커밋이라고 남김, 실제 검증 전 portable 선언 | 미커밋/로컬 의존이면 same-workspace 유지 | 실제 cross-session 재개는 별도 관찰 필요 |
| 교차검증 | 좁은 검색 결과를 전체 부재로 확대, 같은 보고서를 독립 증거로 계수 | 범위·시점·미확인 표시와 원본 대조 | 자동 검색으로 자연어 의미를 확정하지 않음 |
| Core 갱신 | HEAD·index·실행 Core가 다른 후보를 소비 완료로 처리 | 동일 revision 정상 소비와 검증된 새 revision 전환 | 실제 새 revision 전환은 현재 미재현 |

오류가 발생하면 상세 finding과 해당 계약부터 확인하고 최소 범위를 수정한다. 선택된 최종 통합 검사는 생략하지 않되, 문구를 추측해 전체 검사를 반복하지 않는다. 검사 수를 임의의 고정 횟수로 제한하지 않는다.

## 5. Extension과의 연결 및 완료 정의

- Core의 완료/증거 원칙을 영상 상태로 구현하는 일은 E2·E5가 담당한다.
- Core의 실행 전 경계 확인을 Creator worktree와 runtime에 적용하는 일은 E1·E2가 담당한다.
- Core의 상태·재개 원칙을 실제 백룸 핸드오프에 적용하는 일은 E1·E6이 담당한다.
- 현재 공개 계약으로 가능한 Extension 개선은 Core 후보 전체의 완료를 기다리지 않는다. 새 공개 계약이 실제로 필요한 항목만 의존성을 갖는다.

이 계획의 구현 완료는 C1–C6의 처분 근거, 실제 선택 검사 결과, 승인된 변경의 정확한 범위로 판정한다. 현재 문서가 존재한다는 것은 계획 작성 완료일 뿐 개선 구현 완료가 아니다.
