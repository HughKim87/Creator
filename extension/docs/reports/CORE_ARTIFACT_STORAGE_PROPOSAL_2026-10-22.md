# Core 개선 제안 — 프로젝트 산출물의 저장 위치

- 목적: 프로젝트 저장소 밖에 작업 자료·보고서를 임의 저장한 문제의 재발을 막을 Core 공통 개선안을 Maintainer에게 전달한다.
- 읽는 시점: 저장 위치 관련 Core 정책·규칙의 변경 범위를 설계하거나 이번 세션의 Core 보류 범위를 확인할 때.
- 책임: 사용자가 개선 방향·예외를 결정하고 별도 Core Maintainer가 설계·구현·검증한다. Creator Host는 제안 문서만 소유한다.
- 상태: historical. 2026-10-22 제안 당시의 근거다. 현재 Core는 프로젝트 내부 보존·명시적 외부 예외·임시 자원 경계를 소유하므로 이 문서를 새 실행 승인이나 활성 정책으로 사용하지 않는다. 제안 전체의 효과를 실제 제품에서 검증한 것은 아니다.
- 만료 조건: 남은 미반영 주장이 실제로 발견될 때만 해당 범위를 다시 제안하고, 그 밖에는 Git 역사 근거로 유지한다.
- 관련 권위: 최신 사용자 지시, Core 헌장 G2·G3·G4, Core 정보 소유 구조, 작업 계약·문서 작업·파일 정리·규칙 거버넌스 및 Creator Host의 Core 읽기 전용 경계.

## 문제와 소유권

이 세션에서는 프로젝트 자료를 외부 시각화 폴더에 만들고 사용자가 위치를 확인한 뒤에야 프로젝트 안으로 옮겼다. 보고서도 외부 저장을 기본으로 제안했다. 파일이 로컬에 존재하고 Git이 clean이라는 사실만으로 프로젝트가 그 자료와 재개 근거를 소유한다고 볼 수 없다.

처음에는 이 문제 전체를 Extension 실행 누락으로 분류했으나 사용자는 저장소 밖 파일 저장을 Core의 핵심 공통 규칙으로 다뤄야 한다고 명시했다. 이 문서는 다음과 같이 책임을 나눈다.

| 책임 | 소유자 |
|---|---|
| 프로젝트 산출물은 내부 보존을 기본으로 하며 임의 외부 저장을 하지 않는 공통 원칙 | Core 개선 대상 |
| 해당 프로젝트의 보고서·작업·출력 하위 폴더 배치 | Consumer·Extension |
| 이 영상의 원본 대사 발췌·실제 음성 검수 | Extension |
| 사용자 PC의 모든 기존 외부 자료를 자동 이전하거나 삭제하는 권한 | 이번 원칙으로 부여하지 않음 |

## 제안하는 최소 공통 원칙

> 에이전트가 해당 프로젝트 작업을 위해 만드는 산출물·분석 자료·검증 근거·보고서는 그 작업을 소유한 프로젝트 저장소 내부에 보존한다. 외부 저장은 사용자가 대상·목적을 명시해 승인한 범위에서만 사용한다. 파일을 쓰기 전에 실제 저장소 루트와 목적지를 대조하고, 완료 보고 전에 실제 저장 위치와 현재 참조를 확인한다. Core를 읽기 전용으로 소비하는 Host의 작업 자료는 Core 하위가 아닌 Consumer 소유 경로에 둔다.

이는 제안 문구이며 현재 활성 Core 정책을 변경하거나 대신하지 않는다. 저장소 내부 보존은 모든 파일을 Git에 커밋하라는 뜻이 아니다. 미디어·개인 자료·대용량 결과·임시 작업은 Consumer의 보호·ignore·수명 정책을 유지한다. 내부 보존 자체도 백업이나 다른 장치에서의 재현성을 보장하지 않는다.

## 기존 규칙과 실제 빈틈

Core는 이미 프로젝트별 상태·Runtime 데이터를 부모 소비 저장소가 소유한다고 정하고, 작업 계약은 입력·변경 표면·검증을 확인하며 문서 작업은 정본 소유자를 찾게 한다. 그러나 정보의 논리적 소유와 에이전트가 생성할 실제 파일의 기본 목적지, 외부 저장 예외의 승인 조건을 모든 산출물 생성에서 명시적으로 연결하는 보강이 필요하다.

전역 session-close 스킬의 보고서 외부 기본값은 관측 가능한 충돌 사례다. 이 기본값을 프로젝트의 명시적 내부 보존 요구보다 우선할 수는 없다. Core 원칙이 활성화되면 소비 지침·스킬에서 실제 쓰기 목적지를 선택하는 절차도 그 원칙과 맞춰야 한다. 스킬 수정은 Core 파일 변경과는 다른 소유자 작업이며 이번에는 어느 쪽도 수정하지 않았다.

## 최소 변경 소유자 제안

경로는 향후 Maintainer 저장소에서의 Core 상대경로이며 Creator의 core/를 수정하라는 지시가 아니다.

| 대상 | 최소 변경 방향 |
|---|---|
| PROJECT_RULES.md의 기존 승인·쓰기 경계 | 생성 산출물의 내부 기본 위치와 명시적 외부 예외를 공통 불변식으로 둔다. 모든 작은 생성 작업에도 발견 가능해야 한다 |
| rules/work-contract.md | 작업의 실제 저장소 루트·산출물 목적지·승인된 예외를 기존 변경 표면·보호 경계에 연결한다. 별도 중복 정본을 만들지 않는다 |
| rules/document-work.md | 보고서 정본의 논리적 소유와 실제 파일 보존 위치를 연결하고 Git clean 유지를 외부 저장 이유로 쓰지 않는다 |
| 기존 경계·파일 정리 검사와 Core tests | 루트 이탈·예외·현재 참조·보존 검증을 기존 소유자에 통합한다. 새 규칙·스키마가 꼭 필요한지는 구현 조사 후 결정한다 |

구체적인 job ID·영상 폴더·도구 이름·사용자 PC 경로는 Core에 넣지 않는다. Consumer는 자기 하위 디렉터리만 정한다.

## 쓰기 전과 완료 전의 실행 절차

1. 현재 셸 위치와 별개로 실제 작업 소유 저장소 루트를 확인한다. worktree이면 선택된 그 루트가 기준이다.
2. 예정한 목적지를 정규화하고 상대경로 이탈, 절대경로 대체, symbolic link·junction·별도 filesystem 경계로 외부에 쓰게 되는지 확인한다.
3. 사용자 지정 외부 목적지가 있으면 대상·목적·보존 조건을 그 승인 범위와 대조한다. 일반 ‘진행’이나 도구 기본값을 외부 저장 승인으로 만들지 않는다.
4. 생성기·하위 명령·환경 변수·후처리·보고서 저장기가 같은 소유 경계를 따르도록 명시적인 출력 경로를 전달한다. wrapper가 임의 자식 쓰기를 실제로 격리하지 않는다면 그 한계를 밝힌다.
5. 완료 전에 실제 생성 위치와 활성 링크·재개 근거를 확인한다. API 접수나 중간 파일 존재만으로 내부 보존 완료를 주장하지 않는다.

외부 저장 예외가 이미 정확히 승인됐다면 매 파일마다 다시 묻지 않는다. 결과를 보존하는 내부 대안이 있으면 먼저 그 범위에서 작업한다. 외부 도구가 임의 cache·temp를 만드는 경우에도 프로젝트 고유 보고서·증거를 그 위치에 방치하는 근거로 삼지 않으며, 허용되는 임시 자원과 보존 자료의 경계를 별도로 정의한다.

## 적용과 예외

- 적용: 에이전트가 프로젝트 결과·분석·검증·보고·재개를 위해 새로 생성하거나 현재 정본으로 관리할 자료.
- 외부 입력: 사용자가 지정한 외부 원본을 읽는 것은 외부 산출물 생성과 다르다. 원본을 강제로 옮기거나 삭제하지 않는다.
- 명시적 외부 전달: 사용자가 지정한 내보내기·공유·다른 저장소·동기화 폴더는 승인한 예외로 다룬다. 로컬 경로 승인과 외부 게시 권한은 별개다.
- Core Host: ‘저장소 내부’를 읽기 전용 Core submodule 내부로 해석하지 않는다.
- 프로젝트가 없는 작업: 존재하지 않는 저장소를 꾸미지 않는다. 실제 사용자 지정 작업 루트를 확정하고 예외의 의미를 Maintainer 설계에서 결정한다.
- Git: 내부 저장과 stage·commit은 별도 승인·보호 경계를 유지한다. ignore 자료를 억지로 추적하거나 Git clean을 위해 외부로 밀어내지 않는다.

## 기존 외부 자료의 이전

새 원칙만으로 사용자의 외부 폴더 전체에 대한 이동·삭제 권한을 만들지 않는다. 프로젝트가 현재 연결하는 보고서·근거의 정확한 파일을 찾고 소유권·활성 참조·독립 저장소·공유·원본 경계를 확인한다. 사용자 승인 범위에서 내부 보존 후 파일 수·해시·현재 링크를 검증하고 원래 위치의 처분을 수행한다. 출처 경로는 역사 기록으로 보존하되 활성 재개 링크는 내부 파일을 가리킨다.

이번 재검토에서는 비보호 텍스트 253개에서 외부 보고서 참조 두 건을 확인했으며 둘 다 과거 위치의 부재와 내부 본문 해시 일치를 확인했다. 이는 현재 세션의 범위 제한된 관측으로, 다른 실제 Consumer의 반복 사례나 PC 전체 감사의 증거가 아니다.

## 일반화 판단과 검증 제안

G2의 재개 근거 소유, G3의 승인 경계, G4의 실제 보존 완료 주장에 연결된다. Creator 이름·영상·OS 경로 없이 표현할 수 있다. 다만 G2·G3·G4가 곧바로 ‘어떤 파일도 외부에 둘 수 없다’를 도출하는 것은 아니므로 예외를 포함한 최소 기본값의 범위가 적절한지 Maintainer에서 반례 감사를 해야 한다. 단일 프로젝트 경험을 독립된 복수 Consumer 증거로 세지 않는다. 이번 문서는 사용자 지정 Core 후보와 그 검증 요구를 남기는 단계다.

필수 검증 후보는 다음과 같다.

| 시나리오 | 기대 결과 |
|---|---|
| 내부의 일반 보고서·Git 제외 미디어 | 내부 소유 위치에 보존하며 Git 추적은 강제하지 않음 |
| 도구 기본값이 외부 output을 지정 | 내부 경로로 지정하거나 승인된 예외를 확인함 |
| 상대경로 ../ 이탈·절대 외부경로·junction | 실제 외부 쓰기로 판정하고 승인 없이 진행하지 않음 |
| 사용자 지정 외부 내보내기 | 승인한 대상·목적 안에서 허용하고 반복 승인하지 않음 |
| 외부 원본 읽기 | 이 원칙만으로 원본 이동·삭제를 하지 않음 |
| Host가 Core 아래를 출력 경로로 사용 | Consumer 내부라도 Core 읽기 전용 위반으로 거부함 |
| Git clean을 위해 보고서를 외부로 저장 | clean과 보존을 분리하여 내부 보존 정책을 적용함 |
| 내부 복사 성공·현재 링크는 외부 | 실제 재개 참조까지 해소하기 전 완료 주장 제한 |
| 외부 보관본과 내부 해시 일치 | 정확한 승인 범위에서만 원래 파일을 처분함 |
| 프로젝트 미선택·공유 도구 cache | 작업 루트·프로젝트 고유 자료의 경계를 확인하며 임의 폴더를 정본으로 만들지 않음 |

구조·경로 단위 검사와 실제 권한 강제·에이전트 의미 재현을 구분한다. Core 의미 변경에는 일반화 게이트와 독립 반례 감사, route 변경에는 해당 별도 재현 게이트를 적용한다. 프롬프트 문구만으로 실제 OS 쓰기 차단이 성립한다고 주장하지 않는다.

## 다음 작업의 경계

별도 Maintainer 대상과 정확한 변경 범위가 확인된 뒤 설계·구현·검증한다. 이 Creator Host에서는 Core 코드·규칙·gitlink를 변경하지 않는다. 이번 사용자 요청은 Core 구현 제외·문서 보고이므로 전역 session-close 스킬도 수정하지 않았다. 실제 일반화 검증·독립 감사·경로 차단 시험·배포는 not_run이다.
