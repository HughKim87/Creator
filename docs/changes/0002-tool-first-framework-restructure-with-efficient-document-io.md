# 변경 제안 0002 — 신규 프로젝트 청사진: 문서 효율 우선 영상 워크스페이스

- 역할: 지금 구조를 백지에서 다시 만든다면의 전체 구성안. 승인 시 마이그레이션의 기준 설계가 된다.
- 읽는 시점: 이 청사진을 승인·구현·검증하거나 구조 재편 범위를 판단할 때
- 보존 조건: 구현 후에도 설계 근거로 유지하며 후속 변경은 새 change ID로 작성한다.
- 상태: `proposed` — 사용자 승인 전 구현 금지
- change_id: `0002`
- 적용 원칙: 컨텍스트 예산, 결정적 검증, 에이전트 중립, 프레임워크 재사용
- 전제: 문서 읽기·쓰기는 워크플로의 핵심으로 유지한다. 없애는 것이 아니라 단계화한다.

## 1. 설계 목표

- 세션 시작 비용을 고정한다: 어떤 상황이든 시작 로드는 60줄 이내.
- 문서는 3단계(메타데이터→본문→참조)로 열리고, 전부-아니면-전무 읽기를 없앤다.
- 상태 원본은 영상당 1개다. 손으로 쓰는 상태 문서는 존재하지 않는다.
- 프레임워크와 영상 작업을 물리적으로 분리해 소유권 판정 자체를 없앤다.
- 규칙은 그것이 다스리는 폴더 옆에 산다. 중앙 규칙은 안전 커널만 남긴다.

## 2. 저장소 구성 (2-저장소)

### 2.1 `studio/` — 프레임워크 저장소 (버전 릴리스)

```text
studio/
├── AGENTS.md              # 안전 커널 + 진입 (15줄 이내, 전 에이전트 공통)
├── bin/vid                # 단일 CLI 진입점 (projectctl 후계)
├── core/                  # state, render, gate, doccheck 파이썬 패키지
├── stages/<stage>/        # 단계 계약: 01_plan … 08_review
│   ├── AGENTS.md          #   단계 규칙 (L2, 단계 진입 시만 로드)
│   ├── CONTRACT.yaml      #   게이트·입출력·증거 요건 (기계 판독)
│   └── guide.md           #   상세 절차·예시 (L3, 필요 시만)
├── docs/
│   ├── INDEX.md           # 프론트매터에서 자동 생성 (손편집 금지 표식)
│   └── changes/           # SDD 변경 제안 (0001 게이트 유지)
├── tools/                 # ffmpeg 래퍼, synccheck, edit_memory 등 이식
└── tests/
```

### 2.2 `studio-work/` — 작업 저장소 (영상별, 얇게)

```text
studio-work/<video-id>/
├── inputs/                # 원본. 읽기 전용, 도구가 쓰기 자체를 제공하지 않음
├── state.json             # 유일한 상태 원본 (단계·후보·결정·차단·다음 행동)
├── outputs/<stage>/       # 산출물 + edit_memory DB
└── HANDOFF.md             # state.json에서 렌더링되는 생성 뷰. 손편집 금지
```

- 분리 효과: 프레임워크 경로 분류, 커밋 소유권 규칙, 게이트 예외 목록이 작업
  세션에서 사라진다. 영상 작업 세션은 프레임워크 문서를 읽을 일이 없다.
- SDD 게이트(0001)는 `studio/`에만 적용된다. `studio-work/`는 게이트 대상이 아니다.

## 3. 문서 체계 (핵심 — 계층형 지식베이스)

문서가 프로젝트의 영속 자산이고 세션은 무상태 작업자다. 근거 리서치는 세션 보고
(2026-07-17) 참조: Memory Bank, Johnny Decimal, Diátaxis, RAPTOR, 자기유지 KB 패턴.

### 3.1 4계층 구조

- L0 기본규칙(상수, 40줄 이내): 안전 커널 + "상황→인덱스" 결정적 라우팅 테이블.
  모든 세션이 유일하게 무조건 읽는 문서다.
- 인덱스 계층(대분류→중분류→소분류): 각 인덱스는 하위 항목의 이름·역할·읽는 시점만
  담는다. 번호 분류(10 기획, 20 자막, 30 분석, 40 편집, 50 검토, 90 프레임워크)로
  모든 잎이 단 하나의 주소를 갖는다. 인덱스당 항목 10개 이하, 초과 시 분할한다.
  모든 인덱스는 잎 프론트매터에서 생성하며 손편집은 커밋 검사가 차단한다.
- 잎 문서(지식): 한 문서 한 유형 — contract(기준·계약), procedure(절차),
  rationale(근거·설명), log(결정 기록). 유형별 템플릿과 줄 예산을 doccheck가 강제한다.
  잎 사이 링크는 이유를 한 줄 붙일 때만 허용한다(의미 없는 링크 금지).
- 메타 프레임워크(문서의 문서): 작성 위치 결정 규칙, 프론트매터 규격
  (`name`, `role`, `read_when`, `type`, `budget`, `owner`, `updated_at`),
  분할·병합·폐기 기준. 규칙마다 대응 검사가 있어야 한다.

### 3.2 읽기 프로토콜

- 시작 로드 = L0 + 현재 작업의 라우팅 경로(인덱스 2~3개 + 잎 1~2개)로 고정.
- 문서 총량이 늘어도 읽기량은 트리 깊이에 비례한다(경로 총 예산을 doccheck가 강제).
- 같은 상황 입력이면 어떤 에이전트든 같은 경로가 나와야 한다(라우팅 결정성).

### 3.3 쓰기 프로토콜 (write-back 의무)

- 세션에서 생긴 재사용 판단·결정은 해당 분류의 잎에 기록해야 `vid done`이 통과한다.
- 문서화 경계(하이브리드): 지식·판단·결정은 문서, 기계 상태는 state.json/DB,
  사람용 상태 뷰는 렌더링 생성물이다.
- 같은 규칙이 두 문서에 존재하면 오류다(중복 퇴적 방지).
- 신선도 관리: 잎마다 `updated_at`·`owner`를 두고, 검사기가 만료 후보·문서 간 모순·
  끊긴 참조를 주기 감사로 보고한다. 병합·분할·폐기는 보고 후 사용자 승인으로만 실행한다.

## 4. 규칙 배치

- 전역 안전 커널(AGENTS.md, 7줄 이내): 비밀 금지, 원본 보존, 삭제·푸시·업로드·결제 전
  질문, 3회 실패 중단, 나머지는 도구가 강제.
- 단계 규칙은 `stages/<stage>/` 하위 AGENTS 파일에, 도구 규칙은 `tools/` 하위
  AGENTS 파일에 둔다. 해당 폴더에서 작업할 때만 로드된다(AGENTS 계층 표준, 에이전트 중립).
- 산문 규칙 30개 → 노출 명령 10개: 위험 행동은 규칙으로 금지하지 않고 CLI가
  제공하지 않는 방식으로 제거한다. 반복 교정은 규칙 추가가 아니라 검사 추가로 흡수한다.

## 5. 상태 모델과 세션 수명주기

### 5.1 상태

- `state.json` 필드: video_id, source_fingerprint, stage, candidates, decisions[],
  first_pending_action, blockers[], forbidden_now[], updated_at.
- 갱신은 anchored iterative: 재요약 없이 결정·다음 행동·차단만 증분 갱신.
- 편집 판단 계보는 기존 edit_memory DB(이벤트 소싱)를 그대로 이식한다.
- 사람용 HANDOFF 문서와 에이전트용 재개 캡슐은 모두 state.json 렌더링 결과다.

### 5.2 세션 흐름

```text
시작:  vid context            # 안전 커널 + L1 목록 + 캡슐 + 다음 행동 (≤60줄)
작업:  vid <stage-command>    # 단계 진입 시 해당 L2 자동 안내
검증:  vid check              # doccheck + 테스트 + 게이트, compact 출력 (≤2,000자)
종료:  vid done               # 게이트 통과 시 state.json 갱신 + HANDOFF 재렌더링
```

- fast_resume/audit/mutation 모드(0001)는 `vid context`/`vid check`/`vid done`에 흡수된다.
- 상태를 바꾸는 명령은 `vid done`과 명시적 결정 기록 명령뿐이다. 조회는 전부 읽기 전용.

## 7. 마이그레이션 순서 (승인 후)

1. `studio/` 뼈대와 `vid context`·`state.json` 렌더링을 만든다 (신규 코드 최소).
2. 진행 중 영상이 없는 시점에 기존 도구를 이식하고 테스트를 옮긴다.
3. 다음 영상 1편을 새 구조로 처음부터 끝까지 진행하며 실측한다 (파일럿).
4. 파일럿 통과 후 기존 저장소를 읽기 전용 보관으로 전환한다.
5. 각 단계는 독립 커밋, `[change: 0002]`. 파일럿 중 발견 사항은 검사로 흡수한다.

## 8. 승인 기준

- 새 세션 시작 로드가 60줄 이내이고, 현행(126줄·6,269자) 대비 50% 이상 작다.
- 어떤 상태 문서도 손편집되지 않는다: HANDOFF·캡슐이 state.json에서 재생성 가능하다.
- `docs/INDEX.md`가 프론트매터에서 재생성되고 손편집·불일치를 doccheck가 잡는다.
- 영상 작업 세션이 프레임워크 문서를 0개 로드하고 파일럿 1편을 완주한다.
- 중복 규칙 검출이 동작하고, 이식된 전체 테스트와 0001 게이트가 통과한다.
- 라우팅 결정성: 대표 상황 10개에 대해 라우팅 테이블이 항상 같은 경로를 내고,
  경로 총 읽기량이 예산 안이다.
- write-back: 파일럿에서 생긴 재사용 판단이 전부 올바른 분류의 잎에 기록된다.

## 9. 검증 계획

- 프론트매터→INDEX 생성 왕복 테스트(생성→변조→검출).
- state.json→HANDOFF/캡슐 렌더링 스냅샷 테스트.
- 시작 로드 줄·문자 실측 비교(현행 대비, CJK 경로·Windows 포함).
- 파일럿 영상 1편: 각 단계 게이트 통과 기록과 세션당 시작 비용 기록.
- 게이트·훅·CI를 `studio/`에서 재실행해 0001 검증 계획과 동등함을 확인.

## 10. 위험과 rollback 조건

- 재작성 자체가 메타작업 폭주가 될 위험 → 7장 순서 고정, 파일럿 1편 전까지 기존
  저장소를 삭제·동결하지 않는다. rollback은 기존 저장소로 복귀하면 끝이다.
- 생성 뷰가 상태 원본과 어긋날 위험 → 렌더링은 순수 함수로 만들고 스냅샷 테스트로 고정.
- 규칙 분산으로 발견성 저하 위험 → L1 전체 로드가 상쇄하는지 파일럿에서 실측.
- 2-저장소 동기화 부담 위험 → 프레임워크는 릴리스 버전으로만 참조하고 작업 저장소는
  버전을 기록만 한다. 임의 시점 혼합 참조를 금지한다.
