# 정보·문서 책임 구조

- 목적: 활성 정보와 문서의 권위, 유형, 단일 소유자, 배치, 읽기·쓰기 조건을 정의한다.
- 읽는 시점: 새 유지 문서를 만들거나 기존 문서의 책임·위치·정본 여부를 판단할 때, Stage 01.5 문서 지도를 구성할 때.
- 책임: 프로젝트 에이전트가 유지하고 사용자가 정책·범위 변경을 승인한다.
- 상태: Stage 01 활성 계약.
- 관련 권위: `PROJECT_RULES.md`, `docs/build/MASTER_BUILD_PLAN.md`, `SESSION_HANDOFF.md`.

## 1. 기본 원칙

- 권위 역할과 문서 유형을 서로 다른 축으로 판정한다. 하나의 평면 분류로 두 의미를 섞지 않는다.
- 정보마다 활성 소유자는 하나다. 다른 문서는 링크하거나 파생 표현만 제공한다.
- 새 문서는 기존 소유자가 목적을 충족하지 못할 때만 만든다.
- 폴더는 독자보다 책임을 우선해 나누며, 실제 파일이 필요하기 전에는 빈 미래 폴더를 만들지 않는다.
- 구조화 데이터 형식, ID, 자동 생성, 검색 색인은 후속 단계가 소유한다.

## 2. 권위 역할

| 권위 역할 | 의미 | 변경 기준 | 대표 예시 |
|---|---|---|---|
| 권위 정본 | 현재 정책·계약·계획·상태 또는 검증된 장기 지식을 직접 소유 | 승인된 책임자가 해당 소유자에서 갱신 | `PROJECT_RULES.md`, `SESSION_HANDOFF.md`, `failures/*.md` |
| 파생 표현 | 정본을 사용자나 도구가 읽기 쉽게 요약·표시하며 정본을 바꾸지 않음 | 원 정본 변화에 맞춰 재생성·갱신 | `README.md`, 향후 Obsidian 지도·검색 결과 |
| 시점 증거 | 특정 시점의 조사·분석·검증 결과를 보존하며 현재 실행 지시가 아님 | 원칙적으로 불변, 대체 상태와 새 정본 링크만 추가 | `reports/*.md` |

`SESSION_HANDOFF.md`는 현재 상태를 직접 소유하므로 파생 문서가 아니라 `권위 정본 + 현재 상태`다. Git 상태처럼 다시 조회 가능한 동적 사실은 장기 소유하지 않는다.

## 3. 문서 유형

| 문서 유형 | 포함하는 것 | 포함하지 않는 것 | 현재 소유 위치 |
|---|---|---|---|
| 시작 라우터 | 세션 시작 순서와 작업 규칙 선택 경로 | 실제 정책·현재 상태 본문 | `AGENTS.md` |
| 정책 | 항상 적용되는 안전·권한·소유권 경계 | 작업별 절차와 긴 실패 역사 | `PROJECT_RULES.md` |
| 절차 | 특정 행동에서 적용하는 실행·검증 규칙 | 전 작업 공통 정책 | `rules/*.md` |
| 계약·참조 | 정보 구조와 구현 전 합의된 책임·경계 | 현재 실행 상태 | `docs/INFORMATION_ARCHITECTURE.md`, 향후 승인된 계약 |
| 단계 계획 | 단계 목표·범위·결정·검증·점수 | 다른 단계 구현 상세 | `docs/build/*.md` |
| 현재 상태 | 검증된 현재 단계·차단·첫 다음 행동 | 해결된 실패의 장문 지식, 동적 Git 수치 | `SESSION_HANDOFF.md` |
| 사용자 가이드 | 사용자가 목적과 사용 경로를 이해하는 설명 | 내부 실행 절차의 복제 | `README.md`, 실제 필요 시 승인된 추가 가이드 |
| 시점 보고서 | 조사·분석·검증의 당시 근거 | 현재 정책·현재 단계 지시 | `reports/*.md` |
| 실패 지식 사례 | 해결된 실패의 증상·원인·시도·해결·검증·재발 방지 | 현재 미해결 시도, 보호 데이터 원문 | `failures/*.md` |

향후 구조화 데이터는 문서 유형이 아니다. Stage 02 이후 승인된 데이터 계약과 저장 위치가 별도로 소유한다.

## 4. 활성 배치 계약

| 위치 | 책임 | 배치 금지 |
|---|---|---|
| 저장소 루트 | 시작 라우터, 상시 정책, 현재 상태, 사용자 개요, 저장소 설정 | 단계 상세, 사례 모음, 빈 미래 폴더 |
| `rules/` | 작업 행동별 조건부 절차 | 상시 정책, 현재 상태, 사용자 데이터 |
| `docs/` | 활성 계약과 유지 설명 | 시점 보고서, 보호 데이터 |
| `docs/build/` | 마스터 구축 순서와 단계 계획 | 운영 정본 데이터, 실행 결과 데이터 |
| `schemas/` | 공통 외피와 현재 승인된 작업·지식·수명주기·컨텍스트 payload의 기계 판독 구조 계약 | 미승인 미래 유형, 실행 상태 원문 |
| `src/` | 승인된 프레임워크 검증·I/O·수명주기·선택 컨텍스트·유지보수 구현 | 보호 사용자 데이터, 작업별 사실 |
| `tests/` | 중립 fixture와 정상·실패 회귀 검증 | 사용자 원본, 운영 정본 데이터 |
| `data/` | 승인된 공통 기록·event의 프레임워크 데이터 루트 | `inputs/`·`outputs/` 사용자 데이터와 미승인 유형 |
| `failures/` | 원인별 장기 실패 지식과 링크 전용 색인 | 현재 미해결 실패, 단계별 복제본 |
| `reports/` | 날짜가 있는 시점 증거 | 현재 실행 지시, 현재 상태 정본 |
| `backup/` | 읽기 전용 역사 증거 | 활성 의존성, 신규·수정 파일 |
| `inputs/`, `outputs/` | 사용자가 정확히 지정한 보호 데이터 | 프레임워크 문서와 Git 추적 대상 |

에이전트용·사용자용이라는 이유만으로 기존 문서를 전면 이동하지 않는다. 책임이 다른 문서는 현재 역할 폴더로 분리하고, 동일 책임의 독자 차이는 문서 안의 독자·언어 조건으로 처리한다.

## 5. 언어 계약

- 사용자 검토가 필요한 계약, 계획, 상태, 가이드, 보고서, 실패 지식은 한국어를 기본으로 한다.
- 에이전트 전용 시작 라우터와 작업 규칙은 정확성과 간결성을 위해 영어를 사용할 수 있다.
- 사용자와 에이전트가 함께 판단하는 문서는 한국어를 우선한다.
- 기계 필드명과 데이터 직렬화 언어는 Stage 02 전에는 확정하지 않는다.

## 6. 최소 문서 설명

새로 만들거나 책임이 바뀌는 유지 문서는 사람이 읽을 수 있는 다음 정보를 가져야 한다.

- 목적
- 읽는 시점 또는 사용 조건
- 책임 또는 소유자
- 현재 상태
- 관련 권위 또는 출처

YAML이나 공통 기계 스키마를 강제하지 않는다. 기존 문서가 제목·서문·절 구조로 같은 정보를 명확히 제공하면 일괄 변환하지 않고, 실제 수정 시 부족한 항목만 보완한다.

## 7. 문서 생성 게이트

새 유지 문서를 만들기 전에 다음을 순서대로 확인한다.

1. 기존 소유자를 경로와 문서 유형으로 검색한다.
2. 새 문서만의 지속적인 목적과 독자를 한 문장으로 설명한다.
3. 권위 역할과 문서 유형을 각각 하나씩 정한다.
4. 포함 정보와 금지 정보를 정하고 기존 정본을 복제하지 않는지 확인한다.
5. 읽기·쓰기 조건, 책임자, 수명주기를 정한다.
6. 정책·범위·보호 데이터·외부 변경이면 필요한 사용자 권한을 확인한다.
7. 기존 소유자 갱신이나 파생 표현으로 충분하면 새 문서를 만들지 않는다.

### 대표 판정

| 요청 | 판정 | 이유 |
|---|---|---|
| 새로운 상시 안전 규칙 | `PROJECT_RULES.md` 갱신 | 정책 소유자가 이미 존재 |
| 특정 Git 절차 | `rules/version-control.md` 갱신 | 조건부 절차 소유자가 이미 존재 |
| 현재 차단과 첫 행동 | `SESSION_HANDOFF.md` 갱신 | 현재 상태 단일 정본 |
| 해결된 새로운 원인의 실패 | 기존 원인이 없을 때만 `failures/` 사례 생성 | 장기 재사용 목적과 독립 원인이 존재 |
| 특정 시점 조사 결과 | 날짜가 있는 `reports/` 문서 | 현재 정본이 아닌 시점 증거 |
| 전체 구조를 보여주는 Obsidian 화면 | 정본 링크에서 파생 | 화면이 기존 정본을 대체하지 않음 |

## 8. 보고서 보존·대체

- `reports/` 문서는 기간 제한 없이 Git 이력에 보존한다. 삭제·이동은 별도 사용자 승인을 받는다.
- 새 분석이 이전 보고서를 대체해도 과거 본문을 현재 결론으로 다시 쓰지 않는다.
- 대체된 보고서는 상단에 `상태: 대체됨`, 대체 시점, 새 권위 문서 링크를 추가한다.
- 일부만 유효하면 유효 범위와 더 이상 실행 지시가 아닌 범위를 함께 표시한다.
- 현재 정책이나 상태는 보고서가 아니라 해당 활성 정본에서 갱신한다.

## 9. 수명주기와 갱신 책임

| 유형 | 생성 | 갱신 | 종료·대체 |
|---|---|---|---|
| 정책·계약·절차 | 승인된 필요가 있을 때 | 책임 범위가 바뀔 때 | 새 정본에서 대체 관계 명시 |
| 단계 계획 | 단계 착수 전 | 결정·검증·점수 변화 시 | 완료 뒤 결정·검증 증거로 유지 |
| 현재 상태 | 활성 작업 전환 시 | 검증된 상태와 첫 행동이 바뀔 때 | 새 현재 상태로 같은 문서 갱신 |
| 사용자 가이드 | 실제 사용자 경로가 생길 때 | 활성 경로가 바뀔 때 | 정본 링크를 유지하며 축약·대체 |
| 시점 보고서 | 조사·분석 요청 결과 | 대체 안내만 추가 | Git에 역사 증거로 보존 |
| 실패 지식 | 원인·해결·성공 검증이 확인될 때 | 같은 원인 재발·새 검증 시 | Markdown 정본 유지, 구조화 projection 개정은 Stage 06 lifecycle로 옛 record를 보존하며 대체 |

## 10. Stage 01.5 인계 표현

Obsidian 검토 화면은 각 활성 문서에서 다음 의미를 읽어 표시해야 한다.

- 경로와 제목
- 권위 역할
- 문서 유형
- 상태
- 소유 책임
- 관련 권위와 파생 관계
- 보호·역사 경계

이는 관계 표현 계약이며 JSON, YAML, 플러그인, 그래프 저장 형식을 확정하지 않는다. Stage 01.5는 기존 Markdown과 링크에서 파생 화면을 만들고 정본을 복제하지 않아야 한다.

## 11. 변경 절차

- 권위 역할, 문서 유형, 소유 위치의 추가·병합·이동은 사용자 승인 대상이다.
- 문구 정리와 링크 보정은 승인된 의미를 바꾸지 않는 범위에서 프로젝트 에이전트가 수행할 수 있다.
- 새 유형은 실제 사례가 기존 유형으로 표현되지 않을 때만 제안한다.
- 이 계약과 `PROJECT_RULES.md`가 충돌하면 상시 정책이 우선하며 계약을 보정한다.
