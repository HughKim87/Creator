# 점진적 프로젝트 재구축 계획

- 상태: 정본
- 원칙: 기존 자산을 살리고, 실제 문제를 해결하는 최소 변경만 한 단계씩 도입한다.
- 진행 조건: 현재 단계의 완료 기준을 확인한 후에만 다음 단계로 넘어간다.
- 승계 기준: `docs/INHERITANCE_MAP.md`. 새 구현 전에 관련 기존 자산의 승계 결정을 확인한다.

## 기존 체계 처리

### 유지

- 사용자 원본 보호, `inputs/`·`outputs/` 경계, 백업 읽기 전용 원칙.
- Git 이력과 `backup/`의 기존 규칙·워크플로우·품질 기준·도구·스킬 원본.
- 안정된 원본 식별, 원본 시간·프레임 기반 근거, 변경 없는 결과 재사용 방식.
- 촬영 전·촬영 완료본의 제작 경로와 데이터 분석 → 기획 → 편집 순서.
- 과거에 실제로 동작한 코드와 검사 중 현재 문제 해결에 직접 필요한 구현.
- 규칙 정본 1개, 현재 상태 문서 1개, 실행 계획 1개의 최소 문서 체계.

### 단순화

- 과거의 여러 계획과 상태 문서는 이 계획과 `SESSION_HANDOFF.md`로 축소한다.
- 검사와 명령은 실제 반복 작업을 줄이는 진입점만 남긴다.
- 기존 원본 자산 목록은 핵심 식별·원본 범위·경로·검증 필드를 유지하되 실제 소비자가 없는
  필드는 필수 항목에서 뺀다.
- 파일 기반 작업 상태는 여러 정본 대신 사람이 읽을 수 있는 파일 하나로 시작한다.
- 워크플로우는 실제 순서와 필수 완료 조건만 남기고, 예외 처리는 필요할 때 추가한다.
- 기존 도구와 스킬은 전부 이식하지 않고 사용 빈도가 확인된 것만 연결한다.

### 제거 또는 보류

- 새로 만들었던 다층 도메인·서비스·어댑터 구조, SQLite 상태 저장소와 이벤트 기반 편집 기억은
  백업 상태로 보류한다.
- 독립 QA·레드팀·단계별 증거 패키지·장기 관찰 게이트는 도입하지 않는다.
- 기계 판독형 전체 워크플로우 계약, 자동 상태 전이, 복잡한 승인 상태, 이벤트 로그,
  격리·승격 프로토콜은 보류한다.
- 사용 목적이 확인되지 않은 CLI, 플러그인, 스킬 이식은 보류한다.
- 기존 파일의 일괄 이동·개명·마이그레이션과 미래 대비 추상화는 하지 않는다.

## 1단계 — 기본 프로젝트 기반 정비

### 해결하려는 실제 문제

- 기존 루트에는 현재 사용하는 기반과 중단된 재구축 산출물이 섞여 있어 무엇이 정본인지
  판단하기 어려웠다.
- 파일의 위치, 원본 보호, 파생 결과 저장 기준이 실행 가능한 최소 구조로 연결되어 있지 않다.
- 대표 파일 작업을 시작할 작고 분명한 진입점이 없다.
- 기존 자산에서 반드시 이어져야 할 계약과 보류할 구현을 구분하지 않으면 핵심을 잃거나
  같은 기능을 다시 만들 위험이 있다.

### 기존 체계에서 재사용할 요소

- 백업의 파일 경계·원본 보호·원본 식별·결과 재사용 규칙.
- 최소 부트스트랩과 문서 라우팅 방식.
- Python 실행 래퍼, FFmpeg·ffprobe와 대표 파일 작업에 이미 사용한 도구가 있다면 해당 구현과 테스트.
- 기존 Git 이력과 재현 가능한 의존성 정보는 필요한 항목만 참고한다.

### 꼭 필요한 최소 변경

- `docs/INHERITANCE_MAP.md`에서 관련 자산의 승계 결정을 먼저 확인한다.
- 첫 대표 파일 작업 하나를 정하고, 그 작업에 필요한 입력·처리·출력 경로만 만든다.
- 기존 구현을 그대로 쓰거나 작게 고칠 수 있는지 확인한 뒤, 원본을 읽고 별도 결과를 쓰는
  가장 작은 실행 단위를 마련한다.
- 필요한 의존성과 실행 방법을 한 곳에 기록한다.
- 원본 비변경, 출력 위치, 실패 보고를 확인하는 최소 검사만 둔다.
- 파일 도구나 플러그인은 실제 작업 시간을 줄인다는 근거가 있을 때 하나씩 도입한다.

### 기대되는 품질 및 생산성 개선

- 원본 손상과 결과 위치 혼동을 막는다.
- 같은 종류의 파일 작업을 동일한 입력과 명령으로 반복할 수 있다.
- 새 세션이 규칙과 실행 방법을 여러 문서에서 다시 찾지 않아도 된다.

### 추가되는 관리 비용

- 루트 규칙·핸드오프·계획 문서 3개를 유지한다.
- 대표 파일 작업용 실행 진입점과 소수의 검사만 관리한다.
- 단계 종료 시 통합 검증 한 번과 짧은 핸드오프 갱신이 필요하다.

### 완료 기준

- 필수 승계 항목이 현재 규칙 또는 단계별 회수 경로에 빠짐없이 연결돼 있다.
- 대표 파일 하나가 원본 변경 없이 정해진 출력 위치로 처리된다.
- 같은 작업을 다시 실행해도 결과와 실패 방식이 예측 가능하다.
- 실행 방법과 파일 위치를 루트 문서만으로 찾을 수 있다.
- 추가 절차가 수작업보다 느리게 만들지 않았음을 실제 실행으로 확인한다.
- 사용자가 기반이 충분히 단순하고 안정적이라고 확인한다.

### 이번 단계에서 하지 않을 일

- 영상 제작 전체 워크플로우, 단계 전환, 승인 체계를 구현하지 않는다.
- 데이터베이스, 상태 머신, 다층 아키텍처를 도입하지 않는다.
- 사용하지 않은 도구·플러그인·스킬을 미리 설치하거나 이식하지 않는다.
- 기존 프로젝트 데이터를 일괄 정리하거나 변환하지 않는다.

## 2단계 — 프로젝트 워크플로우 정비

### 해결하려는 실제 문제

- 1단계 기반을 실제로 사용한 뒤 확인된 작업 순서 누락, 반복 입력, 재개 비용만 해결한다.
- 문제가 관찰되지 않았다면 이 단계의 해당 변경은 시작하지 않는다.

### 기존 체계에서 재사용할 요소

- 백업의 8단계 제작 순서와 촬영 완료본의 `자막 확인 → 데이터 분석 → 영상 기획 → 편집 → 검수` 경로.
- 원본 `source_id`, 원본 시간·프레임 기반 자산 목록, 현재본·대체본 관계.
- 기존 도구와 단계별 스킬 중 실제 작업에 맞았던 부분.
- 1단계에서 안정적으로 작동한 파일 처리 구조와 검사.
- 사람이 이미 익숙하게 사용한 파일 형식과 폴더 관례.

### 꼭 필요한 최소 변경

- 실제 작업 순서와 단계별 필수 입력·출력·완료 조건만 한 문서에 정리한다.
- 기존 제작 순서와 사용자 판단 지점은 보존하고, 과도한 승인 상태와 중복 메타데이터만 줄인다.
- 반복해서 잊거나 다시 입력하는 항목만 템플릿 또는 파일 하나로 줄인다.
- 자주 쓰는 기존 도구만 현재 진입점에 얇게 연결한다.
- 플러그인은 반복 작업의 시간 절감 효과를 먼저 확인한 뒤 하나씩 도입한다.
- 스킬은 실제로 사용하는 단계부터 기존 규칙과 입출력에 맞춘다.

### 기대되는 품질 및 생산성 개선

- 필수 단계 누락과 산출물 혼동이 줄어든다.
- 중단된 작업을 다시 파악하는 시간이 짧아진다.
- 자주 하는 작업의 명령·경로·입력을 다시 찾는 시간이 줄어든다.

### 추가되는 관리 비용

- 짧은 워크플로우 규칙 문서 하나와 필요한 최소 템플릿을 관리한다.
- 실제로 사용하는 도구 연결부와 스킬만 유지한다.
- 작업자가 직접 갱신해야 하는 상태 기록은 꼭 필요한 한 곳으로 제한한다.

### 완료 기준

- 대표 작업이 정해진 순서로 처음부터 끝까지 한 번 완료된다.
- 중단 후 재개할 때 한 곳만 확인해 다음 행동을 결정할 수 있다.
- 필수 완료 조건은 놓치지 않으면서 불필요한 승인이나 중복 기록이 없다.
- 도입한 도구·플러그인·스킬이 실제 작업 시간이나 오류를 줄였음을 확인한다.
- 사용자가 워크플로우가 안정적이며 과도하지 않다고 확인한다.

### 이번 단계에서 하지 않을 일

- 모든 예외 상황을 미리 모델링하지 않는다.
- 자동 단계 전환, 복잡한 승인 상태, 강제 게이트를 만들지 않는다.
- 기존 도구와 스킬 전체를 한꺼번에 이식하거나 다시 쓰지 않는다.
- 프로젝트 고유 기능을 기반 안정화 전에 확장하지 않는다.

## 3단계 — 프로젝트 목적에 맞는 개선

### 해결하려는 실제 문제

- 1·2단계가 안정된 뒤 실제 영상 제작에서 반복 확인된 품질 또는 생산성 병목 하나를 해결한다.
- 구체적인 병목과 사례가 없으면 이 단계의 새 기능을 만들지 않는다.

### 기존 체계에서 재사용할 요소

- 백업에 있는 원본 근거 추적, 편집 microbeat, 긴 컷 근거, 초·중·후반 표본 검증 기준.
- Premiere XML, 원본 프레임 자산, 동기 검사, 편집 품질 감사 도구와 관련 테스트.
- 영상 제작 규칙, 분석·동기화·자산 관리 도구와 스킬 중
  해당 병목에 직접 관련된 부분.
- 1·2단계에서 검증된 파일 구조, 실행 진입점, 워크플로우 규칙.

### 꼭 필요한 최소 변경

- 한 번에 병목 하나를 선택한다.
- 기존 자산을 그대로 연결하거나 작게 수정하는 방안을 먼저 시험한다.
- 실제 제작 한 사이클에서 효과를 확인하고, 효과가 없으면 되돌린다.
- 효과가 확인된 변경만 정본 규칙·도구·스킬에 반영한다.

### 기대되는 품질 및 생산성 개선

- 프로젝트 고유 품질 문제를 해결하면서 반복 수작업을 줄인다.
- 효과가 확인된 개선만 누적되어 체계가 불필요하게 커지지 않는다.
- 실제 제작 결과와 작업 시간으로 다음 투자 여부를 판단할 수 있다.

### 추가되는 관리 비용

- 한 시점에 개선 항목 하나와 그에 필요한 규칙·도구·스킬만 관리한다.
- 효과 확인과 되돌리기 판단을 위한 짧은 기록만 남긴다.
- 기존 공통 기반을 바꾸는 경우에만 관련 검사를 갱신한다.

### 완료 기준

- 선택한 병목의 품질 오류 또는 반복 시간이 실제 제작에서 줄어든다.
- 새 절차의 실행·학습·유지 비용이 절감 효과보다 작다.
- 기존 기반과 워크플로우의 안정성을 해치지 않는다.
- 사용자가 변경을 유지할 가치가 있다고 확인한다.

### 이번 단계에서 하지 않을 일

- 필요성이 확인되지 않은 목적별 기능을 묶음으로 설계하지 않는다.
- 언젠가 쓸 수 있다는 이유로 플러그인·도구·스킬을 추가하지 않는다.
- 전체 체계를 다시 갈아엎거나 범용 플랫폼으로 확장하지 않는다.
- 실제 제작 검증 없이 새 개선을 다음 개선의 선행 조건으로 만들지 않는다.
