# 단계 01 작업 지시서: 신뢰 가능한 최소 루트

## 1. 단계 목적

검사가 실행되지 않거나 실패하면 반드시 비정상 종료하는 신규 프로젝트 최소 골격을
만든다. 이 단계에서는 영상 기능이나 상태 DB를 이식하지 않는다. 목표는 기능 수가
아니라 실행·검증 결과를 신뢰할 수 있게 만드는 것이다.

## 2. 시작 게이트

- 단계 00 보고서와 이식 목록이 검증됐다.
- `backup/` 무변경 기준선과 롤백 SHA가 식별됐다.
- 사용자가 단계 01의 신규 파일 작성과 필요한 의존성 설치를 승인했다.
- 총괄 에이전트가 공통 파일 소유권을 배정했다.

하나라도 충족되지 않으면 구현을 시작하지 않는다.

## 3. 공개 계약

총괄 에이전트는 구현 전에 다음 계약을 동결한다.

```text
workflow doctor [--json]
workflow check [--scope fast|full]
```

- 모든 검사 성공만 종료 코드 0을 반환한다.
- 검사기, 필수 파일, Python, 의존성, Git 루트를 찾지 못하면 비정상 종료한다.
- 예외를 잡아 경고만 출력하고 성공으로 바꾸지 않는다.
- 사람이 읽는 출력과 기계용 JSON은 같은 판정을 사용한다.
- 로컬 훅과 CI는 `workflow check`라는 동일 진입점을 사용한다.
- 하위 검사가 종료 코드 `7`을 반환하면 `workflow check`와 pre-commit도 정확히 `7`을
  반환한다. 실행 도구 자체를 찾지 못한 경우의 표준 코드는 `127`로 고정한다.
- 외부 명령은 문자열 셸 명령이 아니라 argv 배열, `shell=False`, 명시적 timeout으로
  실행한다. Python 도구는 현재 잠금 환경의 `sys.executable -m <module>`을 사용하며
  PATH에서 우연히 발견한 다른 Python을 사용하지 않는다.
- 실행 파일 결손, 권한 오류, timeout, 신호 종료를 성공이나 `not_run`으로 바꾸지 않는다.

정확한 CLI 옵션을 변경해야 하면 구현 전에 총괄 에이전트와 검증 에이전트가 계약을
갱신한다.

## 8. 세부 작업

### 작업 01-1: Python 환경 고정

1. 지원 Python 버전을 하나로 명시한다.
2. `pyproject.toml`에 프로젝트 메타데이터와 개발 의존성을 선언한다.
3. `uv.lock`을 생성하고 버전 관리 대상으로 둔다.
4. CI는 잠금 파일을 갱신하지 않고 잠금 상태가 맞는지 검사한다.
5. 로컬 표준 명령도 잠금 환경을 사용한다.
6. 기존 Windows 배치 래퍼를 신규 표준 진입점으로 사용하지 않는다.

초기 CLI는 표준 라이브러리로 구현할 수 있으면 별도 프레임워크를 추가하지 않는다.

### 작업 01-2: `doctor` 구현

최소 검사 항목:

- 저장소 루트가 하나로 해석되는지
- 필수 루트 파일이 존재하는지
- Python 버전과 잠금 파일이 맞는지
- 패키지가 설치된 환경에서 import되는지
- `backup/`이 runtime import 경로에 들어가지 않았는지
- `git ls-files` 결과에 어느 깊이에서든 `inputs`·`outputs` 경로 세그먼트가 없는지
- 저장소 검사기가 ignored·미추적 사용자 데이터 트리를 재귀 열거하지 않는지
- 훅과 CI가 존재하는 검사 경로만 참조하는지
- 한글·공백 루트 경로를 처리할 수 있는지
- JSON 출력이 스키마에 맞는지

각 결과는 고유 검사 코드, 상태, 설명, 증거를 가져야 한다. 하나라도 실패하면 전체
판정은 실패다.

### 작업 01-3: 단일 검사 진입점

`workflow check`는 다음을 순서대로 조정한다.

- 저장소·환경 doctor
- 잠금 파일 검사
- 포맷 검사
- 린트
- 타입 검사
- 단위·계약 테스트
- `backup/` 무변경 검사
- 문서 링크 또는 구조 검사는 존재할 때만 명시적 scope로 실행

검사기가 설치되지 않았으면 해당 검사를 건너뛰지 않고 환경 실패로 판정한다.

총괄과 QA 에이전트는 구현 전에 필수 검사 매트릭스를 다음처럼 동결하고 기계가 읽는
설정으로 관리한다.

| scope | 반드시 실행할 검사 |
|---|---|
| `fast` | doctor, lock, format, lint, type, 핵심 unit/contract, `backup/` Git 상태와 추적 프레임워크 매니페스트 검사 |
| `full` | fast 전부, 전체 unit/contract/smoke, 문서 구조, Stage 00 추적 프레임워크 매니페스트 비교 |

필수 검사 하나라도 `missing`, `skipped`, `not_run`이면 전체 실패다. `tests/`가 없거나
pytest가 테스트 0개를 수집해도 실패한다. 새 필수 검사를 추가하거나 제거하려면 계약과
테스트를 함께 바꾸고 총괄·QA 검토를 받는다.

### 작업 01-4: 훅 교체

- pre-commit은 빠른 scope만 실행한다.
- `uv` 또는 CLI를 찾지 못하면 명확한 메시지와 비정상 종료를 반환한다.
- 자식 프로세스 종료 코드를 그대로 반환한다.
- 훅 자체를 유일한 보호 수단으로 보지 않는다.
- 훅 우회가 가능하므로 다음 단계에서 원격 필수 CI를 별도로 설정한다.

### 작업 01-5: CI 교체

- 처음에는 Linux 빠른 검사와 Windows 경로 스모크를 분리한다.
- 의존성은 잠금 파일로 설치한다.
- 로컬과 같은 `workflow check`를 실행한다.
- 실제 영상 파일이나 대용량 산출물을 업로드하지 않는다.
- 로그·작은 테스트 보고서만 짧은 보존 기간으로 저장한다.
- 원격 저장소 접근 권한이 없으면 로컬 파일 완성만 기록하고 원격 성공으로 보고하지
  않는다.

## 9. 필수 부정 테스트

다음 테스트는 모두 실제 subprocess 수준에서 종료 코드를 확인한다.

1. 자식 프로세스가 7로 종료되면 최종 명령도 비정상 종료
   - 실제 subprocess 통합 테스트에서 자식 `7` → `workflow check` `7` → pre-commit
     `7`을 각각 정확히 단언한다.
2. 검사기 모듈 또는 파일이 없음
3. 잘못된 Python 버전
4. 선언 의존성이 설치되지 않음
5. `uv.lock`과 `pyproject.toml` 불일치
6. Git 저장소 밖에서 실행
7. 예상과 다른 Git 루트
8. 깨진 설정 JSON 또는 TOML
9. 검사 중 처리되지 않은 예외 발생
10. `backup/`을 runtime import하려는 코드 존재
11. 어느 깊이에서든 `inputs`·`outputs` 경로가 Git에 추적되려 함
12. 검사기가 ignored·미추적 사용자 데이터 트리를 열거·해시·보고하려 함
13. 한글과 공백이 포함된 임시 루트
14. PATH에서 `uv`를 제거하면 훅이 정확히 127로 종료
15. `tests/` 디렉터리 없음 또는 pytest 수집 0개
16. 필수 검사 결과가 `not_run`, `skipped`, 누락
17. 잘못된 실행 파일, 실행 권한 오류, timeout
18. PATH의 다른 Python을 현재 잠금 환경 대신 사용하려는 시도

성공 테스트만 통과하고 위 테스트가 없으면 단계를 완료로 판정하지 않는다.

## 10. 후속 clean-clone 통합 게이트

2026-07-17 사용자 결정으로 clean-clone은 초기 기반 구축에 비해 과도한 완료 조건이므로
Stage 01 완료 판정에서 제외한다. 첫 수직 기능 이식 전 또는 기본 브랜치 통합 전 중 먼저
도래하는 시점에 수행한다. 사용자 승인 체크포인트 커밋 없이는 실행하지 않는다.

검증 에이전트는 로컬 QA가 통과한 뒤 사용자에게 체크포인트 커밋 승인을 받는다. 승인된
커밋 SHA를 한글과 공백이 포함된 완전히 새로운 경로에 실제 clone하고, 기존 `.venv`,
미추적 파일, 사용자 캐시, 사용자별 PATH에 의존하지 않는 상태에서 다음을 확인한다.

1. 문서에 적힌 단일 설치 절차
2. 잠금 환경 설치
3. 패키지 import
4. `workflow doctor`
5. 빠른 검사
6. 전체 테스트
7. 의도적 실패 명령의 비정상 종료

clone 직후와 검증 후 Git 상태가 깨끗해야 하며 대상 SHA, 설치 명령, `doctor`, fast,
full, 의도적 실패의 모든 종료 코드를 증거에 기록한다. 커밋 전 임시 복사나 현재 작업
디렉터리의 미추적 파일을 포함한 복제는 clean-clone 통과로 인정하지 않고 `pending`으로
남긴다. 사용자 승인 전에는 검증용 커밋을 만들지 않는다.

사용자 전역 `safe.directory` 설정이 없으면 실패하는 구조를 완료로 인정하지 않는다.

## 11. 완료 기준

- 로컬과 CI가 같은 검사 진입점을 사용함
- 직접 실패가 훅·CLI·CI 어디에서도 성공으로 바뀌지 않음
- 검사기 결손이 실패로 처리됨
- Windows 한글·공백 경로 통과
- `backup/` runtime import 0건
- `backup/` Git 변경 0건, 프레임워크 저장소의 사용자 데이터·파일별 메타데이터 0건
- 독립 QA와 레드팀이 단계 통과를 판정함
- 사용자가 단계 02 착수를 승인함

clean-clone과 원격 CI 실제 실행 이력은 섹션 10의 후속 통합 게이트이며 Stage 01 로컬
완료를 막지 않는다. Stage 02 착수 승인은 완료 판정과 별도의 사용자 결정이다.

## 12. 중단 조건

- 한 번이라도 거짓 성공이 재현됨
- 기존 미추적 사용자 파일과 충돌
- 잠금 파일 없이 시스템 Python에 의존해야 함
- 훅 또는 CI가 존재하지 않는 경로를 계속 참조함
- 신규 최소 골격에 구체계 영상 기능을 함께 넣어야 한다는 요구가 발생함

## 13. 롤백

단계 00에서 식별한 HEAD를 기준으로 신규 단계 01 파일만 제거 또는 되돌린다. 사용자
승인 없이 기존 훅·CI를 과거 버전으로 복구하지 않는다. 롤백 후에도 `backup/`은 현재
위치에서 읽기 전용으로 유지한다.
