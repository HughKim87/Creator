# 단계 07 작업 지시서: 백업·관측·문서 운영 정착

## 1. 단계 목적

신규 구조가 같은 문제를 다시 일으키는지 자동으로 판단할 수 있는 운영 체계를 만든다.
문서는 상태 정본을 복제하지 않고, 백업은 생성 여부가 아니라 실제 복구 성공으로
검증한다.

## 2. 시작 게이트

- 단계 06의 `provisional_cutover` 또는 명시적으로 승인된
  `provisional_local_cutover`가 완료됐다.
- 코드·DB·산출물 롤백 훈련이 통과했다.
- 외부 저장소 또는 유료 비용이 있으면 별도 승인을 받았다.
- 운영 지표를 SQLite 이벤트에서 계산할 수 있다.

## 3. 역할과 소유권

### 운영 에이전트

- `src/video_workflow/services/metrics.py`
- 운영 CLI와 관련 테스트

### 백업 에이전트

- 백업 정책·복구 절차·증거
- 실제 자격 증명과 비밀을 저장소에 기록하지 않음

### 문서 에이전트

- 조정 에이전트가 배정한 `docs/index.md`, `architecture.md`, `workflow.md`,
  `operations.md`, `recovery.md`와 MkDocs 설정·링크 검사
- 생성 상태 문서를 수동 편집하지 않음
- 기존 `docs/adr/**`, migration 증거, 다른 에이전트 문서를 범위 없이 덮어쓰지 않음

### 운영 QA 에이전트

- 복구, 지표 결정성, 문서 엄격 빌드, 낡은 상태 탐지

공용 `pyproject.toml`, CI, CLI는 총괄 에이전트만 통합한다.

## 4. 금지 사항

- 별도 수동 스프레드시트나 JSON을 운영 상태 정본으로 사용
- 백업을 만들고 복구하지 않은 채 완료 선언
- 비밀번호·토큰·원본 콘텐츠 전문을 로그에 기록
- CI에 대용량 영상·DB 백업 업로드
- 사용자 승인 없는 B2 등 외부 저장소 생성
- 문서에 현재 작업 상태를 수동 복제
- 이 단계에서 Graphify·Obsidian 설치
- `backup/` 수정·정리·삭제 또는 백업 대상 변환

## 5. 운영 이벤트와 지표

모든 주요 명령은 최소 다음을 기록한다.

- `command_id`, `project_id`, `generation_id`
- 이벤트 종류와 실행 도구 버전
- 시작·종료 시각과 종료 코드
- 실패 코드와 지문
- 입력·출력 해시
- 재시도 횟수
- 기술 검증 상태
- 사람 승인 상태
- `work_category`: `production`, `maintenance`, `recovery`, `research`,
  `documentation`, `waiting_user` 중 하나

`workflow metrics`는 다음을 계산한다.

- 단계별 평균·최대 소요시간
- 단계별 실패율과 재시도율
- 동일 실패 재발 횟수
- 실패 발견부터 수정까지 시간
- 수직 흐름 성공률
- 승인 대기 시간
- 미등록 파일 수
- 입력 무결성 위반
- 핸드오프 후 재개 시간
- 백업·복구 시험 결과
- 개선 작업 시간과 실제 제작 작업 시간의 비율

지표 계산은 DB 이벤트의 읽기 전용 질의여야 하며 상태를 변경하지 않는다.
재시도는 원래 작업 category에 포함하고 `waiting_user`는 제작 시간 분모에서 제외한다.
메타 작업 비율은 `(maintenance + recovery + research + documentation) / production`으로
고정하고 0인 분모를 성공값으로 만들지 않는다.

## 6. 백업 정책

Stage 05의 로컬 최소 복구 시험을 정기 운영으로 확장하는 단계다. 이 단계에서 처음으로
복구 가능성을 발견해서는 안 된다.

### 대상

- 프로젝트별 `workflow.sqlite`의 일관된 백업
- 불변 원본 입력
- 승인된 산출물과 매니페스트
- 프레임워크 Git 저장소의 원격 이력

### 제외

- `.venv`, 캐시, 재생성 가능한 임시 파일
- 비밀값이 포함된 환경 파일의 평문 원격 저장
- CI 캐시에 이미 존재하는 의존성 복사본

### 권장 순서

1. 초기에는 Restic과 외장 드라이브 또는 승인된 로컬 저장소
2. 오프사이트가 필요하면 사용자 승인 후 B2 등 객체 저장소
3. 다중 PC에서 동일 대용량 데이터를 재현해야 할 때만 DVC 재평가
4. 반복 수정 영상은 Git LFS 기본 대상으로 사용하지 않음

### 운영 결정표

백업을 예약하기 전에 다음 값을 사용자가 검토할 표로 확정한다.

| 항목 | 초기 권장값 | 확정 시 기록할 내용 |
|---|---|---|
| 상태 DB 주기 | 작업 종료마다 + 일 1회 | 실제 RPO |
| 원본·승인 산출물 | 등록·승인 직후 | 포함 artifact role |
| RPO | 최대 24시간, 승인 직후는 0에 가깝게 | 허용 데이터 손실 |
| RTO | 30분 목표 | 실측 복구 시간 |
| 단기 보존 | 일 7, 주 4 | snapshot 수 |
| 장기 보존 | 월 6, 분기 4 | 법적·용량 요구 |
| 암호화 | Restic 기본 암호화 | 키 보관자·복구 위치, 저장소 밖 보관 |
| 정리 전 검증 | `restic check`와 최근 snapshot 복원 | 실제 종료 코드 |
| 비용 | 저장량·전송량 기준 월 추정 | 무료/로컬/오프사이트 비교 |

자격 증명과 암호화 키 자체는 표나 저장소에 쓰지 않는다. 외장 드라이브·B2 등 대상별
초기 비용, 월 비용, 구축 시간, 월 유지시간, 무료 대안을 함께 기록한다.

### 복구 훈련

- 빈 임시 경로에 복원한다.
- DB `verify`, 입력 해시, 산출물 매니페스트를 확인한다.
- 복원된 프레임워크로 작은 스모크 흐름을 실행한다.
- 복구 시간과 누락 파일을 기록한다.
- 분기 1회 반복한다.

## 7. 문서 구조

문서는 다음 세 종류로만 구분한다.

1. 규범: `AGENTS.md`, `PROJECT_RULES.md`, 워크플로 계약
2. 설명: README, architecture, workflow, operations, recovery, ADR
3. 생성: 현재 상태, 핸드오프, 운영 지표

권장 구조:

```text
README.md
docs/
├─ index.md
├─ architecture.md
├─ workflow.md
├─ operations.md
├─ recovery.md
└─ adr/
```

- 같은 규칙을 여러 문서에 복제하지 않는다.
- ADR은 결정, 대안, 비용, 위험, 롤백을 기록한다.
- 생성 문서에는 `DO NOT EDIT`와 DB 버전을 표시한다.
- 처음 보는 에이전트의 필수 시작 문서는 4개 이하로 유지한다.

## 8. MkDocs 도입

MkDocs는 Markdown의 정적 빌드와 링크 검증에만 사용한다.

- `docs/`만 문서 소스로 둔다.
- 엄격 빌드를 활성화한다.
- 깨진 내부 링크와 누락 페이지를 CI 실패로 처리한다.
- CI 규범 문서 빌드는 실제 작업 DB 없이 `docs/` Markdown만 엄격 빌드한다.
- 생성 문서 테스트는 비식별화한 작은 fixture DB만 사용한다.
- 실제 운영 상태 문서는 사용자가 선택한 로컬 `workflow.sqlite`에서만 생성하며 CI나
  외부 서비스에 업로드하지 않는다.
- 빌드 결과물을 상태 정본으로 사용하지 않는다.
- 자동 공개 배포는 별도 승인 전 수행하지 않는다.

## 9. 필수 테스트

- 같은 DB에서 지표 두 번 생성 시 정규화 결과 동일
- 고의로 중복 실패 이벤트를 넣은 픽스처에서 재발 횟수 정확
- DB 없음·손상에서 metrics 실패와 자동 초기화 없음
- 백업 생성 후 빈 위치 복구와 전체 무결성 검사
- 깨진 링크에서 MkDocs 엄격 빌드 실패
- 수동 변경 생성 문서를 재생성해 DB와 일치
- 문서·로그에 비밀 픽스처 문자열이 나타나지 않음
- 한글·공백 복구 경로 통과
- 실제 작업 DB가 없는 CI 규범 문서 빌드 통과
- fixture DB 생성 문서 테스트와 로컬 운영 문서 생성 경로가 혼합되지 않음

## 10. 안정화 게이트

단계 06 결과를 다음 순서로 승격한다.

```text
cutover_candidate → provisional_cutover → stabilized
```

`stabilized`는 최소 10개의 실제 제작 작업과 30일 관찰을 모두 채운 뒤에만 선언한다.
그 전에는 provisional 상태다. 다음 중 하나면 즉시 신규 진입을 차단하고 Stage 06 롤백
절차를 실행한다.

- 첫 10개 실제 작업 성공률 90% 미만
- 실패의 거짓 성공, 원본 변조, 승인 우회, 미등록 artifact 중 하나라도 발생
- 동일 Critical 회귀 재발
- 복구 목표를 초과하고 안전한 우회가 없음
- `remote_ci_waived_by_user` 조건이 만료되거나 사용자가 철회함

## 11. 완료 기준

- 실패의 거짓 성공 지표 0건
- 입력 해시 변경과 승인 우회 지표 0건
- 모든 신규 결함에 회귀 테스트 연결
- 백업 생성뿐 아니라 복구 성공
- 30분 이내 복구 또는 실제 기준값 확정
- 지표가 SQLite 이벤트에서 자동 생성됨
- 수동 상태 스프레드시트·별도 JSON 정본 0건
- MkDocs 엄격 빌드와 링크 검사 통과
- 필수 시작 문서 4개 이하
- 운영 점검 주기와 책임자 정의
- `backup/`과 원본 입력 변경 0건
- 최소 10개 실제 제작 작업과 30일 관찰에서 안정화 기준 통과
- 상태가 `stabilized`로 기록되고 근거 지표가 연결됨

## 12. 중단 조건

- 백업 복구가 되지 않음
- 지표 도구가 별도 상태 정본을 생성함
- 외부 저장 비용·전송에 대한 승인 없음
- 문서 빌드를 통과시키기 위해 깨진 링크를 숨김
- 생성 문서를 사람이 계속 수정해야 함
- 비밀값이 로그나 백업 설정에 노출됨

## 13. 롤백

- metrics·MkDocs를 제거해도 핵심 워크플로와 상태 DB가 작동해야 한다.
- 백업 도구 설정 롤백은 저장된 백업 데이터를 먼저 보존하고 진행한다.
- 문서 빌드 결과를 제거해도 원본 Markdown이 남아야 한다.
- 운영 도구가 핵심 실행을 막으면 단계 06 운영 경로로 돌아가 원인을 분리한다.
