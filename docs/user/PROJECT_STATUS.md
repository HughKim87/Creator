# 프로젝트 현재 상태

- 사용 목적: 사용자가 현재 진행 단계, 완료 작업, 검증 결과와 다음 결정을 한글로 확인하는 보고서다.
- 사용 범위: 사용자 확인용 요약만 포함하며 에이전트 실행 규칙이나 현재 상태 정본으로 사용하지 않는다.
- 독자·언어: 사용자, 한글.
- 읽는 시점: 사용자가 현재 상태를 확인하거나 단계 완료 보고를 받을 때.
- 수정하는 시점: 사용자에게 보고할 만한 단계나 문서 구조가 변경됐을 때 `SESSION_HANDOFF.md`를 근거로 갱신한다.
- 정본 여부: 파생 보고서다. 에이전트의 현재 상태 정본은 `SESSION_HANDOFF.md`다.

## 현재 단계

- 프로젝트 공통 기반인 L0부터 L4까지 완료됐다.
- 문서 목적·범위·언어·읽기 경로 재정리도 적용됐다.
- 다음 미착수 단계는 영상 제작 워크플로우가 시작되는 L5이며 아직 승인되지 않았다.

## 이번 정리에서 바뀐 점

- 모든 활성 문서 상단에 사용 목적과 사용 범위를 명시했다.
- 에이전트는 `AGENTS.md`의 작업별 표에 따라 필요한 문서만 읽게 했다.
- 프로젝트 전역 규칙과 재구축 원칙·계획·현재 상태를 서로 다른 정본으로 분리했다.
- 에이전트 실행 문서는 영어, 사용자 확인·보고 문서는 한글로 분리했다.
- 에이전트 문서는 `docs/agent/`, 현재 사용자 문서는 `docs/user/`, 역사 보고서는 `docs/reports/`로 물리적으로 분리했다.
- 문서 등록부에 문서 종류·생명주기·정본성·독자·검증 수준·읽는 조건·참고 관계를 기록했다.
- 역사 보고서는 실행 근거가 아니라는 점을 명확히 표시했다.
- 백업은 장기 정본이 아니라 재구축 중에만 쓰는 임시 이관 원본으로 재분류했다.
- 앞으로의 활성 문서·코드·테스트·명령은 백업을 읽지 않아도 독립적으로 작동해야 한다.
- 백업에 있던 제작 순서, 영상 기획, 편집 품질, 도구와 스킬 계약을 새 에이전트 문서로 재구성했다.
- 백업 삭제는 L8 이후 독립성 검사와 별도 사용자 승인 없이는 실행하지 않도록 계획에 명시했다.

## 검증 상태

- 문서 구조와 상태 계약: 문서 거버넌스 11개, 최소 라우팅 3개, 상태·생명주기 16개,
  스키마 동기화 3개 등 합성 테스트 33개를 통과했다.
- 상단 목적·범위, 언어 분리, 문서 등록 누락, 이전 경로 잔존, 제어 문서 크기,
  JSON 구문과 런타임 동기화를 자동 검사한다.
- 활성 실행 문서와 구현이 백업으로 라우팅되지 않는지, 재구축 계획에 백업 독립성·삭제 전 검증·별도 승인 규칙이 있는지도 자동 검사한다.
- `backup/`: 필요한 내용을 활성 문서로 이관하기 위해 지정 문서만 읽었으며 파일 자체는 변경하지 않았다.
- 사용자 미디어·Premiere: 이번 작업 범위가 아니므로 미검증.

## L2 완료 결과

- 작업별 상태 정본을 `outputs/<project_id>/state.json` 하나로 제한했다.
- 소스 식별자·지문, 현재 단계·출력, 다음 행동, 차단·사용자 판단, 검증 수준만 저장한다.
- 잘못된 버전·필드·타입·경로는 저장 전에 거부하고, 저장 중 교체가 실패해도 기존 상태를 보존한다.
- 실제 사용자 데이터 대신 합성 샘플과 임시 폴더만 사용했다.
- 정상 왕복과 실패 조건을 다룬 테스트 8개가 Python 3.12.13에서 통과했다.

## L3 완료 결과

- 현재 상태 재개, 문서 경로 변경, 영상 상태 처리의 최소 읽기·쓰기 프로필 3개를 확정했다.
- 전체 에이전트 문서 7개를 읽는 경우보다 문서 컨텍스트를 약 46~64% 줄였다.
- 관련 없는 문서 선택은 시나리오별 3~4개에서 0개로 줄었고 회귀 테스트 3개가 통과했다.
- 측정상 별도 문서 인덱스나 보조 명령은 필요하지 않았다.

## L4 완료 결과

- 상태 스키마를 명시적 버전 3으로 올리고 출력의 버전·현재본·이전본·실패본 관계를 유지하면서 승인 목적을 추가했다.
- 역할별 현재본은 하나만 허용하며, 이전본과 실패본은 사용자 요청 없이 삭제하거나 이동하지 않는다.
- 일반 저장은 다음 단계 사용 가능 상태를 기록할 수 없고, 승격 저장은 지정 입력의 지문과 필요한 출력 파일의 SHA-256·크기를 먼저 검증한다.
- 출력 검증은 사용 가능 파일, 승격 관련 파일, 전체 이력의 세 범위로 나눠 불필요한 과거 파일 검사를 피한다.
- JSON Schema와 런타임 검증기의 필수 필드·열거값 동기화를 자동 검사한다.
- 실제 사용자 데이터 대신 합성 파일만 사용했으며 상태·생명주기 및 스키마 테스트 19개가 통과했다.
