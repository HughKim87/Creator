# R-2B 기존 지식 코퍼스 이관 결과

- 목적: 승인된 R-2B 범위에서 기존 결정·재사용 지식·실패 사례·출처·관계를 R-2A work context 폐루프에 넣은 구현 및 검증 결과를 기록한다.
- 사용 시점: R-2B 완료 여부를 감사하거나 R-3 착수 승인 여부를 판단할 때 사용한다.
- 작성·검증 주체: 프로젝트 에이전트가 승인된 R-1.1 §10.2와 현재 저장소 증거를 기준으로 작성·검증했다.
- 언어: 한국어.
- 저장 위치: `docs/reports/2026-07-21_R-2B_기존_지식_코퍼스_이관_결과.md`.
- 권위: 시점 구현 증거이며 정책 권위가 아니다. 현재 계약은 `docs/agent/` 문서가 소유한다.
- 범위: R-2B만 완료했다. R-3 writer 일반화·lifecycle 복구에는 착수하지 않았다.

## 1. 구현 결과

- D-01~D-17을 `decision.r1.1.d01`~`decision.r1.1.d17`의 독립 record로 이관했다. 각 record는 상태, rationale, 사용자 approval 필드와 원출처 locator를 가진다.
- 기존 분석과 구현에서 재사용 가능한 지식 4건을 `verified`로 등록했다: 직접 라우팅, 공유 work context, 단일 문서 owner, 보호 경로 사전 차단.
- 기존 `case.project.document-authority-duplication`의 stable ID와 revision history를 유지하면서 schema-backed JSON record를 추가했다. confirmed symptom과 resolved solution의 상태·근거를 분리했다.
- 프로젝트 문서 4건, Git 기준점 1건, 공식 URL 1건, 역사 후보 1건을 source record로 등록했다.
- active verified relation 5건과 Markdown 링크에서 만든 inactive candidate 1건을 등록했다. candidate는 `pending`, `retrieval_eligible=false`다.
- `catalog/records.jsonl` projection과 exact record ID + verified 1-hop + source trace resolver를 구현했다.

## 2. 정본과 스키마

| 종류 | 정본 | Schema | 실제 record |
|---|---|---|---:|
| Decision | `knowledge/decisions.jsonl` | `schemas/decision.schema.json` | 17 |
| Knowledge | `knowledge/items.jsonl` | `schemas/knowledge.schema.json` | 4 |
| Case | `knowledge/cases/case.project.document-authority-duplication.md` | `schemas/case.schema.json` | 1 |
| Source | `knowledge/sources.jsonl` | `schemas/source.schema.json` | 7 |
| Relation | `knowledge/relations.jsonl` | `schemas/relation.schema.json` | 6 |

모든 source와 relation endpoint는 stable ID로 연결된다. 공식 URL source는 2026-07-21 JSON Schema Draft 2020-12 Core 공식 문서에서 확인했다.

## 3. 대표 Context Fixture

1. `r2b_decision_evidence`: accepted D-14를 exact ID로 선택하고 verified knowledge `knowledge.context.shared-work-context`, R-1.1 및 context contract source locator까지 추적했다.
2. `r2b_case_resolution`: resolved case를 exact ID로 선택하고 confirmed symptom, resolved solution, 해결 지식 및 source evidence를 분리해 반환했다.

두 fixture 모두 conditional rule은 활성 rule pack에서만 선택했다. `source.history.overview`는 사례 근거에 포함되지만 `historical_candidate`, `retrieval_eligible=false`로 유지되어 active instruction이 아니다.

## 4. 검증 결과

- 통합 validator: 통과. kernel 8, conditional rule 21, orphan 0.
- 코퍼스 게이트: decision 17, knowledge 4, case 1, source 7, relation 6 모두 통과.
- provenance: verified knowledge가 등록 source와 content hash/locator까지 추적됨.
- case: resolved case의 confirmed symptom과 resolved solution 양쪽에 evidence가 존재함.
- instruction isolation: 역사 규칙이 active instruction으로 선택된 사례 0건.
- 자동 테스트: 10/10 통과. 기존 R-2A 6건과 R-2B 4건을 함께 검증했다.
- 보호 경계: `backup/`, `inputs/`, `outputs/`는 열거 전에 계속 차단된다.

## 5. 실패와 수정

- fenced code 예시 안의 heading이 실제 Markdown unit으로 오인되던 parser 결함을 발견해 fence 내부 heading을 제외하도록 수정했다.
- Windows CP949 stdout에서 em dash 출력이 실패했지만 resolver 산출물은 이미 정상 생성돼 있었다. CLI stdout을 UTF-8로 고정하고 재검증했다.
- 첫 corpus validation에서 approval 객체에 불필요한 `state` 값을 강제한 과잉 제약을 발견했다. 승인자·승인일·근거 source·locator를 필수 approval 계약으로 정정했다.
- 종료 감사에서 knowledge 정식 JSON에 기존 계약의 언어·작성/수정 시각·작성자·유효 범위·last check·revision metadata가 빠진 것을 발견해 schema와 4개 record를 보강했다.

반복 실패는 없으며 같은 원인의 연속 실패 횟수는 모두 0으로 복귀했다.

## 6. 제외와 승인 경계

SQLite FTS5, vector, graph database, Obsidian, 일반 code/config/test writer, lifecycle/review-history 자동화, commit·push·외부 변경은 수행하지 않았다. 이 항목들은 R-2B 완료 조건이 아니며 일부는 R-3 이후 별도 승인 범위다.

R-2B는 완료됐다. 여기서 중지하고 사용자에게 결과를 보고하며, R-3는 별도 명시 승인이 있을 때만 시작한다.
