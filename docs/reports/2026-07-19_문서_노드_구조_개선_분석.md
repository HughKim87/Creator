# 문서 노드 구조 개선 분석 보고서

- 사용 목적: 사용자가 프로젝트 문서를 중복 없이 분류하고, 작업별 최소 컨텍스트만 단계적으로 읽는 구조로 개선하기 위한 분석과 권고안을 확인하는 보고서다.
- 사용 범위: 현재 에이전트 문서의 크기·중복·참조 구조 진단과 목표 폴더·노드·컨텍스트 예산 제안만 포함한다. 실제 문서 이동이나 분할을 지시하는 실행 정본은 아니다.
- 독자·언어: 사용자, 한글.
- 읽는 시점: 문서 구조 최적화 작업을 승인하거나 구현 범위를 결정할 때.
- 수정하는 시점: 점검 수치의 명백한 오류를 바로잡을 때만 수정한다. 새로운 판단은 새 보고서로 남긴다.
- 정본 여부: 분석 근거 문서다. 전역 규칙은 `PROJECT_RULES.md`, 현재 상태는 `SESSION_HANDOFF.md`, 실제 작업 계획은 `docs/agent/REBUILD_PLAN.md`가 정본이다.
- 상태: analysis / proposal. 아직 구현 승인이나 완료를 의미하지 않는다.
- 작성일: 2026-07-19.

## 1. 결론

현재 구조는 문서의 독자와 용도 분류까지는 개선됐지만, 작업마다 필요한 작은 문서 노드만 읽어
컨텍스트를 쌓는 구조에는 아직 도달하지 못했다.

개선의 핵심은 문서 수를 단순히 늘리는 것이 아니다. 서로 다른 읽기 조건이나 쓰기 이유를 가진
내용만 물리적으로 분리하고, 하나의 개념은 하나의 정본에만 기록해야 한다.

이번 분석에서는 실제 파일을 분할하거나 이동하지 않았다. 권고안은 기존 L3 문서 라우팅을
완성하는 보완 작업으로 처리하는 것이 적절하며 L5 워크플로우 구현과 분리해야 한다.

## 2. 현재 문서 읽기 비용

문자 수를 4로 나눈 단순 추정치이므로 실제 모델 토크나이저 결과와는 차이가 있을 수 있다.

| 작업 경로 | 읽는 문서 수 | 예상 문서 토큰 | 비고 |
|---|---:|---:|---|
| 기본 시작 | 3 | 약 4,242 | `AGENTS.md`, `PROJECT_RULES.md`, `SESSION_HANDOFF.md` |
| 상태 파일 작업 | 4 | 약 7,125 | 기본 시작과 상태 계약 전체 |
| L5 핵심 문서 | 6 | 약 11,456 | 계획 절과 실제 작업 데이터는 제외한 수치 |
| L7 기본 문서 | 4 | 약 5,676 | 선택 도구의 소비자 계약은 제외한 수치 |
| L8 기본 문서 | 4 | 약 5,719 | 선택 스킬의 단계·도구 계약은 제외한 수치 |

가장 큰 에이전트 문서는 다음과 같다.

| 문서 | 줄 수 | 문제 |
|---|---:|---|
| `docs/agent/REBUILD_PLAN.md` | 222 | 완료 단계와 미래 단계가 한 파일에 있어 부분 읽기 규칙에 의존함 |

| `docs/agent/EDITING_QUALITY_RULES.md` | 142 | 편집 판단·검증·자동 감사 소비자가 서로 다름 |

`REBUILD_PLAN.md`가 현재 단계 절만 읽도록 지시하더라도 에이전트나 파일 읽기 도구가 전체 파일을
불러올 수 있다. 중요한 읽기 경계는 문서 내부 절보다 물리적인 파일 경계로 만드는 편이 안전하다.

## 3. 중복과 쓰기 증폭

정확히 같은 긴 문장의 복제는 발견되지 않았다. 문제는 같은 의미를 여러 문서에서 다시 설명하는
의미 중복이다.

- 원본 식별은 상태 계약, 워크플로우, 도구, 스킬, 재구축 맵에 반복된다.
- 버전 생명주기는 전역 규칙, 상태 계약, 계획, 스킬에 반복된다.
- 사용자 승인과 창작 권한은 상태 계약, 워크플로우, 품질, 계획에 반복된다.
- 검증 개념은 거의 모든 에이전트 문서에 다시 서술된다.
- 문서 상단 메타데이터와 `DOCUMENT_REGISTRY.md` 표가 역할·경로·읽기 조건을 이중 관리한다.

이 구조에서는 개념 하나를 바꿀 때 여러 문서를 찾아 수정해야 한다. 수정 누락이 생기면 읽기
비용뿐 아니라 정본 충돌도 발생한다.

## 4. 목표 문서 모델

각 문서를 하나의 컨텍스트 노드로 취급한다.

```text
사용자 요청
└─ 전역 규칙
   └─ 현재 상태(계속 작업일 때만)
      └─ 작업 라우트
         └─ 필요한 도메인 노드
            └─ 사용자가 지정한 실제 데이터
```

각 에이전트 문서의 상단에는 다음 노드 정보만 둔다.

- `Node ID`
- `Purpose`
- `Scope`
- `Requires`
- `Provides`
- `Read when`
- `Write when`

에이전트는 요청에 해당하는 말단 노드에서 시작하고 `Requires`에 선언된 부모 노드만 순서대로
읽는다. 등록되지 않은 암묵적 의존성과 순환 참조는 허용하지 않는다.

## 5. 문서 분할 기준

다음 조건 중 하나라도 다르면 별도 노드로 분리한다.

1. 읽는 작업이나 시점이 다르다.
2. 수정되는 이유와 책임자가 다르다.
3. 다음 소비자가 다르다.
4. 독립 검증 또는 독립 폐기가 가능하다.

반대로 위 조건이 모두 같다면 문서가 조금 길더라도 하나로 유지한다. 제목마다 파일을 만드는
과도한 분할은 컨텍스트 탐색 비용만 늘리므로 금지한다.

## 7. 문서별 개선 방향

- `AGENTS.md`: 시작 규칙과 작업에서 말단 노드로 가는 최소 라우팅만 유지한다.
- `PROJECT_RULES.md`: 모든 작업에 항상 적용되는 전역 규칙만 압축한다.
- `SESSION_HANDOFF.md`: 현재 단계, 차단, 검증, 첫 다음 행동만 유지한다.
- `REBUILD_PLAN.md`: 공통 계획과 백업 독립 원칙만 남기고 단계별 계획을 물리적으로 분리한다.
- `FILE_DATA_CONTRACT.md`: JSON 예시와 필드 구조는 스키마·테스트로 옮기고 생명주기와 I/O를 분리한다.
- `WORKFLOW_FOUNDATION.md`: 제작 경로, 영상 기획, 편집 단계 경계를 분리한다.
- `EDITING_QUALITY_RULES.md`: 판단, 검증, 자동 감사 노드로 분리한다.
- 도구·스킬 문서: 공통 계약과 실제 선택된 기능별 노드를 분리한다.
- 문서 등록부: 문서 메타데이터에서 생성·검증되는 기계 등록부로 전환해 수동 이중 쓰기를 없앤다.

## 9. 권장 컨텍스트 예산

- 항상 읽는 세 문서 합계: 약 2,000토큰 이하
- 일반 에이전트 노드: 권장 800토큰, 최대 1,200토큰
- 한 작업의 문서 컨텍스트: 사용자 데이터를 제외하고 3,000토큰 이하
- 기본 작업 경로: 최대 4~5개 노드
- 문서가 80줄 또는 한 절이 40줄을 넘으면 분할 필요성을 검사
- JSON Schema, 생성 파일, 테스트 픽스처는 일반 문서 크기 제한에서 제외

## 10. 자동 검증 항목

- 존재하지 않는 노드 의존성
- 순환 의존성
- 작업별 의존성 폐쇄 집합의 컨텍스트 예산 초과
- 한 개념에 두 개 이상의 정본 선언
- 라우팅되지 않는 고립 문서
- 사용자 문서나 역사 보고서가 실행 경로에 포함되는 문제
- 백업 경로에 대한 실행 의존성
- 문서 크기 제한 초과
- 문서 메타데이터와 실제 파일 또는 등록부의 불일치

## 11. 권장 적용 순서

1. 노드 메타데이터와 크기 예산을 먼저 확정한다.
2. 루트의 항상 읽는 세 문서를 축소한다.
3. 재구축 계획과 상태 계약을 작업별 노드로 분리한다.
4. 워크플로우와 편집 품질 문서를 소비자별로 분리한다.
5. 도구·스킬 요구사항을 공통 계약과 선택 기능 노드로 분리한다.
6. 의존성 그래프, 순환, 고립 문서, 컨텍스트 예산 검사를 추가한다.
7. 기존 작업 라우팅 회귀 테스트를 새 노드 구조에 맞게 갱신한다.

구현 승인을 받으면 이 순서로 진행하고, 각 단계에서 이전 문서의 내용을 먼저 새 정본에 대응시킨
뒤 이전 경로를 제거해야 한다. 내용 손실을 피하기 위해 일괄 삭제나 전체 재작성은 사용하지 않는다.
