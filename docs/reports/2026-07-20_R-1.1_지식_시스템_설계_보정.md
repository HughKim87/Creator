## 2. 보정 결론

`D` 최종 최소 절차는 다음과 같다.

```text
R-1.1  intent-aligned design correction
  → R-2A  existing rules + all governed files + live read/write vertical slice
  → R-2B  existing decisions + knowledge + cases + sources + relations migration
  → R-3   resolver/writer/review generalization and failure recovery
  → R-4   measured retrieval completion and optional local search projection
  → R-5   maintenance, rebuild, cold-start, and protected-boundary acceptance
```

보정된 핵심은 다음과 같다.

1. 상시 커널은 11개가 아니라 8개다.
2. 나머지 21개 규칙은 7개 **Markdown rule pack**에서 작업·phase별로 선택한다.
3. JSONL rule 목록은 정본이 아니라 Markdown pack에서 생성하는 projection이다.
4. 모든 project-governed file은 file catalog node가 되고 형식별 `unit_strategy`를 가진다.
5. 긴 문서 heading, JSON record, code symbol, 설정 key와 test ID를 addressable artifact unit으로 선택한다.
6. read manifest와 write contract는 같은 work context에 속하며 가능한 경우 file이 아니라 unit까지 범위를 제한한다.
7. R-2A는 정적 구조가 아니라 실제 기존 데이터로 한 번 동작하는 최소 read/write 폐루프를 제공한다.
8. R-2B는 새 빈 구조가 아니라 기존 결정·지식·사례·출처를 같은 폐루프에 추가한다.
9. R-4는 도구 검토가 아니라 고정 검색 목표 충족을 증명한다.
10. R-5에서 오래됨·재구축·실패·새 세션 재현을 종합 검증한 뒤에만 최종 구축 완료를 판정한다.

## 3. 사용자 의도 해석의 확정

### 3.1 “모든 파일”의 범위

사용자는 의도 정합성 보고 후 R-1.1 진행을 승인했다. 이를 다음 범위 해석의 승인으로 적용한다.

`D` **project-governed file**은 프로젝트가 의도적으로 유지·수정·검증하는 모든 파일이다.

포함:

- 규칙과 라우터
- 사용자·에이전트 문서와 보고서
- 코드, 설정, schema와 test
- 지식·결정·사례·source·relation·event 정본
- 프로젝트가 의도적으로 생성하는 context와 index manifest
- 사용자가 정확한 작업 scope로 지정한 보호 task 파일

개별 전역 열거 제외:

- `backup/` 내부: boundary node와 승인된 source locator만 사용
- 지정되지 않은 `inputs/`, `outputs/`: boundary node만 사용
- `.git/`, OS·도구 cache, virtual environment와 temporary file
- 비밀·자격 증명·환경 값

의도적 projection은 file node로 등록하되 `authority=derived`, `rebuildable=true`, `index_scope=none`으로 표시한다. 일시적인 temp 파일은 프로젝트 파일로 보지 않는다.

### 3.2 “문서 기반”의 의미

`D` 규칙·지식·결정·사례처럼 사람이 판단해야 하는 정본은 Markdown 문서로 유지한다. 기계 처리에 필요한 catalog·event·source·relation은 JSONL 정본을 허용하되 모든 행은 ID·출처·schema와 사람이 읽을 수 있는 의미를 가져야 한다.

특정 LLM·GUI·DB만 이해할 수 있는 상태를 정본으로 만들지 않는다.

### 3.3 “필요할 때만 탐색”의 의미

- 모든 파일과 규칙을 system registry에 포함한다.
- resolver는 registry를 기계적으로 읽을 수 있지만 전체 내용을 LLM context에 넣지 않는다.
- task request의 구조 필드와 exact target을 먼저 사용한다.
- rule predicate와 artifact unit locator를 평가한다.
- 선택된 ID·locator·hash·이유만 context package에 넣는다.
- 작업 중 새 필요가 생기면 request revision을 만들고 같은 절차로 확장한다.

## 6. 조건부 규칙: Markdown 7개 pack, 21개 rule

### 6.1 물리 구조

```text
rules/
├─ governance.md
├─ version-control.md
├─ documentation.md
├─ provenance.md
├─ knowledge.md
├─ retrieval.md
└─ validation.md
```

각 pack은 Purpose, Use when, Owner, Language, Location/Links를 가진 영어 에이전트 문서다. pack의 설명은 사람이 읽는 Markdown이고, 각 원자 규칙은 stable heading 아래 JSON block 하나가 정본이다.

### 6.2 pack 문서 형식

```text
---
schema_version: 1.0.0
pack_id: documentation
kind: conditional_rules
language: en
owner: user-approved, agent-maintained
---

# Documentation Rules

## rule.docs.user-language

~~~json
{
  "schema_version": "1.0.0",
  "rule_id": "rule.docs.user-language",
  "text": "Write user-facing reports and guides in Korean.",
  "authority": "project_rule",
  "priority": 500,
  "status": "active",
  "applies_when": {
    "any": [
      {"field": "output_audience", "op": "eq", "value": "user"},
      {"field": "target_kind", "op": "in", "value": ["report", "user_guide"]}
    ]
  },
  "excludes_when": [],
  "phases": ["plan", "write", "close"],
  "task_tags": ["documentation", "user-facing"],
  "source_refs": ["src.repo.project-rules#heading:Language and document boundaries"],
  "validators": ["validate.document-language"]
}
~~~
```

heading과 JSON block이 한 rule record다. parser는 heading ID와 JSON `rule_id`가 일치하는지 검증한다. 사람이 읽을 별도 규칙 문장을 JSON 밖에 복사하지 않는다.

### 6.3 전체 21개 이동표

| pack | 현재 규칙 위치 | 수 | 선택되는 대표 조건 |
|---|---|---:|---|
| `governance.md` | 1.3, 1.4, 3.4 | 3 | staged work, authority owner 변경, 중복 문서 생성 방지, 정책·절차·설계 배치 |
| `version-control.md` | 2.5 | 1 | tracked file 변경·복구·백업 계획 |
| `documentation.md` | 3.1, 3.2, 3.5 | 3 | report·guide·agent document 생성·수정 |
| `provenance.md` | 3.3, 4.1, 4.2, 4.3 | 4 | 분석·연구·번역·사실·추론·결정 작성 |
| `knowledge.md` | 4.4, 4.5 | 2 | 지식 검증·confidence·conflict·supersession |
| `retrieval.md` | 5.1, 5.2, 5.3, 5.5 | 4 | route·search·context·index 작업 |
| `validation.md` | 6.1, 6.2, 6.3, 6.4 | 4 | validate·report·close·handoff phase |
| **합계** |  | **21** |  |

### 6.4 phase 선택

초기 phase enum:

```text
discover → plan → read → write → validate → close
```

규칙은 task 전체가 아니라 필요한 phase에서 추가될 수 있다. 예를 들어 `validation.md`는 일반적으로 validate/close에서 필수지만 읽기 전용 질문의 discover context 전체를 차지하지 않는다.

### 6.5 rule projection

`rules/*.md`의 JSON block을 정렬해 생성한 `rules.jsonl`과 SQLite table은 projection이다.

- projection hash에는 pack path, pack hash, parser version과 생성 시각을 기록한다.
- projection을 직접 편집하지 않는다.
- parser 실패 시 이전 projection을 최신으로 표시하지 않는다.
- rule 검색 점수는 authority·priority·predicate보다 앞설 수 없다.

## 7. universal file catalog와 artifact unit

### 7.1 file node

모든 project-governed file은 `catalog/files.jsonl`의 active node를 가진다.

최소 필드:

```text
schema_version, file_id, path, kind, purpose,
owner, authority, status, language, sensitivity,
index_scope, read_when, write_when, task_tags,
unit_strategy, unit_overrides,
consumes, produces, depends_on, validators,
content_sha256, hash_policy, observed_at
```

등록되지 않은 project-governed file은 orphan 오류다. 새 파일은 `planned → active`, 이동은 stable file ID와 `moved_from`, 삭제는 마지막 hash와 `deleted` 상태를 보존한다.

### 7.2 unit strategy

file record는 형식별 기본 선택 단위를 명시한다.

| 파일 종류 | `unit_strategy` | locator |
|---|---|---|
| 짧은 단일 책임 문서 | `whole_file` | file ID |
| Markdown | `markdown_heading` | explicit anchor 또는 heading path |
| JSON | `json_pointer` | RFC-style pointer |
| JSONL | `jsonl_record_id` | record stable ID |
| YAML/TOML | `key_path` | key path |
| 코드 | `code_symbol` | module/class/function symbol |
| test | `test_symbol` | test ID 또는 symbol |
| 일반 text log | `record_or_line_range` | event ID 또는 stable range |
| binary/media | `binary_sidecar` | sidecar record + whole-file hash |

parser가 안전하게 unit을 만들 수 없으면 조용히 임의 line chunk를 만들지 않고 `whole_file`로 명시한다.

### 7.3 artifact unit record

unit은 file 내용과 catalog 전략에서 결정적으로 생성되는 addressable view다. 기본 unit 목록은 projection이며, 사람이 지정한 예외만 `unit_overrides`가 소유한다.

```json
{
  "unit_id": "unit.file.docs.agent.workflow.heading.validate",
  "file_id": "file.docs.agent.workflow",
  "locator_type": "markdown_heading",
  "locator": "heading:5. Validate",
  "purpose": "Validation procedure",
  "read_when": [],
  "write_when": [],
  "owner": "project-agent",
  "validators": ["validate.markdown", "validate.links"],
  "parent_file_hash": "...",
  "unit_hash": "...",
  "task_tags": ["validation"],
  "status": "active"
}
```

unit ID는 content hash를 포함하지 않는다. 내용 변경은 revision과 unit hash를 바꾸며 stable locator가 사라지면 `needs_review`가 된다.

### 7.4 안정 locator

- 규칙·지식·결정은 stable ID heading을 사용한다.
- 자주 참조하는 Markdown heading에는 명시 anchor를 둘 수 있다.
- code symbol rename은 새 locator와 `moved_to` event를 기록한다.
- line number는 다른 locator가 없는 경우에만 fallback으로 사용한다.
- binary 본문은 LLM context에 직접 넣지 않고 승인된 sidecar·metadata·source ID로 선택한다.

### 7.5 file과 unit의 쓰기 범위

- write contract는 parser가 지원하면 unit ID와 locator까지 제한한다.
- whole-file formatter·생성기는 `unit_mode=whole_file`을 요구한다.
- before 조건은 parent file hash와 선택 unit hash를 함께 검사한다.
- 변경 후 parent hash, 영향 받은 unit hash, 관계와 validator 결과를 갱신한다.
- catalog 자체와 append-only event stream의 자기참조 hash 예외는 R-1의 단순 정책을 유지한다.

## 8. task request와 work context

### 8.1 task request

필수 구조 필드:

```text
task_id, requested_by, intent, actions, phase,
target_paths, target_file_ids, target_unit_ids,
target_kinds, output_audience,
include_scopes, exclude_scopes, task_tags,
as_of, context_budget
```

자연어에서 request를 만들 수 있지만 보호 scope, path와 action은 schema·커널 검증을 통과해야 한다. LLM 분류 결과만으로 보호 경로 접근이나 외부 쓰기 권한을 추가하지 않는다.

### 8.2 work context

```text
work_context
├─ request, request hash, as_of
├─ authority
│  ├─ user scope
│  ├─ kernel rule IDs
│  └─ selected conditional rule IDs + predicate evidence
├─ read_manifest
│  ├─ file/unit IDs, paths, locators, expected hashes
│  ├─ decision/knowledge/case IDs and revisions
│  ├─ source chain and selection reason
│  └─ conflicts, stale items, exclusions, budget
└─ write_contract
   ├─ allowed actions and file/unit IDs
   ├─ before file/unit hashes
   ├─ owner, authority, write_when rules
   ├─ validators and postconditions
   └─ required catalog/event/relation/candidate/handoff updates
```

### 8.3 결정적 resolver 순서

```text
1. kernel
2. request schema and protected pre-filter
3. exact target file/unit
4. conditional rule predicates for current phase
5. owner/dependency/consumes/produces
6. accepted decisions and verified knowledge
7. applicable confirmed/resolved cases
8. active relations, default 1-hop
9. conflict/stale/hash/orphan checks
10. category budget and deduplication
11. read manifest + write contract
```

검색 projection은 6~8의 후보 발견을 보조할 수 있지만 1~5의 권위와 scope를 결정하지 않는다.

## 9. data-first vertical slice 원칙

### 9.1 금지되는 구현 패턴

- 모든 schema·디렉터리를 먼저 만들고 데이터는 나중으로 미룸
- catalog를 채운 뒤 실제 작업에서는 사용하지 않음
- rule pack을 만들고 selector 없이 사람이 전체 pack을 계속 읽음
- context package를 생성하지만 write contract가 없음
- writer가 파일을 바꾸지만 catalog·event·relation을 갱신하지 않음
- sample placeholder만 통과시키고 기존 프로젝트 데이터를 이관하지 않음

### 9.2 record kind별 vertical slice

```text
minimum schema
  → existing real record
  → source and relation
  → task selection
  → actual read/write or review
  → validation and event
  → only then next kind
```

schema만 존재하거나 placeholder만 있으면 해당 kind는 미구현이다.

## 10. 보정된 단계별 구축

### 10.1 R-2A — 기존 규칙·모든 파일·최소 동작 폐루프

목표: 현재 프로젝트의 규칙과 파일을 새 구조로 옮기고 실제 작업 하나가 읽기부터 write-back까지 동작하게 한다.

산출물:

1. 8개 커널의 `PROJECT_RULES.md`
2. 7개 Markdown rule pack과 21개 원자 rule record
3. R-2A 실행 시점의 모든 project-governed file node
4. file별 `unit_strategy`와 Markdown/JSON/JSONL 최소 unit parser
5. rule·file·request·work context·event 최소 schema
6. rule/file/unit validator와 orphan·hash·link 검사
7. exact target + predicate 기반 최소 resolver
8. Markdown 파일용 최소 writer와 catalog/event 갱신
9. read-only fixture 1개와 write fixture 1개

실제 write fixture는 R-2A 한국어 단계 보고서와 handoff 갱신을 새 resolver/writer로 수행한다. 부트스트랩 때문에 처음 만든 도구·catalog 변경은 manual bootstrap event로 명시하고, 이후 보고서 쓰기부터 새 폐루프를 사용한다.

완료 게이트:

- 기존 29개 규칙 누락·중복 0건
- kernel 8개, conditional 21개 계산 일치
- project-governed orphan file 0건
- 보고서 작업에 선택된 규칙·파일·unit과 제외 이유 설명 가능
- write contract 없는 변경 거부
- stage report 생성 후 catalog hash, unit, event와 handoff 갱신 확인
- `backup/`과 보호 경로 사전 차단

R-2A 완료 후 보고하고 R-2B 승인을 기다린다.

### 10.2 R-2B — 기존 corpus 확대

목표: 기존의 실제 결정·지식·실패 사례·source·relation을 R-2A 폐루프에 넣는다.

순서:

1. D-01~D-17 decision record
2. 기존 분석의 재사용 지식
3. 실행 결과 오판·잘못된 기본값·보호 위반·Graphify·sandbox·Obsidian 사례
4. 현재 문서·Git·공식 URL source record
5. Markdown 링크의 typed relation candidate
6. 이미 지정된 역사 locator의 `historical_candidate`

각 kind는 최소 schema와 실제 record를 동시에 추가한다. 후보는 검토·source trace 전 active가 되지 않는다.

완료 게이트:

- D-01~D-17이 독립 ID·상태·근거·approval 필드를 가짐
- 하나 이상의 verified knowledge가 원출처까지 추적됨
- 하나 이상의 resolved/confirmed case가 재현·해결 근거를 가짐
- 역사 규칙이 active instruction으로 선택되는 사례 0건
- 기존 corpus를 사용하는 대표 context fixture 2개 통과

R-2B 완료 후 보고하고 R-3 승인을 기다린다.

### 10.3 R-3 — resolver/writer 일반화와 유지보수

목표: R-2A의 Markdown 중심 thin slice를 등록된 파일 종류와 record lifecycle 전체로 확장한다.

- code/config/test/binary sidecar unit adapter
- 새 파일·이동·삭제와 before-hash conflict
- write failure·partial state·retry event
- knowledge candidate·review·supersession 갱신
- session summary와 handoff 생성
- source hash 변경과 `needs_review`
- 동일 request·catalog·rule revision의 동일 선택 ID 재현
- failure recovery와 regression test

R-3 종료 시 exact·metadata·relation resolver가 LLM 기억 없이 운영돼야 한다.

### 10.4 R-4 — 측정된 검색 목표 달성

목표: 도구 도입이 아니라 대표 질의에서 필요한 context를 정확히 반환하는 것이다.

1. 기존 exact·metadata·relation baseline을 고정 평가셋에서 측정한다.
2. 핵심 규칙·결정 질의, 서술형 한국어 질의, conflict·stale·scope 질의를 구분한다.
3. baseline이 승인 기준을 모두 충족하면 FTS 없이 완료할 수 있다.
4. 누락이 있으면 SQLite FTS5 tokenizer 후보를 구현·비교한다.
5. 채택 projection은 삭제 후 정본에서 재구축하고 동일 논리 결과를 검증한다.
6. 결과마다 source locator, status, conflict와 selection reason을 반환한다.

R-4 시작 보고에서 Recall@k·Precision@k·source trace·protected leakage와 context budget 목표값을 사용자에게 승인받는다. vector·graph·Obsidian은 이 평가에서 추가 필요가 증명될 때만 별도 제안한다.

### 10.5 R-5 — 운영 폐루프 최종 검증

새 기능보다 최종 운영 신뢰성을 검증한다.

필수 시나리오:

1. 파일 생성·수정·이동·삭제 lifecycle
2. source hash 변경과 review 전환
3. 상충·대체 지식 병존
4. 실패·부분 변경·재개
5. index 삭제와 cold rebuild
6. 새 세션 cold start와 동일 context 재현
7. 보호 task namespace 격리와 종료
8. 실제 보고서·지식 변경·영상 작업의 rule/file leakage 0건
9. 작업 결과의 event→candidate→review→next context 환류

R-5를 통과해야 “프로젝트 지식 시스템 구축 완료”를 보고할 수 있다.

## 13. 공통 완료·안전 기준

- 규칙 누락·중복·충돌을 검출하고 임의 우선순위를 만들지 않는다.
- unregistered project-governed file과 dangling unit/relation은 0건이다.
- 모든 write target은 owner, write_when, before hash와 validator를 가진다.
- source trace 성공률과 protected leakage는 타협하지 않는다.
- schema만 있고 기존 실데이터가 없으면 완료가 아니다.
- context가 관련 없는 whole file·rule pack을 포함하면 실패다.
- 작업 결과가 event와 다음 context 후보에 반영되지 않으면 폐루프 미완료다.
- 인덱스가 없어도 정본·direct resolver·writer가 동작한다.
- 각 단계는 한국어 보고와 사용자 승인 후 다음 단계로 진행한다.
