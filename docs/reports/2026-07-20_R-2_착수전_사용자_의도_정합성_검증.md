## 1. 최종 판정

### 1.1 정합성 점수

검증 결과를 목표 해석과 실행 절차로 분리한다.

| 검증 대상 | 점수 | 판정 |
|---|---:|---|
| 사용자 목표 해석 | **93/100** | 문서가 핵심 목표를 거의 정확히 이해함 |
| R-1 세부 설계 | **84/100** | 형식·커널·파일 내부 단위 보정 필요 |
| 최종 교차검증의 R-1→R-4 전체 절차 | **76/100** | 정적 재구조화 반복과 운영 폐루프 지연 위험 |

**종합 판정: 핵심 방향은 일치하지만 전체 절차를 보정하기 전 R-2 착수 금지**

R-1은 다음 핵심 의도를 정확히 반영했다.

- 규칙을 작업별로 선택한다.
- 모든 프로젝트 파일을 읽기·쓰기 컨텍스트 체계에 편입한다.
- 읽기와 쓰기를 같은 manifest에서 연결한다.
- 이미 존재하는 규칙·결정·지식·실패 사례를 첫 corpus로 사용한다.
- LLM 기억에 의존하지 않고 프로젝트 파일과 파생 인덱스로 재현한다.
- 검색·벡터·그래프보다 기존 데이터 구조화를 먼저 한다.

그러나 R-1 세부 설계의 다음 네 지점은 사용자의 표현보다 약하거나 다른 방향으로 구체화됐다.

1. 조건부 규칙을 별도 **Markdown 문서**가 아니라 JSONL pack 정본으로 제안했다.
2. 상시 커널 11개 중 3개는 특정 단계에서만 필요한데도 커널에 남겼다.
3. 모든 파일을 node로 등록했지만 파일 내부의 선택·쓰기 단위까지 공통 계약으로 충분히 정의하지 않았다.
4. R-2가 schema·catalog 제작으로 끝나지 않고 기존 데이터를 즉시 담는 vertical slice여야 한다는 완료 게이트가 더 강해야 한다.

전체 R-1→R-4 절차에도 다음 문제가 있다.

5. R-2가 다시 정적 구조·수동 평가 단계로 끝나고 최초의 실제 resolver/writer가 R-3까지 지연된다.
6. R-4가 검색 도입 “검토”로 끝날 수 있어 최종 RAG·검색 목표의 종료 조건이 불명확하다.
7. 장기 갱신·오래됨·새 세션 재현을 종합 검증하는 최종 운영 승인 단계가 따로 없다.

`D` 따라서 **R-1을 현재 형태 그대로 승인하거나 최종 교차검증의 R-1→R-4 절차를 그대로 실행하지 않는다.** 구현 전에 R-1.1 설계 보정과 전체 단계 재배치를 먼저 승인받아야 한다.

### 2.2 의도의 중심 구조

`I` 사용자가 원하는 것은 지식 시스템을 기존 프로젝트 옆에 추가하는 것이 아니다. **프로젝트 자체의 모든 유지 대상 파일과 작업 행위를 읽기·쓰기·축적 가능한 지식 구조로 바꾸는 것**이다.

이를 다음과 같이 이해한다.

```text
모든 project-governed file
  → 파일 내부의 주소 가능한 단위
  → 작업 조건에 맞는 규칙·파일·지식만 선택
  → 읽기 context와 쓰기 contract 동시 제공
  → 작업·검증
  → 변경 파일·관계·event·지식 후보 갱신
  → 다음 세션에서 같은 근거로 재구성
```

핵심은 “모든 것을 항상 읽기”가 아니라 “모든 것을 체계에 포함하되 필요한 단위만 정확히 읽고 쓸 수 있게 하기”다.

## 3. 문서에 기록된 사용자 의도

### 3.1 최종 교차검증 문서

[최종 교차검증](../../reports/최종_구축상태_교차검증보고.md)은 사용자 의도를 다음처럼 기록한다.

- 최소 커널 이외 규칙은 작업 조건에 따라 선택한다.
- 모든 비보호 활성 파일에 read/write 조건, owner, validator, hash와 관계를 둔다.
- 파일 전체를 항상 읽지 않고 모든 파일을 선택 가능한 node로 등록한다.
- 현재 규칙 29개, D-01~D-11, 기존 지식·사례·출처를 첫 corpus로 사용한다.
- resolver와 writer가 같은 manifest를 사용한다.
- 검색 projection은 실제 corpus와 폐쇄 루프 이후로 보류한다.

`F` 이 문서의 목표 정의는 사용자 직접 의도와 높은 수준에서 일치한다.

### 3.2 R-1 정정 설계

[R-1 설계](2026-07-20_R-1_지식_시스템_설계_정정.md)는 이를 다음 구현 모델로 구체화했다.

- 현재 규칙 29개를 상시 커널 11개와 조건부 규칙 18개로 분류
- 조건부 규칙을 7개 JSONL pack으로 구성
- 모든 project-governed file을 `catalog/files.jsonl`에 등록
- 보호·역사 경로는 boundary node 또는 task namespace로 분리
- work context를 read manifest와 write contract로 구성
- 기존 파일→규칙→결정→지식→사례 순으로 첫 corpus 이관
- R-2 수동 fixture, R-3 resolver/writer, R-4 검색 projection 순서

`F` R-1은 사용자의 방향 정정을 대부분 반영했다. 다만 사용자가 강조한 “별도 문서”와 “모든 파일의 읽기·쓰기 단위”를 구현 형식으로 바꾸는 과정에서 에이전트가 추가한 해석이 있다.

## 5. 최종 교차검증 보고서의 전체 절차 검증

### 5.1 문서가 제안한 전체 순서

[최종 교차검증](../../reports/최종_구축상태_교차검증보고.md)의 실행 절차는 다음과 같다.

| 단계 | 문서상 목적 | 최초 제공 기능 |
|---|---|---|
| R-1 | 커널·규칙·file·record·manifest 설계 정정 | 설계 문서만 |
| R-2 | 파일 등록, 규칙 분류, D-01~D-11과 지식·사례 후보 이관, 수동 선택 평가 | 정적 정본과 수동 fixture |
| R-3 | task request, resolver, writer, event·hash·relation·candidate 환류 | 최초 자동 읽기·쓰기 폐루프 |
| R-4 | 실제 corpus에서 SQLite FTS5와 확장 도구 검토 | 선택적 검색 projection |

목표 구조 자체는 `kernel → task → rules → files → records → context → work → write-back`으로 올바르다. 문제는 이 구조를 실제로 작동시키는 순서와 각 단계의 독립 가치다.

### 5.2 R-1 판정

`F` R-1은 잘못된 기존 4-A를 중단하고 목표를 다시 정의하는 단계라는 점에서 필요했다.

`D` 다만 §6에서 설명할 Markdown rule pack, 8개 커널, artifact unit과 data-first gate를 보정해야 한다. 현재 R-1 결과를 그대로 R-2 계약으로 사용하면 안 된다.

### 5.3 R-2 판정

`F` R-2는 기존 파일·규칙·결정·지식·사례를 먼저 구조화하므로 사용자의 “기존 데이터부터” 요구와 일치한다.

`F` 하지만 문서상 R-2의 동작 검증은 “대표 작업에서 필요한 컨텍스트만 선택되는지 수동 평가”까지다. 실제 writer와 event 환류는 R-3에 있다.

`I` 현재 문제의 원인이 “잘 정리된 정적 문서 체계”였는데, R-2가 다시 catalog·schema·record와 수동 fixture만 만들면 같은 실패를 한 단계 더 반복할 수 있다. catalog가 실제 쓰기 때 갱신되지 않으면 R-2 종료 직후부터 낡을 수 있다.

`D` R-2는 정적 이관 단계가 아니라 **기존 데이터로 작동하는 최소 vertical slice**여야 한다. 최소 두 대표 작업에서 다음이 실제로 이어져야 한다.

```text
task request
  → rule + artifact unit selection
  → read manifest + write contract
  → 한정된 파일 변경
  → validator
  → catalog hash + event + relation update
```

완전한 범용 자동화는 필요 없지만, 이 흐름이 스크립트 또는 결정적 도구로 한 번도 동작하지 않으면 R-2를 완료로 보고하지 않는다.

### 5.4 R-3 판정

`F` resolver/writer, event·hash·relation·candidate 환류와 새 세션 재현은 사용자의 핵심 목표와 직접 일치한다.

`D` R-3는 최초 구현 단계가 아니라 R-2의 얇은 vertical slice를 **모든 등록 파일과 record kind로 확장·강화하는 단계**가 되어야 한다.

R-3 책임:

- task predicate와 artifact unit 선택 범위 확대
- optimistic before-hash와 실패 event 강화
- 새 파일·이동·삭제 lifecycle 자동화
- knowledge/decision/case 후보와 review 갱신
- 반복 작업의 결정적 context 재현
- 오류·부분 변경·복구 시나리오 자동 테스트

### 5.5 R-4 판정

`F` 검색 projection을 corpus와 resolver/writer 뒤로 미룬 것은 과도한 구축 방지 의도와 일치한다.

`F` 그러나 “SQLite FTS5를 검토한다”만으로는 최종 목표가 완료되지 않는다. 사용자는 이후 세션에서 필요한 컨텍스트를 정확히 검색해 사용하고, LLM 독립적인 RAG를 원했다.

`D` R-4는 도구 설치 여부가 아니라 다음 중 하나를 증명해야 한다.

1. exact·metadata·relation resolver가 고정 평가를 충족해 FTS 없이도 목표 검색을 달성함.
2. 목표를 충족하지 못해 FTS5 projection을 구현하고 재평가 결과가 기준을 충족함.

벡터·그래프·Obsidian은 여전히 선택 사항이다. 하지만 최소 검색 결과가 source locator, 상태, 충돌, 선택 이유와 함께 실제 task context로 들어가는 검증은 선택 사항이 아니다.

### 5.6 누락된 최종 운영 검증

최종 교차검증의 완료 기준에는 오래됨·write-back·새 세션 재현이 들어 있지만 이를 어느 단계에서 종합 승인하는지가 없다.

`D` 검색 구현 뒤 **R-5 운영 폐루프 검증**을 둔다. 새 기능을 추가하는 단계가 아니라 다음 시나리오를 통과하고 시스템 완료 여부를 판정하는 단계다.

1. 프로젝트 파일 신규 생성·수정·이동·삭제
2. source hash 변경과 `needs_review`
3. 상충 지식 병존과 현재 우선순위 설명
4. 작업 실패 후 불완전 상태와 안전한 재개
5. 인덱스 완전 삭제 후 정본에서 재구축
6. 새 세션 cold start와 동일 context ID 집합 재현
7. 보호 task 종료 후 namespace 격리·정리
8. 실제 대표 작업에서 불필요한 규칙·파일 context 누출 0건

### 5.7 보정된 전체 실행 순서

```text
R-1.1  의도·문서·unit·단계 계약 보정
  → R-2A  기존 rules + 모든 file/unit + 최소 read/write vertical slice
  → R-2B  기존 decisions + knowledge + cases + sources + relations 이관 확대
  → R-3   resolver/writer/event/review의 범용화와 실패 복구 강화
  → R-4   exact/metadata 평가 + 필요한 최소 검색 projection 구현
  → R-5   유지보수·재구축·cold start·보호 경계 종합 승인
```

각 단계는 독립적으로 유용해야 한다.

- R-2A 종료 시 실제 작업 하나가 새 구조로 읽고 쓸 수 있어야 한다.
- R-2B 종료 시 기존 핵심 지식이 검색 전에도 exact ID와 관계로 재사용돼야 한다.
- R-3 종료 시 새 파일과 작업 결과가 자동으로 다음 context corpus에 반영돼야 한다.
- R-4 종료 시 대표 질의가 출처까지 추적되는 context를 생성해야 한다.
- R-5 종료 시 새 세션과 변경·오래됨·실패 상황에서도 폐루프가 유지돼야 한다.

### 5.8 전체 절차 판정

| 절차 기준 | 현재 R-1→R-4 | 보정 필요 |
|---|---|---|
| 기존 데이터 우선 | 충족 | 유지 |
| 단계별 승인 | 충족 | R-2를 A/B로 더 작게 분리 |
| 각 단계의 독립 가치 | 부분 충족 | R-2A에 실제 vertical slice 포함 |
| 최초 read/write 폐루프 시점 | R-3로 지연 | R-2A로 앞당김 |
| 모든 파일 내부 단위 | 불명확 | artifact unit 계약 추가 |
| 최소 검색 목표의 완료 | “검토”로 모호 | 평가 충족 또는 FTS 구현 중 하나를 증명 |
| 오래됨·재구축·cold start 종합 승인 | 단계 없음 | R-5 추가 |

`D` 전체 절차 정합성은 76/100이다. 목표와 구성요소는 맞지만, 작동하는 첫 폐루프가 늦고 마지막 운영 완료 단계가 없다.

## 6. 확인된 불일치와 누락

### 6.1 “별도 문서”와 JSONL rule pack

`U` 사용자는 기존 규칙을 “별도의 문서들로 분류”한다고 표현했다.

`F` R-1은 `rules/*.rules.jsonl`을 규칙 정본으로 제안했다. JSONL은 기계 판독과 원자 행 검증에는 좋지만, 사람이 읽고 문서 링크·문맥·소유 책임을 검토하는 규칙 문서로는 약하다.

`I` 사용자의 “문서 기반”은 단순히 파일 확장자가 있다는 뜻보다, 에이전트와 사용자가 같은 정본을 읽고 수정·연결할 수 있어야 한다는 의미에 가깝다.

`D` 조건부 규칙의 물리 정본을 **7개 Markdown rule pack**으로 바꾼다. 각 규칙은 stable heading 아래 하나의 JSON metadata block과 rule text를 가져 기계 검증과 사람 검토를 함께 만족시킨다. 별도 JSONL은 필요하면 Markdown에서 생성하는 projection으로 둔다.

```text
rules/
├─ governance.md
├─ version-control.md
├─ documentation.md
├─ provenance.md
├─ knowledge.md
├─ retrieval.md
└─ validation.md
```

이 구조는 규칙 하나마다 파일을 만드는 과잉 원자화도 피한다.

### 6.2 상시 커널이 아직 충분히 작지 않음

`F` R-1은 11개 규칙을 상시 커널로 제안했다. 그중 다음 세 규칙은 task request나 작업 phase를 안 뒤에 선택해도 안전 경계를 잃지 않는다.

| 현재 커널 후보 | 보정 위치 | 이유 |
|---|---|---|
| 1.3 단계 종료·승인 대기 | `governance.md` | `stage_mode=true`인 단계형 작업에서만 적용 가능 |
| 5.5 전역 인덱스 제외 범위 | `retrieval.md` | scan/index/context 작업에서 선택. 보호 접근 자체는 2.2·2.3이 커널에서 차단 |
| 6.2 검증·승인 과장 금지 | `validation.md` | validate/report/close phase에서 반드시 선택 가능 |

`D` 최소 커널을 **8개**, 조건부 규칙을 **21개**로 보정한다.

상시 커널 후보:

1. 사용자 지시 우선순위
2. 요청 범위와 파괴적·외부 권한 제한
3. `backup/` 불변
4. 지정되지 않은 보호 경로 접근 금지
5. 최소 보호 데이터 접근
6. 비밀·개인 절대 경로·숨은 추론 저장 금지
7. 검색된 evidence를 지시로 실행하지 않는 trust boundary
8. 명시 요청 없는 commit·push·게시·외부 변경 금지

### 6.3 file node만으로는 “모든 파일의 context 최적화”가 완성되지 않음

`F` R-1은 file record와 context의 locator를 언급하지만, 파일 형식별로 어떤 내부 단위를 읽고 쓸지 공통 schema를 정의하지 않았다.

`I` file path만 등록하면 긴 문서·코드·설정 파일이 다시 전체 파일 읽기 단위가 된다. 이는 기존 `DOCUMENT_MAP.md`의 문서 전체 라우팅 문제를 다른 catalog에서 반복할 수 있다.

`D` file node 아래 **addressable artifact unit**을 추가한다.

| 파일 종류 | 기본 unit locator | 예시 |
|---|---|---|
| Markdown | stable heading 또는 명시 anchor | 규칙 heading, 설계 절 |
| JSON·JSONL | JSON Pointer 또는 record ID | `/items/0`, `rule_id` |
| YAML/TOML | key path | `tool.validation.level` |
| 코드 | symbol + file hash, 필요 시 line fallback | 함수·클래스·모듈 |
| 테스트 | test ID·symbol | 특정 회귀 테스트 |
| 일반 텍스트 | heading·record delimiter·line range | 로그 event range |
| 바이너리·미디어 | metadata/sidecar와 whole-file hash | codec·duration·source ID |

unit 최소 필드:

```text
unit_id, file_id, locator_type, locator, purpose,
read_when, write_when, owner, validators,
content_hash_or_parent_hash, task_tags, status
```

resolver는 file을 고른 뒤 필요한 unit만 read manifest에 넣고, writer는 가능한 경우 unit locator까지 write contract를 제한한다. whole-file만 안전한 형식은 명시적으로 `unit_mode=whole_file`을 사용한다.

### 6.4 R-2가 빈 schema 구축으로 끝날 위험

`F` R-1은 기존 corpus 선이관을 명시했지만 R-2 범위에 rule/file/source/knowledge/decision/case/relation schema와 validator가 함께 들어 있다.

`I` 구현 순서가 schema 우선으로 흐르면 사용자가 이미 지적한 “기존 데이터는 구조 밖에 있고 새 기반 문서만 늘어나는 문제”가 반복될 수 있다.

`D` R-2는 data-first vertical slice로 수행한다.

```text
최소 schema 1개
  → 해당 기존 실데이터 즉시 이관
  → source·relation 연결
  → 대표 작업에서 선택 검증
  → 통과한 경우에만 다음 record kind 추가
```

R-2 완료를 다음처럼 제한한다.

- schema 파일만 있고 실제 이관 레코드가 없으면 미완료
- file catalog만 있고 파일 내부 unit이 없으면 미완료
- 규칙 pack만 있고 대표 task에서 조건 선택을 검증하지 못하면 미완료
- 후보를 많이 만들었지만 source locator와 상태가 없으면 미완료

### 6.5 “모든 파일” 범위에 대한 해석

`Q` 현재 해석은 다음과 같다.

- 포함: 프로젝트가 유지·수정·검증하는 모든 문서·규칙·코드·설정·schema·test·record·관계·의도적 projection
- task scope 포함: 사용자가 정확히 지정한 보호 파일
- 개별 전역 열거 제외: `backup/`, 지정되지 않은 `inputs/`·`outputs/`, `.git/`, cache, temporary file, virtual environment
- 경계 표현: 제외 디렉터리는 boundary node와 정책만 등록하고 내부 파일명은 전역 catalog에 넣지 않음

이 해석은 사용자의 “모든 파일”과 기존의 보호 경로 금지 원칙을 함께 만족시키기 위한 것이다. 사용자가 `backup/` 내부까지 file node로 등록하려는 뜻이었다면 현재 해석과 다르므로 별도 승인이 필요하다.

## 7. 일치하는 부분

다음 R-1 결정은 사용자 의도와 일치하므로 유지한다.

1. file catalog는 모든 project-governed file을 선택 가능한 node로 만든다.
2. 모든 파일 내용을 매번 LLM 입력에 넣지 않는다.
3. read manifest와 write contract는 하나의 work context에 속한다.
4. writer는 owner·before hash·validator·catalog·event·relation 갱신을 요구한다.
5. 현재 파일·규칙·D-01~D-11·기존 지식·실패 사례를 첫 corpus로 사용한다.
6. `backup/` 자료는 historical candidate로만 검토하고 자동 활성화하지 않는다.
7. LLM은 후보 추출을 도울 수 있지만 schema 검증·source trace·검색·manifest 생성은 파일 기반으로 재현한다.
8. SQLite·vector·graph·Obsidian은 실제 corpus와 평가 뒤로 보류한다.
9. R-2, R-3, R-4를 별도 승인 단계로 유지한다.

## 8. R-1.1과 전체 절차에 필요한 최소 보정

R-2 전에 R-1 문서와 최종 교차검증의 실행 순서를 다음처럼 보정해야 한다.

1. conditional rule 정본: JSONL pack → Markdown pack + 규칙별 구조 metadata
2. D-12와 규칙 분류: 11+18 → 8+21
3. file catalog 아래 addressable artifact unit schema 추가
4. read/write contract를 file뿐 아니라 unit locator까지 제한
5. R-2를 data-first vertical slice로 재정의하고 empty-schema 완료 금지
6. R-2 fixture에 “긴 문서의 특정 heading만 선택”과 “코드 symbol 단위 쓰기” 사례 추가
7. “모든 파일” 범위를 §6.5의 해석으로 명시
8. R-2를 R-2A vertical slice와 R-2B 기존 corpus 확장으로 분리
9. 최소 resolver/writer 폐루프를 R-3에서 R-2A로 앞당김
10. R-4에 검색 목표 충족 판정과 필요한 projection 구현을 명시
11. R-5 운영 폐루프·유지보수·cold start 종합 검증 추가

나머지 정본·출처·관계·migration namespace·writer failure·확장 보류 설계는 유지할 수 있다.

## 10. 사실·추론·판단

### 확인된 사실

- `F` R-1은 사용자의 핵심 방향인 조건부 규칙, 전 파일 catalog, 읽기·쓰기 통합, 기존 corpus 선이관과 LLM 독립성을 명시했다.
- `F` R-1은 conditional rule을 JSONL pack으로, 상시 커널을 11개로, file 선택을 file node 중심으로 설계했다.
- `F` 최종 교차검증은 R-2를 정적 재구조화·수동 평가로, 최초 resolver/writer 구현을 R-3로, 검색 projection 검토를 R-4로 배치했다.
- `F` 현재 R-2 구현은 시작되지 않았고 규칙·catalog·record·resolver/writer 경로도 생성되지 않았다.

### 추론

- `I` JSONL pack은 기계 구조에는 좋지만 사용자가 강조한 별도 문서 기반 규칙 관리와 완전히 같지 않다.
- `I` file-level catalog만 만들면 긴 문서 전체 읽기 문제가 재발할 수 있다.
- `I` 기존 실데이터 없는 schema 완료를 허용하면 이전 방향 오류가 반복된다.
- `I` 실제 폐루프를 R-3까지 미루면 R-2가 또 하나의 정적 문서·metadata 단계가 될 수 있다.
- `I` R-4가 검색 도구 검토로 끝나고 운영 종합 검증이 없으면 최종 목표 달성을 판정할 수 없다.
