# R-4 검색 평가 및 조건부 인덱스 판정 결과

- 작성일: 2026-07-21
- 상태: R-4 구현·평가·구조 검증·자동 검증 완료 / R-5 착수 가능
- 목적: 승인된 R-4 범위의 고정 검색 평가셋으로 direct·metadata·relation 기준선을 측정하고 SQLite FTS5 필요 여부를 증거로 판정한다.
- 사용 시점: R-4 검색 품질과 인덱스 도입 판정을 감사하거나 R-5 운영 인수 기준선을 확인할 때만 사용한다.
- 작성·검증 주체: 프로젝트 에이전트가 구현·자동 검증하고 사용자가 현재 명령에서 R-3~R-5 실행을 승인했다.
- 언어: 한국어.
- 저장 위치: `docs/reports/2026-07-21_R-4_검색_평가_결과.md`.
- 연결 관계: [승인 설계](2026-07-20_R-1.1_지식_시스템_설계_보정.md), [검색 계약](../agent/CONTEXT_RETRIEVAL.md), [지식 계약](../agent/KNOWLEDGE_SYSTEM.md), [유지보수 계약](../agent/KNOWLEDGE_MAINTENANCE.md), [현재 체크포인트](../../SESSION_HANDOFF.md).
- 권위·보존 상태: `retained-evidence`; 검색 동작의 권위는 활성 기술 계약과 코드가 소유하며 이 보고서는 R-4 시점의 평가와 판정만 보존한다.

## 1. 단계 시작 게이트

### 목표와 범위

- exact ID, metadata, 한국어 서술, 상태·충돌, 보호 경계 질의를 고정 평가셋으로 정의한다.
- 각 결과에 source/status/conflict/selection reason을 포함하고 Recall@k, Precision@k, source trace, 보호 경로 누출, context byte budget을 측정한다.
- direct·metadata·verified one-hop relation 기준선이 엄격 기준을 놓칠 때만 SQLite FTS5를 추가한다.

### 제외 범위

- cold start, index 삭제 후 복구, 실제 작업 3종 누출, protected task namespace lifecycle의 종합 인수는 R-5다.
- vector database, graph database, Obsidian은 도입하지 않았다.
- 평가셋을 통과시키기 위한 relevance judgment·threshold 완화나 기대 ID 변경은 하지 않았다.

### 구현 전 테스트와 완료 기준

- 8개 고정 질의 모두 Recall@k=1.0, Precision@k=1.0, source trace rate=1.0이어야 한다.
- 빈 결과가 정답인 stale/conflict/protected 질의는 result 0과 명시적 exclusion 또는 rejection을 반환해야 한다.
- 보호 경로 누출은 0, context budget 실패는 0이어야 한다.
- 같은 corpus revision과 query의 logical result hash가 재실행에서 동일해야 한다.
- 기존 R-2A~R-3 테스트 16개와 R-4 신규 테스트 2개, 통합 구조 검증이 모두 통과해야 한다.

## 2. 구현 결과

- `evaluation/retrieval/r4_queries.json`에 exact rule, decision+1-hop knowledge, 한국어 보호 경계, 한국어 문서 중복 case, tool/test metadata, historical candidate 제외, conflict scan, protected prefilter의 8개 판단을 고정했다.
- 검색기는 canonical corpus·source·rule·file projection만 읽고 status eligibility를 먼저 적용한 뒤 exact, metadata, normalized Korean text, verified one-hop relation을 결정적으로 결합한다.
- 결과마다 locator, source status/hash, retrieval·instruction eligibility, 선택 이유, conflict를 기록한다.
- 평가 결과는 원본 평가셋 hash와 volatile 시각·event ID를 제외한 logical result hash를 기록한다.
- 기준선이 모든 엄격 기준을 통과해 `fts_decision=not_needed_baseline_passed`, `search_projection=null`로 판정했다. `.db`, `.sqlite`, `.sqlite3` 파일은 0개다.

## 4. 자체 검토와 개선

- 발견: 최초 rule source trace 경로가 corpus record 형식만 가정해 rule의 문자열 `source_refs`를 처리하지 못했다.
- 개선: rule/file 전용 source trace를 분리해 locator와 current hash를 검증하고 평가 전체를 다시 실행했다.
- 발견: 최초 conflict 질의는 기대 결과가 빈 경우만 확인해 실제 conflict-bearing record를 검색하지 않았다.
- 개선: eligible record의 `conflict_ids`를 실제 검사하는 conflict scan을 구현하고 빈 현재 corpus 결과를 확인했다.
- 발견: 실행 시각과 event ID가 결과 재현성 비교를 방해할 수 있었다.
- 개선: 평가 의미만 canonicalize한 logical result hash를 추가하고 재실행 동일성을 테스트했다.
- 발견: historical source가 case의 provenance에는 남아도 지시 근거로 오인될 여지가 있었다.
- 개선: 모든 source trace에 retrieval/instruction eligibility를 명시해 historical candidate는 둘 다 false로 표시했다.
- 경계 검토: R-5의 cold rebuild·새 세션·실제 작업 누출 시나리오는 구현하지 않았다.

## 7. 완료 게이트와 잔여 위험

- R-4 요구사항과 고정 평가 기준: 전부 충족.
- 필수 단위·통합·구조·회귀 테스트: 전부 통과.
- 자체 검토 필수 개선: 반영 후 전체 재검증.
- R-5 경계 선행 구현: 0건.
- 잔여 위험: 현재 작은 corpus에서 기준선이 완전 통과했으므로 FTS와 그 물리 인덱스 복구는 의도적으로 존재하지 않는다. R-5는 derived projection cold rebuild 등가성을 검사해야 한다.
- 잔여 위험: 원본의 untracked `blog_images/`는 사용자 작업으로 판단해 읽기·수정·catalog·commit에서 제외했다.
