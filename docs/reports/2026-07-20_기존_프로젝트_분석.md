- 사용 시점: 기존 자산을 이식하거나 설계 판단의 역사적 근거를 확인할 때 사용한다.
- 작성·수정 주체: 에이전트가 확인된 저장소 근거로 작성·정정하고, 분류 판단의 채택 여부는 사용자가 승인한다.

- 비범위: 최신 외부 공식 자료 조사, 새 구조 설계, 코드·도구·RAG 구현, `backup/` 변경.

## 1. 판정 표기와 분석 방법

이 보고서는 사실, 과거 결정, 추론, 이번 분석의 분류 판단을 다음처럼 구분한다.

| 표기 | 의미 |
|---|---|
| `F` | 현재 Git·파일·코드에서 직접 확인한 사실 |
| `H` | 과거 보고서나 실행 증거에 기록된 사실. 이번 단계에서 다시 실행하지 않은 역사적 검증 결과 |
| `D` | 과거 프로젝트에서 명시적으로 채택·제외·보류한 결정. 현재 새 프로젝트에는 아직 재승인되지 않음 |
| `I` | 여러 사실을 교차해 도출한 추론 |
| `R` | 새 프로젝트에 대한 이번 분석의 유지·개선·폐기 분류. 설계·구현 승인이 아님 |

분석은 다음 원칙으로 수행했다.

1. `git ls-files`로 추적 프레임워크 파일을 먼저 확정했다.
2. 보호 대상 경로와 민감 패턴은 파일을 열기 전에 제외했다.
3. 세 스냅샷의 시작 문서, 권위 문서, 워크플로우·상태 계약, 코드 표면, 테스트 이름, 단계 보고서, 실패 보고서를 교차 대조했다.
4. `backup/`은 읽기 전용으로 유지했다.
5. 분석 단계이므로 백업 안의 테스트나 도구는 재실행하지 않았다. 과거 통과 수치는 `H`로만 사용한다.

## 2. 한눈에 보는 결론

1. `F` 현재 활성 루트는 사실상 비어 있다. Git 추적 기준으로 루트에는 `.gitattributes`, `.gitignore`와 세 백업 스냅샷만 있고, 활성 `PROJECT_RULES.md`, 워크플로우, 도구, 테스트, 지식 시스템은 없다. 2026-07-20의 `5e8b254` 커밋이 기존 활성 파일을 세 백업 스냅샷으로 정리했다.
2. `F` 기존 프로젝트의 기능적 핵심은 첫 스냅샷에 있다. 8단계 영상 제작 흐름, 11개 스킬, 소스 자산·동기 검사·Premiere XML·품질 감사·상태 게이트 도구와 74개 테스트 메서드가 보존돼 있다.
3. `H` 첫 번째 재구축은 안전성과 테스트를 크게 강화했지만, 실제 영상 0건·측정된 생산성 개선 0인 상태에서 계층형 애플리케이션과 159개 통과 테스트를 먼저 만들었다. 사용자 의도와 비용 상한을 벗어나 폐기됐다.
4. `F/D` 두 번째 재구축은 파일 기반 상태, 원자 문서, 직접 라우팅, Obsidian Properties/Base를 남기고 SQLite 상태 플랫폼과 Graphify를 보류·제외했다. 이 방향은 이전보다 단순하지만 현재는 모두 `backup/` 안의 역사 자산이다.
5. `F` 기존 Obsidian/Base는 메타데이터 필터와 문서 후보 탐색이다. 원문·지식 단위 임베딩, 벡터 검색, 원본 작업 기록에서의 지식 추출, 지식 검증·갱신, 출처가 포함된 컨텍스트 패키지 생성은 구현돼 있지 않다. 따라서 사용자가 요구한 독립형 RAG는 아직 없다.
6. `R` 새 프로젝트는 기존 폴더를 복원해서는 안 된다. 검증된 행동 계약, 도메인 지식, 실패 교훈만 새 정본으로 재구성하고, 작업 기록→지식→검색→컨텍스트→결과 반영 흐름은 별도의 최소 지식 시스템으로 새로 설계해야 한다.

## 3. 스냅샷 계보와 규모

Git 추적 프레임워크 기준으로 `backup/`에는 250개 파일이 있다. 사용자 데이터의 파일 수나 내용은 이 수치에 포함하지 않았다.

| 스냅샷 | 역할 | 파일·문서 규모 | 확인된 상태 |
|---|---|---|---|
| `origin` | 원형 영상 제작 프레임워크 | 86파일, Markdown 38개/5,599줄, Python 34개/8,944줄, 테스트 메서드 74개 | 실제 제작 지식과 도구가 가장 풍부하나 상태 분산과 실행 안전 결함이 있음 |
| `refactorying_snapshot_1` | Stage 0~4 전면 재구축 | 130파일, Markdown 41개/5,088줄, Python 65개/9,794줄, 테스트 메서드 121개 | `H` 최종 기록 159 passed·1 skipped. 실제 사용자 미디어·Premiere 앱·생산성은 미검증 |
| `refactorying_snapshot_2` | 파일 상태·문서 라우팅·Obsidian 중심 재설계 | 34파일, Markdown 22개/3,191줄, Python 5개/1,264줄, 테스트 메서드 38개 | `H` 38/38 통과. L5 이후 실제 워크플로·도구·스킬은 미구축 |

계보는 다음과 같다.

```text
원형 제작 프레임워크
  └─ 전면 코드 재구축(Stage 0~4)
       └─ 과도한 구축 판정으로 활성 루트에서 제거
            └─ 파일 기반 상태 + 문서 원자화 + Obsidian 실험
                 └─ Graphify 취소, Obsidian GUI 미해결
                      └─ 전체를 backup으로 이동하고 현재 루트 초기화
```

중요한 해석은 다음과 같다.

- `F` 세 스냅샷은 서로 동시에 적용할 수 있는 정본이 아니다.
- `I` 새 프로젝트에서 어느 한 스냅샷을 그대로 복원하면 이미 확인된 충돌과 비용을 되살리게 된다.
- `R` 최신 스냅샷을 우선 참고하되, 기능 지식은 `origin`, 실패·회귀 지식은 첫 재구축, 문서·상태 단순화 지식은 두 번째 재구축에서 선택적으로 가져와야 한다.

## 4. 기존 기능과 구조 분석

### 4.1 영상 제작 도메인

`F` 원형 프레임워크에는 다음 제작 경로가 정의돼 있다.

- 촬영 전: `1 소재 조사 → 2 채널 기획 → 3 대본 구성 → 촬영/녹화 → 4 자막 정리 → 6 근거 분석 → 5 영상 기획 → 7 편집 자료 → 8 최종 검수`
- 촬영 완료본: 원본·자막 신뢰 확인 후 `6 근거 분석 → 5 영상 기획 → 7 편집 자료 → 8 최종 검수`
- 7단계 내부: `7A 후보 범위 해석 → 7B microbeat·경계 검증 → 7C 대표 캘리브레이션 → 사용자 방향 확인 → 7D 전체 확장`

`F` 워크플로의 중요한 품질 원칙은 다음과 같다.

- 영상 기획은 원본 근거 분석보다 먼저 오지 않는다.
- 생성 파일의 존재는 다음 단계 승인과 같지 않다.
- 원본 시간·프레임 근거와 편집본 렌더 근거를 구분한다.
- AI는 기본 결함을 먼저 찾고, 사용자는 소재·메시지·편집 감각·배포를 결정한다.
- 초반만 검증하지 않고 초반·중간·후반을 대표 표본으로 본다.
- 긴 컷이나 컷 수 임계값은 자동 판단이 아니라 재검토 신호다.

### 4.2 도구와 자동화

기존 도구군과 판정은 다음과 같다.

| 도구군 | 보존된 기능 | 현재 분석 |
|---|---|---|
| 소스 식별·자산 | 동일 원본 지문↔동일 `source_id`, 원본 시간/프레임 자산, 재사용, 해시 등록 | 핵심 행동 계약. 새 구현에서 필수 승계 후보 |
| 미디어 probe | 컨테이너·FPS·해상도·오디오 정보 | 필요. 단, 실패 시 기본값으로 계속하는 경로는 폐기 |
| 자막·동기 검사 | SRT 파싱, 음성/VAD·경계 위험, lag 점수 | 보조 검사로 가치 있음. 편집 판단이나 자동 승격으로 사용 금지 |
| Premiere XML | 컷 CSV에서 XML 생성, 프레임 경계, 오디오·멀티소스 처리 | 실제 사용 환경이 확인되면 특성 테스트와 함께 선택 승계 |
| 편집 품질 감사 | 평균·최장 컷, 후반 밀도, 누락 프로필, 근거 있는 waiver | 경고 도구로 유지. 종료 코드와 게이트 의미를 분리해야 함 |
| remux·실행 래퍼 | MKV→MP4 무재인코딩, Python/Git 실행 | 하위 실패 코드 보존과 실제 스트림 검증을 고친 뒤에만 사용 |
| 문서·프로젝트 검사 | 문서 경계, Git 추적, 실행 환경 검사 | 새 최소 구조에 맞춘 얇은 검사로 재작성 필요 |
| `projectctl`·전체 workflow gate | 작업 점유, 전환, 영수증, 다중 상태 교차검사 | 현재 1인 순차 작업에는 과도함. 필요한 불변조건만 남김 |
| edit memory·SQLite | 이벤트, revision DAG, working/approved 기준본 | 반복 손실이 실측될 때까지 보류. 일반 지식 시스템과 혼합 금지 |

### 4.3 상태와 파일 생명주기

세 세대의 상태 모델은 서로 다르다.

- `origin`: 핸드오프, `WORKFLOW_STATE.json`, 여러 `CURRENT.json`, 편집 기억 DB, 산출물 메타데이터가 병존했다.
- 첫 재구축: 프로젝트별 SQLite를 단일 정본으로 삼고 domain/service/storage 계층, 이벤트, 승인 challenge, 생성 뷰를 구축했다.
- 두 번째 재구축: `outputs/<project_id>/state.json` 하나로 축소하고 JSON Schema v3, 원자 저장, SHA-256, 현재/대체/실패, 승인 범위, 다음 사용 가능성을 구현했다.

`F` 두 번째 재구축의 `state_io.py`는 정확한 키 집합, 경로 탈출, symlink, source ID, 무결성, 계보, 승인, 원자 교체를 엄격히 검사한다. `F` 테스트는 정상 왕복뿐 아니라 중단 저장, 손상 JSON, 잘못된 계보, 다중 current, 무결성 불일치, 제한된 검증 범위를 포함한다.

`I` 이 파일 상태 모델은 영상별 작업 재개에는 유용하지만 프로젝트 지식 저장소의 대체물이 아니다. 지식에는 주장 단위 출처, 신뢰도, 검토일, 상충 관계, 갱신 이력이 추가로 필요하기 때문이다.

### 4.4 문서 거버넌스와 Obsidian

두 번째 재구축은 문서를 `navigation`, `rebuild`, `workflow`, `tooling`, `state`, `user`, `history`로 분리하고 각 관리 문서에 목적·범위·권위·읽기/수정 시점 등의 Properties를 부여했다.

`F` 유지 가치가 있는 점:

- 알려진 작업은 `AGENTS.md`의 직접 경로로 읽는다.
- 모르는 작업만 좁은 도메인에서 최대 3개 후보를 찾는다.
- 검색 결과·링크·백링크는 읽기 권한이나 정본이 아니다.
- 문서 속성은 원문에 한 번만 기록하고 `.base`는 파생 화면으로 사용한다.
- 역사 보고서는 실행 경로에서 제외한다.

`F` 한계:

- `.base`는 `domain`, `kind`, `lifecycle`, `purpose` 등을 필터링하는 메타데이터 뷰다.
- 콘텐츠 청크, 키워드 역색인, 임베딩, 벡터, 하이브리드 검색, 결과 점수, 출처 묶음이 없다.
- Obsidian 공식 CLI가 실행 중인 데스크톱 앱과 설치 경로에 의존한다.
- 마지막 핸드오프에는 CLI는 응답하지만 GUI 주 창이 없는 문제가 해결되지 않은 것으로 기록돼 있다.
- UI 제외 패턴은 보안 경계가 아니다.

따라서 `F` Obsidian 도입은 로컬 Markdown 검토·탐색 인터페이스로는 유효했지만, LLM과 독립적으로 유지되는 RAG나 지식 수명주기 시스템은 아니다.

## 5. 유지·개선·폐기할 기능

### 5.1 유지

| 대상 | 분류 | 유지 이유와 조건 |
|---|---|---|
| 원본·파생·프레임워크 경계 | `R 유지` | 데이터 보호의 핵심. 보호 경로는 명시 항목과 목적 없이는 열거·색인하지 않음 |
| `backup/` 읽기 전용 | `R 유지` | 역사 근거를 보존하되 활성 정본·런타임 의존성으로 사용하지 않음 |
| 한 규칙·상태·결정당 한 정본 | `R 유지` | 중복 수정과 세션별 재해석을 줄임 |
| 사용자용 한국어 / 에이전트용 영어 | `R 유지` | 독자와 실행 목적이 명확함. 사용자 소유 파일명은 보존 |

## 6. 기존 문제와 원인

### 6.1 상태와 지식의 분산

- `F` 현재 상태가 핸드오프, 워크플로 JSON, 여러 현재본 포인터, 편집 DB, 산출물 메타데이터에 반복됐다.
- `I` 상태·결정·지식·검증 증거의 역할을 구분하지 않고 각 기능이 자체 현재본을 만들었기 때문이다.
- 영향: 세션마다 현재 기준본을 다시 판단하고, 같은 변경을 여러 파일에 반영하며, 충돌 시 어느 쪽이 정본인지 불명확했다.

### 6.2 실행 실패가 성공으로 보이는 문제

- `H` `run_python.bat`에서 자식 종료 코드 `7`이 최종 `0`으로 바뀌는 현상이 재현됐다.
- `F/H` remux는 개별 FFmpeg 실패를 최종 실패로 누적하지 않았고, guard·pre-commit은 일부 결손·예외에서 fail-open이었다.
- 원인: 메시지 출력이나 파일 존재를 성공으로 취급하고, 자식 종료 코드와 기대 결과를 함께 검증하지 않았다.

### 6.3 잘못된 기본값과 검증 범위 혼동

- `F` 과거 Premiere XML 경로는 ffprobe 실패 시 미디어 기본값으로 계속 진행했다.
- `F` XML 테스트는 구조를 검사했지만 실제 Premiere import, 연속 A/V, 콘텐츠 품질은 증명하지 못했다.
- `I` 생성·파싱·도구·앱·사용자 검증을 한 성공 상태로 뭉뚱그린 것이 원인이다.

### 6.4 사용자 데이터 경계 위반

- `H` 초기 Stage 00 인벤토리가 파일시스템 전체를 재귀 열거해 보호 대상의 파일별 메타데이터를 기록했다가 정정됐다.
- 원인: Git 추적 프레임워크 목록이 아니라 파일시스템 탐색부터 시작했다.
- 재사용 교훈: 색인·RAG 수집기도 반드시 허용 경로 목록을 먼저 만들고, 보호 경로는 접근 전에 차단해야 한다.

### 6.5 실제 생산보다 관리 시스템을 먼저 구축

- `H` 첫 재구축은 최종 통합 검사 159 passed·1 skipped를 기록했지만 실제 영상 제작 0건, 생산성 개선 측정 0이었다.
- `F` 현재 스냅샷의 정적 합계는 `src/` Python 약 6,456줄, 테스트 Python 약 3,337줄이다. 당시 핸드오프의 “신규 코드 약 2,000줄”과도 일치하지 않는다.
- 원인: 대표 작업과 비용 지표 없이 미래의 동시성·승인·감사 요구를 먼저 일반화했다.

### 6.6 Graphify 정확도·비용·보고 실패

- `H` Graphify+Ollama는 대표 작업 2개에서 관련 없는 문서를 8개와 5개 추가했고 예상 문맥량을 각각 21,054, 14,197토큰 늘렸다. 나머지 작업도 이점이 없었다.
- `H` 이후 자체 typed 라우터를 Graphify 도입으로 표현했으나 활성 경로는 Graphify 제품을 호출하지 않았다.
- 원인: 제품 사용 증거와 결과 정확성을 분리하지 않았고, 세 차례 실패 뒤 중단하지 않고 다른 구현을 같은 제품 이름으로 보고했다.

### 6.7 샌드박스·외부 도구 실행 경계 반복 실패

- `H` 직접 Obsidian CLI의 승인 경계를 이미 확인한 뒤 Python 래퍼를 기본 샌드박스에서 다시 실행해 같은 권한 실패를 반복했다.
- 원인: 래퍼가 자식 실행 파일의 승인을 상속받는다고 잘못 가정했고, 실제 운영 진입점을 먼저 고정하지 않았다.

### 6.8 Obsidian 활성 상태와 사용자 화면 불일치

- `H` 공식 CLI와 Base 분류는 과거에 검증됐지만 마지막 핸드오프에는 네 개의 응답 프로세스가 모두 주 창 핸들을 갖지 않는 문제가 남았다.
- `I` 도구 검증과 사용자에게 보이는 앱 검증을 별도로 관리하지 않으면 “도입 완료” 상태가 실제 사용 가능성과 어긋난다.

### 6.9 현재 루트와 과거 ‘완료’ 상태의 불일치

- `F` 두 번째 스냅샷 문서는 L0~L4와 L3.1~L3.3 완료를 주장한다.
- `F` 그러나 현재는 그 문서·코드·테스트가 모두 `backup/`으로 이동해 활성 프로젝트 기능이 아니다.
- `I` 새 프로젝트의 완료 상태는 과거 보고서가 아니라 새 활성 경로에서 다시 검증해야 한다.

| 구현 규모 기록 | 핸드오프는 신규 코드 약 2,000줄, 현재 정적 집계는 `src/` 약 6,456줄 | 향후 자동 산출 가능한 수치는 파일에 고정하지 않고 실행 시 조회 |

### 8.2 사용자가 요구한 지식 시스템 기준의 누락

`F` 다음 구성요소는 세 스냅샷 어디에도 완성된 시스템으로 존재하지 않는다.

1. 모든 작업의 원본 기록을 append-only로 보존하는 공통 원장
2. 원본 로그와 분리된 세션 요약·인수인계 기록
3. 원본 기록에서 재사용 지식을 추출하는 명시적 절차와 상태
4. 확인된 사실·추론·결정을 주장 단위로 구분하는 지식 스키마
5. 각 지식의 출처, 작성일, 신뢰도, 검증자/검증 방법, 관련 항목, 갱신 이력
6. 지식 간 typed relation과 상충·대체 관계
7. 오래된 지식의 검토 기한, 재검증, 폐기·대체 절차
8. 내용 검색용 로컬 역색인·벡터 인덱스와 결정적 재구축 절차
9. 키워드·메타데이터·의미 검색을 결합한 RAG
10. 검색 결과에서 원문 파일과 정확한 지식 항목으로 돌아가는 provenance
11. 작업별 토큰 예산과 목적에 맞춘 컨텍스트 패키지 생성
12. 작업 결과를 다시 로그·지식·결정·문제 사례에 반영하는 폐쇄 루프
13. 검색 정확도, 누락, 오탐, 오래된 지식, 보호 경로 비색인을 검증하는 평가 세트

현재 Properties 스키마에도 `source`, 작성일, 신뢰도, 관련 지식, 검토 예정일, 변경 이력이 없다. `state.json`은 영상 산출물 상태를 다루며 지식 주장 모델이 아니다. `AGENT_DOCUMENTS.base`는 문서 속성 화면일 뿐 내용 검색 인덱스가 아니다.

## 9. 새 프로젝트의 필수 요구사항

이 절은 구현안이 아니라 명령 2 설계가 반드시 만족해야 할 요구조건이다.

### 9.1 프로젝트 기반

1. 활성 루트에 `PROJECT_RULES.md`, 최소 에이전트 라우터, 현재 상태 문서가 각각 하나의 정본으로 존재해야 한다.
2. `PROJECT_RULES.md`에는 모든 작업에 항상 적용되는 데이터 경계, 권한, 언어, 검증·보고 원칙만 둬야 한다.
3. 절차, 재구축 계획, 기술 설계, 도메인 워크플로, 지식 스키마는 별도 목적 문서로 분리해야 한다.
4. 모든 활성 문서는 목적, 사용 시점, 작성·수정 주체, 언어, 저장 위치, 연결 관계를 명시해야 한다.
5. 활성 코드·문서·테스트·인덱스는 `backup/` 없이 동작해야 한다.

### 9.2 기록과 지식의 분리

다음 일곱 데이터군을 물리적 또는 명확한 논리 경계로 분리해야 한다.

1. 원본 작업 기록
2. 세션별 요약과 인수인계
3. 검증된 지식
4. 의사결정과 근거
5. 문제·실패·해결 사례
6. 문서·지식 관계 정보
7. 작업별 컨텍스트 패키지

원본 기록은 수정 대신 추가를 기본으로 하고, 요약·지식·결정은 반드시 원본 기록이나 외부 1차 출처로 역추적돼야 한다.

### 9.3 지식 항목 최소 계약

각 지식 항목에는 최소한 다음 정보가 필요하다.

- 안정 ID와 제목
- 주장 본문과 `fact` / `inference` / `decision` 유형
- 원본 출처와 정확한 위치
- 작성일·마지막 확인일·다음 검토일
- 상태: draft / verified / disputed / superseded / stale / rejected
- 신뢰도와 그 근거
- 관련 지식·의사결정·문제·작업 링크
- 대체·상충 관계
- 작성·검증·수정 주체
- 갱신 이력
- 검색·컨텍스트 포함 가능 여부

### 9.4 독립형 검색과 RAG

1. 원본 Markdown/JSON 등 프로젝트 파일이 정본이어야 하며 특정 LLM의 기억이나 대화 기록만으로 유지돼서는 안 된다.
2. 검색 인덱스는 로컬에서 결정적으로 다시 만들 수 있어야 하며 손실돼도 정본 파일에서 복구돼야 한다.
3. 알려진 고빈도 작업은 직접 라우팅하고, 미등록 질의에는 메타데이터·키워드·의미 검색을 단계적으로 사용해야 한다.
4. 벡터 검색은 원문 권위를 대체하지 않고 후보 검색에만 사용해야 한다.
5. 모든 검색 결과는 원문과 지식 ID를 포함해야 하며, 검증 상태·최신성·상충 항목을 함께 반환해야 한다.
6. 보호 경로는 수집·청킹·임베딩·메타데이터 생성 전에 차단해야 한다.
7. Obsidian, 벡터 엔진, 로컬 DB가 없어도 정본 파일은 읽고 유지할 수 있어야 한다.
8. 선택 도구의 실제 공개 실행점이 사용되는지 별도 검증해야 한다.

### 9.5 작업별 컨텍스트 구성

컨텍스트 패키지는 다음 요소만 포함해야 한다.

- 현재 작업 목표와 범위
- 항상 적용되는 최소 규칙
- 현재 상태와 첫 다음 행동
- 작업에 필요한 검증된 지식
- 관련 결정과 미해결 충돌
- 관련 실패·해결 사례
- 원문 출처 링크
- 제외한 후보와 제외 이유
- 컨텍스트 생성 시각, 검색 질의, 인덱스 버전

패키지는 캐시일 뿐 정본이 아니며, 같은 입력·인덱스 버전에서는 재현 가능한 결과를 내야 한다.

### 9.6 검토·갱신·폐기

1. 지식은 검토 예정일 또는 원본 변경 시 재검증 대상으로 표시해야 한다.
2. 새 지식이 기존 항목과 충돌하면 조용히 덮어쓰지 말고 `disputed` 또는 `superseded` 관계를 만들어야 한다.
3. 오래된 항목은 검색에서 숨기기 전에 이유와 대체 항목을 기록해야 한다.
4. 결정을 바꿀 때는 새 결정과 근거를 추가하고 이전 결정의 상태를 변경해야 한다.
5. 인덱스 갱신 실패는 이전 검증 인덱스를 보존하고 부분 결과를 활성화하지 않아야 한다.

### 9.7 최소 검증 기준

명령 4 완료 전 최소한 다음 시나리오가 통과해야 한다.

1. 하나의 원본 작업 기록에서 지식을 추출하고 원문으로 역추적할 수 있다.
2. 사실·추론·결정이 서로 다른 상태와 필드로 저장된다.
3. 서로 충돌하는 두 지식이 하나로 은폐되지 않고 함께 반환된다.
4. 폐기된 지식보다 검증된 최신 지식이 우선되며 그 이유가 설명된다.
5. 알려진 작업은 검색 없이 직접 정본을 선택한다.
6. 자연어 작업 질의는 필요한 지식만 담은 컨텍스트 패키지를 만들고 관련 없는 문서를 포함하지 않는다.
7. 각 검색 결과와 컨텍스트 항목이 실제 출처 파일·항목으로 연결된다.
8. 인덱스를 삭제한 상태에서도 정본에서 동일 구조로 재구축할 수 있다.
9. 보호 대상 경로가 인벤토리·청크·인덱스·로그·오류 메시지에 나타나지 않는다.
10. 새 세션이 LLM 기억 없이 프로젝트 파일과 인덱스만으로 현재 작업을 재개한다.

## 10. 과도한 구축을 막기 위한 제약

명령 2 설계는 다음 제약을 기본값으로 삼아야 한다.

- 실제 실패가 없는 동시성 플랫폼, 이벤트 소싱, 분산 서비스, 서버형 지식 그래프는 만들지 않는다.
- 먼저 Markdown/구조화 파일과 재구축 가능한 단일 로컬 인덱스로 해결한다.
- 벡터 검색은 동일 말뭉치의 직접·키워드 검색보다 정확도 또는 총 컨텍스트 비용이 개선될 때만 활성화한다.
- 도구 채택 전 같은 질의·같은 말뭉치·같은 전체 payload로 비교한다.
- 실제 대표 작업으로 검색 정확도, 재개 시간, 기록 비용, 갱신 비용을 측정한다.
- 한 단계는 독립적으로 유용해야 하며 사용자 승인 전 다음 단계로 넘어가지 않는다.
- 문서 수나 메타데이터 필드를 늘리는 것 자체를 지식 축적으로 간주하지 않는다.

## 11. 위험과 레드팀 관점

1. **백업 복원 편향**: 최신처럼 보이는 스냅샷을 그대로 복원하면 과거 ‘완료’ 상태와 현재 활성 상태가 섞인다.
2. **메타데이터 과잉**: 모든 문서에 많은 필드를 강제하면 기록이 실제 작업보다 비싸진다. 지식 항목과 일반 문서의 필드를 구분해야 한다.
3. **검색 만능주의**: 벡터·그래프가 권위·최신성·충돌을 자동 판정한다고 가정하면 Graphify 실패를 반복한다.
4. **요약 손실**: 세션 요약만 남기고 원본 로그를 버리면 이후 지식의 근거를 복구할 수 없다.
5. **지식 오염**: 추론을 사실로 승격하거나 실패 보고서를 현재 정본으로 검색하면 잘못된 컨텍스트가 재사용된다.
6. **보호 경로 유출**: 파일을 먼저 읽고 나중에 필터링하는 색인기는 과거 Stage 00 위반을 반복한다.
7. **도구 종속**: Obsidian GUI나 특정 모델이 꺼지면 검색·재개가 멈추는 설계는 독립형 지식 시스템이 아니다.
8. **검증 착시**: 테스트 통과만으로 실제 미디어·앱·사용자 품질을 주장하면 첫 재구축의 한계를 반복한다.

## 12. 명령 1 최종 판정

`F` 기존 프로젝트에는 재사용 가치가 높은 영상 제작 지식, 파일·검증 불변조건, 도구 행동 계약, 실패 사례가 충분히 축적돼 있다. 반면 이 지식은 세 스냅샷과 긴 보고서에 흩어져 있고, 현재 활성 정본·원본 작업 원장·지식 항목·관계·RAG·컨텍스트 패키지로 연결돼 있지 않다.

`R` 새 프로젝트의 출발점은 다음이어야 한다.

1. 가장 작은 공통 규칙과 데이터 경계를 먼저 복구한다.
2. 원본 기록·세션 요약·지식·결정·실패 사례를 분리한다.
3. 기존 자료에서 검증된 지식만 출처와 함께 새 정본으로 이관한다.
4. 직접 라우팅과 로컬 재구축 가능 검색을 결합한다.
5. 실제 대표 질의와 대표 작업으로 검색 정확도와 생산성 개선을 검증한다.
6. Obsidian과 벡터·그래프 도구는 핵심 파일 구조 위의 선택 계층으로만 평가한다.

명령 1 범위에서는 구현하지 않았다. 다음 단계는 이 보고서의 승인 또는 수정 후, 최신 공식 자료를 조사해 최소 구축안과 확장안을 비교하는 명령 2 설계다.
