# Obsidian 도입 타당성 분석 보고서

- 사용 목적: 현재 프로젝트의 문서 구조 문제를 Obsidian이 실제로 완화할 수 있는지 판단하고, 도입 범위와 이전 원칙을 결정하기 위한 근거를 제공한다.
- 사용 범위: 문서 탐색, 링크, 메타데이터, 에이전트·사용자 문서 관리, 이전 비용과 위험을 분석한다. Obsidian 설치나 기존 문서 이동·분할은 포함하지 않는다.
- 독자·언어: 사용자, 한글.
- 읽는 시점: Obsidian 시험 도입 또는 문서 노드 구조 개선을 승인하기 전.
- 수정하는 시점: 인용한 사실이나 현재 프로젝트 수치의 명백한 오류를 바로잡을 때만 수정한다. 새로운 판단은 새 보고서로 남긴다.
- 정본 여부: 2026-07-19 시점의 분석 근거다. 전역 규칙은 `PROJECT_RULES.md`, 현재 상태는 `SESSION_HANDOFF.md`, 문서 분류는 `docs/agent/DOCUMENT_REGISTRY.md`가 정본이다.
- 상태: analysis / recommendation. 도입 승인이나 구현 완료를 의미하지 않는다.
- 작성일: 2026-07-19.

## 1. 결론

**최종 판단은 `조건부 도입 권장`이다.** 다만 권장하는 것은 Obsidian으로 문서 체계를
교체하는 전면 이전이 아니라, 현재 Markdown 저장소 위에 Obsidian을 사용자용 탐색·검토
인터페이스로 얹는 제한된 시험 도입이다.

Obsidian은 다음 문제에는 효과가 크다.

- 사용자에게 폴더 탐색, 백링크, 속성 표, 검색, 관계 그래프를 제공한다.
- 기존 Markdown 파일을 복제하거나 별도 데이터베이스로 변환하지 않고 그대로 볼 수 있다.
- YAML 속성과 Bases를 사용하면 문서 상태·독자·정본 여부를 표로 확인할 수 있다.
- 공식 CLI로 미해결 링크, 고립 문서, 백링크 등을 점검할 수 있다.

반면 다음 핵심 문제는 Obsidian만으로 해결되지 않는다.

- 에이전트가 작업별 최소 문서만 읽도록 강제하는 컨텍스트 라우팅
- 의미가 비슷한 규칙의 중복 판정과 단일 정본 보장
- 노드 의존성 순환, 컨텍스트 예산, 승인 게이트의 검증
- 에이전트 문서와 사용자 문서 사이의 파생 관계 통제

따라서 Obsidian은 **문서 아키텍처를 대신하는 시스템이 아니라, 잘 설계된 문서 노드 구조를
사람이 확인하기 쉽게 만드는 클라이언트**로 사용해야 한다. 기존 문서 노드 개선안은 여전히
필요하며, Obsidian 도입은 그 L3 개선 위에 얹는 보조 계층으로 처리하는 것이 맞다.

## 2. 조사 기준과 근거

판단 기준은 제품 홍보 문구가 아니라 현재 프로젝트의 실제 병목을 얼마나 줄이는지로 정했다.

- 현재 프로젝트 근거: `docs/reports/2026-07-19_문서_노드_구조_개선_분석.md`
- 제품 동작: Obsidian 공식 도움말과 가격 문서
- 실제 운영 사례: Obsidian 공식 도움말 저장소, Obsidian Community Hub 공개 저장소
- 에이전트 연동 사례: 공식 CLI·Headless 문서와 공개 MCP 연동 저장소

공식 문서에 따르면 Obsidian 볼트는 로컬 폴더이고, 노트는 일반 Markdown 파일이다. 다른
편집기가 파일을 수정해도 Obsidian이 변경을 반영한다. 다만 `.obsidian` 설정 폴더와 별도
메타데이터 캐시를 만들며, 캐시는 실제 파일과 어긋날 수 있다.
([데이터 저장 방식](https://obsidian.md/help/data-storage))

## 3. 현재 문서 구조의 문제점

### 3.1 에이전트 시작 컨텍스트가 크다

기존 분석에서 항상 읽는 세 문서의 추정 비용은 약 4,242토큰이고, L5 핵심 경로는 계획 절과
사용자 데이터를 제외하고도 약 11,456토큰이다. `REBUILD_PLAN.md`,
`FILE_DATA_CONTRACT.md`, `EDITING_QUALITY_RULES.md`, `WORKFLOW_FOUNDATION.md`는 서로
다른 소비자의 내용을 한 파일에 함께 담고 있다.

문서 내부의 특정 절만 읽으라는 규칙은 읽기 도구가 전체 파일을 불러올 때 무력해질 수 있다.
이 문제는 Obsidian의 그래프나 검색이 아니라 물리적 파일 분리와 기계 라우팅으로 해결해야 한다.

### 3.2 같은 개념이 여러 문서에 의미상 반복된다

원본 식별, 버전 생명주기, 사용자 승인, 검증 단계가 여러 정본 후보에 반복된다. Obsidian의
백링크와 미연결 언급은 같은 단어의 출현은 보여주지만, 두 문장이 같은 규칙인지 또는 어느 쪽이
정본인지 판정하지 않는다. 의미 중복 제거에는 여전히 명시적 정본 모델과 검증기가 필요하다.

### 3.3 문서 본문 메타데이터와 등록부를 이중 관리한다

각 문서 상단의 목적·범위·읽기 조건과 `DOCUMENT_REGISTRY.md`의 역할·상태·읽기 조건이
겹친다. Obsidian Properties는 YAML frontmatter를 사람이 편집하고 Bases에서 조회하게 해
이중 쓰기를 줄일 수 있다. 그러나 등록부를 계속 수동 편집하면 Obsidian을 추가해도 쓰기 지점만
하나 더 생긴다.

### 3.4 사용자에게는 현재 구조가 탐색 친화적이지 않다

문서는 에이전트 라우팅 기준으로 분류돼 있으나 사용자가 다음을 한 화면에서 보기 어렵다.

- 현재 승인 대기 항목
- 활성 정본과 역사 보고서의 차이
- 한 문서가 어떤 문서에 의존하고 어디에서 소비되는지
- 검증 수준과 마지막 사용자 승인 여부

이 부분이 Obsidian 도입의 가장 분명한 효익이다.

### 3.5 Git 상태와 문서 상태가 서로 다른 계층이다

현재 프로젝트는 동적 Git 상태를 문서에 복제하지 않는 원칙을 갖고 있다. Obsidian 속성에
수정 시각, 브랜치, dirty 상태를 다시 기록하면 금방 낡는다. Obsidian 메타데이터에는 문서의
의미 상태만 두고 동적 저장소 상태는 Git에서 조회해야 한다.

## 4. Obsidian 도입 시 개선되는 부분과 한계

| 현재 문제 | 개선 효과 | 남는 한계 | 판단 |
|---|---|---|---|
| 사용자가 문서 관계를 찾기 어려움 | 백링크, 나가는 링크, 검색, 로컬 그래프로 탐색 가능 | 링크가 없는 의미 관계는 나타나지 않음 | 크게 개선 |
| 활성·역사·정본 상태를 한눈에 보기 어려움 | YAML Properties와 Bases 표·필터로 상태 표시 가능 | 속성 스키마와 값 검증은 별도 필요 | 크게 개선 |
| 문서 이동 후 링크 갱신 | 앱 안에서 이동하면 내부 링크 자동 갱신 가능 | 에이전트·Git·외부 도구가 이동하면 같은 보장 없음 | 일부 개선 |
| 등록부와 문서 메타데이터 이중 쓰기 | frontmatter에서 등록부·뷰를 생성하면 단일 입력 가능 | 생성기 없이 수동 등록부를 유지하면 개선 없음 | 설계에 따라 개선 |
| 작업별 최소 컨텍스트 | CLI 검색·링크 조회는 후보 탐색에 도움 | 읽기 경로와 예산을 강제하지 않음 | 직접 해결 못 함 |
| 의미 중복과 정본 충돌 | 미연결 언급과 백링크가 조사 단서 제공 | 의미 동일성·권한 충돌을 판정하지 않음 | 직접 해결 못 함 |
| 순환 의존성·고립 노드 | 공식 CLI가 미해결 링크·고립·막다른 문서를 조회 가능 | 의존성 타입, 순환, 컨텍스트 예산은 별도 검사 필요 | 일부 개선 |
| 에이전트 자동화 | 일반 파일 I/O, 공식 CLI, Headless, MCP 방식이 가능 | 현재 에이전트는 이미 파일 접근 가능하며 추가 통합은 권한·운영 복잡도 증가 | 기본 도입에는 불필요 |

Obsidian은 Wikilink와 표준 Markdown 링크를 모두 지원하며, 상호운용성이 중요하면 Wikilink
생성을 끄라고 공식 문서가 안내한다. 블록 참조는 Obsidian 전용 문법이므로 다른 도구에서
작동하지 않는다. 이 프로젝트에서는 표준 Markdown 링크만 쓰고 블록 참조는 피해야 한다.
([내부 링크 형식](https://obsidian.md/help/links))

Properties는 YAML에 저장되고 텍스트·목록·날짜·숫자 등을 지원하지만 중첩 속성과 앱 내 대량
편집은 지원하지 않는다. 따라서 메타데이터는 평평한 열거형 필드로 제한하고, 일괄 변경은 검증된
스크립트로 해야 한다. ([Properties](https://obsidian.md/help/properties))

Bases는 Markdown 속성을 표·목록·카드로 조회하는 공식 코어 플러그인이다. 원본 데이터는
Markdown에 남지만 뷰 정의는 `.base` 파일 또는 Obsidian용 코드 블록으로 저장된다. Bases는
사용자 대시보드에는 적합하지만 에이전트 라우팅의 정본으로 삼으면 안 된다.
([Bases](https://obsidian.md/help/bases))

## 5. 에이전트 문서와 사용자 확인용 문서의 관리 방법

### 5.1 공통 원칙

1. 파일은 하나만 두고 Obsidian은 그 파일을 보는 인터페이스로만 사용한다.
2. 정본·파생·근거 문서 구분은 YAML 메타데이터와 프로젝트 검증기가 통제한다.
3. Obsidian 그래프와 Bases는 파생 뷰이며 실행 정본이 아니다.
4. 에이전트 라우팅은 안정적인 `node_id`와 `requires`를 사용한다.
5. 사용자용 요약은 정본을 복제하지 않고 현재 상태와 정본 링크만 제공한다.

### 5.2 에이전트 작업 문서

- 위치와 언어: `docs/agent/`, 영어.
- 역할: 정책, 계약, 계획, 요구사항 등 실행 정본.
- 읽기: `AGENTS.md`가 작업을 말단 노드로 라우팅하고 에이전트는 `requires` 폐쇄 집합만 읽는다.
- 쓰기: 각 노드의 `write_when`에 해당할 때만 수정한다.
- 보기: 사용자는 Bases의 `Agent Documents` 뷰에서 종류, 생명주기, 정본 여부, 검증 수준,
  컨텍스트 예산을 확인한다.
- 금지: 그래프에서 잘 보이게 하려고 불필요한 링크·태그를 추가하거나, 읽기 편의를 위해 같은
  규칙을 여러 문서에 복제하지 않는다.

### 5.3 사용자 확인용 문서

- 위치와 언어: `docs/user/`, 한글.
- 시작점: `HOME.md`를 사용자용 탐색 화면으로 두고 `PROJECT_STATUS.md`, 승인 대기 항목,
  최신 보고서, 주요 정본 링크를 연결한다.
- 역할: 현재 상태의 파생 요약, 승인 요청, 검토 화면.
- 보기: Bases의 `User Review` 뷰에서 `lifecycle=active`, `audience=user`,
  `needs_user_decision=true` 조건을 우선 표시한다.
- 금지: `SESSION_HANDOFF.md`와 별도의 현재 상태 정본을 만들지 않는다. 사용자 문서에는
  필요한 판단과 링크만 남긴다.

### 5.4 역사 보고서

- 위치: `docs/reports/`.
- 속성: `kind=report`, `lifecycle=historical`, `authority=evidence`.
- 기본 뷰: 사용자 홈에서는 최신 관련 보고서만 보여주고, 에이전트 실행 라우트에서는 제외한다.
- 새 판단은 기존 보고서를 고치기보다 날짜가 있는 새 보고서로 남긴다.

## 6. 권장 폴더·링크·메타데이터 구조

### 6.1 볼트 범위

**저장소 루트를 하나의 볼트로 여는 방식을 권장한다.** 그래야 루트의 `AGENTS.md`,
`PROJECT_RULES.md`, `SESSION_HANDOFF.md`와 `docs/` 문서가 같은 링크 그래프에 들어간다.

다만 `inputs/`, `outputs/`, `backup/`, `.git/`, `.agents/`, `.codex/`, `tools/`,
`tests/`는 Obsidian의 제외 패턴에 넣어야 한다. 공식 설정의 제외 기능은 Search, Graph,
Unlinked Mentions에서 숨기는 UI 필터다. **접근 통제나 보안 경계가 아니므로** 커뮤니티 플러그인에
민감한 볼트 접근 권한을 줘서는 안 된다. ([제외 파일 설정](https://obsidian.md/help/settings))

### 6.2 목표 폴더

```text
AGENTS.md
PROJECT_RULES.md
SESSION_HANDOFF.md

docs/
├─ agent/
│  ├─ node_registry.json          # frontmatter에서 생성되는 기계 등록부
│  ├─ rebuild/
│  │  ├─ PLAN.md
│  │  ├─ PRINCIPLES.md
│  │  ├─ RECONSTRUCTION_MAP.md
│  │  └─ layers/
│  ├─ state/
│  ├─ workflow/
│  ├─ quality/
│  └─ capabilities/
├─ user/
│  ├─ HOME.md                     # 파생 사용자 탐색 화면
│  ├─ PROJECT_STATUS.md
│  └─ decisions/
├─ views/
│  ├─ agent_documents.base        # 파생 뷰
│  ├─ user_review.base            # 파생 뷰
│  └─ migration_audit.base        # 파생 뷰
└─ reports/

.obsidian/                         # 볼트 설정; 안정 파일만 선별 관리
```

이 구조는 기존 문서 노드 분석안과 같다. Obsidian 때문에 별도 문서 트리를 추가하지 않고,
기존 노드 구조에 사용자용 뷰만 보탠다.

### 6.3 링크 규칙

- `Use [[Wikilinks]]`를 끄고 저장소 상대경로의 표준 Markdown 링크를 사용한다.
- 정본 링크는 가능한 한 파일과 안정적인 제목 앵커를 함께 적는다.
- 노드 의존성은 본문 설명이 아니라 `requires`의 안정적 `node_id`로 검증한다.
- 관련 참고는 본문의 `Related` 절에 링크하되 `normative`, `derived-from`, `evidence`,
  `supersedes` 관계를 명시한다.
- `![[embed]]`, 블록 ID, Canvas를 정본 문서에 사용하지 않는다.
- 파일 이동은 Obsidian의 자동 링크 수정만 믿지 않고 등록부 생성·링크 검사·회귀 테스트를 함께
  실행하는 승인된 이전 작업으로 수행한다.

### 6.4 권장 메타데이터

```yaml
---
node_id: doc.rules
kind: policy
lifecycle: active
authority: normative
audience: agent
language: en
requires: []
provides:
  - project_global_rules
read_when:
  - every_workspace_task
write_when:
  - approved_project_rule_change
validation: tool_validated
context_budget: 1200
---
```

필드는 평평한 열거형과 목록으로 유지한다.

| 필드 | 용도 | 규칙 |
|---|---|---|
| `node_id` | 경로와 독립적인 안정 ID | 전체 저장소에서 유일 |
| `kind` | policy, state, plan, report 등 | 등록된 열거형만 사용 |
| `lifecycle` | active, historical, superseded 등 | 실행 가능성과 분리 |
| `authority` | normative, derived, evidence 등 | 단일 정본 검사에 사용 |
| `audience` | agent, user, both | 폴더와 일치 검사 |
| `language` | en, ko | 프로젝트 언어 규칙 검사 |
| `requires` | 먼저 읽어야 할 노드 ID | 존재·순환·예산 검사 |
| `provides` | 소비자에게 제공하는 개념 ID | 의미 중복 후보 검사 |
| `read_when` | 라우팅 조건 ID | 자유 문장 대신 열거형 |
| `write_when` | 변경 허용 조건 ID | 자유 문장 대신 열거형 |
| `validation` | 검증 수준 | generated와 user_validated 구분 |
| `context_budget` | 문서별 최대 토큰 예산 | 자동 검사 대상 |

경로, 파일 수정 시각, 현재 브랜치, dirty 상태는 파일 시스템과 Git에서 계산할 수 있으므로
frontmatter에 기록하지 않는다. `aliases`와 `tags`는 사용자 검색 보조에만 쓰고 정본·상태 판정에
사용하지 않는다.

## 7. 기존 문서의 이전 방법

현재 파일이 이미 Markdown이므로 형식 변환은 거의 필요 없다. 공식 도움말도 Markdown 파일을
볼트 폴더에 두는 것만으로 가져올 수 있다고 안내한다.
([Markdown 가져오기](https://obsidian.md/help/import/markdown))

권장 이전은 다음 여섯 단계다.

### 단계 1. 무이동 시험 도입

- 사용자 승인 후 Obsidian을 설치한다.
- 저장소 루트를 볼트로 열되 파일을 이동하지 않는다.
- Restricted Mode를 유지하고 커뮤니티 플러그인을 설치하지 않는다.
- Wikilink 생성을 끄고, 삭제 확인과 내부 링크 자동 갱신 여부를 명시적으로 설정한다.
- 제외 폴더를 지정한다.

이 단계는 기존 Markdown을 건드리지 않으므로 가장 쉽게 철회할 수 있다.

### 단계 2. 메타데이터 계약 확정

- 위 frontmatter 스키마와 열거형을 JSON Schema 또는 동등한 검사기로 고정한다.
- 루트 문서 3개, 에이전트 문서 1개, 사용자 문서 1개에만 시범 적용한다.
- 기존 상단 역할 설명과 frontmatter의 중복을 제거할 기준을 결정한다.

### 단계 3. 등록부 생성 전환

- 모든 활성 문서에서 `node_registry.json`과 사람이 읽는 등록표를 생성한다.
- 기존 `DOCUMENT_REGISTRY.md`를 정본으로 유지한 상태에서 생성 결과를 비교한다.
- 경로·분류·관계가 모두 일치한 뒤에만 frontmatter를 입력 정본으로 승격한다.

### 단계 4. 노드 분할과 이동

- 기존 보고서의 섹션별 목적지를 먼저 매핑한다.
- 한 번에 한 문서군만 분할하고 이전 경로의 모든 내용을 대응시킨다.
- 루트 문서 축소, 재구축 계획·상태 계약, 워크플로우·품질, 도구·스킬 순으로 진행한다.
- 일괄 재작성이나 원본 삭제를 사용하지 않는다.

### 단계 5. 사용자 뷰 추가

- `HOME.md`와 공식 Bases 뷰를 만든다.
- 사용자 화면에는 활성 상태, 승인 대기, 최신 보고서, 검증 수준만 보여준다.
- Bases 파일은 파생 뷰로 등록하고 실행 라우트에서 제외한다.

### 단계 6. 검증과 철회 판단

- 미해결 링크, 고립 문서, 막다른 링크, 순환 `requires`, 중복 `node_id`, 복수 정본,
  컨텍스트 예산을 검사한다.
- Git diff와 기존 33개 문서·라우팅·상태 테스트를 실행한다.
- Obsidian 앱에서 링크 이동, Bases 필터, 한글 표시, 파일명 변경 후 링크 갱신을 확인한다.
- 시험 도입 전후의 작업별 문서 토큰과 사용자 탐색 시간을 비교한다.

## 8. 실제 활용 사례에서 얻을 수 있는 교훈

### 8.1 Obsidian 공식 도움말 저장소

Obsidian 도움말 자체는 언어별 폴더를 독립 볼트로 열고 GitHub PR로 수정하며, `main` 커밋을
자동 게시한다. 영어를 정본으로 두고 각 언어에서 같은 `permalink`를 안정 ID로 공유한다.
([obsidianmd/obsidian-help](https://github.com/obsidianmd/obsidian-help))

이 사례는 Obsidian 볼트와 Git 기반 문서 운영이 함께 가능함을 보여준다. 동시에 성공 원인이
그래프 화면이 아니라 **명시적 정본, 안정 ID, 결정적 스크립트, PR·게시 자동화**에 있음을 보여준다.

### 8.2 Obsidian Community Hub

Community Hub는 폴더, Markdown lint 설정, GitHub 편집 흐름을 가진 공개 실험 볼트이며
2,800회 이상의 커밋 이력이 보인다.
([obsidian-community/obsidian-hub](https://github.com/obsidian-community/obsidian-hub))

큰 연결형 볼트를 Git으로 공동 관리할 수 있다는 실사용 근거는 되지만, 저장소 스스로
`experimental vault`라고 밝힌다. 따라서 이 사례를 권한 체계나 장기 유지보수 품질의 증거로
확대 해석하면 안 된다.

### 8.3 에이전트 연동 사례

공개 `mcp-obsidian` 프로젝트는 검색·읽기·패치·추가·삭제 도구를 제공하지만 Local REST API
커뮤니티 플러그인, API 키, 상시 실행 앱이 필요하다.
([MarkusPfundstein/mcp-obsidian](https://github.com/MarkusPfundstein/mcp-obsidian))

이는 연동 수요가 실제로 있음을 보여주지만, 현재 프로젝트에는 이 방식이 불필요하다. 에이전트가
이미 작업공간 Markdown을 직접 읽고 쓸 수 있기 때문에 MCP를 추가하면 API 키·삭제 권한·플러그인
공급망이라는 새 위험만 생긴다.

공식 Obsidian CLI는 검색, 파일 읽기, properties, Bases, 미해결 링크, 고립 문서 조회를
지원하지만 데스크톱 앱이 실행 중이어야 한다. Headless는 에이전트 접근을 사용 사례로 들지만
현재 open beta이고 Node.js 22 이상과 Obsidian 서비스가 필요하다.
([CLI](https://obsidian.md/help/cli), [Headless](https://obsidian.md/help/headless))

따라서 1차 도입에서는 파일 시스템과 기존 테스트를 정본 도구로 유지하고, 공식 CLI는 앱 수준
검증 보조로만 사용하는 것이 적절하다.

## 9. 도입 비용

### 9.1 제품 비용

2026-07-19 공식 가격 기준으로 데스크톱 앱과 업무 사용은 무료이며 계정도 필수가 아니다.
Commercial은 선택 후원 라이선스다. Sync Standard는 연간 결제 시 사용자당 월 4달러,
월 결제 시 5달러이고, Publish는 연간 결제 시 사이트당 월 8달러, 월 결제 시 10달러다.
([공식 가격](https://obsidian.md/pricing))

이 프로젝트의 1차 시험에는 Sync, Publish, Commercial이 모두 필요하지 않으므로 **제품 직접
비용은 0달러**다. Git을 계속 버전 관리 수단으로 사용한다.

### 9.2 작업 비용 추정

다음은 현재 활성 문서 수와 기존 문서 크기를 바탕으로 한 프로젝트별 추정이며 공식 수치가 아니다.

| 작업 | 예상 투입 |
|---|---:|
| 앱 설정과 무이동 시험 | 2~4시간 |
| 메타데이터 스키마·생성기·검사 | 4~8시간 |
| 기존 활성 문서 메타데이터 이전 | 4~8시간 |
| 큰 문서의 노드 분할·링크·테스트 갱신 | 1~3작업일 |
| 사용자 HOME·Bases 뷰·앱 검증 | 2~4시간 |
| 시험 안정화 관찰 | 1~2주, 실제 수정 작업은 소량 |

Obsidian 자체보다 메타데이터 단일화와 노드 분할에 대부분의 비용이 든다. 이 비용은 Obsidian을
쓰지 않더라도 현재 에이전트 컨텍스트 문제를 해결하려면 필요한 비용이다.

## 10. 예상 위험과 대응

| 위험 | 영향 | 가능성 | 대응 |
|---|---|---|---|
| Obsidian을 구조 개선의 대체재로 오해 | 컨텍스트와 중복 문제 미해결 | 높음 | L3 노드 구조와 검증을 선행 조건으로 명시 |
| Wikilink·블록 참조·embed 종속 | 다른 에디터와 에이전트 도구 호환 저하 | 중간 | 표준 Markdown 링크만 사용 |
| 커뮤니티 플러그인 공급망 | 볼트 전체 읽기·쓰기, 외부 전송 가능 | 중간 | Restricted Mode 유지, 1차 플러그인 0개 |
| `.obsidian` 설정 노이즈 | 잦은 Git 변경과 개인 레이아웃 충돌 | 높음 | `workspace.json` 계열 제외, 안정 설정만 선별 관리 |
| 동시 편집·Sync 충돌 | 중복 텍스트, 설정 덮어쓰기 | 중간 | 1차 Sync 미사용, Git 작업 중 앱 편집 규칙 정의 |
| 제외 폴더를 보안 경계로 오해 | 사용자 데이터가 플러그인에 노출 | 중간 | 제외는 UI 필터로만 취급, 플러그인 금지 |
| 속성 스키마 드리프트 | Bases와 에이전트 라우터 불일치 | 중간 | JSON Schema, 생성 등록부, CI 검사 |
| 앱 캐시와 실제 파일 불일치 | 그래프·링크 화면이 오래된 상태 표시 | 낮음~중간 | 파일과 테스트를 정본으로 유지, 필요 시 캐시 재구축 |
| Sync와 다른 동기화 서비스 병용 | 삭제·충돌·중복 동기화 | 중간 | 한 동기화 방식만 사용 |
| File Recovery를 백업으로 오해 | 장기 복구 실패 | 중간 | Git과 별도 백업 유지 |

Obsidian 공식 문서는 커뮤니티 플러그인을 제3자 코드로 보고 기본 Restricted Mode를 제공한다.
([플러그인 보안](https://obsidian.md/help/plugin-security)) 또한 Sync의 자동 병합이 중복 텍스트나
서식 문제를 만들 수 있고, Canvas 등 비Markdown 파일은 최근 수정본이 이전 변경을 덮을 수 있다고
안내한다. ([Sync 충돌 처리](https://obsidian.md/help/sync/troubleshoot))

공식 백업 문서도 Sync와 File Recovery가 완전한 백업이 아니라고 명시한다. Git 기록과 별도
백업 정책을 유지해야 한다. ([백업 지침](https://obsidian.md/help/backup))

## 11. 최종 권고와 도입 게이트

### 권고: 제한된 시험 도입은 승인할 가치가 있다

다음 조건으로만 `Go`를 권고한다.

1. Obsidian의 역할을 사용자 탐색·검토 인터페이스로 한정한다.
2. 기존 Markdown과 Git을 정본 저장 형식과 버전 관리로 유지한다.
3. 기존 문서 노드 개선을 계속하며 Obsidian이 이를 대체하지 않는다.
4. 표준 Markdown 링크와 공식 코어 기능만 사용한다.
5. 1차 시험에는 Sync, Publish, Headless, MCP, 커뮤니티 플러그인을 사용하지 않는다.
6. 설치·볼트 설정·파일 변경은 별도의 사용자 승인 후 수행한다.

### 전면 도입은 아직 `No-Go`다

다음 성공 기준을 충족하기 전에는 기존 문서 이동이나 등록부 권한 전환을 승인하지 않는 것이
좋다.

- 루트 시작 컨텍스트 약 2,000토큰 이하
- 일반 작업 문서 컨텍스트 약 3,000토큰 이하
- 모든 활성 문서에 유일한 `node_id`
- `requires` 순환과 미해결 의존성 0건
- 복수 정본 선언 0건
- 표준 Markdown 링크 오류 0건
- 사용자 HOME에서 현재 상태와 승인 대기 문서까지 2회 이내 이동
- 기존 문서·라우팅·상태 테스트 모두 통과
- Obsidian 앱에서 한글, 링크 이동, Bases 필터를 직접 확인

이 기준을 만족하면 Obsidian은 현재 프로젝트의 **사용자 확인 비용과 문서 관계 탐색 비용을
실질적으로 줄일 수 있다.** 그러나 에이전트 컨텍스트와 문서 거버넌스 문제의 해결 주체는 계속
노드 메타데이터, 물리적 문서 분리, 생성 등록부, 자동 검증이어야 한다.
