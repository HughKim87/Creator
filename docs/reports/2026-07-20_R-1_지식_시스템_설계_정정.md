## 2. 설계 정정 결과

`D` 기존의 “문서 지도 → 문서 전체 읽기 → 나중에 RAG 추가” 구조를 다음 구조로 교체한다.

```text
minimal boot kernel
  → structured task request
  → conditional rule selection
  → universal file catalog resolution
  → accepted decisions + verified knowledge + applicable cases
  → bounded read context + explicit write contract
  → work and validation
  → file hashes + relations + work event + knowledge candidates
  → deterministic next-session context
  → optional search projection only after the loop works
```

핵심 변경은 다섯 가지다.

1. `PROJECT_RULES.md`는 모든 세션에 필요한 최소 안전·권위 커널만 가진다.
2. 나머지 기존 규칙은 별도 rule pack에 원자 ID로 저장하고 작업 조건에 따라 선택한다.
3. 모든 프로젝트 관리 파일은 universal file catalog의 노드가 된다.
4. 같은 work context가 읽을 자료뿐 아니라 수정 가능 파일, 소유자, 쓰기 조건과 validator까지 제공한다.
5. 새 빈 구조가 아니라 현재 규칙·결정·지식·실패 사례·파일을 첫 corpus로 이관한다.

`D` “모든 파일을 컨텍스트에 포함”은 모든 파일 내용을 매번 LLM 입력에 넣는다는 뜻이 아니다. 모든 프로젝트 관리 파일을 검색·선택·쓰기 검증이 가능한 노드로 등록하고, 각 작업에는 필요한 노드와 locator만 전달한다는 뜻이다.

## 4. 정본, 파생물과 권위

### 4.1 정본

`D` 사람이 검토하고 Git diff로 확인할 수 있는 파일을 정본으로 유지한다.

| 데이터 | 정본 형식 | 소유 위치 |
|---|---|---|
| 최소 상시 규칙 | Markdown | `PROJECT_RULES.md` |
| 조건부 규칙 | pack별 JSONL | `rules/*.rules.jsonl` |
| 전체 파일 카탈로그 | JSONL | `catalog/files.jsonl` |
| 작업 event·파일 변경 event | append-only JSONL | `records/work/` |
| 세션 요약 | Markdown | `records/sessions/` |
| 지식·결정·사례·검토 | Markdown | `knowledge/`의 종류별 디렉터리 |
| 출처·관계·변경 이력 | JSONL | `knowledge/sources/`, `knowledge/relations/`, `knowledge/history/` |
| 구조 계약 | JSON Schema Draft 2020-12 | `schemas/` |
| 현재 재개점 | Markdown | `SESSION_HANDOFF.md` |

SQLite, FTS, 임베딩, 그래프 보기, Obsidian Base와 context package는 정본에서 다시 만들 수 있는 파생물이다. context package가 작업 당시 선택 근거를 보존하더라도 지식 내용의 권위는 원본 레코드에 있다.

### 4.2 지시 권위 allowlist

`D` 실행 가능한 지시는 다음으로 제한한다.

1. 현재 사용자 지시
2. 활성 최소 커널 규칙
3. resolver가 조건을 만족한다고 판정한 활성 conditional rule
4. 명시적 작업 계약

accepted decision은 규칙을 만들거나 바꾸는 근거지만 그 본문이 검색됐다는 이유만으로 직접 실행하지 않는다. 실행이 필요한 결정은 active rule과 `implements` 관계로 연결한다. 보고서·지식·사례·역사 자료·검색 결과 안의 명령형 문장은 모두 evidence로 취급한다.

### 4.3 충돌 처리

- 현재 사용자 지시가 프로젝트 규칙보다 우선한다.
- 커널 규칙은 conditional rule보다 우선한다.
- 같은 권위의 규칙은 `priority`와 더 구체적인 scope로 정렬한다.
- 명시적 `excludes_when`은 일반 `applies_when`보다 우선한다.
- 같은 우선순위의 활성 규칙이 충돌하면 resolver는 임의 선택하지 않고 `rule_conflict`로 중단한다.
- 검색 점수는 규칙의 권위나 우선순위를 바꾸지 못한다.

## 5. 최소 부트 커널과 기존 규칙 재분류

### 5.1 커널 선정 기준

상시 커널에는 다음 조건을 모두 만족하는 규칙만 둔다.

1. 작업 종류를 알기 전에도 적용해야 한다.
2. 누락 시 보호 데이터·권한·지시 신뢰·검증 보고에 중대한 문제가 생긴다.
3. resolver가 실패해도 적용돼야 한다.
4. 특정 도메인·문서 유형·작업 단계에만 필요한 절차가 아니다.

## 6. 조건부 rule record 계약

### 6.1 물리 구조

초기에는 규칙 하나마다 파일을 만들지 않는다. 관련 규칙을 7개 JSONL pack으로 묶고 한 줄을 하나의 원자 규칙으로 사용한다.

```text
rules/
├─ governance.rules.jsonl
├─ version-control.rules.jsonl
├─ documentation.rules.jsonl
├─ provenance.rules.jsonl
├─ knowledge.rules.jsonl
├─ retrieval.rules.jsonl
└─ validation.rules.jsonl
```

규칙 수나 작업 영역이 실제로 커졌을 때만 pack을 분할한다. 물리적 pack은 관리 단위이고 stable rule ID가 선택·관계·검증 단위다.

rule record는 에이전트 실행 계약이므로 영어를 기본으로 쓰고, 역사 원문은 `source_refs`와 원문 언어 메타데이터로 보존한다.

### 6.2 필수 필드

```json
{
  "schema_version": "1.0.0",
  "rule_id": "rule.docs.user-language",
  "pack_id": "documentation",
  "text": "Write user-facing reports in Korean.",
  "authority": "project_rule",
  "priority": 500,
  "status": "active",
  "applies_when": {
    "any": [
      {"field": "output_audience", "op": "eq", "value": "user"},
      {"field": "target_kind", "op": "in", "value": ["report", "user_guide"]}
    ]
  },
  "excludes_when": [],
  "phases": ["plan", "write", "close"],
  "task_tags": ["documentation", "user-facing"],
  "source_refs": ["src.repo.project-rules#heading:Language and document boundaries"],
  "validators": ["validate.document-language"],
  "relations": []
}
```

조건은 자유문장만 저장하지 않고 `field/op/value`의 제한된 predicate로 표현한다. 초기 허용 필드는 `intent`, `actions`, `phase`, `target_paths`, `target_kinds`, `output_audience`, `scopes`, `task_tags`로 제한한다. 알 수 없는 필드·연산자는 규칙 미적용이 아니라 schema 오류로 처리한다.

### 6.3 rule lifecycle

```text
proposed → active → needs_review → superseded/revoked
```

- `active`만 기본 선택된다.
- 사용자 승인이 필요한 정책 변경은 `proposed`에서 멈춘다.
- 규칙 본문·조건·우선순위 변경은 새 revision과 history event를 만든다.
- 삭제 대신 superseding ID와 이유를 보존한다.
- 같은 규칙을 여러 pack에 복사하지 않는다.

## 7. universal file catalog

### 7.1 포함 범위

`D` catalog는 모든 **project-governed file**을 등록한다.

- Git 추적 파일
- 프로젝트가 의도적으로 생성·유지하는 비추적 정본과 파생 파일
- 규칙, 문서, 코드, 설정, 스키마, 테스트, 레코드, 인덱스 manifest, 보고서

다음은 개별 file node로 전역 열거하지 않는다.

- `.git/`, OS·도구 캐시, 가상환경과 임시 파일
- `backup/` 내부 파일: `backup/` 경계 node 하나와 이미 승인된 source locator만 유지
- 사용자가 지정하지 않은 `inputs/`, `outputs/`: 경계 node만 유지
- 보호 task 파일: 정확한 사용자 승인 범위의 별도 task namespace에서만 등록

따라서 “모든 파일”은 보호 규칙을 무시한 전체 디스크 스캔이 아니라, 프로젝트가 관리하는 모든 비보호 파일과 승인된 task 파일을 뜻한다.

### 7.2 file record 필수 필드

```json
{
  "schema_version": "1.0.0",
  "file_id": "file.docs.agent.workflow",
  "path": "docs/agent/WORKFLOW.md",
  "kind": "procedure",
  "purpose": "Common project work procedure",
  "owner": "project-agent",
  "authority": "procedure",
  "status": "active",
  "language": "en",
  "sensitivity": "project-global",
  "index_scope": "global",
  "read_when": [],
  "write_when": [],
  "task_tags": ["workflow", "validation", "handoff"],
  "consumes": [],
  "produces": [],
  "depends_on": ["file.project-rules"],
  "validators": ["validate.markdown", "validate.links"],
  "content_sha256": "...",
  "hash_policy": "content_sha256",
  "observed_at": "2026-07-20T00:00:00+09:00"
}
```

정식 관계는 relation record가 소유한다. `depends_on`, `consumes`, `produces`는 resolver가 자주 쓰는 file-specific edge이며 relation index로도 투영할 수 있지만 서로 다른 값을 중복 정본으로 유지하지 않는다.

### 7.3 lifecycle과 무결성

```text
planned → active → missing/needs_review → moved/deleted
```

- 새 파일은 write plan에서 `planned` node를 먼저 만든 뒤 파일 생성과 검증 성공 시 `active`가 된다.
- 이동은 새 경로·기존 file ID·이동 event로 처리한다.
- 삭제는 catalog 행을 제거하지 않고 `deleted` 상태, 마지막 hash와 삭제 event를 보존한다.
- 등록되지 않은 project-governed file은 `orphan` 검사 실패다.
- 활성 node의 파일이 없거나 hash가 다르면 기본 context에서 제외하고 `needs_review`로 보낸다.

### 7.4 자기참조 hash 예외

catalog가 자기 자신의 현재 hash를 내부에 저장하면 내용이 바뀔 때마다 다시 hash가 바뀌는 순환이 생긴다.

`D` 다음 예외를 명시한다.

- `catalog/files.jsonl`: `hash_policy=self_excluded`, 내부 `content_sha256=null`. resolver가 읽을 때 계산한 실제 hash를 context package와 완료 event에 기록한다.
- append-only event stream: `hash_policy=event_chain`. 각 event는 `previous_event_hash`와 자신의 canonical event hash를 가진다. catalog는 매 append마다 로그 파일 hash를 갱신하지 않는다.
- 그 밖의 일반 파일: `content_sha256` 필수.

이 예외는 검증 생략이 아니라 자기참조 없는 검증 방법의 차이다.

## 8. 공통 데이터 모델

### 8.1 레코드 종류와 소유 책임

| kind | 소유 내용 | 기본 상태 |
|---|---|---|
| `rule` | 실행 가능한 조건부 프로젝트 규칙 | `proposed`, `active`, `needs_review`, `superseded`, `revoked` |
| `file` | 프로젝트 파일의 읽기·쓰기·검증 계약 | `planned`, `active`, `needs_review`, `moved`, `deleted` |
| `source` | 파일·event·공식 URL과 locator·hash | `active`, `changed`, `unavailable`, `archived` |
| `knowledge` | 검증 가능한 사실·추론·절차·제약 | `candidate`, `reviewed`, `verified`, `needs_review`, `superseded`, `rejected` |
| `decision` | 선택지·근거·범위·승인 | `proposed`, `accepted`, `superseded`, `revoked` |
| `case` | 증상·원인·해결·회귀 검증 | `observed`, `confirmed`, `resolved`, `recurring`, `retired` |
| `relation` | 두 ID 사이의 방향·타입·근거 | `candidate`, `active`, `invalidated` |
| `work_event` | 요청·읽기·쓰기·검증·실패의 시간순 원본 | append-only |
| `session_summary` | 종료 세션의 불변 요약 | immutable revision |
| `review` | 변경·충돌·오래됨에 대한 검토 결과 | `open`, `resolved` |
| `context_request` | 작업 의도·범위·단계·예산 | immutable request |
| `context_package` | 선택된 읽기 항목과 쓰기 계약 | derived |

### 8.2 공통 원칙

- ID는 생성 후 바꾸지 않는다.
- 저장소 경로는 상대 POSIX 경로를 쓴다.
- 모든 사실은 source ID와 stable locator를 가진다.
- 추론은 지원 사실 ID와 공개 가능한 근거 요약을 가진다.
- 결정은 선택지, 채택 이유, 범위, 승인자와 대체 관계를 가진다.
- 관계는 별도 record가 정본이며 각 문서의 `related_ids`는 생성 가능한 편의 필드로만 취급한다.
- 상태와 confidence는 분리한다. 높은 confidence가 `verified`나 `accepted`를 대신하지 않는다.
- 현재 revision은 사람이 읽는 파일에 있고 모든 변경은 append-only history에 연결된다.

### 8.3 최소 관계 유형

초기 allowlist는 다음으로 제한한다.

- 출처: `derived_from`, `supported_by`, `contradicted_by`
- 권위·구현: `implements`, `governed_by`, `validated_by`
- 시간·대체: `supersedes`, `invalidates`, `moved_from`, `deleted_by`
- 작업 흐름: `consumes`, `produces`, `changed_by`, `selected_for`
- 문제 해결: `caused_by`, `resolved_by`, `prevents`, `failed_in`
- 구조: `part_of`, `depends_on`, `related_to`

self relation, dangling ID, 허용되지 않은 type와 `supersedes` cycle은 거부한다. 자동 관계 추출은 `candidate`만 만들 수 있다.

## 9. task request와 work context 계약

### 9.1 context request

```json
{
  "schema_version": "1.0.0",
  "task_id": "task.20260720.example",
  "requested_by": "user",
  "intent": "design",
  "actions": ["read", "analyze", "write_report"],
  "phase": "plan",
  "target_paths": [],
  "target_kinds": ["report", "technical_contract"],
  "output_audience": "user",
  "include_scopes": ["project-global"],
  "exclude_scopes": ["backup", "protected-user-data"],
  "task_tags": ["knowledge-system", "architecture"],
  "as_of": "2026-07-20T00:00:00+09:00",
  "max_chars": null
}
```

자연어 요청을 이 구조로 바꾸는 데 LLM을 사용할 수 있지만, 생성된 request는 실행 전에 schema와 보호 scope 규칙으로 검증한다. exact path가 필요한 보호 작업은 사용자 지정 값 없이는 request가 유효해지지 않는다.

### 9.2 work context package

기존 context package를 읽기 결과에서 **읽기 manifest + 쓰기 contract**로 확장한다.

```text
work_context
├─ request_hash and as_of
├─ authority
│  ├─ current user scope
│  ├─ kernel rule IDs
│  └─ selected conditional rule IDs + reasons
├─ read_manifest
│  ├─ file IDs, paths, locators, expected hashes
│  ├─ decision/knowledge/case IDs and revisions
│  ├─ source chain and selection path
│  └─ conflicts, stale items, exclusions, budget
└─ write_contract
   ├─ allowed operations and target file IDs
   ├─ expected before hashes
   ├─ owner and authority
   ├─ write_when rules
   ├─ validators and postconditions
   └─ required catalog, relation, event and handoff updates
```

package는 파생물이지만 `task_id`, request hash, catalog hash, rule revision과 선택 이유를 기록해 같은 입력에서 같은 선택을 재현할 수 있어야 한다.

## 10. resolver 설계

### 10.1 결정적 선택 순서

```text
1. root kernel load
2. task request schema validation
3. protected-path pre-access filter
4. exact target file and direct authority resolution
5. active conditional rule predicate evaluation
6. file owner/dependency/input/output expansion
7. accepted decision and verified knowledge selection
8. applicable confirmed/resolved case selection
9. active typed relation expansion, default 1-hop
10. conflict/stale/hash/orphan checks
11. category budget and deduplication
12. read manifest + write contract generation
```

R-2에서는 이 순서를 사람이 실행 가능한 fixture와 검증기로 먼저 확인하고, R-3에서 최소 resolver를 구현한다. FTS나 vector가 없어도 exact ID, predicate, path, tag와 relation만으로 동작해야 한다.

### 10.2 budget 우선순위

1. 사용자 요청과 금지 범위
2. 최소 커널
3. 선택된 conditional rule
4. exact target와 직접 권위 문서
5. 현재 상태와 accepted decision
6. verified knowledge
7. 관련 case와 보조 출처

규칙과 exact target은 검색 결과에 밀려 제거되지 않는다. `max_chars`가 없으면 구현이 임의의 큰 상수를 숨기지 않고, 평가에서 정한 프로젝트 기본값을 사용하거나 크기와 선택 결과를 명시한다.

### 10.3 실패 정책

- 규칙 충돌, 보호 scope 누락, owner 불명, before hash 불일치, dangling source가 있으면 쓰기 contract를 발급하지 않는다.
- 검색 또는 관계 확장이 실패해도 직접 지정 파일과 규칙만으로 안전하게 수행 가능한지 구분한다.
- 기능 제한을 숨긴 채 broad scan으로 우회하지 않는다.
- 실패 결과와 다음 조건을 work event 또는 현재 수동 보고에 남긴다.

## 11. writer 설계

### 11.1 입력 조건

writer는 유효한 work context의 write contract 없이는 프로젝트 파일을 변경하지 않는다. 사용자 직접 요청으로 새 파일을 만드는 경우에도 planned file node, owner, write rule, validator와 예상 postcondition을 먼저 만든다.

### 11.2 쓰기 순서

```text
1. write_started event
2. current before-hash recheck
3. target file change
4. target-specific validation
5. file catalog status/hash update
6. typed relation update
7. knowledge/decision/case/review candidate update
8. session summary and current handoff update when required
9. write_completed or write_failed event
10. derived context/index invalidation or refresh marker
```

R-3 초기 구현은 한 로컬 작성자와 낙관적 before-hash 검사를 전제로 한다. 여러 파일 변경을 완전한 데이터베이스 transaction처럼 과장하지 않는다.

### 11.3 실패와 복구

- validation 실패 시 완료 event를 쓰지 않고 `write_failed`와 실제 남은 파일 상태를 기록한다.
- 사용자 변경을 자동 rollback하거나 destructive restore하지 않는다.
- 부분 변경이 남으면 catalog와 handoff에 incomplete 상태와 첫 복구 행동을 기록한다.
- 파생 인덱스는 completed event만 반영한다.
- 재시도는 새 attempt ID를 사용하고 이전 실패 event를 덮어쓰지 않는다.

## 12. 기존 데이터 선이관

### 12.1 migration namespace

```text
historical_source
  → extracted_candidate
  → deduplicated
  → source_and_scope_reviewed
  → proposed_active_record
  → user/contract approval
  → active
```

역사 문서는 검색 evidence로 직접 활성화하지 않는다. 후보가 active가 되기 전에는 `instruction_authority=false`, `retrieval_scope=migration-review`를 강제한다.

### 12.2 첫 corpus 순서

1. R-2 실행 시점의 모든 비보호 project-governed file을 catalog에 등록한다.
2. 현재 29개 규칙을 11개 커널 후보와 7개 조건부 pack의 18개 레코드로 이관한다.
3. D-01~D-11을 legacy alias와 함께 독립 decision record로 만든다.
4. 기존 분석 §7의 재사용 지식·결정 후보를 knowledge/decision candidate로 추출한다.
5. 실행 결과 오판, 잘못된 기본값, 보호 경로 위반, Graphify, sandbox, Obsidian 상태 불일치를 case 후보로 만든다.
6. 현재 Markdown 링크에서 typed relation 후보를 추출하되 링크 의미를 자동 확정하지 않는다.
7. 이미 분석 보고서가 지정한 `backup/` locator만 최소로 열어 내용·hash를 검증한다.
8. 대표 작업 fixture에서 필요한 항목만 선택되는지 확인한 뒤 active 승격을 승인받는다.

### 12.3 deduplication

- 같은 주장이 여러 보고서에 있으면 가장 권위 있는 원출처 하나를 source chain의 끝으로 사용한다.
- 보고서는 claim이 발견·검증된 event source로 연결하고 원문과 동일한 권위를 갖는다고 보지 않는다.
- 중복 후보는 삭제하지 않고 `duplicates` 또는 `merged_into` 관계와 처리 결과를 남긴다.
- 현재 규칙과 역사 규칙이 충돌하면 둘 다 보존하되 역사 규칙은 활성화하지 않는다.

## 15. 최소안과 확장안

### 15.1 최소안

| 단계 | 결과 | 검색 기술 |
|---|---|---|
| R-1 | 본 정정 설계 | 없음 |
| R-2 | 규칙 pack, file catalog, 첫 corpus, schemas, validator, 수동 resolver fixture | exact path·ID·predicate만 |
| R-3 | 최소 resolver/writer, event·hash·relation 반영, context 재현 | exact·metadata·1-hop file relation |
| R-4 | 재구축 가능한 SQLite projection과 한국어 FTS 평가 | FTS5 후보 비교 |

### 15.2 확장안

- Obsidian: 사람이 검토 대기열과 관계를 자주 탐색할 때만.
- vector retrieval: FTS recall 실패가 고정 평가에서 반복되고 같은 예산에서 개선될 때만.
- graph DB: 3-hop 이상 질문과 관계 규모가 SQLite 1-hop으로 관리되지 않을 때만.
- 자동 외부 source watcher: 공식 URL 변경이 반복 병목이고 allowlist·검토 절차가 준비된 뒤에만.

어떤 확장도 정본 형식, file ID, record ID와 source chain을 바꾸지 않는 projection이어야 한다.

## 16. 평가 계약

### 16.1 R-2 수동 fixture

최소 여섯 작업을 고정한다.

1. 한국어 분석 보고서 작성: documentation·provenance·validation 규칙만 선택하고 영상 규칙은 제외.
2. 지식 schema 변경: governance·knowledge·validation과 관련 파일만 선택.
3. 기존 결정 검토: decision·source·conflict 관계만 선택.
4. 영상 XML 작업: 해당 도메인 규칙·도구·validator·사례만 선택하고 지식 시스템 설계 전체는 제외.
5. 새 파일 생성: planned file node, owner, write rule, validator와 catalog 반영을 요구.
6. 보호 task 파일 작업: 사용자가 지정한 exact scope만 별도 namespace로 선택하고 전역 catalog에 내용을 노출하지 않음.

### 16.2 필수 지표

- 예상 conditional rule 누락 0건
- 관련 없는 rule leakage 0건
- project-governed orphan file 0건
- owner·write rule·validator 없는 쓰기 대상 0건
- source locator 추적 성공률 100%
- protected scope 침범 0건
- 같은 request·catalog·rule revision에서 동일 선택 ID 집합
- hash mismatch, stale source, rule conflict의 fail-closed 성공
- 새 파일·이동·삭제 후 catalog lifecycle 일치
- 작업 완료 후 event·relation·candidate·handoff 반영 여부

### 16.3 검증 수준

- R-1: 설계 문서의 구조·근거·내부 일관성 검증
- R-2: schema·catalog·fixture의 구조 및 수동 선택 검증
- R-3: resolver/writer 자동 테스트와 세션 재현 검증
- R-4: 검색 품질·지연·재구축·한국어 tokenizer 비교

한 단계의 검증은 다음 단계나 사용자 내용 승인을 대신하지 않는다.

## 17. R-2 승인 범위

본 설계가 승인되면 다음 단계에서만 수행한다.

1. R-2 실행 시점의 비보호 project-governed file inventory를 생성한다.
2. `PROJECT_RULES.md`를 최소 커널로 축소하고 기존 18개 규칙을 7개 pack으로 이동한다.
3. file catalog와 종류별 schema·validator를 만든다.
4. D-01~D-17을 독립 decision candidate로 이관하고 승인 상태를 반영한다.
5. 기존 분석이 지정한 지식·실패 사례·source locator를 candidate로 이관한다.
6. 수동 resolver fixture 6개와 orphan·dangling·conflict·hash 검증을 수행한다.
7. agent contract와 `DOCUMENT_MAP.md`를 새 구조에 맞게 연결한다.
8. 결과를 한국어로 보고하고 R-3 승인 전 중단한다.

R-2에서 하지 않는다.

- 자동 resolver/writer 운영
- SQLite·FTS5·vector·graph DB
- Obsidian 설정
- 보호 사용자 데이터의 전역 등록
- `backup/` 전체 스캔·수정
- 영상 제작 기능 이식
- 외부 게시·commit·push

## 18. R-1 완료 기준과 검증

### 18.1 완료 기준

- 최소 커널과 조건부 규칙 경계가 29개 기존 규칙 전체에 대해 정의됐다.
- rule, file, source, knowledge, decision, case, relation, event, request와 package 책임이 분리됐다.
- 모든 project-governed file의 포함·제외·보호 경계가 정의됐다.
- resolver와 writer가 공유할 read/write manifest와 실패 정책이 정의됐다.
- 기존 corpus의 첫 이관 순서, 상태와 deduplication이 정의됐다.
- D-01~D-11 재판정과 D-12~D-17 신규 결정이 승인 후보로 제시됐다.
- 최소안·확장안·단계별 평가와 R-2 경계가 정의됐다.

### 18.2 사실·추론·결정 요약

#### 확인된 사실

- `F` 현재 기반에는 조건부 규칙, universal file catalog, 이관된 corpus와 resolver/writer가 없다.
- `F` 현재 29개 규칙, D-01~D-11, 기존 분석의 지식·사례와 유효한 링크가 이관 원료로 존재한다.
- `F` JSON Schema 2020-12, SQLite FTS5, 파일 기반 Obsidian과 W3C PROV의 공식 문서는 기존 기술 판단을 계속 뒷받침한다.

#### 추론

- `I` 모든 파일을 catalog에 등록하되 실제 내용은 작업별로 선택해야 사용자의 “전 파일 포함”과 “최소 컨텍스트” 요구를 동시에 만족한다.
- `I` rule pack과 stable ID를 병행하면 문장마다 파일을 만드는 과잉 원자화 없이 조건부 선택이 가능하다.
- `I` read manifest와 write contract가 분리되면 기존 읽기 편향이 반복되므로 하나의 work context로 묶어야 한다.

#### 승인 요청 결정

- `D` §13의 D-01~D-11 재판정과 D-12~D-17을 정정 설계로 채택한다.
- `D` 다음 단계는 §17의 R-2이며, 본 보고서에 대한 사용자 승인 후에만 시작한다.
- `D` R-3 resolver/writer와 R-4 검색 projection은 각각 별도 결과 보고와 승인을 요구한다.

### 18.3 이번 단계 변경 범위

이번 R-1에서는 이 설계 보고서와 현재 인수인계만 갱신했다. 실제 규칙·계약·구조는 변경하지 않았다. 보고서의 strict UTF-8, NUL 0건, 후행 공백 0행, fenced block 균형, 필수 메타데이터, JSON 예시 3개, 커널 11행, 조건부 규칙 18행, 기존 결정 11행과 신규 결정 6행 검증을 통과했다. 전체 비보호 활성 Markdown 15개의 로컬 링크 144개는 누락 0건이며, R-2 이후 경로는 생성되지 않았고 `backup/` 변경과 `git diff --check` 오류도 0건이다.
