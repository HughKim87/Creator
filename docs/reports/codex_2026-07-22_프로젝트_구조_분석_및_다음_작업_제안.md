### 7.2 충족하지 못한 범위

1. `F` **포괄적인 역사 지식 이관이 없다.** 명령 1은 잘못된 종료 코드, 잘못된 미디어 기본값, 보호 경계 위반, Graphify, sandbox, Obsidian, 상태 분산 등 여러 재사용 사례를 식별했지만 R-2B는 knowledge 4건과 case 1건만 대표 이관했다. 현재 case가 2건으로 늘었어도 전체 목록과 대응하지 않는다.
2. `F` **세션 요약이 포괄적이지 않다.** 현재 종료 세션 문서는 2026-07-20 R-1/R-1.1 세션 1건뿐이다. 이후 R-2A~R-5와 후속 작업은 work event와 보고서는 있지만 세션별 불변 요약으로 모두 남아 있지 않다.
3. `F` **원본 작업 기록의 시간 범위가 제한된다.** append-only event 원장은 R-2A bootstrap 이후의 구조화 작업 이벤트를 보존한다. 시스템 구축 이전의 모든 대화·작업 원문을 소급 보존한 원장은 아니며, 프로젝트 파일에 durable transcript ID가 없었던 한계도 기존 세션 기록에 명시돼 있다.
4. `F` **모든 레코드 종류의 lifecycle이 자동화되지 않았다.** `KNOWLEDGE_MAINTENANCE.md`와 R-5는 decision·case lifecycle writer, 자동 review scheduler/queue가 미구현이라고 명시한다.
5. `F` **검색 검증 범위가 작고 고정돼 있다.** R-4의 8질의와 R-5의 9시나리오는 현재 작은 코퍼스와 합성 인수 조건을 강하게 검증하지만, 기존 프로젝트 지식 전체나 이후 모든 실제 작업 질의의 정확도를 증명하지 않는다.
6. `F` **현재 사용자 안내가 갱신되지 않았다.** `README.md`와 `docs/user/GUIDE.md`는 writer·schema·context가 미구현이고 R-2A가 다음 단계라고 적어 현재 상태와 충돌한다.

`I` 이 여섯 항목은 단순한 선택적 확장이 아니다. 특히 역사 코퍼스·세션 범위와 레코드 lifecycle은 사용자가 말한 ‘모든 작업 경험과 지식이 계속 축적·연결·갱신’되는 최종 목표에 직접 연결된다.

## 8. R-5 완료 문구의 정확한 해석

`F` R-5는 승인 설계 §10.5의 9개 시나리오를 9/9로 통과했고, 구조·자동 검증 수준에서 ‘프로젝트 지식 시스템 구축 완료’라고 판정했다.

`D` 이 문구는 **최소 시스템의 기능 인수 완료**로는 유효하다. 다음 의미로 확대해서는 안 된다.

- 모든 과거 작업 원문과 세션이 이관됐다.
- 명령 1에서 식별한 모든 지식·실패·결정이 원자 레코드가 됐다.
- 이후 실제 작업의 검색 정확도가 포괄적으로 검증됐다.
- 모든 record kind의 생성·검토·대체가 자동화됐다.
- 사용자 안내와 현재 체크포인트가 항상 최신이다.

`D` 따라서 현재 상태는 ‘지식 시스템 기반 및 최소 폐루프 완료, 역사 코퍼스와 운영 내용 완전성 미완료’로 기록해야 한다.

## 9. 남은 필수 보완안

이번 명령은 분석만 수행한다. 아래 작업은 사용자가 승인할 때 단계별로 진행해야 한다.

### 9.1 1단계 — 코퍼스 커버리지 원장

- 명령 1 §5~§8, 모든 단계 보고서, 현재 세션·event·Git 증거의 재사용 지식 후보를 stable ID 목록으로 만든다.
- 각 후보를 `migrated`, `missing`, `rejected-with-reason`, `not-recoverable`, `deferred`로 판정한다.
- ‘모든 지식’의 완료 기준을 레코드 수가 아니라 후보 100%가 상태와 근거를 가진 것으로 정의한다.
- 결과를 한국어로 보고하고 다음 단계 승인을 기다린다.

### 9.2 2단계 — 누락 지식·세션·사례 이관

- 명령 1에서 식별한 미이관 문제·실패·해결·결정·재사용 지식을 source locator와 함께 원자화한다.
- R-2A 이후 완료 세션을 불변 요약으로 연결한다. 원문 대화를 복구할 수 없는 경우 추정하지 않고 `not-recoverable` 한계와 대체 증거를 기록한다.
- 기존 4개 knowledge와 2개 case를 중복 생성하지 않고 update/history로 연결한다.

### 9.3 3단계 — 운영 폐루프 보완

- decision·case·session lifecycle writer 또는 명시적 수동 절차를 승인된 범위에서 완성한다.
- review queue와 자동 scheduler는 실제 필요와 운영비를 비교해 선택한다. 필수는 ‘누락 없는 검토 가능성’이지 특정 도구가 아니다.
- `README.md`, `docs/user/GUIDE.md`, handoff를 동일 현재 상태로 갱신한다.

### 9.4 4단계 — 확대 검증

- 확대된 코퍼스에서 실제 대표 질의와 실패 질의를 고정한다.
- source trace, stale/conflict, protected leakage, precision/recall, context budget, cold start를 다시 측정한다.
- lexical baseline이 실패할 때만 FTS·vector·graph 도입을 별도 승인한다.

## 10. 현재 승인 경계

`D` 이번 재분석으로 누락 기능 구현, 백업 재조사, 보호 데이터 접근, 자동 scheduler 도입, README/GUIDE 수정, commit·push·배포·게시 권한이 생기지 않는다.

`D` 다음 승인 대상은 **9.1 코퍼스 커버리지 원장 작성** 하나다. 이 단계는 구현이나 이관을 시작하지 않고, 무엇이 이미 이관됐고 무엇이 빠졌는지를 전체 후보 기준으로 확정한다.
