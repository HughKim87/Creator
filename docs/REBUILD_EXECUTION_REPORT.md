# 기존 프로젝트 재구축 통합 실행 보고서

- 사용 목적: 사용자가 Codex·Claude의 첫 재구축 구현 후보와 교차검증 결과를 역사 자료로 확인하는 보고서다.
- 사용 범위: 2026-07-18 당시 첫 미디어 구현 제안만 다루며 현재 실행 지시나 승인 상태로 사용하지 않는다.
- 독자·언어: 사용자, 한글.
- 읽는 시점: 사용자가 폐기된 첫 구현안이나 당시 교차검증 근거를 확인해 달라고 요청할 때만 읽는다.
- 수정하는 시점: 역사 보고서이므로 원칙적으로 수정하지 않으며, 사실 오류·링크·상태 표시만 바로잡는다.
- 정본 여부: 정본이 아니다. 현재 계획은 [`REBUILD_PLAN.md`](REBUILD_PLAN.md), 현재 상태는
  [`SESSION_HANDOFF.md`](../SESSION_HANDOFF.md), 승계 판단은 [`INHERITANCE_MAP.md`](INHERITANCE_MAP.md)다.
- 상태: historical / superseded (2026-07-18). 현재 실행 근거로 사용하지 않는다.
- 데이터 확인 경계: 당시에도 `inputs/`·`outputs/` 내부 파일과 내용은 열거하거나 읽지 않았다.

## 1. 최종 결론

재구축은 기존 프로젝트나 최근 전면 재구축 스냅샷을 통째로 복원하는 작업이 아니다. 현재의 작은
제어 문서 구조를 유지하고, **대표 파일 작업 하나를 실제로 완성하는 데 필요한 기존 계약·코드·
테스트만 결함을 고쳐 선별 활성화**한다.

두 분석을 교차검증한 결과, 1단계의 권장 대표 작업은 다음과 같이 통합된다.

> 사용자가 지정한 원본 영상 한 건을 등록하고 안정된 `source_id`를 부여한 뒤, 원본 시간 기준의
> 대표 프레임 자산을 원본과 분리된 위치에 생성한다. 같은 입력으로 다시 실행하면 기존 자산을
> 재사용하고, 실패는 정확한 종료 코드와 원인으로 보고한다.

이 작업은 아직 **권장안**이다. `SESSION_HANDOFF.md`가 현재 상태 정본이며, 그 문서에는 첫 대표
작업이 아직 정해지지 않았다고 기록되어 있다. 사용자가 이 권장안을 확정한 뒤에만 구현에 착수한다.

## 2. 교차검증 판정

| 쟁점 | Codex 분석 | Claude 분석 | 통합 판정 |
|---|---|---|---|
| 재구축 방식 | 대표 작업에 필요한 기능만 선택 승계 | 기존 동작의 확인된 결함만 고쳐 회수 | **일치.** 전체 복원이 아닌 결함 단위 선택 승계 |
| 첫 대표 작업 | 미디어 정보 확인 + `source_id` 등록 권장 | 원본 등록 + 프레임 자산이 사용자 결정이라고 주장 | **부분 일치.** 프레임 자산까지 포함한 안을 권장하되 사용자 확정 전 |
| 데이터 위치 | 실제 사용자 파일을 지정받기 전 조사하지 않음 | 실제 데이터가 `backup/inputs`, `backup/outputs`에 있다고 판단 | **조건부 확인.** 폴더 존재는 확인했지만 내용·용량·현재본 여부는 미확인 |

| 원본 자산 도구 | 기존 구현을 우선 재사용 | `source_frame_assets.py` 436줄이 핵심 동작을 이미 제공 | **확인.** 식별·경계·프레임·재사용 로직이 존재하므로 재작성 금지 |
| FFprobe 오류 처리 | 실패를 숨기지 않아야 함 | timeout과 JSON 파싱 오류 변환이 부족하다고 지적 | **확인.** 현재 `subprocess.run`에 timeout이 없고 `json.loads` 예외를 변환하지 않음 |
| 재사용 검사 | 같은 입력의 결과 재사용을 종단 확인 | 신규 재실행 테스트 필요 | **확인.** 단위 재사용 검사는 있지만 실제 두 번 실행하는 종단 검사는 별도 필요 |
| 매니페스트 필드 | 실제 소비자가 읽는 핵심 필드만 필수화 | 기존 19개 중 4개를 필수에서 제외 | **방향 일치.** 19열 호환은 유지하고 미사용 필드는 필수 입력에서만 제외 |
| 상태·승인 구조 | SQLite·상태 머신·강제 게이트 보류 | 동일 | **일치.** 현재 활성화하지 않음 |
| 2단계 워크플로우 | 순서와 사용자 판단만 간결하게 승계 | 과거 기계 계약 참조를 끊어야 한다고 지적 | **일치.** `WORKFLOW_CONTRACT.json` 전체 전환 그래프는 보류 유지 |

최근 스냅샷의 정확한 코드 줄 수는 재구축 결정을 바꾸지 않는 보조 수치이므로 통합 결론의 근거로
사용하지 않는다. 현재 판단에는 기존 도구가 필요한 행동을 이미 제공한다는 사실이면 충분하다.

## 3. 확인된 사실과 확인하지 않은 주장

### 3.1 직접 확인된 사실

- 현재 활성 루트에는 `inputs/`, `outputs/` 디렉터리가 없다.
- `backup/inputs/`, `backup/outputs/` 디렉터리는 존재한다.
- `.gitignore`는 활성 루트의 `inputs/`, `outputs/`를 사용자 데이터로 제외하도록 설정되어 있다.
- `backup/tools/source_frame_assets.py`는 436줄이며 다음 동작을 이미 포함한다.
  - 프로젝트 밖과 임시·백업 출력 경로 거부
  - 원본 크기·수정 시각을 이용한 `source_id` 일관성 검사
  - FFprobe 기반 FPS·길이 확인
  - 원본 시간 기반 프레임 추출과 기존 프레임 재사용
  - CSV 매니페스트 기록
- `backup/tools/run_python.bat`은 괄호 블록 안에서 `%ERRORLEVEL%`을 사용한다.
- 해당 래퍼로 종료 코드 3을 발생시킨 실제 검사에서 최종 종료 코드 0이 관찰됐다.
- 기존 `test_tool_wrappers.py`는 Python 래퍼의 성공 경로만 검사하고 실패 코드 보존을 검사하지 않는다.
- 기존 `test_source_frame_assets.py`는 경계, 식별 충돌, 재사용 함수 동작을 검사한다.

### 3.2 현재 확인하지 않은 주장

- `backup/inputs/`, `backup/outputs/` 내부 데이터의 용량과 파일 수
- 그 데이터가 현재 사용자가 작업할 기준본인지, 역사적 보존본인지
- 기존 결과 중 현재본과 폐기 후보의 구분
- 전체 매니페스트에서 `source_id`가 일관되게 이어지는지
- Premiere CS6가 현재도 실제 편집 환경인지

이 항목들은 사용자 작업 데이터 또는 현재 환경에 관한 판단이다. 사용자가 대표 파일이나 조사
범위를 명시한 뒤에만 확인한다.

## 4. 데이터 경계 문제에 대한 최종 판단

Claude 분석은 `backup/inputs/`, `backup/outputs/`를 즉시 활성 루트로 복원해야 하는 차단 요인으로
판정했다. 디렉터리 위치 문제는 실제로 존재하지만, **현재 단계 전체를 무조건 막는다고 확정할 수는
없다.** 해당 디렉터리가 현재 기준 데이터인지 확인되지 않았기 때문이다.

1단계에는 두 가지 안전한 시작 경로가 있다.

1. 사용자가 새 대표 원본을 활성 루트의 `inputs/`에 지정하고 결과를 `outputs/`에 생성한다.
   이 경우 `backup/inputs/`, `backup/outputs/`를 건드릴 필요가 없다.
2. 사용자가 과거 데이터 중 특정 파일을 대표 원본으로 지정한다.
   이 경우 `backup/` 읽기 전용 원칙을 지키는 별도 활성 경로 복원 방식을 먼저 결정해야 한다.

백업 경로 쓰기를 허용하도록 도구를 약화해서는 안 된다. 사용자 승인 없이 대용량 데이터 이동·
복사·삭제도 하지 않는다. 따라서 현재 즉시 필요한 결정은 **백업 전체 이동 승인**이 아니라
**어떤 원본 한 건으로 1단계를 검증할지 지정하는 것**이다.

## 5. 재구축 원칙

### 5.1 회수 단위는 계층이 아니라 행동 계약과 결함

기존 파일을 그대로 복사할지 전부 다시 작성할지 양자택일하지 않는다. 현재 대표 작업에 필요한
행동 계약을 고정하고, 기존 구현에서 확인된 결함만 최소 수정한다.

### 5.2 상류 데이터부터 활성화

활성화 순서는 다음 흐름을 따른다.

```text
source_id → 원본 시간·프레임 자산 → 근거 분석 → 메시지·구조 기획 → 편집 → 실제 편집본 검수
```

상류 식별과 좌표가 불안정한 상태에서 Premiere XML이나 편집 자동화를 먼저 활성화하지 않는다.

### 5.3 자동 검증과 사용자 판단 분리

도구는 추출·변환·반복 검사를 맡고 AI는 후보·해석·설명을 맡는다. 생성, 파싱, 구조, 도구, 앱,
사용자 확인은 각각 따로 기록한다. 자동 테스트 통과만으로 단계 완료나 콘텐츠 품질을 선언하지 않는다.

## 6. 1단계 실행안 — 원본 등록과 프레임 자산

### 6.1 구현 전 게이트

1. 사용자가 대표 원본 한 건과 기대 출력 범위를 지정한다.
2. 과거 백업 데이터를 사용할지 새 대표 원본을 사용할지 결정한다.
3. `INHERITANCE_MAP.md`의 원본 식별·원본 근거 좌표 계약을 다시 확인한다.
4. 지정된 기존 도구와 관련 테스트만 읽어 최종 회수 범위를 확정한다.

### 6.2 우선 회수 후보

| 대상 | 출처 | 처리 방향 |
|---|---|---|
| `source_frame_assets.py` | `backup/tools/` | 기존 동작 유지, 확인된 probe 오류 처리만 보강 |
| `register_source_assets.py` | `backup/tools/` | 실제 대표 작업에 필요한 등록 동작만 연결 |
| FFprobe·FFmpeg | 기존 보존 도구 또는 검증된 현재 실행 파일 | 버전·경로를 한 곳에서 찾도록 연결 |
| `run_python.bat` | `backup/tools/` | 하위 종료 코드를 보존하도록 수정 후 회수 |
| 원본 자산 관련 테스트 | `backup/tests/` | 현재 활성 경로와 행동 계약에 맞는 검사만 회수 |

백업 파일을 런타임 의존성으로 직접 사용하지 않는다. 회수 대상으로 확정된 파일은 활성 영역으로
옮겨 현재 경로만 실행한다.

### 6.3 확인된 필수 수정

| 결함 | 최소 수정 계약 | 필수 검사 |
|---|---|---|
| Python 래퍼가 실패 코드 3을 0으로 반환 | 하위 프로세스 종료 코드를 그대로 반환 | 실패 코드 3 전달 검사 |
| FFprobe가 무한 대기할 수 있음 | 합리적인 timeout 후 명시적 실패 | timeout 오류 검사 |
| FFprobe JSON 손상 시 저수준 예외 노출 | 문맥이 있는 도구 오류로 변환 | 손상 JSON 오류 검사 |

구체적인 배치 구현 방식은 하나로 미리 고정하지 않는다. 지연 확장 사용 또는 블록 밖 종료 코드
처리 중 단순하고 테스트 가능한 방법을 선택한다.

### 6.4 유지할 기존 행동

- 같은 원본 지문은 같은 `source_id`를 사용한다.
- 같은 `source_id`에 다른 원본 지문을 섞지 않는다.
- 원본 시간과 프레임 번호를 자산에 기록한다.
- 같은 원본·시점·출력 조건이면 기존 프레임을 재사용한다.
- 원본과 파생 결과를 분리하고 기존 원본을 덮어쓰지 않는다.
- 임시·백업 경로를 활성 출력 위치로 사용하지 않는다.

### 6.5 매니페스트 호환 원칙

기존 `FIELDS` 19개를 즉시 삭제하거나 순서를 바꾸지 않는다. 기존 소비자와 파일 호환을 유지하되,
다음 네 필드는 실제 소비자가 생길 때까지 필수 입력에서 제외한다.

- `candidate_ids`
- `bit_ids`
- `tags`
- `notes`

필수 식별·경로·시간·상태 필드는 유지하고, `source_frame`, FPS, 폭, 해시, 정밀도처럼 작업에 따라
필요한 값은 해당 도구가 소비할 때 기록한다.

### 6.6 최소 검사

| 검사 | 통과 조건 |
|---|---|
| 원본 비변경 | 실행 전후 원본 크기·수정 시각 등 확인 가능한 기준이 변하지 않음 |
| 출력 분리 | 결과가 활성 `outputs/` 하위에 있고 원본을 덮어쓰지 않음 |
| 식별 일관성 | 같은 원본은 같은 ID, 다른 지문은 같은 ID로 합쳐지지 않음 |
| 재실행 재사용 | 동일 조건으로 두 번 실행했을 때 두 번째 프레임을 새로 추출하지 않음 |
| 실패 전파 | Python·FFprobe 하위 실패가 성공으로 바뀌지 않음 |
| 오류 문맥 | timeout·손상 JSON이 원인을 식별할 수 있는 오류로 보고됨 |
| 경로 처리 | 한글·공백이 포함된 Windows 경로에서 동작함 |
| 문서 경계 | 실행 명령과 결과 위치를 루트 진입 문서에서 찾을 수 있음 |

### 6.7 완료 기준

1. 지정된 대표 원본 한 건이 원본 변경 없이 처리된다.
2. `source_id`와 원본 시간 기반 대표 프레임이 별도 출력 위치에 기록된다.
3. 같은 조건으로 다시 실행하면 기존 프레임이 재사용된다.
4. 실패 경로가 실제 하위 종료 코드와 문맥 있는 오류를 반환한다.
5. 추가 절차가 수동 처리보다 느리거나 복잡하지 않음을 확인한다.
6. 사용자가 결과 위치, 명령, 품질과 유지 비용을 확인한다.

### 6.8 이번 단계에서 하지 않을 일

- 전체 영상 제작 워크플로우, 자동 단계 전환, 승인 체계 구현
- SQLite, 상태 머신, domain/service/storage 계층 활성화
- `synccheck`, Premiere XML, 편집 품질 감사의 선행 회수
- 사용하지 않는 스킬·플러그인·Hook·CI·pre-commit 설치
- `src/` 패키지나 범용 CLI를 미래 대비 목적으로 생성
- 사용자 데이터의 일괄 이동·변환·정리

## 7. 2단계 실행 방향

1단계를 실제로 사용한 뒤 관찰된 재개 비용과 단계 누락만 해결한다.

- 촬영 전 콘텐츠: `1 → 2 → 3 → 4 → 6 → 5 → 7 → 8`
- 촬영 완료본: 자막 신뢰 확인 뒤 `6 → 5 → 7 → 8`
- 작업 상태는 현재 단계, 기준 입력, 현재 산출물, 다음 행동, 차단 사유, 사용자 결정을 한 파일에
  기록한다.
- 과거 8단계 문서에서는 순서·완료 조건·사용자 판단 지점만 발췌한다.
- 과거 `WORKFLOW_CONTRACT.json` 전체 전환 그래프와 강제 승격 구조는 정본으로 되살리지 않는다.
- 실제 사용하는 단계 스킬과 도구만 현재 실행 경로에 연결한다.

관찰된 문제가 없다면 2단계를 시작하지 않는다.

## 8. 3단계 실행 방향

1·2단계가 안정된 뒤 실제 제작에서 반복 확인된 병목 하나만 선택한다.

| 병목 | 회수 후보 | 유지 조건 |
|---|---|---|
| 원본 프레임을 반복 생성 | 원본 프레임 자산 확장 | 재사용으로 시간과 중복 파일 감소 |
| 말 중간 컷 위험 반복 확인 | 동기 검사 | 사람 판단을 보조하고 잘못된 자동 차단을 만들지 않음 |
| Premiere 자료 수동 작성 | XML·CSV·EDL 생성기 | 실제 Premiere 가져오기와 프레임 수 확인 |
| 긴 구간·후반 밀도 누락 | 편집 품질 감사 | 고정 컷 길이 강제가 아닌 검토 경고로 유효 |

효과가 실제 제작 한 사이클에서 확인되지 않거나 유지 비용이 더 크면 활성 경로에서 되돌린다.

## 9. 예상 활성 구조

다음 구조는 미리 생성할 폴더 목록이 아니라 대표 작업이 실제로 요구할 때만 추가할 후보이다.

```text
김실버유튜브/
├─ README.md                 실행 진입점이 검증된 뒤 추가
├─ tools/                    활성 실행 래퍼와 원본 자산 도구만
├─ tests/                    활성 기능의 회귀·실패 경로 검사만
├─ docs/                     현재 정본과 이 통합 보고서
├─ inputs/                   사용자가 지정한 원본, Git 제외
├─ outputs/                  파생 결과와 작업 상태, Git 제외
└─ backup/                   읽기 전용 보존
```

활성 도구가 늘어나 실제 공통 코드 중복이 생길 때만 패키지화를 재검토한다.

## 10. 검증 수준

| 수준 | 1단계 확인 내용 | 완료 주장 범위 |
|---|---|---|
| 정적 확인 | UTF-8, NUL, 링크, Git·원본 경계 | 문서·파일 구조 |
| 회귀 확인 | 선택 승계한 기존 행동과 신규 실패 경로 | 코드 행동 |
| 파일 확인 | 원본 비변경, 출력 위치, 재사용 | 대표 파일 처리 |
| 미디어 확인 | FFprobe 값과 추출 프레임 좌표 | 미디어 도구 결과 |
| 앱 확인 | 1단계 해당 없음 | 주장하지 않음 |
| 내용 확인 | 1단계 판단 산출물 없음 | 주장하지 않음 |
| 사용자 확인 | 명령, 위치, 부담, 유지 가치 | 단계 완료 결정 |
| 생산성 확인 | 수동 처리 대비 시간과 반복 단계 | 다음 단계 투자 판단 |

## 11. 현재 필요한 결정과 다음 행동

현재 필요한 사용자 결정은 두 가지다.

1. 첫 대표 작업을 **원본 등록 + 원본 시간 기준 대표 프레임 생성**으로 확정할지
2. 새 대표 원본을 사용할지, `backup/`에 있는 과거 데이터 중 특정 원본을 지정할지

사용자가 권장안을 확정하면 다음 순서로 실행한다.

1. 대표 원본과 기대 프레임 범위를 지정한다.
2. 해당 작업의 기존 도구·테스트만 최종 확인한다.
3. 실행 래퍼와 FFprobe 오류 처리를 최소 수정해 활성 경로로 회수한다.
4. 실패 코드·timeout·손상 JSON·종단 재사용 검사를 추가한다.
5. 대표 원본 한 건으로 파일·미디어·생산성 검증을 실행한다.
6. 사용자 확인 후 `SESSION_HANDOFF.md`를 갱신한다.

현재는 데이터 이동, 새 플러그인 설치, 전체 도구 복원, 워크플로우 자동화, 데이터베이스 도입을
실행하지 않는다.
