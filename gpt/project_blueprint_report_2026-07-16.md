# 유튜브 영상 제작 프로젝트 진단 및 개선 청사진

- 역할: 현재 프로젝트의 구조·운영·검증·Git 경계를 진단하고 개선 우선순위를 제안하는 의사결정 보고서
- 작성일: 2026-07-16
- 읽는 시점: 프레임워크 개선 범위를 승인하거나 다음 개선 작업을 고를 때
- 보존 조건: 권고안이 적용·검증될 때까지 유지하고, 후속 청사진이 승인되면 `superseded`로 표시
- 분석 범위: 공용 프레임워크와 현재 활성 영상 작업 상태. 원본 영상의 내용 평가는 제외
- 상태: 보고서와 교차검증 계약 생성 완료. `gpt/` 소유권 등록 외 개선안은 아직 적용하지 않음
- 검증 수준: 로컬 파일·Git·프로젝트 검사 결과에 근거한 구조 진단
- 위치: `gpt/`는 사용자 요청에 따라 프로젝트 진단·교차검증 전용 영역으로 등록했으며 운영 규칙이나 영상 상태의 정본이 아님

## 1. 한눈에 보는 결론

이 프로젝트는 이미 단순한 문서 모음이 아니라 **단계 게이트, 상태 계약, 회귀 테스트, 편집 기억을 갖춘 재사용형 영상 제작 프레임워크**다. 특히 잘된 부분은 다음과 같다.

- `doccheck` 오류·경고 0건, 단위 테스트 74개 통과
- 데이터 분석 → 기획 → 대표 캘리브레이션 → 전체 편집 → 실제 검증의 단계 게이트 작동
- 승인 기준본이 없거나 실제 A/V 검증이 끝나지 않으면 다음 단계가 차단됨
- `source_id`, `CURRENT.json`, 변경 원장, 편집 기억으로 버전과 근거를 추적함
- Claude·Codex·Gemini가 같은 문서 정본을 읽도록 진입 구조를 얇게 유지함

핵심 문제는 설계 부족이 아니라 **선언된 규칙과 실제 저장소·도구 사이의 간극**이다. 가장 먼저 해결할 세 가지는 아래와 같다.

1. `outputs/`를 Git에 넣지 않는다는 규칙과 실제로 345개 산출물이 추적되는 상태를 일치시킨다.
2. 사용자 응답 대기 작업이 단일 활성 슬롯을 점유해 다른 작업 등록을 막는 제어 구조를 개선한다.
3. 이미 작성된 변경 제안 0001을 승인 여부 결정 후 실행해 재개 컨텍스트와 검증 출력을 줄인다.

## 3. 문제 진단과 개선 방향

### P0. 저장소 경계가 규칙과 반대로 작동한다

**증거**

- [`PROJECT_RULES.md`](../PROJECT_RULES.md)는 `inputs/`와 `outputs/`를 영상별 산출물로 보고 커밋하지 않도록 정한다.
- [`.gitignore`](../.gitignore)는 `inputs/`는 제외하지만 `outputs/`는 추적한다고 명시한다.
- 실제 Git 추적 파일 중 `outputs/`가 345개이며, 최신 커밋은 그 345개를 한 번에 추가했다.
- 그럼에도 현재 `doccheck`는 오류·경고 0으로 통과한다.

**영향**

- P1 “프레임워크가 제품” 원칙과 영상별 작업본이 한 저장소에 섞인다.
- 새 영상이 늘어날수록 clone·diff·검토 비용과 개인정보·저작권 노출 위험이 커진다.
- 검사 통과가 실제 규칙 준수를 보장하지 못하므로 P2의 결정적 검증이 약해진다.
- “Git을 백업으로 사용”하는 관행과 “outputs는 커밋 금지”라는 규칙이 동시에 존재해 에이전트마다 다른 결정을 내릴 수 있다.

**권고**

1. 정본을 하나로 결정한다. 권고안은 `outputs/`를 로컬 작업 상태로 유지하고 Git에서는 비추적하는 것이다.
2. 삭제 없이 먼저 `outputs/`의 외부 백업 보유 여부를 사용자에게 확인한다.
3. 승인 후 Git 인덱스에서만 추적을 해제하고 실제 작업 파일은 보존한다.
4. `.gitignore`와 문서 규칙을 일치시킨다.
5. `doccheck` 또는 별도 Git 경계 검사에 다음 조건을 추가한다.
   - `inputs/` 추적 파일 0개
   - `outputs/` 추적 파일 0개
   - 예외가 필요하면 파일이 아니라 승인 기록과 manifest만 허용
6. 과거 Git 기록 정리는 별도 결정으로 둔다. 즉시 history rewrite를 하지 않는다.

### P0. 현재 영상은 실제 A/V 승인 전 단계에서 멈춰 있다

**증거**

- 현재 후보 `integrated-calibration-v2-r2`는 음원 신호·편집 의미·사용자 방향 검사를 통과했다.
- 연속 A/V와 Premiere 검증은 `pending`이며 approved 기준본이 없다.
- `workflow_gate`는 `edit_full`, `validation`, `final` 전환을 정상적으로 차단했다.

**판단**

이것은 게이트 실패가 아니라 게이트가 제대로 작동한 결과다. 문제는 다음 단계로 넘어갈 **표준화된 실제 A/V 검토 표면과 증거 기록 절차가 아직 운영 병목**이라는 점이다.

**권고**

- 검증 페이지를 사용자가 명시적으로 열어 검토한 뒤, A·B·C 각각에 대해 문맥·감정 피크·호흡·메시지 자립 여부를 기록한다.
- 통과 시에만 approved 이벤트, `generation_lock_released`, 전체 확장 입력을 한 번에 갱신한다.
- 실패 시 기존 파일을 고치지 말고 descendant revision을 만든다.
- 프레임워크 개선으로는 “검토 요청 → 사용자 재생 → 결과 기록 → 잠금 해제”의 최소 필드를 계약과 테스트로 고정한다.

### P1. 단일 활성 작업 제어가 사용자 대기 상태를 표현하지 못한다

**증거**

- `outputs/AGENT_CONTROL.json`에는 활성 작업을 한 개만 기록한다.
- 현재 `backrooms-full-edit-expansion`이 사용자 A/V 검토를 기다리면서도 활성 슬롯을 계속 점유한다.
- 이번 독립 보고서 작업은 새 작업 ID로 `projectctl start`를 실행할 수 없는 상태였다.

**영향**

- 사용자 응답 대기와 실제 실행 중 상태가 구분되지 않는다.
- 읽기 전용 진단이나 독립 문서 작업도 충돌로 취급된다.
- 에이전트가 기존 작업을 부정확하게 완료 처리하거나 제어 도구 밖에서 작업하게 만드는 유인이 생긴다.

**권고 상태 모델**

```text
active_mutation -> waiting_user -> active_mutation -> completed
               -> paused       -> active_mutation
               -> blocked      -> resumed
```

- 변경 권한을 가진 `active_mutation`은 한 개만 허용한다.
- `waiting_user`는 현재 영상의 재개 정보를 유지하되 독립적인 읽기·보고서 작업을 막지 않는다.
- 새 작업 등록 시 기존 작업을 덮어쓰지 않고 `task_id`, 상태, 소유 범위만 분리한다.
- 이 변경은 아직 `proposed` 상태인 변경 제안 0001에 승인 전 추가하거나, 범위가 커지면 변경 제안 0002로 분리한다.

### P1. 재개 컨텍스트와 성공 검증 출력이 목표보다 크다

**증거**

- 현재 기본 재개 4개 문서는 242줄·12,023자다.
- 변경 제안 0001의 목표는 최대 5개 문서, 200줄·10,000자다.
- 현재 `projectctl verify` 성공 출력은 clean 분석 시점에도 2,959자로 목표 2,000자를 넘었다. 변경 중 경고가 포함되면 3,520자까지 늘었다.
- [`docs/changes/0001-governed-context-efficient-resume.md`](../docs/changes/0001-governed-context-efficient-resume.md)는 이 문제의 해법을 이미 설계했지만 상태가 `proposed`다.

**권고**

- 제안 0001을 승인할지 먼저 결정한다.
- 승인 시 성공 출력은 검사명·PASS/FAIL·오류/경고/테스트 수만 보여주고 상세 로그는 실패 또는 `--verbose`에서만 표시한다.
- `outputs/SESSION_HANDOFF.md` 첫 15줄에 현재 단계, 후보, 첫 행동, 금지 행동, 검증 한계를 압축한다.
- 상세 실패 원장과 증거 경로는 조건부 라우팅으로 내린다.
- 재개 예산을 doccheck 회귀 검사로 강제한다.

### P1. 에이전트 간 안전 강제가 동일하지 않다

**증거**

- Claude는 `agent_guard.py` 훅으로 일부 위험 행동을 차단한다.
- Codex·Gemini 파일은 사용자 설정에 합치는 템플릿이며 저장소가 강제하지 않는다고 명시되어 있다.
- pre-commit은 Python이 없으면 검사를 건너뛰는 fail-open 방식이다.
- CI는 doccheck와 테스트를 실행하지만 현재 outputs Git 경계와 변경 승인 상태는 검사하지 않는다.

**영향**

- 같은 규칙을 읽어도 실행 표면마다 실제 차단 강도가 다르다.
- P3 “에이전트는 교체 가능한 부품”이 문서 수준에서는 성립하지만 강제 수준에서는 완성되지 않았다.

**권고**

- 에이전트별 개인 설정은 보조 방어선으로 두고, Git 훅과 CI를 공통 최종 방어선으로 삼는다.
- 프레임워크 변경에는 Python 미설치 시 fail-closed가 되도록 한다.
- CI에 Git 경계 검사와 승인된 change ID 검사를 추가한다.
- 동일한 위반 fixture를 Claude 훅, 로컬 게이트, CI에서 돌려 판정 일치를 검증한다.

### P1. 산출물 생명주기는 정의됐지만 정리 실행이 약하다

**증거**

- `CURRENT.json`, `superseded`, historical failure evidence 규칙은 잘 정의돼 있다.
- 로컬 `outputs/`에는 386개 파일, 약 479MB가 있으며 legacy 프레임과 여러 편집 세대가 함께 존재한다.
- 자동 삭제 금지는 안전하지만, 실제 정리 후보를 한눈에 보는 보고와 승인 절차는 약하다.

**권고**

- 파일을 자동 삭제하지 말고 `artifact_inventory`를 생성한다.
- 각 파일을 `active`, `reusable_evidence`, `historical_failure`, `superseded_cleanup_candidate`, `unknown`으로 분류한다.
- `CURRENT.json`, manifest, edit memory가 참조하는 파일은 보호한다.
- 참조가 끊긴 항목만 사용자 승인용 정리 후보로 제시한다.
- 크기·최종 참조일·삭제 위험을 함께 보여줘 사용자가 한 번에 결정하게 한다.

### P2. 새 최상위 폴더의 소유권을 함께 등록해야 한다 — 이번 요청에서 해소

**증거**

- 최초 생성 시 doccheck의 최상위 허용 목록에 `gpt/`가 없어 폴더 소유권 오류가 발생했다.
- 사용자 요청이 일회성 로컬 파일이 아니라 교차검증 후 원격 공유로 확장되어 영구 소유권 결정이 필요해졌다.

**적용**

- README와 프로젝트 규칙에 `gpt/`를 사용자 요청 기반 진단·교차검증 영역으로 등록했다.
- `docs/INDEX.md`는 교차검증 요청만 `gpt/CROSS_VALIDATION.md`로 라우팅한다.
- doccheck allowlist와 회귀 테스트를 함께 변경해 이름만 허용하는 예외를 피했다.
- `gpt/` 문서는 운영 규칙이나 현재 영상 상태의 정본으로 사용할 수 없다.

**잔여 위험**

- `planning_research/`와 역할이 겹치지 않도록 `gpt/`에는 다른 에이전트가 재현할 진단·교차검증 문서만 둔다.

## 4. 개선 청사진

### 0단계 — 정본 충돌 해소

목표 기간: 0.5~1일

1. `outputs/`를 Git 비추적으로 돌릴지 사용자 결정
2. 외부 백업 보유 여부 확인
3. 삭제 없이 Git 인덱스 경계만 정리
4. `.gitignore`, 규칙, doccheck, CI를 같은 정책으로 통일
5. `gpt/`를 진단·교차검증 전용 영역으로 등록 — 적용 완료

**완료 기준**

- Git 추적 `inputs/` 0개, `outputs/` 0개
- 같은 위반을 로컬 검사와 CI가 모두 차단
- 실제 로컬 영상·산출물은 손실 없음

### 1단계 — 변경 제안 0001 결정 및 구현

목표 기간: 1~2일

1. 제안 0001의 범위·승인 기준 검토
2. 필요하면 `waiting_user/paused` 상태 모델을 승인 전에 추가
3. `sdd_gate`, `projectctl --change`, compact verify 구현
4. `fast_resume/audit/mutation` 라우팅 적용
5. 새 세션 재개 시뮬레이션 실행

**완료 기준**

- 빠른 재개 5개 문서 이하, 200줄·10,000자 이하
- 성공 검증 출력 2,000자 이하
- 사용자 대기 작업이 독립 읽기·보고서 작업을 막지 않음
- 승인되지 않은 프레임워크 구현을 로컬과 CI가 차단

### 2단계 — 공통 강제층 강화

목표 기간: 1~2일

1. Git 경계 검사 추가
2. change ID와 승인 상태 검사 추가
3. 훅·CI 동일 fixture 회귀 테스트 추가
4. Python 미설치·훅 우회·다른 clone 조건 검증
5. 성공·실패 출력 형식 표준화

**완료 기준**

- Claude·Codex·Gemini 중 어떤 에이전트를 써도 커밋 가능 여부가 동일
- `--no-verify` 우회가 CI에서 차단
- 문서상 금지와 실제 자동 차단의 차이가 목록화되고 감소

### 3단계 — 현재 영상의 A/V 승인 병목 해소

목표 기간: 사용자 검토 1회 + 반영 0.5일

1. 준비된 r2 검증 페이지를 사용자 요청에 따라 재생
2. A·B·C 판정 기록
3. 통과 시 approved 기준본과 생성 잠금 해제
4. 실패 시 영향 구간만 descendant revision으로 수정
5. 전체 편집은 승인 이후에만 확장

**완료 기준**

- `continuous_av=passed`
- approved edit baseline 존재
- `generation_lock_released=true`
- 사용자 방향 판단이 검증 기록과 연결됨

### 4단계 — 산출물 정리와 운영 대시보드

목표 기간: 1일

1. 비파괴 artifact inventory 생성
2. CURRENT·manifest·memory 참조 무결성 검사
3. 정리 후보와 예상 절감 용량 보고
4. 사용자 승인 후에만 정리 수행
5. 다음 영상에서 동일 규칙 재사용 검증

**완료 기준**

- `unknown` 산출물 0개
- 활성·재사용 증거는 모두 manifest나 CURRENT로 추적
- 정리 작업이 현재 기준본과 실패 기억을 훼손하지 않음

## 5. 권장 실행 순서

```text
저장소 경계 결정
  -> 변경 제안 0001 승인 여부 결정
  -> projectctl 대기 상태 + compact resume 구현
  -> 공통 Git/CI 강제층 보강
  -> 현재 r2 실제 A/V 승인
  -> 전체 편집 확장
  -> 비파괴 산출물 정리
```

저장소 경계를 먼저 정해야 이후의 CI·SDD·정리 도구가 잘못된 정책을 자동화하지 않는다. 현재 영상은 게이트를 건너뛰지 말고 별도의 사용자 A/V 검토 흐름으로 계속 진행한다.

## 7. 레드팀 검토

### outputs 추적 해제 시 백업 손실 위험

Git이 사실상 유일한 백업일 수 있다. 외부 백업 확인 없이 추적 해제·기록 정리를 하면 복구 가능성이 낮아진다. 따라서 **실제 파일 삭제와 history rewrite는 별도 승인 전 금지**한다.

### 게이트 강화가 작업 속도를 떨어뜨릴 위험

모든 작은 수정에 긴 제안을 요구하면 우회 동기가 커진다. 짧은 제안 템플릿과 위험도별 필드 깊이를 사용하되 change ID와 승인 상태는 생략하지 않는다.

### 대기 상태 모델이 제어 복잡도를 키울 위험

다중 writer를 허용하면 더 큰 충돌을 만든다. 병렬 변경이 아니라 **writer 한 개 + 읽기/보고 작업 허용**으로 제한한다.

### A/V 자동 검사가 사용자 창작 판단을 대체할 위험

신호·경계·구조 자동 검사는 결함을 줄일 뿐 재미와 메시지를 확정하지 못한다. 최종 방향 판단은 실제 대표 샘플을 본 사용자에게 남긴다.

### `gpt/`가 두 번째 보고서 저장소가 될 위험

`planning_research/`와 역할이 겹치면 라우팅과 보존 규칙이 다시 분산된다. 이번 등록은 다른 에이전트가 독립 재현할 진단·교차검증으로 범위를 제한하며, 운영 설계 연구는 계속 `planning_research/`에 둔다.

## 8. 적용 여부가 필요한 결정

다음 두 가지는 자동으로 적용하지 않고 사용자 결정이 필요하다. `gpt/` 영구 소유권은 이번 교차검증·푸시 요청으로 결정되어 반영했다.

1. Git에 들어간 `outputs/`를 앞으로 비추적으로 전환할지
2. 변경 제안 0001을 현재 범위로 승인할지, 대기 상태 모델까지 보강한 뒤 승인할지
